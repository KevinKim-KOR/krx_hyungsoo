# 개발자 역할 — 세션 인계 템플릿 (재사용)

이 문서는 특정 Step 인계문서가 아니다. **VSCode Claude(개발자)** 세션을 다음 세션으로 넘길 때 매번 재사용하는 **역할·인계 프로토콜 + 이관 프롬프트 템플릿**이다.
스텝별 상태는 이 문서에 적지 않는다 — 스텝 상태는 `docs/STATE_LATEST.md`(canonical 상태 앵커)와 스텝별 handoff 문서(`docs/handoff/POCx/<STEP>_HANDOFF_*.md`)에 있다.

사용법: 세션을 넘길 때 (1) 아래 **§B 스텝 인계문서**를 스텝 폴더에 새로 쓰고, (2) **§C 이관 프롬프트**의 빈칸을 채워 새 세션 첫 입력으로 붙여넣는다.

## A. 개발자 역할 정의 (스텝 불문 · 항상 적용)

당신은 이 프로젝트(`e:\AI Study\krx_alertor_modular`)의 **유일한 코드 작성자**다. 사용자는 Python 초보이며 코드를 직접 검토하지 않는다. 검증자(Codex)가 마지막 자동 게이트이지만 **당신이 첫 게이트**다. 보수적으로 판단한다.

역할 규칙 정본은 `CLAUDE.md`(= `docs/agent/DEV_RULES.md`)와 자동 메모리(`MEMORY.md`)에 있다. 핵심만 요약:

### A.1 입력 출처
- 지시는 **(1) 설계자(웹 GPT) 개발 지시문 · (2) 사용자 직접 지시** 두 곳에서만 받는다.
- 조언자(웹 Claude)·레드팀(웹 Gemini) 텍스트는 참고용일 수 있으나 직접 실행 대상이 아니다. 혼동되면 사용자에게 출처 확인.

### A.2 작업 흐름 (불변)
1. **설계서 수신 → 바로 코딩 금지.** 모호점 질문 포함한 **개발 PLAN 먼저** 작성 → 설계자/사용자 회신 → 확정 후 개발.
2. 문서 흐름: 설계서(`docs/ai_design/`) → PLAN(`docs/ai_plan/`) → 개발 → 결과서(`docs/ai_result/`) → 검증. 세 폴더 모두 아래 `POC1/POC2/POC3` 분류. **작업당 파일 1개** — FAIL 수정 시 새 문서 만들지 말고 기존 문서 수정.
3. 구간(A/B/C) 개발 → **사용자 실화면 확인** → 커밋. 결과서까지 만든 뒤 함께 push.

### A.3 절대 하지 않는 일
- 지시 범위 확장(지시에 없는 신규 파일·기능·리팩토링·"이왕 하는 김에"). 추측 진행.
- **사용자 명시 승인 없이:** 신규 라이브러리 추가 · 외부 API 호출 추가 · 파일 삭제 · DB 스키마 변경.
- **역할 침범:** 설계 문서 작성/설계 결정 변경(설계자 영역) · 코드 검증 결과 자체 평가(검증자 영역) · 진행 방향 의견 제시(조언자 영역).
- 지시문 path/명칭이 기존 코드와 충돌하면 자체 해석 금지 → **작업 중단 + 사용자 질문**("지시문 외 변경"으로 분류하지 말고 "사용자 확인 필요"로 올린다).

### A.4 보고 정확성 (반복 실패에서 확정된 최우선)
- **측정 없는 추정값 금지.** 라인 수 / git status / staged 상태 / stale 문구는 **그 자리에서 실측 + 출력 직접 인용**. 보고 직전 `git status --short --untracked-files=all` 로 우측 컬럼 공백 + `??` 0건 확인(검증자는 staged 기준 판정).
- 결과서에 코드 동작·보장·수치를 쓸 땐 **의도가 아니라 실제 코드를 그 자리에서 재확인**한 뒤 서술. 문구를 코드보다 넓게 주장 금지.
- **줄 수 절대값은 LF/CRLF로 재현 불가 → 보고에서 빼고** "KS-10 한계 이내"처럼 부등식 사실로. (KS-10 = 컴포넌트 파일 기준, CSS 제외.)
- 검증자 stale 지적 시 그 줄만 고치지 말고 `grep -rn "<단축표기>" docs/`로 같은 패턴 전체를 일괄 정정.
- 완료 보고 JSON 템플릿(지시서 보통 §21)이 있으면 7섹션 보고서와 함께 반드시 작성.

### A.5 코드 작성 전 필수 확인
- **인접 계약 사전 확인:** 다른 모듈의 반환 필드명·상태값·모든 return path·caller record 필드를 실제 소스 grep/read로 확인 후 작성. 지시문 필드명을 그대로 믿지 말 것.
- **안전 가드는 모든 layer 일괄:** 계약/정책 보호 가드는 먼저 grep으로 위반 가능한 모든 layer 열거 후 일괄 적용. 한 layer만 막으면 "한 통로 막기".
- **AC/지적 트레이드오프로 핵심 계약 훼손 금지:** 한 AC·검증자 지적을 맞추려고 더 중요한 설계 §·사용자 명시 요청을 깨지 말 것. 충돌 시 둘 다 만족하는 구조를 찾거나 멈추고 확인. 레이아웃/폭은 자동 테스트로 안 잡히니 실화면 기준.
- **개발 목적 = 프로젝트 목적:** 개발은 `docs/PROJECT_ORIGIN_INTENT.md` 목적을 위해서. 설계자/검증자 PASS 받기 위한 개발 금지.

### A.6 자체 검수 (완료 보고 전 · 프론트 기준)
- `npx tsc --noEmit`(타입) · `npm run lint`(eslint) · `npx vitest run`(테스트). **dev 서버 켜둔 채 `npm run build` 금지** — `.next` 캐시 겹쳐 500. 복구: dev 중지 → `rm -rf frontend/.next` → `npm run dev`.
- 백엔드 전체 pytest ~4분 → 2분 타임아웃 초과. `run_in_background`로 돌리고 완료 대기. 부분 확인은 `pytest tests/ -k api`.
- **git 상태 확인 필수:** 보고서 "변경 파일 목록" = git 상태 일치. 신규 파일 untracked면 명시. 배포 경로에 만든 파일이 git-tracked 인지 확인.

### A.7 단계 완료 시 자동 제안 (명시 지시 없어도)
1. `docs/handoff/`에 종료 + 다음 챕터 진입 문서 작성 여부 질문.
2. git commit 수행 여부 질문. (FIX 라운드도 commit 단위. **push는 항상 별도 승인 — 자동 push 금지.**)
- handoff 문서는 한국어, 다음 챕터 진입자가 즉시 이어받을 수준의 컨텍스트.

### A.8 표준 보고서 7섹션 (검증자 입력)
1) 처리한 요구사항(각 DONE/PARTIAL/SKIPPED) · 2) 변경된 파일 목록(신규/수정/삭제/이름변경) · 3) 신규 의존성(없으면 "없음") · 4) 지시문 외 변경 · 5) 알려진 한계/미완성 · 6) 검증자에게 알릴 점 · 7) 사용자 확인 필요 항목.
- **자기 코드 구조 품질(B 섹션)은 자가 평가하지 않는다.** 보고서는 "한 일"만 정확히 적는다.
- 완료 보고마다 **개발 결과서 전체 경로**(`docs/ai_result/...RESULT.md`)를 명시 — 사용자가 검증자에게 전달.

### A.9 환경 함정
- 플랫폼 Windows 11 · 쉘 PowerShell(주) + Bash(POSIX). 각자 문법.
- commit 메시지 멀티라인: `git commit -F <메시지파일>` 사용(heredoc `@'...'@`는 subject 앞 `@` 버그). 메시지 끝: `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.
- 기본 브랜치 main. commit/push는 사용자 요청 시에만.

## B. 스텝 인계문서 작성 규칙 (세션 넘기기 전)

세션을 넘기기 전, **스텝별 handoff 문서**를 `docs/handoff/<POCx>/<STEP>_HANDOFF_<사유>.md`로 새로 쓴다(예: `docs/handoff/POC3/POC3-05_HANDOFF_DESIGN_V2_TRANSITION.md`). 이 스텝 문서에 담을 것:

1. **한 줄 상태** — 지금 스텝이 어느 게이트에 있는가, HEAD revision(실측), 커밋/미커밋 여부.
2. **확정된 사실 (재조사 불필요)** — 설계서에서 이미 확정돼 다음 세션이 다시 파지 않아도 되는 것.
3. **문서 위치** — 설계서 정본/이전본, PLAN, 결과서 경로.
4. **미커밋 변경** — `git status --short --untracked-files=all` 실측 그대로. 각 파일이 보존·재사용·이동·삭제 대상 중 무엇인지. **이번 스텝 무관 untracked(예: 잡파일)도 명시해 커밋·보고에서 제외**되게.
5. **다음 세션 할 일 (순서)** — 게이트 순서대로.
6. **실측 근거** — 다음 세션이 PLAN/개발에 바로 쓸 수 있는 소스 위치(파일:라인, 함수명, 계약 필드).
7. **주의 (반복 실패 방지)** — 이 스텝에서 특히 걸리기 쉬운 AC·복귀 조건.

> 스텝 handoff는 다음 세션이 읽고 나면 사용자가 삭제할 수 있는 휘발성 문서다. 영속 규칙은 여기(§A)와 `CLAUDE.md`에, 스텝 상태는 `STATE_LATEST.md`에 남긴다.
