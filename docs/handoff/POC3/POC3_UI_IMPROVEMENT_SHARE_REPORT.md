# UI 개선 작업 공유 보고서 (2026-08-12 ~ 08-16)

- **수신**: 설계자 · 조언자
- **발신**: 개발자
- **성격**: **공유용**. 승인 요청이 아니다. 이 기간의 UI 작업은 전부 **사용자가 직접 주도·확정**했고 설계서 없이 진행됐다(사용자 명시: "UI 바꾸는 것은 제가 주도하는 것이니 설계자에게 안 넘깁니다").
- **요청 사항**: **없다.** 초안에 설계 결정 1건(개별주 종목명 조회)을 올렸으나, 사용자 판단과 실측 확인으로 §7 에서 철회했다.

---

## 1. 한 줄 요약

**표(table) 중심이던 판단 화면 3개를 카드형으로 바꾸고, 메뉴에 섞여 있던 성격(정상 업무 / ML 실험 / 개발용)을 분리했다.** 판정 로직·API·백엔드는 변경 0건이며, 표시 형태와 화면 배치만 바뀌었다.

---

## 2. 진행 방식 (설계자 참고용)

설계서가 없는 사용자 직접 지시였으므로, 다음 절차로 통제했다.

1. **현재 구조를 먼저 제시** — 코드에서 실제 컬럼·컴포넌트·계약을 추출해 보여준다.
2. **목업(HTML)으로 목표 구조 승인** — 배치·색·상태 표기를 눈으로 확인받은 뒤 착수.
3. **구현 → 실화면 확인 → 지적 반영**.
4. **결과서 작성**(검증자 입력) → 커밋 → 푸시.

임의 라벨 생성·범위 확장은 하지 않았고, 판단이 갈리는 지점은 매번 선택지를 제시해 사용자 결정을 받았다.

## 3. 화면 변경 — 표 → 카드

### 3.1 공통 형태

세 화면 모두 같은 규칙을 쓴다. **좌측 2단×2열 카드 + 우측 지표 고정 열**.

```
┌─────────────────────────────────────────┬──────────────────┐
│ 종목명 [배지…]              핵심 수치    │  지표 2~3칸       │
│ 티커 / 비중 / 금액          보조 수치    │  ─────────────    │
│                                          │  비교 지표 1줄     │
└─────────────────────────────────────────┴──────────────────┘
      행 클릭 → 기존 선택 상세(차트·근거) 유지
```

기준이 된 것은 POC3-08 에서 사용자가 확정한 **보유 현황 증권사 스타일**(`.hld-row`)이다. 그 형태를 나머지 화면으로 확산한 것이다.

### 3.2 화면별

| 화면 | 이전 | 이후 |
|---|---|---|
| ETF 비교하기 — 후보 탭 | 9열 표 | 카드 + **정렬 세그먼트 바** |
| ETF 비교하기 — 보유 탭 | 14열 표 | 카드 + 상태 배지 4종 |
| 확인 근거 | 8열 표 | 카드 + 지표 2칸 |
| (기준) 보유 현황 | — | POC3-08 에서 이미 카드 |

**`확인 필요` 탭은 미전환** — 표가 아니라 항목 목록이라 성격이 다르다.

### 3.3 보존한 계약 (설계자 확인 요망 없음 · 기록용)

표시 형태만 바꾸고 아래는 전부 그대로 유지했다. 과거 검증 라운드에서 확정된 것들이다.

- 같은 ticker 다계좌 **한 행 집계**(`aggregateHoldings`)
- **부분 평가 `(N/M)`** 표기 — 부분값을 전체값처럼 보이지 않게
- 다계좌 시 평가수익률 **"계좌별 상이"** (첫 값을 대표값으로 쓰지 않음)
- 관계 **3-state**(`relationState`) — 미포함과 "확인 불가" 구분
- `holdingEvidenceState` — Evidence 부재/실패는 "정상" 아님
- NAV / 구성종목 **상태 분리 표시**
- stale 줄 `⚠ 이전 조회값 (재조회 실패 — 최신 아님)`
- 값 없는 칸을 채우지 않음 (`자료 확인 필요` / `—`)
- 행 클릭 → 선택 상세(가격 차트·수치 근거)

### 3.4 표시 문구가 바뀐 것 (검증자 중점 확인 대상)

3-state 등 **구분은 유지**하되 문구가 바뀌었다.

| 이전 | 이후 |
|---|---|
| `◆ 후보` | `후보 포함` 배지 |
| `◆ 보유` / `—` | `보유` / `미보유` 배지 |
| `상태` 열의 `ok` | 정상이면 **숨김**, 비정상만 `⚠ 데이터 <상태>` |
| `데이터 상태` 열의 `확인됨` | 정상이면 **숨김**, `자료 확인 필요` 만 표시 |

## 4. 메뉴 재편 (MenuKey 10 → 13)

사용자 지적 두 가지에서 출발했다. (1) ML 카드가 판단 화면에 박혀 화면이 무겁다 (2) 진단·상태에 **실제로 써야 하는 것이 섞여 있다.**

```
진단·상태
├─ 데이터 상태        (data_status)  ← 복원
├─ OCI 운영 상태      (oci_status)   ← 분리
├─ ML 실험            (ml)           ← 신설, 카드 5개 집결
└─ 개발·실험용        (diagnostics)  ← 축소·개명
```

**`data_status` 복원 건은 설계자가 알아야 할 사실이 있다.**

POC3-07 은 `data_status` 를 **"placeholder"** 로 보고 `diagnostics` 에 흡수했다(`PROGRAM_TRUTH §14` 에 "진단 격리 ✅ 완료"로 기록). 그런데 그 화면은 **2026-06-08 NAV/Discount Display FIX 로 이미 전체 ETF NAV·괴리율 조회 화면**이 된 상태였다. 컴포넌트 주석에 그 전환이 명시돼 있다.

> 이전 정책 (2026-06-06 placeholder): "시장 데이터 / refresh 상태 들어갈 자리".
> 변경 사유: NAV / Discount Display FIX 의 전체 ETF 조회 위치를 Data Status 로 채택.

즉 **두 달 전 상태를 근거로 판단이 내려졌고, 그 결과 정상 업무 화면이 두 달 넘게 "진단 서랍"에 들어가 있었다.** 사용자가 이를 발견해 복원을 지시했다. `PROGRAM_TRUTH` 의 해당 항목은 "⚠ 2026-08-16 재조정" 으로 정정했다.

**ML 카드 5개 집결**: `DataStatusView` 3 + `ETFExposureView` 1 + `MarketDiscoveryView` 1 → `MLView`. 카드 내용·API 는 무변경이다.

## 5. 이번에 드러난 기존 결함 3건

UI 작업 중 발견한 것으로, **원래 지시 범위 밖**이었다. 각각 사용자 승인을 받고 처리했다.

### 5.1 `KODEX초과` 가 전 종목 `—` 로 표시되던 버그

`candExcess()` 가 응답에 **존재하지 않는 키** `excess_return_pct` 를 읽고 있었다. 실제 키는 `vs_kodex200_1m_pctp` 다.

```
excess_return: {'vs_kodex200_1m_pctp': 29.55, 'vs_kodex200_3m_pctp': 35.56, ...}
```

같은 파일의 보유 탭용 `evidenceExcess()` 는 이미 올바른 키를 읽고 있었다. **표 시절부터 있던 버그**이며, 표시뿐 아니라 **`KODEX초과` 정렬도 전부 `-Infinity` 라 동작하지 않았다.** 1M 기준으로 정정했다.

### 5.2 선택 상세가 모든 탭에 잔존

선택 상세가 탭 분기 바깥에 있는데 탭 전환 시 `selected` 를 비우지 않아, 보유 탭이 "조건에 맞는 보유 종목 없음" 인데도 후보 탭에서 고른 종목의 상세가 붙어 있었다. 탭 전환 시 선택 해제로 수정했다.

### 5.3 기동 스크립트가 다른 프로젝트의 서버를 종료

`stop.sh` / `stop.bat` 이 **포트 번호만 보고 종료**했다. 3000·8000 은 가장 흔한 개발 포트라, 다른 프로젝트가 쓰고 있으면 `start` 만 눌러도(내부에서 stop 호출) 남의 서버가 죽었다. **실제로 다른 프로젝트가 이 프로젝트의 백엔드를 종료시킨 사례가 발생**해 발견됐다.

작업 디렉터리를 확인해 이 프로젝트 것만 종료하도록 가드를 넣었고, **확인 불가 시 죽이지 않는다.** 가짜 외부 프로세스로 실측 검증했다. (`stop.bat` 은 맥에서 작성해 **PC 실행 검증 미완**.)

## 6. 검증

각 단계마다 프론트 3종 검증을 돌렸고, 최종 실측은 다음과 같다.

| 항목 | 결과 |
|---|---|
| `npx tsc --noEmit` | 0건 |
| `npm run lint` | 0건 |
| `npx vitest run` | **167 passed (15 files)** |
| 백엔드 전체 pytest | **1139 passed · 실패 0건** (§6.1) |

**테스트를 여러 건 수정했다.** 화면 구조가 바뀌면 조회 방식이 바뀌기 때문이며, **검사 항목은 유지**했다. 다만 §3.4 의 문구 변경과 메뉴 계약(개수·그룹 귀속)은 실제 계약 변경이라 테스트 기대값을 바꿨다.

특히 기록해 둘 것 두 가지다.

- **`aria-label` 충돌** — 행을 `role="button"` 으로 바꾸자 `자료 확인 필요` 배지가 행의 접근가능 이름에 섞여, 같은 문구의 빠른보기 버튼 조회와 다중 매치로 깨졌다. **기존 테스트는 fixture 에 해당 행이 없어 우연히 통과 중**이었다. 이름을 고정하고 재현 테스트를 추가했다.
- **`data_status` 계약 반전** — POC3-07 이 못박은 `expect(allKeys).not.toContain("data_status")` 를 복원에 맞춰 `toContain` 으로 뒤집었다.

### 6.1 상시 실패 2건 — **해소 (2026-08-16)**

`tests/test_factor_signals.py` 2건이 티커 `AAA`/`BBB`/`CCC`/`ZZZ` 를 쓰는데 **POC3-08 (A) 의 종목코드 6자리 검증**이 이를 막아 `PUT /holdings` 가 422 를 반환하고 있었다.

개발자가 이를 "설계 판단 필요" 로 분류해 미수정으로 두었으나, **사용자가 판단 오류를 지적했다** — 검증을 약화시킬지 fixture 를 고칠지는 답이 정해져 있고, fixture 교체는 설계 결정이 아니다. 더 중요하게는 **"2 failed" 가 상시화되면 진짜 실패가 그 뒤에 숨는다.**

**검증은 그대로 두고 fixture 티커만 실제 형식으로 교체**했다(`069500`/`360750`/`379810`, 시세 미확인 fallback 테스트는 형식만 유효한 `999999`). 해당 2개 테스트 구간만 바꿨고, 같은 파일·다른 파일의 나머지 플레이스홀더는 `PUT /holdings` 를 타지 않아 통과 중이므로 건드리지 않았다.

**결과: 백엔드 전체 `1139 passed` · 실패 0건** (이전 1137 passed / 2 failed). 상시 빨간불이 없어져 새 실패가 즉시 드러난다.

## 7. 설계 판단 요청 — **철회 (요청 없음)**

초안에서는 **개별주 종목명 자동 조회**를 신규 외부 source 도입 건으로 올렸다. 이후 사용자가 "종목명은 직접 입력하면 된다. **평가금액·홀딩스 평가에서만 안 빠지면 안 해도 된다**" 로 조건을 좁혔고, 그 조건이 **이미 충족돼 있음을 실측 확인**해 철회한다.

**개별주는 평가에서 빠지지 않는다.**

| 지점 | 개별주 취급 |
|---|---|
| `TICKER_PATTERN` (`app/holdings.py`) | 통과. 주석에 "ETF 실존 여부는 여기서 막지 않는다 — 실존 게이트로 막으면 정상 개별주까지 차단됨" 명시 |
| 시세 조회 (`app/market_naver.py`) | 네이버 `stock/{ticker}/basic` 은 ETF·개별주 공통 |
| 평가 계산 (`app/holdings_enrich.py :: enrich_holdings`) | ticker 종류를 가리지 않음 — `market_quotes` 딕셔너리 조회뿐 |

실측 (2026-08-16):

```
069500 KODEX 200(ETF)    → name=KODEX 200   price=110,060
005930 삼성전자(개별주)     → name=삼성전자     price=274,500
000660 SK하이닉스(개별주)   → name=SK하이닉스   price=1,645,000
```

남는 제약은 **종목 관리 화면에서 종목명이 자동으로 채워지지 않는 것 하나**이며, 사용자가 직접 입력하는 것으로 갈음한다.

**참고**: 위 실측대로 네이버 응답에 `name` 이 이미 포함된다. 나중에 자동조회를 원하면 **신규 외부 source 없이** 이 경로를 재사용하면 되므로, 그때도 설계 결정 사안이 아닐 가능성이 높다. 이 사실은 백로그 항목에 기록해 두었다.

   - 남은 표 5개: `HoldingsCompareView`(14) · `OverlapTab`(11) · `AISessionsListTab`(8) · `ConstituentsTab`(6) · `EvidenceDetails`(8).
2. ~~손익 색 국내 관례 전환~~ — **완료(2026-08-16)**. 전용 토큰 `--pnl-up`/`--pnl-down` 신설. 착수 전 "두 곳" 으로 보고했으나 전수 조사 결과 **여섯 곳**이어서 전부 통일했다. 상태 색 3종은 방향이 아니므로 제외.
