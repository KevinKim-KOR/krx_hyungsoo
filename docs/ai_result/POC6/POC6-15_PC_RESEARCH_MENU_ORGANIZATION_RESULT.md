  - **예측과 결과 비교**: 기존 key `ml` 그대로 · POC6-14 카드 1개.
  - **이전 자료·실험**: 새 key `ml_legacy` · 옛 POC2 줄기 카드 5개 · 맨 위 '이 자료를 다시 만들어도 현재 예측 비교의 입력이나 모델이 갱신되는 것은 아닙니다.'
- 폴더는 한 단계이고 펼침 · 접힘만 한다(화면 전환 없음 · `useState` · 저장 없음). 활성 화면이 폴더 안이면 자동으로 펴고, 접어 두면 폴더 줄에 '· 현재 화면'을 보인다. 고른 화면의 카드만 그리고 조회한다(예측과 결과 비교 GET 1 · 이전 자료·실험 GET 4 · 전에는 한 화면에서 GET 5).
- 여섯 카드의 순서를 '제목 → 현재 결론 한 줄 → 주요 버튼 · 선택 → 설명 → 근거 표 → 접힌 자세한 정보(개발 정보)'로 바꾸고, 사용자용 글자를 쉬운 한국어로 바꿨다. 표 이름 · 파일 경로 · 작업 번호 · 실행 · 보고 · 모델 버전 id · 원문은 접힌 개발 정보로 옮겼다. 경고 · 날짜 · 판정은 기본 화면에 남는다.
- 백엔드 · API · 명령 핸들러 · 막힘 조건 · 반복 조회 · 숫자 · 단위 · 반올림은 바꾸지 않았다(변경 파일에 Python 0개 · 카드별 API 호출 · 막힘 조건 · 반복 조회 간격 변경 전후 대조 §8-2).

## 4. 지시문 외 변경 · 구현 판단

**작업 방식**: 메뉴 · 화면 · 공용 부품 · 예측과 결과 비교 카드는 개발자가 직접 고쳤다. 이전 자료 카드 5개는 카드마다 한 작업자가 고치고(같은 지시 · 목업 3 · 판정 §3 ~ §5 · 공용 부품 사용 · 핸들러 · API 변경 금지), 카드마다 다른 검토자가 변경 전 코드(`git diff`)와 백엔드 코드를 대조해 한 번 검토했다. 검토에서 찾은 결함 13건은 그 자리에서 고쳤다(아래 4-2). 그 뒤 개발자가 막힘 조건 · 조회 · 반복 조회를 다시 대조하고(§8-2), 실제 앱에서 캡처했다.

### 4-1. 판단

1. **공용 부품 `MLCardParts.tsx`**: 판정 §3 '결론을 분리하는 작은 표시 컴포넌트 허용'에 따라 결론 줄 · 접힌 개발 정보를 한 곳에 두었다. 한국 시각(`kstText` — 시간대가 붙은 ISO 만 받고, 아니면 null → 카드가 원문을 그대로 보임) · 건수 쉼표(`fmtCount` — 정수만 · 소수는 자릿수 그대로)도 같이 둔다.
2. **'갱신은 CLI 로만' 문구 정정**(준비도 · 자료 점검 · Baseline): 지금 사실과 다르다 — 「다시 만들기」 작업(`app/ml_job_runner.py`)이 CLI 와 같은 핵심 함수를 부른다. '다시 만들기는 「이전 자료와 실험 다시 만들기」에서'로 고치고 명령 이름은 개발 정보로 옮겼다(PLAN §8-3).
3. **조회 실패 결론 이름 통일 '불러오지 못함'**: 카드마다 '불러오기 실패' · '상태를 읽지 못함' 등으로 달랐던 것을 하나로 맞췄다. 실패 종류(서버 오류 HTTP n · 시간 초과 · 연결 실패 · 화면 설정 오류 · 모르는 실패)는 결론 문장에서 나눈다(근거 = `lib/api/core.ts` 의 고정 오류 문장 · 틀에 안 맞으면 '원인 확인 필요 · 원문'). 예측과 결과 비교는 POC6-14 의 `describeError` 문장을 그대로 쓴다.
4. **예측과 결과 비교**: 보고 경고(info · error)를 누적 비교 안에서 결론 바로 아래로 옮겼다(판정 §3 '결론 근처'). 결론에 '실행 기록을 확인해야 합니다'를 따로 두어 실행 기록 손상과 보고 손상을 합치지 않았다. 백엔드 고정 표시 '연구용 · 운영 미채택'은 '연구용 · 운영에 쓰지 않음'으로 보인다(모르는 값은 원문). 기록 실행 · 모델 버전은 기본 화면에 시각 · 개수만, id 는 개발 정보 · 복사문에.
5. **상대 상승 참고점수**: 결론 '미채택' + '2026-08-29 판정 · 연구용 기준선 · 투자 판단에 쓰지 않음'. 목업 3에는 날짜가 없었으나 판정 §2 '카드마다 당시 결론 · 실제 날짜'에 맞춰 넣었다. `relative_upside_v0` · `REJECT` 원문은 개발 정보. 제목 h3 → h2(다른 카드와 같은 단계) · 요청 오류 = `message error` 상자(버튼 바로 아래) · 마지막 계산 시각 = 한국 시각(전에는 브라우저 시간대 · ISO 아니면 'NaN-…') · 모르는 상태 값 = 원문 + '알 수 없는 상태 · 확인 필요'(전에는 '미실행').

#### 3. 종료 전 표시 문구 두 곳만 보완

결과서 §5에 공개한 아래 두 한계는 데이터/계산을 고치지 않고도 기본 결론의 과한 표현을 줄일 수 있다. 사용자에게 먼저 보이는 결론을 정확히 만드는 이번 목적에 따라 표시 문구만 정리한다.

| 위치·현재 문구 | 최종 표시 | 유지할 것 |
|---|---|---|
| 상대상승 참고점수의 `unavailable` → ‘데이터 부족’ | **‘결과를 사용할 수 없음’** | 바로 아래 기존 응답 사유. 파일 손상·실행 기록 없음·학습 자료 부족·후보 0건의 실제 원인을 새로 추정하지 않음 |
| Baseline의 보고 `ok` 배지 → ‘계산 정상’ | **‘보고 있음’** | 아래 경고·오류·날짜 순서 이상을 그대로 표시. 보고 존재와 모든 점검 정상 여부를 구분 |

이는 기존 상태의 **한글 표시만 바꾸는 수정**이다. 상태 분기·오류 판정·버튼 조건·백엔드·산식·응답을 고치지 않는다. 필요한 경우 짧은 설명 ‘점검 결과는 아래 경고·오류를 확인하세요’를 함께 둘 수 있다. 미채택·연구용 표시는 유지한다.

두 카드의 기존 시험 기대 문구를 맞추고 해당 카드 시험만 한 번 실행한다. 이 문자열 정리 때문에 새 시험 체계·전체 프런트 회귀·사용자 실화면 재확인·검증자 재검증을 요구하지 않는다. 지정한 문구·설명 외 새 동작 변경을 추가하지 않는다.

#### 4. 수용하는 한계와 남길 범위

다음은 결과서 §5에 남기며 이번 완료로 해소했다고 적지 않는다.
- 자료 → 학습 → 예측 → 결과 전체의 실제 상태 화면은 아직 없다.
- 상대상승의 ‘아직 계산 안 함’은 이 화면에서 아직 실행하지 않았다는 뜻이며, 과거 실행 기록이 없다는 인증이 아니다. 기존 요청 오류 핸들러가 버리는 원문은 이번에 복구하지 않았다.
- 해석하지 못하는 시간 형식은 원문으로 보이고, 실제 사용 환경 밖 모든 브라우저의 시간 해석까지 보장하지 않는다.
- 자료 점검 응답이 null일 때의 화면 중단, 죽은 작업이 ‘실행 중’으로 남을 때의 반복 조회 등 기존 동작은 미해소다. 이번 수정으로 모든 비정상 응답·작업 복구 경로가 견고해졌다고 선언하지 않는다.
- 1000px 일부 표의 줄바꿈은 가로 넘침 없이 확인된 배치의 한계로 수용한다.

이 한계들을 이유로 이번에 백엔드 복구·작업 만료 판정·API 방어 전반으로 범위를 넓히지는 않는다. 이미 존재하는 결함 기록이 있으면 그 식별자를 유지하고 중복 등록하지 않는다. 실제 사용을 막는 문제가 확인되면 별도 현재 결함으로 처리하며 대시보드 개선 완료에 묻어 두지 않는다.

실제 비교 결과가 아직 0인 화면과 일부 방법만 비교 가능한 가짜 자료의 검증은 서로 다른 근거다. 사용자에게 아직 오지 않은 성숙 결과를 확인받으려고 기다리거나 연구를 재실행하지 않는다.

#### 6. 이번 진전과 다음 설계의 기준

이번 완료는 **현재 연구와 이전 실험을 구분하고, 결론을 먼저 읽고, 쉬운 말로 근거를 확인하도록 만든 사용성 개선**이다. 투자 판단을 돕는 시스템의 실제 진전으로 기록한다. UI 개선을 단지 ML 성능 개선의 보조 작업으로 취급하지 않는다.

사용자와 합의한 기준은 다음과 같이 유지한다. 자료의 정확한 축적, 이해하기 쉬운 화면과 동선, 검증된 ML 활용을 함께 발전시키되 어느 하나가 전체 목적을 대신하지 않게 한다. ML 활용은 계속 중요한 미완료 요구이며, 이번 완료를 추천 효용 검증·총수익 확보·운영 ML 채택으로 확대하지 않는다. Q6 OPEN·기존 미완료 요구·12 SOURCE_BLOCKED·05/06/13 운영을 유지한다.

다음 설계는 **기존 대시보드의 요약 구조와 이동 동선 재정비**를 대상으로 한다. 늘어난 정보를 새 요약으로 무조건 복제하지 않고, 현재 대시보드·영역별 요약·상세가 맡는 역할과 연결을 먼저 좁게 확인한다. 자료 → 학습 → 예측 → 결과 현황 요구도 이 과정에서 기존 자료로 어디까지 제공할 수 있는지 구분한다. 구체적인 카드·조회·구현 범위는 별도 설계에서 정한다.
