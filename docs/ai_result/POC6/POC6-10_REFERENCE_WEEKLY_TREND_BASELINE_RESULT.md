   - 그래서 순수 함수로 계산해 신호 표로 넘긴다.

| 공개 main | 코드 없는 설계/PLAN/결과/판정·종료 요약·상태 문서만. 연구 구현과 연구 의존성·시험은 미포함임을 표시 |

로컬 연구 브랜치는 원격에 올리지 않는다. **연구 코드가 들어 있는 커밋을 공개 main에 merge한 뒤 파일을 삭제하는 방식도 쓰지 않는다.** 공개 문서 반영은 그 코드 커밋을 조상으로 포함하지 않는 문서 변경으로 만든다. 문서만 올린다는 말과 실제 공개 커밋 이력이 일치해야 한다.

브랜치 전환·분리 전 기존 stage와 사용자 handoff 문서를 보존한다. 완료 뒤 로컬 연구 브랜치명·구현 커밋·공식 실행 ID·산출물 해시·공개 문서 커밋을 종료 기록에서 연결한다. 미래 검산은 그 로컬 연구 코드 판과 고정 입력으로 수행하도록 명시한다. 공개 main의 PROGRAM_TRUTH 등에는 이 CLI가 main 코드로 제공되는 것처럼 쓰지 않는다.

이 작업은 Git 보관/문서 분리다. 연구 Python이나 공식 산출물을 수정하지 않으며, 분리 후 원래 연구 코드 해시가 같은지만 확인한다. 실제 연구 경로를 바꿔 구현을 다시 검증할 작업으로 확대하지 않는다. OCI 업로드·새 보관 형식은 추가하지 않는다.

### 5. 종료 기록과 기존 PLAN 판정 보완

현재는 **RESULT PASS · 보관 방식/커밋 승인 대기**다. 연구 결론 판정은 완료됐으며, 사용자가 아직 고르지 않은 공개/보관 처리가 남아 있다.

기존 PLAN 판정 §7의 ‘공개 조건 미충족 상태를 단계 종료로 기록하지 않음’은 연구 코드를 공개 배포하는 절차를 전제로 했다. **이번 RESULT에서는 사용자에게 (나)가 선택되고 아래 보존/문서 처리가 완료되면 공개 코드 배포 없이 연구 단계를 종료할 수 있도록 명시적으로 보완한다.**

(나) 선택과 승인된 작업의 성공 확인 뒤 다음을 기록한다.

```text
STATUS             = IMPLEMENTED_VERIFIED_CLOSED
RESEARCH_STATUS    = NO_REFERENCE_CASE
CODE_DISTRIBUTION  = LOCAL_ONLY
PUBLICATION        = DOCS_ONLY (공개 문서 push 성공 시)
운영 채택          = 없음
```

‘23개 구현 파일 공개 push 완료’, ‘main에서 연구 CLI 제공’, ‘라이선스 해결 완료’로 적지 않는다. 로컬 연구 보관과 공개 문서 반영의 실제 범위를 각각 적는다. 공개 main과 로컬 연구 브랜치가 서로 다른 커밋인 것은 이 방식의 의도된 상태다. 실제 문서 push가 실패하면 성공한 부분과 남은 부분을 구분한다.

결과서 끝에 이 판정 원문과 종료 절을 추가하고 PLAN·STATE·PROGRAM_TRUTH·BACKLOG에는 연구 결론·보관 범위를 맞춘다. §2-2 해석 주석도 결과서에 추가한다. **공식 report.md/json·protocol·원래 실험 산출물과 실행 코드는 그대로 둔다.**

추가 실화면 확인·PC 재기동·OCI pull·cron·키 변경·별도 handoff는 없다. 종료 작업 성공 사실과 보관 커밋/공개 문서 커밋을 짧게 보고하면 재판정 없이 닫는다. 사용자가 다른 공개 방식을 선택하면 그 선택의 미해결 조건부터 처리하며, 이 문서를 해당 방식의 공개 승인으로 사용하지 않는다.
