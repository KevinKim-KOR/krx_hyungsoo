### 4-1. 구현 판단

1. **실행 흐름 위치**: PLAN §4 는 CLI 에 lock → run → verify 를 둔다고 적었다. 실제로는 흐름 함수를 `study.lock` · `study.run` · `verify.verify` 에 두고, CLI 는 인자 · 결과 줄 · 종료 코드만 맡는다(시험이 같은 함수를 부르게).
2. **B 상태 `NOT_JUDGED`**: 설계 §6-3 은 'A를 충족한 후보만 B 판단', 판정 §3-2 는 'B 는 A 와 별도로 평가 · A 결과를 지우지 않음'이다. 둘을 함께 지키려고 다음처럼 나눴다.
   - B 의 **수치 · 조건**(RIDGE · MEDIAN 대비 개선율 · 큰 하락 날짜 · 종목 · U · 조건 참거짓)은 **모든 후보**에 계산한다.
   - **상태는 A 충족 후보만** B 규칙 순서로 정한다. A 미충족이면 상태는 `NOT_JUDGED`(report.md '판단 안 함(A 미충족)')이고, B 규칙 상태 · 사유 글은 남기지 않는다.
   - 이유(검토 M1): A 미충족 후보에 `RESEARCH_CANDIDATE` · `FEATURE_GAIN_ONLY` 가 찍히면 '정보 효과 확인'으로 읽힌다.
   - 상태 이름은 설계에 없는 이름이라 설계자 확인을 받았다 → **정식 상태 이름으로 수용**(설계자 RESULT 판정 §3). NOT_JUDGED = A 를 충족하지 않아 다음 사용 검증 후보 지위를 판단하지 않음(설계자 RESULT 판정 §3 정식 이름 · B 수치는 계산 · 보존 · 자료 부족 · 실행 실패 · U=0 · 정보 효과 확인 아님).

### 5-2. B와 큰 하락 수치의 해석

B는 §3대로 `NOT_JUDGED`, 사용 검증 후보는 0으로 확정한다. B 후보 지위를 새로 판정하지 않으면서도 다음 공개 수치는 해석에 포함한다.
