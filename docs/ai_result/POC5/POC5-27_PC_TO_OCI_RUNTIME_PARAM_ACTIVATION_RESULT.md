## 0. 요약

- **지금까지**(OPS-04 ~ POC5-26):
  - ② 버튼 [현재 기준 OCI 전달]은 PC 기준을 만들고(PC DB 활성 + PC JSON) OCI 에 JSON 만 보냈다.
  - OCI 러너는 실행 시작 때 **OCI DB 활성값**만 읽는다. 그래서 전달은 러너가 쓰는 값을 바꾸지 않았다.
  - OCI 에서 실제로 바꾸려면 수동 스크립트(`create_three_push_runtime_param.py`)를 돌려야 했다. 이 스크립트는 전달된 JSON 이 아니라 **코드 기본값으로 새 PARAM 을 만든다.**
  - 전달 스크립트는 확인 전에 파일을 교체했고, 확인 스크립트가 없으면 '확인 생략'으로 성공 처리했다. 안팎 제한 시간도 맞지 않았다(합 180초 > 화면 120초).
- **이제**(설계 §2 · §3 · §4 · 판정 §1 ~ §5):
  - 버튼 이름은 **[현재 기준 OCI 적용]**이다. 누를 때만 실행된다(기동 · 조회 · 저장 · 전달로 자동 실행 없음).
  - **순서**(PC `app/three_push_param_activation.py`):
    1. PC 기준 만들기(지금 그대로 · 코드 기본 14값).
    2. **OCI 활성값을 먼저 읽는다**(`mode=ro`). 못 읽으면 OCI 에 아무것도 쓰지 않고 '적용 실패'.
    3. 유효값이 같으면 **OCI 쓰기 0**(전달 · 업로드 · 새 버전 · 포인터 변경 없음) → **'일치 · 변경 없음'**.
    4. 다르면 JSON 전달(이제 tmp 를 확인한 뒤에만 교체) → OCI 쪽 도구를 임시 업로드해 OCI venv 로 실행(PC 가 보낸 JSON 바이트의 SHA-256 을 함께 넘김) → 임시 도구 삭제.
    5. 도구 결과를 그대로 믿지 않는다. **함께 돌아온 실제 활성값이 요청과 같을 때만** 성공이다. 결과가 애매하면 같은 예산 안에서 **읽기만** 0 · 2 · 5초 다시 한다.
  - **OCI 쪽 도구**(`scripts/apply_three_push_param_oci.py` · OCI 에 이미 있는 저장 함수만 사용):
    - 전달된 파일이 PC 가 보낸 바이트와 같은지 SHA-256 대조(다르면 쓰기 전에 실패 · 다른 값을 대신 발행하지 않음).
    - 파일 검증(`from_dict`) → 지금 활성값과 비교(같으면 쓰기 없이 SAME).
    - 버전 기록(PC 값 그대로) → DB 에서 다시 만든 후보가 러너 읽기 함수를 통과하고 유효값이 요청과 같은지 검사.
    - 직전 활성 기억 → 전환(한 문장 upsert · 빈 활성 상태 없음) → 다시 읽기.
    - 다시 읽은 값이 요청과 다르면 직전 버전으로 한 번 되돌리고, **이전 값까지 읽혀야만 '적용 실패'**다. 되돌림 실패 · 확인 불가는 '확인 불가'다.
    - 발행 · 복구는 잠금 파일(`state/three_push/params/.param_apply.lock` · git 무시 폴더)로 한 번에 하나만 돈다. 앞 실행이 아직 돌면 손대지 않고 '확인 불가(busy)'로 끝내고, PC 는 읽기만 다시 해 판정한다.
    - 복구용 `--list`(읽기만) · `--activate-version <id>` 도 같은 도구에 있다.
  - **결과 4종**(카드 배지 · 문구):
    - 일치 · 변경 없음 — "OCI 활성값이 이미 지금 기준과 같습니다 (14/14). 새로 바꾼 것은 없습니다."
    - 적용 완료 — "OCI 활성값을 지금 기준으로 바꾸고 다시 읽어 같음을 확인했습니다 (14/14). 다음 실행부터 이 기준을 씁니다."
    - 적용 실패 — "OCI 에 적용하지 못했습니다 ({사유}). 기존 OCI 활성값이 그대로입니다." + 안내 "OCI 활성값은 바뀌지 않았습니다 …"
    - 확인 불가 — "적용 결과를 확인하지 못했습니다. OCI 활성값이 바뀌었는지 알 수 없습니다." + 안내 "… 자동으로 되돌리거나 다시 적용하지 않습니다."
  - **① '운영 기준 활성' 행**(판정 §3): 적용 요청 **안에서 실제로 읽은 값**으로만 이 행의 캐시를 바꾼다(다른 행 · 다른 OCI 상태는 다시 읽지 않음 · 폴링 없음).
    - 같음: "지금 PC 기준과 OCI 활성값이 같음 (14/14) · {기동 때 | 적용 때} 확인 M/D HH:MM"
    - 다름: "OCI 는 다른 값으로 동작 중 (14개 중 N개 다름 · 알림 종류 2 · 안전 정책 1 …) · … 확인 M/D HH:MM"
    - 확인 불가: "적용 뒤 OCI 활성값을 확인하지 못함 — 다시 적용하면 먼저 실제 값을 읽음 · 적용 M/D HH:MM"(기동 때의 일치를 방금 확인한 것처럼 보이지 않게)
    - 적용 전에 실패해 읽은 값이 없으면 행을 그대로 둔다(읽지 않은 값 · 시각을 채우지 않음).
  - **예전 '전달' 기록**(판정 §5): '미적용'이 아니라 **'이전 전달 기록'**(회색) + "이전 전달 기록(10-04 11:09) · 활성화 확인 없음. 지금 OCI 활성값과의 일치 여부는 위 ① '운영 기준 활성' 행에서 확인하세요."
  - **전달(sync) 결함 4건**(판정 §5): tmp 확인 뒤에만 교체 · 확인 스크립트 없음/업로드 실패 = 실패 · 단계별 제한 시간 합 38초(전달 예산 40초) · 전체 예산 105초(화면 120초 안) · 서버 적용 잠금 하나(진행 중이면 '적용 중').
- **바뀌지 않는 것**: 러너 · 원장 · 중복 발송 키(판정 Q2) · OCI cron · PUSH 발송 · Holdings · ML · 수집. 적용은 러너를 실행 · 중단 · 재시작하지 않고 발송하지 않는다.

## 5. 알려진 한계 / 미완성

- **중복 발송 키(판정 Q2 · 러너 불변)**: 값이 다른 PARAM 으로 바꾼 날, 이미 돈 칸(예: 09:15 보유 브리핑)을 손으로 다시 돌리면 중복 발송 키(`push_kind::param_id::날짜(+칸)`)가 달라져 막지 못한다.
  - 같은 값이면 OCI 새 버전이 없어 키가 그대로라 해당 없다(지금 OCI = PC 14/14).
  - 점검 · 복구 때 같은 날 같은 칸을 손으로 다시 돌리지 않는다.
- **PC 쪽은 누를 때마다 쓴다**(기존 동작 · 판정 §2): PC 기준 생성이 PC DB 새 버전 · 활성과 PC JSON 을 매번 만든다. '쓰기 0'은 OCI 쪽 이야기다.

- **잠금은 두 겹이고 범위가 다르다**(설계자 RESULT 판정 §2 정리): PC 잠금은 PC 백엔드 프로세스 하나 안의 동시 적용만 막는다(지금 uvicorn 1개). OCI 도구 잠금은 OCI 에서의 발행 · 복구 실행을 한 번에 하나로 직렬화한다(겹치면 손대지 않고 busy → PC 는 읽기로 판정). 두 번째 실행이 SAME 으로 끝나는 것은 그때 OCI 의 실제 유효값이 그 요청값과 같을 때뿐이다 — 서로 다른 요청값이면 SAME 이 아니라 각자 비교 · 발행된다(다중 PC 지원은 범위 밖 · 새로 만들지 않음).
- **① 의 다른 행은 기동 때 값 그대로다**(판정 §3 · 폴링 없음). 적용은 '운영 기준 활성' 행만 바꾼다.

- **적용 응답을 받지 못한 뒤의 '확인 불가'는 그 화면에서만의 표시다**(r1 · r2 정정 · 설계 §4). 화면을 다시 열면 서버 기록(끝났으면 그 요청의 실제 결과 · 진행 중이면 '적용 중')이 보인다. '마지막 적용' 칸은 마지막으로 기록된 적용 시각 그대로 둔다(이번 시도의 시각을 모르므로). 첫 상태 조회부터 실패했다면 '적용 기준' · '마지막 적용'은 '—'다.

## 3. 실제 확인 범위와 순서

원 설계의 실제 확인 조건은 이미 충족했다. 사용자 실화면에서 '일치·변경 없음'을 확인했고, 개발자의 별도 읽기 전용 대조에서 OCI 활성 버전·활성화 시각·버전 수 2가 그대로이며 임시 파일이 없음을 확인했다는 §7 기록을 수용한다.

이 확인은 개발 서버의 미커밋 구현에서 RESULT 판정 전에 수행됐다는 순서를 그대로 남긴다. 사용자 원격 쓰기 구현 승인과 명시 클릭이 있었으며, 해당 실호출의 OCI 쓰기는 0이었다. r1/r2 정정은 일반 성공 흐름을 바꾸지 않았다는 보고와 검증 근거를 수용한다. **같은 실화면·버튼 클릭·OCI 대조를 다시 요구하지 않는다.**

'다른 값의 실제 OCI 활성 전환/실제 운영 복구까지 실측 완료'라고 쓰지 않는다. 그 경로는 격리 시험이고 실제 OCI 확인은 동일값 경로다. 이 범위는 원 설계가 허용한 종료 근거이며 시험 때문에 실제 정책을 바꿀 필요가 없다.

## 4. 종료 지시와 다음 범위

1. 판정 원문을 결과서에 붙이고 RESULT·PLAN·STATE·PROGRAM_TRUTH의 현재 상태를 종료로 맞춘다. BACKLOG #50은 완료로 정리하고 과거 조건부/진행 표시는 이력으로 보존한다.
2. 사용자 승인 범위에서 구현·시험·종료 기록을 커밋·push한다. 최종 파일 목록과 건수는 실제 범위에 맞추고 사용자 handoff는 제외한다. 이번 판정만으로 새 커밋·push 승인을 대신하지 않는다.
3. 반영 후 IMPLEMENTED_VERIFIED_CLOSED로 종료한다. 추가 재검증·추가 실화면·추가 실제 적용·OCI pull·PC 재기동·거래일 대기·별도 인계 문서는 필요 없다.
4. 사용자 선정 개발 대상의 잔여는 **#48 추가 runtime 자료원**이다. 사용할 자료·소비 화면/알림·기준일·실패 의미·자료원을 정하는 다음 설계로 진행한다. 이 판정으로 원래 목록의 모든 자료 수집이나 새 외부 호출을 승인한 것은 아니다.
5. ML 고도화 목표·검증·종료 기준 설계 병행은 유지한다. #50의 완료가 프로젝트 전체 또는 ML 고도화의 완료를 뜻하지 않는다. 조건부 백로그를 다시 전부 개발 대상으로 돌리지 않는다.
