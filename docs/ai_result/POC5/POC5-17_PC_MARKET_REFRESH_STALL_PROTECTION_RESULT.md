## 0. 요약

- **요청 대기 상한**: PC 갱신 작업(`app/market_refresh_service.py :: _execute_refresh_job`)에서 FinanceDataReader 를 부르는 세 단계를 기존 `fdr_request_timeout()`(요청 20초 · OCI 배치 · PC VIX 와 같은 함수)으로 감쌌다.
  - 세 단계: ETF 목록 · ETF 가격 · 보유 개별주.
  - 20초는 연결 · 읽기 대기 설정이다. 종목 하나나 작업 전체가 20초 안에 끝난다는 보장이 아니다(판정 §3).
  - 멈춘 요청은 예외가 되어 그 종목만 실패로 세고 다음 종목으로 간다. 작업이 끝까지 가므로 마지막 기록에서 `running` 이 풀린다.
- **연속 시간 초과 중단(ETF 가격만)**: 공유 함수 `app/market_data_fdr.py :: refresh_price_history` 에 선택 인자 `stop_after_consecutive_timeouts` 를 더했다. PC 가 5(`PRICE_TIMEOUT_STOP_STREAK`)를 넘긴다.
  - 조회한 종목의 결과가 연속 5번 실제 시간 초과면, 다섯 번째를 처리한 뒤 남은 종목은 조회하지 않는다.
  - 실제 시간 초과 = `requests` Timeout 계열 · 내장 `TimeoutError` · 본문을 받는 중의 읽기 시간 초과(`requests` 가 `ConnectionError(urllib3 ReadTimeoutError)` 로 올림 · §4-5). 예외 종류로만 판단하고 메시지 문자열로 판단하지 않는다.
  - 시간 초과 아닌 결과(성공 · 빈 자료 · HTTP 오류 · 연결 거부 · 파싱 오류 · 저장 실패)가 끼면 연속 수를 0으로 되돌린다.
  - 인자를 주지 않는 호출(OCI 배치)은 그대로다.
- **멈춘 회차의 결과**: `failed`. 뒤 단계(보유 개별주 · KOSPI · VIX · NAV)는 기존대로 돌고, 성공해도 completed 로 덮이지 않는다.
  - 중단 사실은 공유 함수가 멈추는 순간, 가격 기록 행을 쓰기 **전에** 선택 인자 `on_stop(조회하지 않은 수)` 로 서비스에 넘어간다. 그래서 그 뒤 가격 기록 쓰기가 실패해도 `failed` 다. 이때 사유 끝에 `· refresh_unexpected: …` 를 붙인다(검증자 r1 P2 정정 · §11).
  - 성공 시각을 만들지 않아 6시간 대기가 시작되지 않는다. 작업이 끝난 뒤 바로 다시 누를 수 있다.
  - 화면 사유(판정 §5 문장): '가격 조회가 연속으로 시간 초과되어 남은 N종목은 받지 않았습니다. 앞서 받은 자료는 보존했습니다. 갱신 작업 종료 후 다시 실행할 수 있습니다.'
  - 가격 기록 행(`FinanceDataReader/prices`)은 기존 뜻(시도 = 대상 · 실패 = 대상 − 성공)을 그대로 둔다. 사유 앞에 `stopped_after_consecutive_timeouts=5 queried=Q not_started=N` 을 적는다.
  - 반환값 `PriceRefreshResult` 에 `not_started` · `stopped_on_timeouts` 를 더했다(기본 0 · False).
- **그대로 둔 것**: 일부 종목만 실패한 완료(기존 6시간 대기 · 판정 Q2) · ETF 목록 실패 · 보유 개별주 실패 문구 · NAV(8초) · KOSPI(40초) · VIX(20초) · 서버 재시작 정리 · 화면 · 터미널 수동 스크립트(판정 Q3).

## 4. 지시문 외 변경 · 구현 판단

1. **마지막 다섯 종목이 시간 초과인 경우**: 남은 종목이 없으므로 '중단'이 아니다(`not_started` 0). 기존 부분 실패 규칙대로 판정한다(시험 `test_last_five_timeouts_with_nothing_left_is_not_a_stop`).
   - **설계자 RESULT 판정 §2에서 보충 확정 · 수용(2026-10-16)**: 조기 중단과 failed 강제는 아직 조회하지 않은 종목이 남아 실제로 순회를 중단한 경우에만 적용한다.
   - 남은 종목이 0이면 기존 성공 · 부분 실패 · 전체 실패 판정(completed 면 6시간 대기)을 따른다. 시간 초과 실패 건수는 그대로 남긴다.
2. **내장 `TimeoutError` 도 시간 초과로 셈**: 소켓 시간 초과(`socket.timeout` = `TimeoutError`)가 `requests` 로 감싸지지 않고 올라오는 경우를 위해서다. 판정 §4 '실제 시간 초과로 식별되는 경우'에 넣었다.
3. **PROGRAM_TRUTH 자료원 표 정정**: 기존 문구 'NAV 단계 … timeout 0' 은 사실과 달랐다. NAV 는 `urlopen(timeout=8)` 을 쓴다. 이번 갱신 때 같이 정정했다.
4. **서비스 파일 줄 수**: 처음 반영 때 601줄이 되어 PLAN '600줄 미만'을 넘었다. 문구를 상수로 바꾸고 주석을 줄여 595줄로 맞췄다.
5. **본문 읽기 중 시간 초과도 시간 초과로 셈**(자체 확인 · §6-5)
   - 로컬 실측(requests 2.34.2 · urllib3 2.7.0): 헤더를 받은 뒤 본문이 멈추면 `requests` 는 `Timeout` 이 아니라 `ConnectionError` 를 올리고, 그 안(`args[0]`)이 urllib3 `ReadTimeoutError` 다.
   - 이것을 세지 않으면 이런 원천에서는 연속 판정이 늘 0으로 돌아가 중단이 걸리지 않는다. 예외 종류(`args[0]` 이 urllib3 `TimeoutError`)로 식별해 센다. 메시지 문자열은 보지 않는다.
   - 연결 거부 등 다른 `ConnectionError`(안이 시간 초과가 아님)는 그대로 세지 않는다.

## 5. 알려진 한계 / 미완성

- **전체 종료 보장 없음(판정 §3)**: 요청 상한은 연결 · 읽기마다 걸린다. 다음은 막지 못한다. 서버 재시작 정리가 마지막 수단으로 남는다.
  - 주소 찾기(DNS) 대기 · 여러 주소 연결 · 조금씩 계속 오는 응답
  - 파싱 · 저장 등 네트워크 밖 지연
- **프로세스 공통 바꿔 끼우기(판정 §6)**: `fdr_request_timeout` 은 감싼 동안 `requests.Session.request` 를 프로세스 전체에서 바꾼다.
  - 같은 서버의 다른 요청 중 timeout 이 없는 것에도 20초가 들어간다.
  - 감싸는 범위는 PC FDR 단계 블록뿐이고, 성공 · 예외 모두 원래 함수로 되돌린다(시험).
- **실제 외부 장애 재현 없음**: 로컬 소켓 서버 · 가짜 fetcher 근거다. 실제 네이버 장애를 만들지 않았다. 정상 갱신 실행은 사용자가 필요할 때 한다(판정 §7).
- **터미널 수동 스크립트**(`scripts/refresh_market_timeseries.py`)는 그대로 시간 제한이 없다(판정 Q3).
- **사유 문구 언어**: 다른 실패 사유(`universe_fetch_failed: …` · `price_partial_failure: fail=N`)는 기존 영어 코드 그대로다.
- **기존 판정 관찰(이번 범위 밖 · 바꾸지 않음)**: ETF 목록을 받은 뒤 가격 단계 바깥에서 예상 못 한 예외가 나면 그대로 둔다.
  - 예: 종목 목록 읽기(`list_etf_tickers`) 실패.
  - 기존 판정은 가격 시도 0건이라 `completed`(사유 `refresh_unexpected: …`)이고 6시간 대기가 시작된다.
  - 연속 중단이 아닌데 가격 기록 행 쓰기가 실패한 경우도 같다(가격 시도 수를 못 받음 → `completed` · `refresh_unexpected`).
  - 시간 초과와 무관하고 판정 §4 '다른 단계 정책을 새로 바꾸지 않는다'에 따라 고치지 않았다(시험 두 건이 이 기존 동작을 그대로 확인).
  - **설계자 RESULT 판정 §3: 정상 완료로 승인한 것이 아니라 남은 기존 결함**이다. BACKLOG `DEF-PC-REFRESH-UNEXPECTED-COMPLETED` 로 등재했다(이번 범위 미수정 · 다음 설계 우선 후보).

## 6. 다음 검증자(Codex)에게 알릴 점

1. **연속 판정**: `market_data_fdr.refresh_price_history` 의 `consecutive_timeouts` 는 예외 경로에서만 늘고, fetch 가 값을 돌려주면 0이 된다(그 뒤 빈 자료 · 저장 실패여도 0). 다음 종목 시작 전에 확인하므로 다섯 번째 시간 초과를 처리한 뒤 멈춘다.
2. **기록 뜻**: `attempted` · `fail` 은 기존처럼 대상 기준이다(OCI 배치 · 화면 상태 필드와 같은 뜻). 미조회 수는 `not_started` 와 기록 사유로 구분한다(판정 §5 '기존 의미 보존 + 사유에 별도').
3. **failed 판정 위치**: `success_overall = … and not price_stopped`. 뒤 단계 결과와 무관하다. `vix_only_failure` 는 `error_summary` 가 있으므로 거짓이 된다(VIX 다시 받기 표식 안 생김).
4. **실제 상한 시험**: `test_real_request_timeout_ends_the_job` 은 연결만 받고 응답하지 않는 로컬 소켓 서버에 `requests.get` 을 보낸다. 같은 함수에 상한만 0.3초로 줄여 끼운다(운영 값 20초 · 시험 쪽 `functools.partial`).
5. **변이**: 저장소 사본에서 14개 · 모두 검출(§8).
6. **중단 사실 전달(검증자 r1 P2 정정)**: 서비스는 `price_stopped` 를 반환값이 아니라 `on_stop` 으로 받은 값(`stop_box`)으로 정한다.
   - 반환 전 가격 기록 쓰기 예외가 나도 중단은 `failed` 다. 기록 실패 사유를 숨기지 않고 사유 끝에 붙인다.
   - 인자 없는 호출(OCI)은 `on_stop` 을 넘기지 않으므로 그대로다.

### 6-5. 독립 검토

- 독립 검토 에이전트를 PLAN 단계 · 구현 단계에 한 번씩 띄웠으나 두 번 모두 네트워크 오류(API 서버 연결 실패 · ENOTFOUND)로 중간에 멈춰 결과를 받지 못했다.
- 구현 단계 검토가 멈추기 직전 마지막 기록은 '예외 경로 복원 시험'을 보던 중이었다. 그 항목과 검토 요청서의 질문을 개발자가 직접 확인했다.
  - **예외 경로 시험 보강**: 처음 시험은 ETF 목록 fetcher 안에서 예외를 냈는데, 목록 함수가 안에서 잡아 감싼 블록을 통과하지 않았다.
    - 블록 밖으로 실제로 빠져나가는 두 경로(가격 단계 목록 읽기 · 보유 개별주 단계)로 바꿨다.
    - `finally` 복원을 뺀 변이(M11)를 잡는다.
  - **본문 읽기 시간 초과 누락**: `requests` 가 `ConnectionError` 로 감싸 올리는 경우를 찾아 고쳤다(§4-5 · 시험 2건 · 변이 M12).
  - OCI 경로 무변경 · 세 단계 감쌈 · VIX 단계 중첩 없음 · 전체 갱신과 VIX 다시 받기 같은 잠금 · 문서 문구는 §8 시험 · 변이와 코드 대조로 확인했다.
