### 1.2 중복률 탭 — 표 2개 → 카드

카드 골격은 다른 화면과 같은 `.wb-hrow.compact`(좌 2단 + 우 지표)를 **그대로 재사용**했고,
이 화면에만 필요한 것(쌍 표기 `↔` · 공통 종목 칩 · 중복률 막대)만 CSS 로 더했다.

**① ETF 쌍별 중복률**

```
KODEX AI반도체TOP2플러스 ↔ HANARO Fn K-반도체        93.22% 비중 중복 ┃ 공통 상위 종목 8 / 10
395160 / 395270 | 삼성전자 · SK하이닉스 · 한미반도체 …               ┃ ▉▉▉▉▉▉▉▉▉░
```

**② 반복 등장 핵심 종목**

```
SK하이닉스                                        5 개 ETF ┃ 최고 비중 27.58%
000660 | PLUS 글로벌HBM반도체 27.58% · HANARO … 26.58% …   ┃ PLUS 글로벌HBM반도체
```

### 1.3 사용자 확정 3건

**① ETF 이름** — 티커만 나와 어느 ETF 끼리 겹치는지 읽을 수 없었다.
**응답의 `etf_name` 은 쓸 수 없다** — 네이버 구성종목 API 가 ETF 자기 이름을 주지 않아
**저장 시점부터 전부 `NULL`** 이다(DB 실측 100행 전부). 그래서 화면이 이미 들고 있는
**draft 후보 스냅샷**에서 이름을 가져온다. `ETFExposureView` 가 맵을 만들어
`OverlapTab` · `ConstituentsTab` 양쪽에 넘긴다. **백엔드·API·수집 경로 변경 0건.**

- draft 에 없는 티커는 **티커 그대로** 둔다 — 이름을 지어내지 않는다.
- 응답의 `etf_name` 이 나중에 채워지면 그 값이 우선한다(`c.etf_name ?? nameByTicker[...]`).

**② `최고 비중`** — 응답 `items` 중 최대값을 고르고, 그 ETF 이름을 아래 줄에 적는다.
칩도 비중 높은 순으로 놓는다(**값은 그대로, 순서만**).

**③ 정렬** — 세그먼트 3종(`중복률 높은순`(기본) / `공통 종목 많은순` / `응답 순서`).
이전에는 정렬이 없어 93% 짜리 쌍이 목록 중간에 묻혔다.
**겹침 없는 쌍(`weighted_overlap_pct == null`)은 0 으로 취급하지 않고 항상 뒤로 보낸다.**

### 1.4 표시 계약

| 상황 | 표시 |
|---|---|
| 겹치는 종목 없음 | `-` + `겹치는 종목 없음` 배지 — **0% 로 쓰지 않는다** |
| 티커 없는 구성종목 | `티커 없음` 배지 — **해외 종목이라 단정하지 않는다** |
| 공통 핵심 종목 | 쉼표 한 줄 → **칩 단위**(몇 개인지 눈으로 셈) |
| 각 ETF 내 비중 | `0167A0:26.26%, …` → 칩 + **ETF 이름** + 비중 |

### 1.5 구성종목 탭 식별 줄 (사용자 실화면 지적)

```
이전   [ok] 0223A0 · RISE 코스닥커버드콜액티브 · naver_stock_etf_component · (캐시)
이후   RISE 코스닥커버드콜액티브  [ok]  0223A0  [캐시]
```

- **이름 먼저(굵게) · 티커는 뒤에 작게** — 다른 카드 규칙과 동일.
- **source 를 summary 줄에서 제거** → 펼친 상세 맨 위로 이동. 버리지 않은 이유는
  "어디서 온 값인지" 를 필요할 때 볼 수 있어야 해서다. 이동하면서 **`asof` 를 함께
  표시**했다(이전에는 개별 ETF 기준일을 볼 방법이 상단 요약뿐이었다).
- **배지를 공용 `.wb-hb` 로 교체.** 이 화면만 테두리 있는 알약
  (`.constituent-status-badge` — `border-radius: 9999px` + `1px solid`)이라 형태가 달랐다.
  색 구분은 유지(`ok` 초록 / `unavailable` 회색 / `skipped_timeout` 주황).
  **정상일 때도 배지는 남겼다** — 사용자 판단("배지 있어도 되는데").

> 다른 화면은 *정상이면 배지 숨김* 규칙을 쓴다. 이 화면만 다르게 두는 것은
> **사용자가 명시적으로 정한 것**이며, 형태(클래스)만 통일했다.

### 5.1 설계 판단 요청 2건 — 별도 문서로 분리

| # | 항목 | 왜 결정 불가 |
|---|---|---|
| ① | 구성종목 **상위 10건 제한** | `MAX_TOP_K = 10` 은 *"외부 fetch 의존성을 강하게 가두기 위한 K6 방어 정책(지시문 §4)"*. 조회가 아니라 **저장 시점** 제한 |
| ③ | 구성종목 **등락률 미연결** | 채우려면 개별주 시세 조회 신설 → `KILL_SWITCHES §5 "실시간 외부 API 의존 강화"` |

> **⚠ 정정 (2026-08-19)**: 위 참고에 *"캐시에 ETF당 30건 저장된 과거분이 있다"* 고
> 적었으나 **사실이 아니다.** DB 실측 — `최대 rank(전체) = 10`, 스냅샷(ETF+asof) 50개가
> **전부 10행**이다. `0167A0` 을 30건으로 본 것은 `group by etf_ticker` 로만 세어
> **서로 다른 날짜 3개(06-17·06-19·06-22)를 한 스냅샷으로 착각**한 것이다.
> ETF당 30건이 저장된 적은 없고, 따라서 "재수집하면 덮인다" 는 걱정도 근거가 없었다.
> 이 잘못된 사실이 설계 판단 근거에 들어갔다 — **보고 정확성 위반**이다.
