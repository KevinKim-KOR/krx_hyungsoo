## 3. 구현 내용

### 3-1. 흐름(맥북 · Windows PC)

```text
맥북        archive --selected <고른 ETF> [--answer GPT=<파일> …]
            → 맥북 서버 「주간 ETF 점검」 읽기 조회 한 번(프록시 · 되돌림 없음) → cases/<사례>/ 응답 원본 · case.json · 답
            lock-key --case <사례> --key <채점용 메모>   (묶음 전에만 · 묶음이 생기면 다시 잠그지 못함)
            pack --case <사례>   → bundles/<묶음>/bundle.zip(실행기 · 공유 코드 4개 · .bat · README · 입력 · manifest)
형수님      USB 로 Windows PC 의 비어 있는 새 폴더에 풀고 run_summary.bat 한 번
Windows PC  묶음 해시 → 앞 결과 확인(같은 묶음만) → 환경(Python · nvidia-smi · Ollama 판 · 지정 모델 digest) → 합성 점검
            → 토큰 세기 → 본 호출 직전 관문 → 시작 표지 main_started.json → 실제 요약 → 받은 원문 main_raw.json
            → result_<n>/ result.json · one_page.html · hashes.json
형수님      result 폴더를 모두 지우지 말고 USB 로 맥북에 복사
맥북        merge --case <사례> --result <폴더>   → 대조 · runs/<묶음>__<실행 id>/ 보관(한 폴더씩 · 앞 폴더부터)
            report --case <사례> --score <채점> --usage <사용 기록>   → 비교표 · AC4
```

### 3-2. Windows 실행기(표준 라이브러리만)

- **이 PC 안만:** Ollama 주소는 127.0.0.1 · localhost · ::1 만 받는다. 프록시(환경 변수 · Windows 레지스트리)를 쓰지 않고 되돌림을 따라가지 않는다(판정 Q5). 맥북 조회도 같은 방식이다.
- **정체 먼저(검토 B):** 실행의 첫 줄에서 manifest(못 읽으면 묶음 입력)의 사례 · 묶음 id 를 결과 기록에 남긴다. 묶음 입력을 못 읽어 '묶음 바뀜'으로 멈추거나 묶음 확인 중 Ctrl+C 로 꺼져도 맥북이 그 기록을 받는다. 실행 코드 해시는 묶음 확인 때 잰 값을 그대로 쓴다(끝에 다시 읽지 않음 · 검토 E).
- **설치 · 받기 없음:** Ollama 가 없거나(`NEED_OLLAMA`) 지정 태그가 없으면(`NEED_MODEL`) 모델을 부르지 않고 멈춘다.
- **본 실행 전 판 고정(판정 Q3):**
  - 어떤 모델 호출보다 먼저 Ollama 판과 지정 모델 digest(`sha256:` + 64자 또는 64자)를 읽는다. 없거나 꼴이 다르면 `NEED_ENV_RECORD` 로 멈춘다.
  - 고정값은 같은 폴더의 같은 묶음 앞 실행 중 합성 점검까지 간 실행(또는 본 요약 시작 표지)의 digest 다. 판 확인에서 거부된 digest 는 고정값이 아니다(검토 C). 지금 digest 가 고정값과 다르면 '모델' 멈춤(`NEED_ENV_RECORD` · 멈춤 분류 `MODEL`)이고, 같은 폴더 다시 실행도 막는다(모델 교체는 설계자 판단).
  - 본 요약 뒤에 다시 읽어 바뀌었으면 '기술 실패', 다시 읽지 못했으면 상태는 그대로 두고 메모만 남긴다(§14-5 Q-C).
- **합성 점검:** 실제 값이 없는 같은 형식의 입력이다. 길이는 본 사례 이상이고 2.2만 자보다 짧지 않다. 통과해야 본 요약으로 가고, 못 넘으면 종류를 남긴다.
  - 설정: 문맥 · 출력 길이 · 잘림 · 메모리 부족 호출 오류 · CPU 단독(문맥이 GPU 메모리에 들지 않았을 수 있음 · PLAN §2-2 '설정 문제(문맥 · 출력 길이 · 메모리)')
  - 모델: 한글이 거의 없음 · 깨진 글자 · 형식 다름 · 표지 복창 안 함
  - 환경: 드라이버 551.61 미만 · 판을 못 읽음 · GPU 실행 미확인(CPU 단독 · ps 없음) · `server.log` 에 이번 호출 기록 없음 · 할당 문맥 미기록 · 그 밖의 호출 오류
  - 글자당 토큰 수도 남긴다.
- **본 호출 직전 관문(검증자 r2 F6 · 판정 §3 '입력 토큰과 출력 여유'):** 토큰 세기 뒤 아래를 모두 넘어야 본 요약을 부른다. 하나라도 못 넘으면 `PRE_MAIN_STOPPED` 로 멈추고 본 요약을 부르지 않는다(한 번뿐인 시도를 쓰지 않음).
  - 환경: 판 · digest 를 다시 못 읽음 · 판이 처음과 다름 · 세기 호출 오류 · 세기 값 없음 · 세기의 `server.log` 기록을 못 읽음(줄이 늦게 붙는 경우를 위해 최대 5초 다시 읽음) · 합성 점검이나 세기 뒤 모델이 안 내려감(본 호출이 캐시를 읽음 · PLAN §2-2)
  - 모델: digest 가 처음과 다르거나 빠짐
  - 설정: 세기에서 잘림 · 입력 토큰이 문맥 이상 · 입력 + `num_predict` 가 문맥 초과(출력 여유 부족) · 메모리 부족 세기 오류
- **입력 확인(판정 §3):** 한 값으로 정하지 않는다. 아래가 모두 맞아야 '완료'이고, 표지 복창은 따로 적는다(표지만 빠지면 답을 버리지 않음).
  - 같은 모델 · 템플릿으로 두 번 센 입력 토큰(세기 호출 · 본 호출)이 같다.
  - 실제 할당 문맥(`/api/ps` · 없으면 `ollama ps` 글)이 요청 이상이다.
  - 입력 + 출력 토큰이 그 안에 든다.
  - 종료 이유가 정상이다.
  - `server.log` 의 이번 호출 구간에 `/api/chat` 줄이 있고, 진짜 잘림 기록이 없다. 정상 줄 `truncated = 0` 은 잘림이 아니다.
- **새로 읽기:** 호출마다 모델을 내리고 `/api/ps` 에서 빠질 때까지 기다린다(최대 60초 · 걸린 시간 기록). 캐시 토큰(`prompt_eval_cached_count`)이 있으면 따로 적는다.
- **GPU:** `100% GPU` · 혼합 · CPU 단독 · ps 없음 · 측정 누락을 나눠 적는다. 실행 중 1초마다 `nvidia-smi` 를 남긴다(표본을 못 떠도 본 호출은 한다 · 기록만).
- **첫 결과 보존(검증자 r1 F1 · r2 F5):**
  - Ctrl+C 는 시작 표지를 쓰기 전부터 미룬다. 표지 → 본 호출 → 받은 원문 → 받은 값(본문 · 토큰 · 종료 시각)을 다 채운 뒤에 풀고 멈추며, 이때 진단은 건너뛴다(구분 · 한 장은 남음).
  - 시작 표지 `main_started.json`(실행 id · 묶음 · 사례 · 결과 폴더 · 시각 · Ollama 판 · 모델 digest · 설정)은 본 호출 직전에 쓴다.
  - 응답을 받으면 다른 무엇보다 먼저 받은 원문 `main_raw.json` 을 쓴다(끊겨도 남은 바이트를 지키려고 바로 씀). 원문을 못 쓰면 그 오류를 남기고, 받은 값은 결과 기록에 그대로 남긴다.
  - 시작 표지 · 한 장 · 결과 · 해시는 임시 이름(`.<이름>.part`)에 다 쓴 뒤 이름을 바꾼다. 그래서 다 쓴 파일이거나 아예 없다. 이름 바꾸기가 잠깐 막히면(백신 · 동기화 프로그램) 다시 시도하고, 덮어쓰지 않는다. 해시 목록에는 시작 표지 · 받은 원문도 들어간다.
  - 멈춤 종류는 상태와 따로 `stop` 칸에 남는다. 멈춤 안내를 띄우는 중 Ctrl+C 로 상태가 '중단'이 돼도 무슨 멈춤이었는지 남는다(검토 A).
  - 본 요약 응답을 받은 뒤 중단 · 실행기 오류로 끝나면 응답 구분은 '기술 실패'(실행이 끝나지 않음 · PLAN §2-4 ① '중단')다. 원문 · 한 장은 남는다(검증자 r3 F11).
  - 합성 점검의 구분과 통과 판단은 한 번에 기록한다(둘 사이 중단으로 반쪽 기록이 남지 않게 · 검토 E).
  - 실행 시간 `run_wall_s` 는 단조 시계로 잰다(PC 시계 맞춤과 상관없음 · 검토 H).
  - 진단(ps · 로그 · 모델 내림) 실패는 기록만 하고 계속한다. 한 장을 만들거나 쓰지 못해도 결과 · 해시 · 받은 원문은 남는다(`render_error`).
  - 결과 폴더는 덮지 않는다. 실행 내내 `running.lock` 을 열어 두고 끝에 지운다.
- **같은 폴더 다시 실행(회수와 같은 해석 · 검증자 r3 F9):** 앞 폴더를 폴더 번호 순으로 읽는다. `result.json` 이 없으면 다 쓴 `.result.json.part` 를 그 실행의 기록으로 읽는다(쓰는 중 깨진 임시 결과는 기록 없음). 다른 묶음의 결과는 뺀다. 앞 폴더가 아래 중 하나면 모델을 부르지 않고 `ALREADY_RAN` 으로 멈추고 어느 폴더를 먼저 보낼지 알려 준다.
  - 본 요약을 시작했다(시작 표지 또는 받은 원문이 있음).
  - 합성 점검 · 본 호출 직전 관문 · 판 확인(앞 실행과 다른 digest)이 설정 · 모델 문제로 멈췄다(맥북 새 묶음 · 설계자 보고 대상 · PLAN §2-2).
  - 기록이 없는데 잠금이 아직 열려 있다(다른 창에서 실행 중).
  - 결과 기록을 읽지 못한다(세 번 읽어도 막힘 · 이름이 붙은 결과가 깨짐). 무슨 멈춤이었는지 모르므로 '없음'으로 보지 않는다(검토 I).
  - 환경 문제로만 멈췄거나, 본 요약 전에 꺼져 비어 남은 폴더는 같은 폴더로 다시 돌 수 있다.
- **`.bat`:** 실제로 도는 Python 을 고른다(`py -3 -c` 먼저 · 다음 `python -c` · Microsoft Store 별칭은 걸러짐). 못 찾으면 안내하고 멈춘다.

### 3-3. 지시문 · 설정(판정 Q3)

- 모델 `qwen3.5:9b-q4_K_M` · 생각 모드 · temperature 1.0 · top_p 0.95 · top_k 20 · min_p 0 · presence_penalty 1.5 · repeat_penalty 1.0 · seed 20261123 · `num_ctx` 49,152 · `num_predict` 24,576. 판 `poc7-02-prompt-v1`(지시문 · 설정 해시를 묶음에 기록). 길이 설정은 모델 문맥 256K(262,144) 이하만 받는다(PLAN §2-2 모델 표).
- 지시문은 PLAN §3-2 9개 규칙이다. 판정 §3 에 따라 강조점과 이견을 구분하고, 최신 확인에는 확인 주체 · 값 · 기준일 · 출처 · 확인 시각을 붙인다. 매매 결론 · AI 합의 단정은 쓰지 않는다(KS-4).
- **새 묶음 규칙(검증자 r1 F2 · r3 F12 · 검토 A · D):**
  - 한 사례에 본 요약 시도는 한 번이다. 본 요약을 시작한 기록이 하나라도 회수됐으면 결과(완료 · 실패 · 꺼짐)와 관계없이 새 묶음을 만들지 않는다(다시 실행은 설계자 판단 · §14-5 Q-A).
  - 앞 묶음은 모두 회수돼 있어야 새 묶음을 만든다. 다시 실행 멈춤(`ALREADY_RAN`) 기록만으로는 회수로 치지 않는다(다른 창에서 아직 실행 중일 수 있음).
  - 기록은 상태 글자가 아니라 멈춤 종류(`stop_kind`)로 본다. 멈춤 안내 중 Ctrl+C 로 '중단'이 된 기록, 임시 결과로만 남아 기록 미완으로 받은 기록도 원래 멈춤으로 본다(검토 A).
  - 새 묶음은 바로 앞 묶음의 '실제로 돈 마지막 기록'이 설정 · 모델 멈춤(실행기가 같은 폴더 다시 실행을 막는 멈춤)일 때만 만든다. 환경 · 설치 · 묶음 바뀜 · 중단 멈춤은 같은 폴더에서 다시 돌리는 멈춤이라 그 폴더에 첫 본 요약이 있을 수 있다. 맥북이 그것을 모르는 채 두 번째 묶음을 판정하지 않게 막는다(검토 D · §16-4 Q-O).
  - '실제로 돈 기록'은 다시 실행 멈춤 · 묶음 바뀜 · 결과 기록을 대조하지 못한 기록 미완을 뺀 기록이다. 그 가운데 '마지막'은 나머지를 모두 앞 결과(`prior_runs`)로 적은 기록이다(벽시계를 쓰지 않음 · 검증자 r3 F12). 정할 수 없으면(여러 곳에 풀어 돌림 등) 설계자 판단으로 멈춘다(§16-4 Q-N).
  - 첫 묶음은 시작 설정 그대로다. 두 번째부터는 사유가 필요하고, 지시문 해시가 첫 묶음과 같아야 하며, 바로 앞 묶음 설정을 이어받는다.
  - 길이 설정은 그 마지막 기록이 합성 점검 · 본 호출 직전 관문의 '설정' 문제로 멈췄을 때만 바꾼다.

### 3-4. 회수 · 대조(merge)

- USB 폴더는 보통 파일만 읽는다(링크 · 폴더 · 64MB 초과 거부). 폴더 이름 = 결과에 적힌 이름 · 실행 id 꼴을 확인한다. 결과 파일의 사본 이름(`result (2).json` · `result - 복사본.json` · `hashes 2.json` 처럼 같은 이름 폴더를 겹쳐 복사할 때 생기는 이름)이 폴더에 있으면 거부한다. 두 시도의 결과 폴더가 겹쳐 하나만 보이면 시도를 하나로 셀 수 있어서다(§18 · OS 가 붙이는 `._이름` · `.DS_Store` · `Thumbs.db` · `desktop.ini` 는 해당 없음). JSON 은 유한하지 않은 수 · 같은 키 두 번 · 너무 깊은 중첩을 받지 않는다.
- 한 장 · 결과 · 해시는 이름이 없으면 같은 이름의 임시 파일(`.<이름>.part`)을 읽는다. 다 쓴 임시 해시가 있으면 그대로 검증해 완전한 기록으로 받는다(`from_part` 표시). 시작 표지의 임시 파일은 표지로 쓰지 않는다(이름을 못 바꿨으면 본 요약을 부르지 않았다).
- 대조 항목:
  - `hashes.json` ↔ 파일 바이트(시작 표지 · 받은 원문 포함)
  - 사례 · 묶음 id
  - 실행기가 본 묶음 해시 · 실행 코드 해시(묶음 확인 때 잰 값) = 맥북 manifest · 묶음 입력 해시
  - 맥북 zip 안 파일 = manifest
  - 잠근 채점 메모 = 묶음에 적힌 해시(잠금 → 묶음 순서는 구조로 지킨다 · 잠금이 없으면 묶음을 만들지 않고 묶음 뒤에는 다시 잠그지 못함 · 맥북 시각 비교는 뺐다 · 검증자 r3 F12)
  - 시작 표지 = 이 실행(실행 id · 묶음 · 사례 · 결과 폴더 · 설정 · 판 · digest · 시각 꼴)(검증자 r2 F7)
  - 받은 원문 ↔ 결과의 본문 · 종료 이유 · 토큰 수 · 모델(원문 쓰기 실패를 기록한 실행은 결과 기록만)
  - Ollama 판 · 모델 digest 가 있고 꼴이 맞으며, 결과 · 본 요약 · 시작 표지가 서로 같음 · 세기 토큰 · 응답 모델
  - 본 호출 직전 관문을 원값(처음 판 · 다시 읽은 판 · 세기 · 모델 내림)에서 다시 계산한 결과 = 실행기 기록
- 시각 순서(묶음 뒤 · 실행 시작 뒤 · 본 호출 · 원문 앞)는 거부하지 않고 메모(`clock`)로만 남긴다. 맥북 · PC 의 시계가 다르거나 실행 중 시간 맞춤이 되돌릴 수 있어서다. 순서를 정하는 곳은 모두 벽시계를 쓰지 않는다(§16-2).
- 묶음 바뀜 · 본 요약 없는 멈춤의 일관성도 대조한다: 멈춤 종류 ↔ 상태, 묶음 바뀜인데 모델 호출 기록 있음(거부), 본 요약이 없는데 한 장이 있거나 상태가 멈춤이 아님(거부), 판 멈춤(다른 digest) 기록의 꼴(멈춤 종류 · 분류 · 뒤 단계 없음).
- '그 묶음에 들어간' judge 로 원값에서 다시 구분하고, '그 묶음에 들어간' render 로 한 장을 다시 만들어 바이트를 비교한다. 그래서 뒤에 저장소 코드를 고쳐도 앞 묶음의 첫 결과를 회수할 수 있다.
- **결과 기록이 다 쓰이지 않은 폴더(꺼짐 · 창 닫힘):** `result.json` 이나 `hashes.json` 이 없거나 해시가 깨졌으면 `INCOMPLETE_RECORD` 로 남은 바이트를 그대로 보관한다(판정에는 쓰지 않음). 누구의 기록인지는 시작 표지나 읽히는 `result.json` 으로 확인한다. 읽히는 결과 기록이 있으면 완료 경로와 같은 함수(`_check_body`)로 해시만 빼고 같은 원값 대조를 한다(묶음 · 코드 해시 · 결과 기록의 원문 해시 · 원문 내용 · 판 · 다시 구분 · 한 장 다시 만들기 · 합성 점검 · 직전 관문 · 검증자 r3 F10). 통과한 기록만 멈춤 종류 · 분류를 새 묶음 규칙에 쓴다(`claim_checked`). 거부하는 경우는 다음과 같다.
  - `hashes.json` 이 있는데 `result.json` 이 없다(복사 누락).
  - 이름이 붙은 `result.json` 이 깨졌다(복사 손상 · 임시 이름의 깨진 결과는 받음).
  - 결과 기록에 받은 원문이 있는데 `main_raw.json` 이 없다(복사 누락).
  - 한 장이 결과 기록으로 다시 만든 것과 다르다(복사 손상 · 다른 실행). 한 장 만들기 오류 기록인데 이름이 붙은 한 장이 있다(완료 경로와 같음).
  - 받은 원문이 결과 기록의 원문 해시와 다르다(복사 손상).
  - 시작 표지가 깨졌다(손상 · 설계자 판단).
  - 시작 표지 · 결과 · 원문 중 어느 것도 없다(보관할 것 없음).
- **같은 실행을 다시 받기(검증자 r3 F10 · 검토 F):** 기록 미완으로 먼저 받은 실행은 같은 실행의 완전한 폴더나 더 담긴 복사본이 오면 대신 받는다(`replaces`).
  - 해시로 검증된 완전한 폴더: 앞서 받은 시작 표지의 정체 칸(사례 · 묶음 · 실행 id · 결과 폴더)만 같으면 받는다. 판 · 설정 · 시각 등 나머지 칸 · 결과 · 원문 · 한 장이 달라도 받고, 달랐던 파일은 `kept_differs` 로 남긴다(손상 복사본이 원본을 막지 않게). 표지의 임시 파일은 정체로 쓰지 않는다.
  - 기록 미완 → 기록 미완: 더 담긴 복사본이고 앞서 받은 표지 · 결과가 같은 바이트, 원문은 같거나 앞서 받은 끊긴 원문이 이어진 것일 때만 받는다. 더 얇은 복사본(빠진 파일 · 더 짧게 끊긴 원문)은 '이미 보관됨'(중복)이다. 그래서 같은 실행의 복사본들은 어느 순서로 받아도 가장 많이 담긴 것이 남는다(§18). 비교는 같은 이름끼리 한다(표지 임시 파일은 그 이름 그대로).
  - 실행 id 가 다른 기록은 대신 받지 않는다. 같은 초에 시작한 다른 시도(같은 zip 을 두 곳에 풂)와 실행 id 만 손상된 복사본은 시작 표지로 구별할 근거가 없어서, 둘 다 시도로 센다(검증자 r4 F13 · 손상 추정으로 시도를 합치지 않음).
  - 완전한 기록 뒤의 같은 실행은 받지 않는다.
- **회수 순서(검증자 r1 F2):** 앞 묶음 결과가 모두 회수돼 있어야 하고(다시 실행 멈춤 기록만은 아님 · 멈춤 종류로 봄), 같은 폴더의 같은 묶음 앞 결과(기록이 있는 것)를 먼저 회수해야 한다. 정체(묶음)를 남기지 못하고 모델도 부르지 않은 앞 결과는 받을 수 없으므로 건너뛴다(검토 B). 실행 id 를 알 수 없는 앞 결과(시작 표지 손상)가 있으면 설계자 판단으로 멈춘다.
- 회수 기록 목록의 순서는 묶음 순서 → 결과 폴더 번호 → 실행 id 다(시각이 아님 · 검증자 r3 F12). 회수 기록에 같은 묶음 앞 결과의 실행 id 사슬(`prior_runs`)을 남긴다.
- **두 번째 본 요약 시도(같은 zip 을 두 곳에 풀기 등 규칙 밖):** 회수 순서로 '첫 결과'를 고르지 않는다. 거부하지 않고 보관한 뒤 나중에 받은 쪽에 `attempt_conflict` · 다른 시도 목록을 남긴다. `report` 는 이 표시가 아니라 보관된 시도 수로 판정을 막으므로 회수 순서와 상관없이 판정 불가다(§14-5 Q-B · 검증자 r4 F13).
- 보관은 숨김 폴더(`.stage-…`)에 다 쓴 뒤 이름을 바꾼다(끊겨도 반쪽 기록이 보이지 않음 · 묶음 만들기도 같음).

### 3-5. 비교표 · AC4(판정 Q4 · §3)

- `report` 는 먼저 채점 · 사용 기록의 꼴을 검사한다(아래 오류 · 판정 불가로 일찍 끝나는 경우에도 · 검토 G). 다음에 메모 잠금을 다시 확인하고(출력 뒤 고침 거부), 회수한 본 요약 시도를 읽는다.
  - 시도가 없거나, 둘 이상이거나(설계자 판단), 같은 묶음 앞 실행과 모델 digest 가 다르거나(검토 C), 기록 미완이거나, 한 장이 없거나(만들기 · 쓰기 실패 · 꺼짐 · §14-5 Q-E) 판정 불가다.
  - 실행 상태와 응답 구분이 둘 다 '완료'여야 판정한다(받은 뒤 중단 · 실행기 오류는 판정 불가 · 검증자 r3 F11).
  - 채점(score)은 그 한 장의 해시(`one_page_sha256`)를 적어야 받는다(빈 값 불가).
- 시간:
  - 형수님 직접 시간 · 개발자 반복 시간 · 총 사람 시간 · 전체 경과
  - 개발자 반복 시간(L)은 그 사례의 모든 `pack` · `merge` 명령 기록(ms · 멈춤 뒤 새 묶음 · 기록 미완 뒤 다시 받기 포함)의 합이 최소값이다. 직접 잰 값이 그보다 작으면 오류로 멈추고, 없으면 그 합을 쓰고 출처를 적는다.
  - 평소 방식(U)의 개발자 반복 시간은 계약상 0 으로 고정한다. 다른 값을 넣으면 오류로 멈춘다(검증자 r1 F4).
  - L 전체 경과는 실행기 기록(단조 시계 실행 시간 `run_wall_s`)보다 짧을 수 없다(PLAN §3-3 '실행기 기록과 대조'). PC 시계 맞춤으로 벽시계 차가 커져도 정직한 값을 거부하지 않는다(검토 H).
  - 모르는 값은 '미측정'이다. 아래는 오류로 멈춘다(검증자 r2 F8).
    - 음수 · 글자 · 참/거짓 · 무한대 · NaN · 하루(86,400초)를 넘는 초(잠정 상한 · §14-5 Q-J)
    - 0초 직접 시간 · 직접 시간 > 전체 경과
    - 맞음 · 부분 · 틀림 밖의 답 · 글 목록이 아닌 수정 · 예 · 아니오 · 모르겠음 밖의 재사용
    - 객체가 아닌 채점 · 사용 기록
  - 표의 시간은 소수 한 자리 초로 적는다(판정에 쓴 차이가 표에서 같은 값으로 보이지 않게).
- '관찰'은 다음이 모두 맞을 때만이다.
  - 중요한 오류 0
  - L 세 답 틀림 0 · 각 답 L ≥ U
  - 형수님 직접 시간 · 총 사람 시간 둘 다 L < U
  - 사실 수정 L ≤ U
  - 재사용 '예'
- 실측이 빠지면 '미확인'이고, 빠진 항목은 '판정 불가(항목)'로 적는다.
- CLI 는 인자 오류 · 기록 모양 오류도 마지막 줄 `RESULT {"status": "CHECK_REQUIRED" …}` · rc 2 로 끝낸다.

## 6. 알려진 한계 / 미완성

1. **Windows 실측 전:** 아래 사항은 Windows 기록으로만 확인된다(판정 §1). 모의 시험의 가짜 Ollama 는 독립 검토가 Ollama 원본 코드(2026-11-22 판)와 대조한 응답 · 로그 모양을 따른다.
   - 실제 Ollama 판의 `/api/ps` `context_length` · `server.log` 줄 모양 · `think` 지원 · 메모리 부족 오류 글(설정 분류는 'memory · cuda · alloc · oom' 낱말로 본다)
   - 드라이버 · 디스크 · VRAM 적재
   - Windows 에서 열린 파일을 다른 프로세스가 지우지 못하는 동작(`running.lock` 의 '실행 중' 판단 근거 · 맥북 시험은 지우기 실패를 흉내 냄) · 이름이 있으면 실패하는 이름 바꾸기
2. **일부러 고친 결과:** USB 의 결과를 사람이 일부러 고치고 해시까지 다시 맞추면, 대조가 쓰지 않는 칸(시각 · 생각 글 등)은 막지 못한다. 실수 · 손상 · 뒤섞임 · 폴더 바꿈 · 다른 묶음 결과는 잡는다. 시작 표지만 손으로 만든 폴더도 사례 · 묶음 · 폴더 · 설정 · 판 꼴 · 잠금 확인만 거친다.
3. **같은 zip 을 두 곳에 풀기:** PC 에서는 같은 풀기 폴더 안만 본다. 다른 폴더에 다시 풀어 돌리면 본 요약이 한 번 더 돌 수 있다. 맥북 회수에서 두 폴더를 모두 받으면 회수 순서와 상관없이 둘 다 시도로 보관하고 판정을 막는다(§3-4 · 같은 초에 시작해 표지가 실행 id 만 다른 경우 포함 · 검증자 r4 F13). 실행 id 만 손상된 '표지만 있는 기록 미완' 복사본도 같은 이유로 다른 시도로 세어 판정이 막힌다(안전 쪽 · §18-4 Q-Q · 해시나 결과 기록이 남은 복사본은 손상이 드러나 거부됨). 두 풀기 폴더의 같은 이름 결과 폴더(`result_1`)를 USB 한 곳에 겹쳐 복사하면, '둘 다 유지'는 사본 이름으로 드러나 거부하지만 '덮어쓰기 · 건너뛰기'는 흔적이 남지 않아 맥북이 한 시도만 본다. README 에 '푼 폴더마다 따로 복사 · 같은 이름 창이 뜨면 취소'를 적었고, 겹칠 수 없는 결과 폴더 이름은 실행기 · 회수 규칙을 바꾸는 일이라 설계자 질문으로 올렸다(§18-4 Q-S). 다만 첫 폴더를 맥북에 보내지 않고 두 번째 폴더만 회수하면 맥북은 그것을 유일한 시도로 본다(맥북이 모르는 폴더라 막을 수 없음 · README '한 곳에만 풀기'로 줄임). PC 전체 표지(묶음 폴더 밖 쓰기)는 설계자 승인 대상이라 만들지 않았다(§14-5 Q-F).
4. **창 닫기 · 꺼짐:** 창을 닫으면 Python 이 바로 끝나 받은 원문을 못 쓸 수 있다. 그 폴더는 시작 표지로 '시도함'을 남기고(`INCOMPLETE_RECORD` · 출력 없음) 다시 실행 · 새 묶음은 없다(§14-5 Q-A). README 와 화면에 '창을 닫거나 클릭하지 마세요'를 적었다(콘솔 빠른 편집 모드에서 클릭하면 멈춘 것처럼 보임 · 그럴 땐 Esc).
5. **관문과 본 호출 사이:** 본 호출 직전 관문 뒤 밀리초 사이에 판 · digest 가 바뀌거나 Ollama 가 꺼지면 시도로 남고(기술 실패) 다시 실행은 없다. 이 틈은 없앨 수 없다.
6. **시작 표지만 있는 기록 미완:** 앞 결과 목록을 모른다. 그래서 같은 폴더 앞 결과의 회수 순서를 확인하지 않는다(앞 폴더에 본 요약 시도가 있었다면 실행기가 이 실행을 막았으므로 해가 없음).
   - 임시 결과(`.result.json.part`)가 쓰는 중 깨졌으면 실행기 · 회수 모두 '기록 없음'으로 본다. 본 요약 전이면 다시 돌며 모든 확인을 처음부터 하고, 본 요약 뒤면 시작 표지가 다시 실행을 막는다.
   - manifest 와 묶음 입력을 둘 다 못 읽은 실행은 어느 사례인지 몰라 맥북이 받을 수 없다. 모델을 부르지 않았으므로 뒤 폴더 회수를 막지 않고 건너뛴다(검토 B).
7. **시간 측정:** 형수님 직접 시간은 휴대폰 스톱워치 기록이다. L 전체 경과의 하한은 실행기의 단조 시계 실행 시간이다(PC 시계 맞춤과 상관없음). 개발자 시간 최소값은 명령 안에서 잰 ms 이고 Python 시작 시간은 들어가지 않는다(직접 잰 값이 더 크면 그 값을 쓴다). 최소값은 보관된 회수 기록만 더하므로, 같은 실행의 복사본을 어떤 순서로 받았는지에 따라 거부된 회수(기록 없음)가 빠져 몇백 ms 달라질 수 있다(직접 잰 값을 넣으면 해당 없음 · §18-4 Q-R). 하루 상한은 잠정값이다(§14-5 Q-J).
8. **사례 하나 · 순서 효과:** 결론은 그 한 건까지다(판정 Q2).
9. **한국어 품질:** 따로 재지 않는다. 본 사례 AC2 로만 판단한다.
10. **전체 회귀:** 기존 모듈을 고치지 않았다(새 파일만 · 사용처 = 새 CLI · 새 시험). 그래서 바뀐 모듈 시험과 변이로 대신하고, 전체 백엔드 회귀는 STEP 끝 커밋 전에 한 번 돌린다.
11. **판정서 Q-R 과 지금 `report` 의 차이(정정 예정):** 개발자 반복 시간(L)을 직접 넣지 않으면 지금 `report` 는 하한(보관된 `pack` · `merge` 합)을 그 값으로 써서 총 사람 시간 판정까지 한다(`report.py` `build`). 판정서는 하한만으로 절감을 판정하지 말라고 했다. 비교표를 만들기 전에 '직접값이 없으면 총 사람 시간 = 미측정 · 하한과 출처만 기록'으로 고치고 검증자 확인을 받는다(맥북 판정 단계만 · Windows 실행기와 무관).

#### F2 (P2) 회수 전 새 묶음으로 후속 요약을 만들고 먼저 보관 가능

PLAN §2-2는 다시 실행을 실행 실패를 고친 경우로 제한한다. `bundle.py:145–190`은 맥북에 보관된 본 요약만 차단하며, 이전 묶음이 미회수이면 사유 문자열만으로 같은 설정의 새 묶음을 만든다. `merge.py:235–244`의 중복 검사는 먼저 보관된 본 요약만 기준으로 삼는다.

합성 사례의 첫 묶음에서 본 요약을 완료하되 회수하지 않았다. 같은 사례에 ‘아직 회수 전’이라는 사유만 적어 두 번째 묶음을 만들자 본 요약이 다시 실행됐다. 두 번째 결과를 먼저 회수하면 보관됐고, 실제 첫 결과를 회수하면 두 번째 본 요약이라는 사유로 거부됐다. 현재 경로는 본 실행 실패 확인이나 첫 결과의 보존 순서를 강제하지 않는다.

#### F3 (P2) Ollama 버전이나 모델 digest가 없어도 본 실행 완료 및 보관

설계자 판정 Q3은 본 실행 전에 Ollama 버전과 모델 digest를 고정하도록 한다. `runner_win.py:269–291, 325`는 빠진 값을 비어 있는 채 기록한다. `merge.py:126–135`는 digest 두 값의 동일 여부를 보며 비어 있는 값끼리도 통과한다.

가짜 Ollama에서 버전 필드만 없앤 경우와 지정 모델의 digest만 없앤 경우를 각각 실행했다. 두 경우 모두 본 요약을 호출해 `COMPLETED`와 종료 코드 0을 냈고 이후 맥북 회수도 성공했다. 이 결과는 Windows 버전의 실제 응답 모양과 별개로 필수 기록을 비운 채 본 실행을 시작할 수 있음을 보여 준다.

#### F4 (P2) 평소 방식의 반복 개발 시간 입력 때문에 사용 이점 판정이 뒤집힘

PLAN §3-3의 평소 방식 반복 개발자 시간은 0초다. `report.py:85, 147`은 입력된 U의 `dev_s`가 기준값 0을 덮도록 합친다. 같은 입력이 비교표와 AC4의 총 사람 시간에 들어간다.

나머지 조건을 모두 충족하는 대조에서 L 직접 8초·반복 개발 3초, U 직접 10초를 넣으면 `사용 이점 미확인`이었다. U에 `dev_s=2`만 더하자 U 총 사람 시간이 12초로 계산돼 `사용 이점 관찰`로 바뀌었다.

- **A-2 보고 정확성 — 일부 불일치.** 신규 20개·수정 2개, 작업 트리와 index 일치, 기존 코드 수정 0을 확인했다. r1 판정 때 stage한 Git blob과 현재 §11 본문이 일치한다. 개발 보고의 212건을 재실행해 모두 통과했다. §12-2의 중단 복구·회수 순서와 §1의 Q3 완료에는 F5~F7의 예외가 있다.
- **A-3 산출물 정합성 — 위반.** 정상 합성 보관·ZIP·실행·회수·HTML 바이트 대조가 통과했다. 실패 경계에서 회수가 막히고 다른 실행의 시작 표지가 정합 판정을 받았다. 실제 Windows 산출물과 AC1~AC4는 대기다.
- **A-4 금지사항 위반 — 없음.** 새 라이브러리, 외부 API, 운영 코드·DB·배포 변경은 발견하지 않았다. 전달 방식 등 §12-4의 설계자 의제는 아래 결함과 별개로 남아 있다.

### 13-2. B. 구현 규칙·구조 품질 검증

- **B-1 fallback 위반 — 있음.** 회수 성공 뒤에도 시작 표지의 ID를 쓰지 않고 null로 남겨 앞 결과 대조에 실패한다. 유효하지 않은 초 입력도 실측값으로 처리한다(F5·F8).
- **B-2 단일 책임 위반 — 없음.** 실행, 환경 I/O, 원문 대조·회수, 비교판정이 모듈로 구분돼 있다.

- **B-4 실험·운영 경계 위반 — 없음.** 연구 CLI와 PC 실행 묶음으로 분리돼 있고 운영 진입점 수정은 0건이다.
- **B-5 배포 경로 영향 — 없음.** CLI·모듈·시험의 Git index 등록과 묶음의 실행 파일 사본을 확인했다. Dockerfile·배포 스크립트 변경은 없다.
- **B-6 기술부채·구조적 퇴행 — 있음.** 정상 회수와 중단 회수에서 시작 표지의 식별자를 다르게 대조한다. 환경을 읽은 시점과 본 실행에 쓰는 시점이 분리돼 있다(F5~F7).

Windows 본 요약 전에 멈춤 기록의 재사용, 원문 회수 대조, 실행 상태와 AC4의 연결, 앞 실행 순서를 정정해야 한다. 검증자는 이 절만 추가했다.

## 16. 검증자 r3 정정(개발자 · 2026-11-23)

네 지적을 네 종류로 보았다: 실행기와 회수가 같은 폴더를 다르게 읽음, 기록 미완 경로의 대조가 완료 경로보다 약함, 실행 상태와 응답 상태가 따로 놂, 벽시계로 순서를 정함. 각 종류의 칸을 모두 맞췄다(§16-2). 잠그기 전에 네 관점의 반박 검토를 한 번 더 받아 24건을 같은 종류 9묶음으로 고쳤다(§16-3).

## 17. 검증자 r4 판정 (Codex · 2026-11-23)

기준 `d6afb1b7`의 staged 소스를 설계 원문·설계자 판정·확정 PLAN·개발 보고와 대조했다. 저장소 밖에서 합성 사례와 모의 Ollama를 사용했다. 범위는 Windows 본 실행 전 맥북 구현과 실행 묶음이다.

### 17-1. A. 기능·산출물 검증

- **A-1 지시 일치 — 위반.** F9~F12의 재현 5건이 모두 통과했다. 설정 멈춤이 임시 파일에 남은 두 경로, 원문이 손상된 미완 복사본 뒤의 원본 회수, 중단 실행의 AC4 차단, 시계 보정 뒤의 마지막 설정 멈춤을 재검증했다. 두 실행을 한 건으로 집계하는 F13이 추가로 재현됐다.
- **A-2 보고 정확성 — 일부 불일치.** 신규 24개·수정 2개가 stage돼 있다. 수정은 STATE·PROGRAM_TRUTH 두 문서이고, 제출 시 작업 트리와 index가 일치했다. §11·§13·§15 본문을 r3 판정 직후의 Git blob과 대조했다. 제출 시험 5파일 411건은 모두 통과했다. 두 시도가 모두 회수되면 판정을 막는다는 §6-3의 설명과 F13 재현 결과가 다르다.
- **A-3 산출물 정합성 — 위반.** 정상 합성 사례의 생성·실행·회수와 HTML 대조가 통과했다. 시작 초와 회수 순서에 따라 같은 두 실행에서 AC4 결과가 달라졌다.
- **A-4 금지사항 위반 — 없음.** 새 라이브러리·외부 API·운영 코드·DB·배포 변경은 발견하지 않았다. 공유 폴더 제안과 잠정 규칙은 설계자 검토 항목에 있다.

#### F13 (P2) 실행 ID가 다른 실제 두 시도가 하나로 합쳐져 AC4가 승인됨

같은 ZIP을 두 폴더에 풀어 각각 `result_1`에서 모의 본 요약을 호출했다. 두 번의 본 호출을 요청 기록에서 확인했다. 두 시도의 시작 표지에 같은 초가 기록되도록 하고, 첫 시도는 응답 뒤 원문을 쓰기 직전에 전원이 끊긴 상태로 만들었다. 두 번째 시도는 완료했다. 두 표지의 실행 ID는 다르고 나머지 칸은 같다. 회수 전에 파일을 고치지 않았다.

- **미완 → 완료:** 두 폴더가 디스크에는 보존됐다. 완료본은 미완 기록을 `replaces_damaged_copy`로 대신하고, 판정 대상은 1건으로 줄었다. 시간·채점 조건을 충족한 입력에서 ‘사용 이점 관찰’이 나왔다.
- **완료 → 미완:** 같은 두 시도의 회수 순서를 바꾸면 2건이 집계됐고 AC4는 ‘판정 불가’였다.

시작 표지의 시각은 초 단위다. `_phantom`은 실행 ID를 뺀 칸이 모두 같으면 미완 기록을 손상 복사본으로 간주한다. 동일 초·폴더 번호·모델·설정은 서로 다른 실행에서도 일치할 수 있다. §6-3의 ‘첫 폴더를 보내지 않은 경우’와 달리, 이 재현은 두 폴더 모두 회수했다. 근거는 `runner_files.py:27–28`, `runner_win.py:454–463, 549–553`, `merge.py:475–499, 510–527`, `bundle.py:162–170`, `report.py:330–341) 및 설계자 판정 §3의 최초 출력 보존 조건이다.

독립 시험 17건 중 16건 통과, F13 한 경우가 실패했다. 과거 독립 재현 14건을 포함하며, 이전 시간 입력 시험의 정상 대조군에는 현재 판정이 요구하는 실행 완료 상태를 추가했다. ZIP을 따로 푼 폴더에서 `run_summary.py --help`를 실행해 저장소 모듈 없이 시작되는 것도 확인했다. `black --check`·`flake8`·`py_compile` 19파일과 staged 공백 검사를 통과했다. 개발자의 변이와 전체 회귀는 다시 실행하지 않았다.

## 18. 검증자 r4 정정(개발자 · 2026-11-23)

F13 은 r3 정정 때 넣은 '손상 복사본' 추정 규칙(`_phantom`)에서 나왔다. 잠금 전 검토 지적(실행 id 한 칸이 손상된 복사본이 가짜 두 번째 시도가 됨)에 맞춰 넣은 규칙이다. 그런데 실행 id 만 다른 두 시작 표지는, 같은 초에 시작한 다른 시도와 손상 복사본을 구별할 근거가 없다. 규칙은 근거 없이 둘을 하나로 합쳤고, 그것도 '기록 미완을 먼저 회수'한 순서에서만 그랬다. 이 규칙을 빼고, 실행 id 가 같을 때만 같은 실행으로 잇는다.
