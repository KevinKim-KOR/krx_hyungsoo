## 5. 알려진 한계 / 미완성

1. **가격 기준:** 분배금 미포함 합성 가격지수다. 총수익 판단은 유보한다(POC6-12 SOURCE_BLOCKED).
2. **분류의 빈자리:** 미확인 270행(본 구간 · 그중 나중에 폐지 193)은 후보와 분모에서 빠졌다. 생존 편향이 일부 남는다. 미확인을 국내 주식형으로 넣는 대조는 하지 않았다(설계자 의견 범위).
3. **회고 자료:** 2021 ~ 2026-09 는 다른 연구에서 이미 본 구간이다. 독립 시험 성적이 아니다.
4. **비용 민감도:** 양쪽 매수 비용이 같은 배율로 붙어 40bp 결과는 20bp 와 부호가 늘 같다(실측 Δ −0.003665%p 대 −0.003672%p).
5. **체결 시각:** 과거 날짜별 실제 수신 시각은 없다(봉인 수집 기록 3,339건 = 2026-09-23 일괄). D+1 시가는 개장 전에 자료를 이용했다는 가정의 모의 체결값이다.
6. **1주 노출 경로:** 주마다 원금이 따로라 실제 계좌가 아니다. 낙폭은 D+1 → D'+1 주 간격으로 잰다.
7. **검산의 독립성 범위:** 검산은 분류 규칙(`classify`)을 본 계산과 함께 쓴다(고정 규칙 그 자체). 대신 결과 이름 목록 전체를 잠금의 분류표와 대조한다.
8. **기록 문구:** `report.md` · `report.json` 의 '실행 · 검산 성립'은 검산 전에 쓰여 '검산 대기(verify)'로 남는다. 검산 결과(VERIFIED_OK)는 verify 기록과 이 결과서에 있다.
9. **Finder 숨김 파일:** 실행 폴더 · `runs/` 를 Finder 로 열면 macOS 가 `.DS_Store` 를 만들 수 있다. 그러면 다음 검산이 `run_dir_files` · `single_run_in_lock` 불일치(닫힌 쪽)가 된다(r4 F11 규칙 · 지금 공식 실행 폴더에는 없음). 설계자 RESULT 판정 §2 = 이 불일치 처리를 유지한다. 연구 폴더는 Finder 로 열지 않고, Finder 로 볼 때는 실행 폴더 밖에 둔 보고서 사본을 쓴다.
10. **확인과 쓰기 사이:** 위치 확인은 쓰기 · 이름 붙이기 바로 앞마다 다시 하지만, 확인과 바로 다음 시스템 호출 사이에 다른 프로그램이 폴더를 바꾸는 경쟁은 막지 않는다(같은 프로그램끼리는 `.run.lock`).

  - 연구 폴더 안에서는 링크를 따라가지 않는다. 파일은 '폴더 사슬 실제 · 파일 자체 보통 파일(링크 · FIFO · 폴더 아님) · 하드 링크가 모두 그 폴더 안(정리 실패로 남은 프로그램 임시 이름 짝만 허용)'을 확인한 뒤에만 연다(`.run.lock` 포함). 폴더 목록도 실제 폴더로 확인된 곳만 읽는다.
  - 확인에 실패한 경로는 내용도 목록도 읽지 않는다. 연구 폴더 · 잠금 · `runs` · `verify/` · `.run.lock` 이상이면 기록 없이 거부(CHECK_REQUIRED · rc 2), 실행 폴더 · 실행 파일 이상이면 읽지 않은 채 불일치(MISMATCH)다.
  - 쓰기는 모두 `write_once` · `stage_once` · `link_name` 을 지나며 직전에 다시 확인한다. 못 보는 이름(권한 등)은 '없음'으로 치지 않고 거부한다.
- 기본 연구 폴더(`Path(__file__).resolve()` 기준)는 늘 실제 경로다. 기본이 아닌 폴더로 사본을 검산할 때는 실제 경로로 지정한다. macOS `/tmp` · `$TMPDIR`(`/var/folders/…`)는 상위 링크라 거부되므로 `/private/tmp/…` · `realpath` 결과를 쓴다. `..` 가 든 경로도 링크가 없어도 거부한다(의도).
- 잠금 폴더 안 다른 이름(`verify/` 기록 등)은 승인에 쓰이지 않아 목록을 검사하지 않는다. 다만 `verify/` 는 기록을 쓰는 자리라 위치를 본다.

## 23. 검증자 r6 지적 처리(개발자 · 2026-11-22)

r6 도 C 판정 · Δ −0.0037%p · 결과 · 분모를 재현했다. F13 은 확인에 실패한 경로의 파일을 그래도 읽은 문제다. 형수님이 '단계단계 수정은 토큰 · 시간 낭비'라고 걱정하셨다. 그래서 이번에는 지적한 두 장면만 막지 않았다. 연구 폴더 안 파일 · 폴더에 닿는 모든 동작을 표로 열거해 한 규칙으로 닫았다. 그리고 잠금 전에 독립 반박 검토 1회(에이전트 하나 · 합성 자료만 · 저장소 변경 0)를 돌려 남은 곳까지 고쳤다. 방식은 앞 라운드와 같다(PLAN §4 '코드 결함을 고친 다시 실행만').

### 23-1. 규칙과 동작 열거

- **규칙 = 확인한 것만 연다.**
  - 연구 폴더 안에서는 링크를 따라가지 않는다.
  - 파일은 세 가지를 확인한 뒤에만 연다(`protocol.regular_inside` · `read_inside`).
    - 폴더 사슬이 실제 폴더다.
    - 파일 자체가 보통 파일이다(링크 · FIFO · 폴더 아님).
    - 하드 링크가 모두 그 폴더 안에 있다. 정리 실패로 남은 프로그램 임시 이름 짝만 허용한다.
  - 열 때도 링크를 따라가지 않고, 연 파일이 확인한 그 파일인지 다시 본다.
  - 폴더 목록은 실제 폴더로 확인된 곳만 읽는다.
  - 이름이 있는지는 링크를 따라가지 않고 본다. 권한 등으로 못 보면 '없음'으로 치지 않고 거부한다.

| 동작 | 곳 | 지금 |
|---|---|---|
| 연구 폴더 목록 · 잠금 찾기 | `flow.locks` | 확인한 연구 폴더만 목록. 그 안의 링크 = 거부(따라가지 않음). 숨김 이름 = 잠금 아님(읽지 않음). `protocol.json` = 확인 뒤 읽기. 못 보는 이름 = 거부 |
| 잠금 파일 열기 · 잠그기 | `flow.run_lock` | 확인 뒤 링크를 따라가지 않고 막히지 않게 연다(FIFO 대기 없음). 연 파일을 다시 확인하고 잠근다 |
| `runs/` 목록 | `flow._runs`(run · prepare · verify) | 확인된 `runs/` 만. 링크면 목록 전에 거부 |
| 앞 실행 판정 | `flow._is_run` | 이름 꼴 · `run.json` 을 링크를 따라가지 않고 확인(내용은 읽지 않음) |
| 실행 폴더 목록 · 파일 확인 | verify | 실행 폴더가 실제 폴더로 확인될 때만 목록. 항목마다 보통 파일 · 하드 링크 확인(내용은 읽지 않음). 확인 실패면 목록도 읽지 않고 불일치 |
| 실행 파일 5개 읽기 | verify | 확인을 통과한 파일만 읽는다. 실패한 파일은 읽지 않고 그 파일에 기대는 대조 = 불일치 |
| 실행 폴더 이름 | verify | 실행 id 꼴만(앞 실행 판정과 같은 규칙) |
| 쓰기 · 이름 붙이기 | `write_once` · `stage_once` · `link_name` | 직전 위치 확인(r5). 같은 이름 확인도 링크를 따라가지 않음 |
| 임시 파일 정리 | `discard` | 폴더 위치가 확인될 때만 지운다(바뀌었으면 밖을 건드리지 않고 남김) |
| 실패 기록 | run · verify 의 FAILED | 있는지 미리 보지 않고 쓰기 함수에 맡김(링크를 따라가지 않음) |
| 밖 고정 입력 | 봉인 DB · 기본정보 CSV · 코드 파일 | 설계상 연구 폴더 밖 · 해시로 고정(변경 없음) |
