## 0. 요약

- **공유 코드는 바꾸지 않는다.** 기존 두 어댑터(키움 `KiwoomClient` · Yahoo `fetch_completed_daily`)에 이미 있는 주입 인자(`http_post` · `http_get`)로 원시 응답을 가로채 보관한다. 새 연구 패키지 하나와 CLI 하나, 시험 파일 하나만 더한다. 설치는 없다(`requests` 기존).
- **표본 날짜는 저장 코스피 달력에서 고정했다.** 수급 8일은 2026-09-21 · 2025-09-30 · 2024-01-02 · 2022-01-03 · 2020-01-02 · 2018-01-02 · 2016-01-04 · **2014-04-10** 이다.
  - 코스피 저장 계열이 2014-04-10 부터 시작하므로, 2014년 표본은 그날이다.
- **예상 요청 수**
  - A: 데이터 14회(키움 8 · Yahoo 6), 재시도를 모두 해도 28회 이하, 약 1분.
  - B: 키움 최대 3,046회 + Yahoo 2회, 약 51 ~ 56분(1초 간격).
  - 두 구간 모두 설계 상한(A 32회 · 30분 / B 7,000회 · 120분) 안이다.
- **설계자 판정은 PASS_WITH_REQUIRED_CORRECTIONS 다(2026-11-03).** §1-4 의 두 사실은 수용됐다. 보완 2건을 §1-2 · §3-3 · §3-4 · §3-5 에 반영했다(§5).
  - 수급 13분류 값이 다른 날짜와 같아도 '반복 의심' 표시만 한다.
  - Yahoo 와 기존 저장본의 날짜 집합이 달라도 기록만 하고 B 를 막지 않는다.
- **사용자 승인은 새로 필요하다.** 기존 키움 · Yahoo 승인(2026-10-20)은 'PC 시장 갱신 때만'이라 이번 범위를 덮지 않는다. 또 개발자는 맥북이 지금 키움 등록 망에 있는지 알 수 없다(§4).

### 1-2. 날짜 · 단위 검사(새 코드가 하는 것)

- **수급**
  - 응답 본문 · HTTP 상태 · `return_code` · 응답 헤더 `cont-yn` · `next-key` 를 날짜마다 보관한다.
  - 성공 판정 조건: 코스피 종합 행 `001` 있음 + 13분류를 모두 읽음 + 지수 대조 통과.
  - 날짜 확인의 성격: 응답에 날짜 칸이 없다면 '날짜 인자 + 그날 지수 대조'에 의한 **간접 확인**으로 기록한다(설계 §4-3). POC6-01 표본 기록(POC5-28 PLAN §9-8)에는 응답 날짜 칸의 유무가 적혀 있지 않다. A 원시 응답에서 확인한다.
  - POC6-01 표본에서 이미 확인된 사실: 과거 `base_dt` 2025-01-02 까지 지수 대조 일치 · 토큰 만료 24시간(한 실행에 토큰 1개면 충분).
  - 날짜 유효성은 독립된 날짜 근거로만 판단한다(판정 보완 1).
    - 응답에 날짜 칸이 있으면: 요청일과 일치 + 그날 지수 대조 통과.
    - 날짜 칸이 없으면: 지수 대조 통과(간접 확인으로 기록).
    - 날짜를 무시한 최신 응답은 이 근거(요청일 불일치 · 지수 대조 실패)로 실패 처리한다. 옛 날짜의 코스피 종가는 최신과 다르므로 지수 대조에서 걸린다.
  - 13분류 값이 다른 날짜와 통째로 같으면 '반복 응답 의심'으로 표시만 한다. 그것만으로 무효로 하거나 연속 실패 횟수에 넣지 않는다. 유효한 0 · 음수는 그대로 둔다.
- **연속 조회**
  - POC6-01 표본(2026-10-20)은 한 페이지였다(`cont-yn N` · 28행 · `001` 이 첫 페이지에 있음). 그래서 연속 조회 코드는 만들지 않는다.
  - `cont-yn Y` 인데 `001` 이 없으면 그날은 '미완료 페이지' 실패다. `001` 이 첫 페이지에 있으면 뒤 페이지는 필요 없다(다른 행을 쓰지 않음).
- **Yahoo**
  - 응답 전체를 보관한다: 원시 timestamp · `exchangeTimezoneName` · `currentTradingPeriod` · quote 종가 · `adjclose` 유무.
  - 종가 종류는 `indicators.quote[0].close` 다(기존 어댑터와 같음).
  - 요청 기간 처리: 기존 어댑터는 `period1 = 시작일 00:00 UTC`(현지 날짜 ≥ 시작일)이고, `period2` 는 넘긴 시각이다. 현지 날짜 기준의 끝일 포함 규칙은 없다.
    - 런던 서머타임 기간에는 현지 자정이 전날 23:00 UTC 다. 그래서 시작일 봉이 빠지거나 끝 다음 날 봉이 들어올 수 있다(미실측 가능성).
    - 연구 명령은 앞뒤를 하루씩 넓혀 요청한다(`start − 1일` · `now_utc = 끝일 + 2일 00:00 UTC`). 그런 뒤 **현지 날짜 [시작일, 끝일] 포함 구간만** 남기고, 잘라 낸 봉 수를 기록한다.
  - 원/달러는 양수여야 한다. 0 이하면 손상으로 표시한다.
  - **WTI 0 이하는 원본 그대로 유효 관측으로 두고 따로 표시한다**(설계 §6 · 2020-04 창 포함). 비율 · 로그 · 월물 조정은 계산하지 않는다.
- **기존 저장값 대조**
  - 수급 대조: 날짜 · 투자자별 정수 원.
  - 환율 · WTI 대조: 같은 현지 날짜의 값.
  - 같음 · 다름 개수와 최대 차이를 적는다. 다르면 새 값과 옛 값을 함께 보존한다. 다름을 실패로 판정하지 않는다.
  - 한쪽에만 있는 날짜는 양쪽 각각 목록 · 개수 · 확인된 사유(없으면 미확인)로 적는다. 결측을 0 · 직전 값으로 채우지 않고, 기존 저장본을 새 응답에 맞춰 고치지 않는다.

### 1-4. 설계 문구와 실제 위치가 다른 점(질문 아님 · 판정 때 확인만)

1. **봉인 가격 판에는 코스피 지수가 없다.** 봉인 DB 표는 ETF 일별 원시 · 판 구성원뿐이다. 지수 대조는 설계 §3 대로 POC6-01 접점을 쓴다. 즉 운영 DB 의 코스피 저장 계열(읽기 전용)과 대조하고, 그 사본을 실행 폴더에 남긴다.
   - 그 계열의 출처는 세 가지다: NAVER_FDR(2014-04-10 ~ 2025-12-18 · 2,870일) · FDR KS11(2025-12-19 ~ 2026-09-16 · 181일) · KRX Open API(2026-09-17 ~ · 28일).
   - 봉인 판 달력과 코스피 저장 달력은 2014-04-10 ~ 2026-09-21 에서 똑같다(3,054일 · 양쪽 어느 방향으로도 차이 0일).
2. **수급의 2014년 시작은 2014-04-10 이다.** 봉인 판에는 그보다 앞선 68일(2014-01-02 ~ 04-09)이 있지만, 비교할 저장 코스피 종가가 없다. 그래서 설계 §4-2('첫 저장 코스피 거래일') · §5('기존 코스피 거래일만')대로 요청하지 않는다. 보고서에 '지수 대조 근거 없음 · 미요청 68일'로 적는다.
   - 원/달러 · WTI 는 2014-01-02 부터 요청한다.
