## 0. 결론 요약 [V1.2]

### 트리거는 **하나**다 (설계자 확정)

```
DAY_DROP = runtime 현재가 / 직전 거래일 종가 - 1
```

"즉시" 는 **장중 여러 시각에 평가한다**는 뜻이지 분모를 당일 시가로 제한한다는
뜻이 아니다. **당일 시가 기준은 갭 하락을 놓치므로 트리거에서 제외**한다.

### 후보별 판정 [V1.1]

| 후보 | 판정 | 근거 |
|---|---|---|
| **`DAY_DROP`** | **유일 트리거** | 현재가 29/29 · 직전 종가 29/29 |
| `DRAWDOWN` (고점 대비) | **트리거 제외** — 보조 정보만 | 09:15 보유 브리핑이 이미 제공 |
| 시가 대비 변화 | **트리거 제외** — 보조 정보만 | 갭 하락을 놓친다 |
| `CONCENTRATION` | **트리거·fingerprint 제외** | 사건이 아니라 포트폴리오 **상태**. 별도 evidence 후보로만 기록 |
| 동조 움직임 | **제외 승인** | 공통 거래일 54일 · '미국 익스포저' 등 근거 없는 분류 금지 |

### [V1.2] 확정 계약

| 항목 | 확정 |
|---|---|
| 임계 구간 | **`D5_7` / `D7_10` / `D10_PLUS`** (−5 / −7 / −10%) |
| 동시 발생 | **억제하지 않고 한 메시지로 묶는다** |
| 완화·해소 | **미발송** |
| cron | 7개 시각 유지 · **push-kind 를 신규 종류로 교체**(방법 c) |
| 신규 flag | `PUSH_AUTOSEND_HOLDINGS_RISK_ALERT_ENABLED` = **`false`** 로 시작 |

> 설계자: "시장 전체가 흔들릴 때 **18개의 알림이 오는 게 아니라, "29종목 중
> 18종목 동시 하락" 이라는 메시지 한 건**이 온다. 알림 폭탄을 막으면서도 중요한
> 사건을 숨기지 않는 쪽이다."

**−3% 는 제외**한다 — 2026년 기준 월 9.4일로 빈도가 지나치게 높다.
**추가 임계값 조사는 하지 않는다.**

## 4. [V1.2] 확정 계약 — 구현 대상

### 4.1 트리거 · 구간

```
DAY_DROP = runtime 현재가 / 직전 거래일 종가 - 1
```

| state | 범위 | 메시지 표기 |
|---|---:|---|
| `D5_7` | `−7% < DAY_DROP ≤ −5%` | 전일 대비 하락 5~7% |
| `D7_10` | `−10% < DAY_DROP ≤ −7%` | 전일 대비 하락 7~10% |
| `D10_PLUS` | `DAY_DROP ≤ −10%` | 전일 대비 하락 10% 이상 |

**경계 계약** — 정확히 −5% → `D5_7` · 정확히 −7% → `D7_10` · 정확히 −10% →
`D10_PLUS`. (OPS-01A `classify_decline` 과 같은 상한배타·하한포함 패턴)

**분모는 직전 거래일 종가**다. 당일 시가가 아니다(갭 하락 누락).
**분자는 runtime 현재가** — OPS-01A 와 같은 값·같은 유효성 규칙.

> 이 값은 **투자 성과 기준이 아니라 보유종목의 사실형 당일 하락 알림 구간**이다.
> 판단어(관찰/주의/경고)를 쓰지 않는다.

### 4.2 동시 발생 — **묶어서 한 건**

동시 발생 종목이 많다는 이유로 **알림을 억제하지 않는다.** 여러 보유종목의 동시
하락은 오히려 중요한 포트폴리오 위험이다.

한 실행 시각에 **새로 진입하거나 악화된 종목을 Telegram 메시지 한 건으로 묶어**
발송한다.

| 규칙 | 내용 |
|---|---|
| 그룹 | **구간별** |
| 표시 | 해당 종목 **전부**. 임의 Top N 제한 **없음** |
| 헤더 | `보유 29종목 중 N종목 동시 하락` |
| 금지 | 국가·섹터 원인 해석 (**'미국 익스포저 하락' 같은 문구 금지** — 입증되지 않음) |

**종목별 표시 항목**

| 항목 | 성격 |
|---|---|
| 종목명 | — |
| **전일 대비** | **트리거** |
| ~~시가 대비~~ | **제외** (§4.2-b — 원본 응답에 없음) |
| 고점 대비 | 보조 |
| 매입 대비 | 보조 |

**보조 3종은 trigger·state·fingerprint 에 포함하지 않는다.**

| 당일 시가 대체 원천 | **없음** — `etf_daily_price` 당일 행 0건(OCI·로컬 모두 최신 2026-09-04). 일별 가격은 마감 후 배치로 적재된다 |

→ **판정 2 적용: 시가 대비 표시를 완전히 제외**한다. 별도 endpoint 호출 · 장중
DB 적재 · 수집 파이프라인 변경 **하지 않는다.**

adapter 가 버리고 있던 것이 아니라 **응답에 애초에 없다**. `basic` endpoint 는
현재가·등락 정보만 주고 OHLC 를 주지 않는다.

> `fluctuationsRatio`(전일 대비 등락률)는 응답에 있으나 **쓰지 않는다.**
> `DAY_DROP` 계약은 **현재가 / 직전 거래일 종가 − 1** 로 확정돼 있고, 외부 계산
> 값으로 대체하면 계약이 달라진다.

**표시 항목은 4종으로 확정**한다 — 종목명 · **전일 대비**(trigger) · 고점 대비 ·
매입 대비.

#### 4.2-c [V1.4] 메시지 이름·단수 문구 — **사용자 확정 (2026-09-07)**

> **2026-09-07 사용자 확정**: 표시 이름은 `[보유 급락 알림]` 으로 하고, 1종목일
> 때는 `동시` 를 붙이지 않는다. 내부 식별자 `holdings_risk_alert` 와 flag 계약은
> 변경하지 않는다.

목업 확인 결과 사용자가 두 가지를 확정했다.

**1) 메시지 이름**

| | 문구 |
|---|---|
| 기존 (09:15, 운영 중) | `[보유 종목 관찰 브리핑]` |
| **신규 (본 작업)** | **`[보유 급락 알림]`** |

`[보유 종목 위험 알림]` 은 09:15 브리핑과 이름이 비슷해 혼동을 낳았다. 두
메시지는 역할이 다르다.

| 메시지 | 주기 | 내용 |
|---|---|---|
| 보유 관찰 브리핑 | 하루 기준 | 20거래일 하락 · 매입 대비 · 고점 대비 정리 |
| **보유 급락 알림** | 장중 **7회** | 전일 대비 **−5% 이하로 새로 하락**하거나 **−7%·−10% 로 악화**될 때만 |

**2) 단수 문구 분기**

| 종목 수 | 헤더 |
|---|---|
| 1종목 | `보유 23종목 중 1종목 하락` |
| 2종목 이상 | `보유 23종목 중 5종목 동시 하락` |

"1종목 동시 하락" 이 어색하다는 사용자 확인에서 나왔다.

> `push_kind` 식별자 `holdings_risk_alert` 와 flag 이름
> `PUSH_AUTOSEND_HOLDINGS_RISK_ALERT_ENABLED` 는 **바꾸지 않는다** — 표시 문구만
> 바뀌었고, 식별자를 바꾸면 registry·PARAM·cron 계약이 함께 깨진다.

**3) 3-PUSH 현황 (사용자 정리)**

| 기존 3종 | 현재 처리 |
|---|---|
| 08:00 시장 브리핑 | 실패·비활성 → **OPS-02B 에서 재개발** |
| 09:15 보유 관찰 브리핑 | **성공 · 운영 중** |
| 급등락·상승 관찰 | `REJECT` → **본 작업(보유 급락 알림)으로 교체** |

OPS-02A 가 활성화되면 **3종 중 2종 완료**.

> 목업의 `보유 23종목` 과 종목명·수치는 **합성 fixture** 다. 운영에서는 실제
> 고유 보유종목 수가 들어간다(현재 29종목).

### 4.3 상태 변화 계약

| 상황 | 발송 |
|---|---|
| 처음 `D5_7` 이상 진입 | **발송** |
| `D5_7` → `D7_10` | **재발송** |
| `D7_10` → `D10_PLUS` | **재발송** |
| 한 번에 더 나쁜 구간으로 진입 | **해당 구간으로 발송** |
| 같은 구간 유지 | 억제 |
| 완화·해소 | **미발송** |
| 완화 후 같은 날 기존 구간 재진입 | **미발송** |
| 같은 날 도달한 **최악 구간보다 더 악화**된 경우에만 | 추가 발송 |
| 다음 거래일 시작 | **상태 초기화** |
| 나중 실행에서 **새 종목이 처음 진입** | 그 종목은 **신규로 발송** |

> state 에 **그날 도달한 최악 구간**(`worst_state`)을 기록해야 "완화 후 재진입
> 억제" 와 "최악보다 더 악화된 경우에만" 을 구현할 수 있다. OPS-01A 의
> `reasons{state}` 만으로는 부족하다.

### 4.4 PUSH 종류와 cron — 방법 **(c)**

| 항목 | 확정 |
|---|---|
| cron **실행 시각 7개** | **그대로 유지.** 실행 횟수 추가 금지 |
| cron 인자 | `--push-kind spike_or_falling_alert` → **`--push-kind holdings_risk_alert`** 로 **교체** |
| 기존 `spike_or_falling` | 신호·본문·상태 **재사용 안 함**. `REJECT / disabled` 유지 |
| 실행 이력 | **`holdings_risk_alert`** 로 별도 기록 |
| **금지** | 러너에서 기존 종류 실행 시 **두 기능을 함께 돌리는 방식** |

> cron **시각**은 바뀌지 않지만 **push-kind 인자는 변경**된다. cron 편집은
> OCI 쓰기이므로 **개발자가 하지 않는다** — 배포 시 사용자·설계자 판단.

### 4.5 종류별 flag

| 변수 | 초기값 |
|---|---|
| **`PUSH_AUTOSEND_HOLDINGS_RISK_ALERT_ENABLED`** | **`false`** |
| `PUSH_AUTOSEND_SPIKE_OR_FALLING_ALERT_ENABLED` | `false` 유지 |

개발·검증·**OCI 배포 직후까지 `false`** 를 유지한다. 검증자 `VERIFIED` + 사용자
목업 확인 + **별도 활성화 지시** 후에만 `true` 로 바꾼다.

### 4.6 OPS-01A 계약 재사용 (신규 발명 금지)

| 계약 | 재사용 |
|---|---|
| 비거래일 판정 | 고유 ticker **집합 일치** + 전 종목 `price_asof < 오늘` |
| 분자 유효성 | `price_asof` 가 **실행일** |
| 상태 확정 | **발송 성공 후에만** state 저장 |
| 가드 순서 | 조립 → **모든 skip·fail 은 flag guard 뒤** |
| 부분 실패 | 오늘 quote 하나라도 있으면 실패 종목만 표시하고 진행 |
| 다계좌 | **ticker 기준으로 합쳐 한 번만** 표시 |
| 면책문구 | **넣지 않는다** |

### 4.7 데이터 결손 처리

**직전 거래일 종가가 정확히 없으면** 더 오래된 값으로 **대체하지 않고** 해당
종목을 **데이터 확인 대상**으로 처리한다(OPS-01A `DATA_UNAVAILABLE_OR_STALE` 과
같은 원칙).

**역검증 운영 규칙** (OPS-01A 에서 실제로 겪은 사고 반영)

- 사보타주 스크립트에 `atexit` + SIGTERM/SIGINT/SIGHUP 핸들러로 **어떤 경로로
  죽어도 원본 복원**
- 적용·복원 **양쪽에서 `__pycache__` 삭제** + 하위 pytest 를
  `PYTHONDONTWRITEBYTECODE=1` — **같은 크기 사보타주를 같은 초에 복원하면
  stale `.pyc` 로 오염**된다(실제 발생)
- 사보타주가 **실질적 무력화인지 먼저 확인** — 기본값만 바꾸거나 결과가 같은
  조작은 미탐지로 나와 헛돈다
- **흐름 통과 테스트 필수** — 단위 테스트만 있으면 배선이 끊겨도 못 잡는다
  (OPS-01A 에서 `avg_buy_prices` 배선 유실이 실제로 미탐지였다)
- **발송 0건 보장** — sender 를 아예 전달하지 않거나 호출 시 예외를 던지는 mock.
  state write 는 임시 경로

## 7. 구현 범위 [V1.2]

### 7.1 한다
