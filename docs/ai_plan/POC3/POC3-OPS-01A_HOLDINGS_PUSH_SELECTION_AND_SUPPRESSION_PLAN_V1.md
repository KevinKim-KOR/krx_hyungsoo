### 1.4 [V1.2] `RECENT_DECLINE` 실제 운영 계산 — 장중에 변하는 값

**V1.1 결함**: 원천을 `etf_daily_price.close` 로만 정의했다. 이 값은 07:20 배치 후
장중에 변하지 않는다. **OPEN·MIDDAY·CLOSE 가 같은 종가를 읽으므로 §3.2 의 예시
(`−8.2% → −10.4%` 재발송)가 구조적으로 발생할 수 없었다.**

확정 계산:

```
20일 수익률 = OCI 실행 시점 현재가 / 20거래일 전 종가 − 1
```

| 항목 | 원천 |
|---|---|
| **분자** | **OCI runtime 현재가** — `three_push_runtime/price_refresh.refresh_runtime_quotes()` (Naver) |
| **분모** | `etf_daily_price` 의 **20거래일 전 종가** |

| 계약 | 처리 |
|---|---|
| runtime 현재가 없음 | `DATA_UNAVAILABLE_OR_STALE` |
| 분모(20거래일 전 종가) 없음 | `DATA_UNAVAILABLE_OR_STALE` |
| 분모가 stale | `DATA_UNAVAILABLE_OR_STALE` |
| **stale 종가로 조용히 대체** | **금지** |
| DB 불변 + runtime 현재가가 구간 이동 | **MIDDAY·CLOSE 에서 변화 감지 → 발송** |

기존 러너가 이미 holdings 경로에서 runtime quote 를 조회한다(최근 실행
`attempted 32 / success 29 / failed 0`). **신규 외부 조회를 추가하지 않는다.**
러너에는 이미 `runtime_price_partial_failed` Fail-Closed 가드가 있다.

> §2 의 60거래일 분포는 **종가 기준**이다. 운영 계산은 분자가 장중 현재가라
> 실제 발생 빈도가 분포와 다를 수 있다. **추가 임계값 조사는 하지 않는다**(설계자 지시).
> 이 차이를 결과서에 사실로 기록한다.

### 2.1 `RECENT_DECLINE` 확정 구간 [V1.2 — 명칭 사실화]

**임계값은 바꾸지 않고 명칭만 사실형으로 바꾼다.** 최상위가 67%를 차지하는 분류는
위험의 심각도를 설명하지 못한다. 01A 는 종합 위험 판정이 아니라 **최근 하락 종목을
추리는 작업**이다.

| 내부 구간 | 정확한 범위 | 화면 표기 |
|---|---:|---|
| `D5_8` | `−8% < r ≤ −5%` | `20거래일 하락 5~8%` |
| `D8_10` | `−10% < r ≤ −8%` | `20거래일 하락 8~10%` |
| `D10_PLUS` | `r ≤ −10%` | `20거래일 하락 10% 이상` |

**경계는 상한 배타 · 하한 포함**이다. `r = −8.0%` 는 `D8_10` 이다
(`D5_8` 의 `−8% < r` 조건을 만족하지 않는다).
**판정값과 표시값을 동일하게 정규화**해 `−8.0%인데 5~8% 그룹` 같은 경계 불일치를
만들지 않는다.

`DATA_UNAVAILABLE_OR_STALE` 은 이 구간과 **섞지 않고** `데이터 확인 필요` 별도
그룹으로 둔다.

> 실제 보유 위험의 `관찰·주의·경고` 는 이후 **별도 위험 알림 Gate** 에서 의미와
> 발생 빈도를 검증한 뒤 사용한다. 01A 는 쓰지 않는다.

| 지표 | 실측 |
|---|---:|
| 일평균 선정 ticker | **12.4** |
| 중앙값 | 11 |
| 최대 | 27 |
| **선정 0일** | **4일 / 60일 (7%)** |

**구간 분포 (연인원 · 60일 누적 · 종가 기준)**

| 구간 | 건수 | 비율 |
|---|---:|---:|
| **`D10_PLUS`** (≤ −10%) | **501** | **67%** |
| `D5_8` (−8% < r ≤ −5%) | 168 | 23% |
| `D8_10` (−10% < r ≤ −8%) | 74 | 10% |

이 쏠림이 **명칭을 사실형으로 바꾼 근거**다. 최상위 구간이 3분의 2를 차지하면
`경고` 라는 이름이 정보를 주지 못한다. `20거래일 하락 10% 이상` 은 쏠려 있어도
사실 그대로다.

## 3. 메시지 계약

### 3.1 OPEN — 전체 현재 상태 [V1.1 · 면책문구 제거 / V1.2 · 구간 명칭]

**운영 메시지 형식** — 구조만 보인다. 구체 숫자가 든 예시는 §3.3 preview 에만 둔다
(운영 헤더에 과거 종가 실측값을 섞으면 §3.3 에서 없앤 시점 모순이 되살아난다).

```
[보유 종목 관찰 브리핑] 09:15
기준: 20거래일 전 종가 {YYYY-MM-DD} · 시세 {YYYY-MM-DD HH:MM}

■ 20거래일 하락 10% 이상 (n)
  {종목명}                    20거래일 −xx.x%   [고점 대비 −xx.x%]
  {종목명} (2개 계좌)          20거래일 −xx.x%

■ 20거래일 하락 8~10% (n)
  …

■ 20거래일 하락 5~8% (n)
  …

■ 데이터 확인 필요 (n)
  {종목명}                    현재가 조회 실패
```

- 헤더의 **두 날짜는 서로 다르다** — 분모는 과거 종가일, 분자는 실행 시점 시세다
  (§1.4). 같은 날짜로 적으면 안 된다.
- 그룹 표시 순서: `10% 이상` → `8~10%` → `5~8%` → `데이터 확인 필요`

**면책·주의 문구를 넣지 않는다. 다른 면책·운영 설명으로 대체하지도 않는다.**
(사용자가 명시적으로 불필요하다고 판정 — 설계자 필수 수정 1)

- 고유 ticker **1회만**. 다계좌는 종목 1행 + `(N개 계좌)`
- **개수 상한 없음**
- 평가금액·현재가·NAV·구성종목 등 **선정과 무관한 숫자 제외**
- 표시 숫자는 **선정 근거 값 1개** + 보조 `[고점 대비 x%]`

### 3.2 MIDDAY · CLOSE — 변화분만 [V1.1]

```
[보유 종목 관찰 브리핑] 12:30 — 변화 2건

■ 새로 선정 (1)
  TIGER 200 IT              20거래일 −8.4%   (하락 8~10%)

■ 구간 이동 (1)
  KODEX 미국우주항공         20거래일 −8.2% → −10.4%
                             (하락 8~10% → 하락 10% 이상)
```

면책문구 없음. 변화 0건이면 **runner 는 실행하되 Telegram 을 보내지 않는다**
(`status=skipped` · `reason=no_change`). **cron 은 변경하지 않는다.**

### 3.3 사용자 확인용 preview [V1.1 신규 — 필수 수정 4]

현재 `RECENT_DECLINE` 이 0건이라 구현 후 아무 메시지도 오지 않을 수 있다.
형식을 확인할 수 없으므로 **실제 발송하지 않는 preview** 를 만든다.

#### [V1.2] 시점 모순 제거

V1.1 예시는 `2026-06-30 종가` 와 `2026-06-30 09:14 시세` 를 **동시에** 썼다.
**09:14 에는 당일 종가를 알 수 없다.** 과거 장중 현재가도 저장돼 있지 않다.
실제 OPEN 재현처럼 표기해서는 안 된다.

preview 헤더는 다음으로 **고정**한다.

```
[보유 종목 관찰 브리핑 — 형식 미리보기]
과거 종가 기준: 2026-06-30
```

- **`09:14` 삭제**
- **실제 과거 OPEN·MIDDAY 재현이라고 주장하지 않는다**
- 산출물 메타데이터에 **`"basis": "EOD_CLOSE_PROXY"`** 기록
- **운영 메시지에는 이 설명을 넣지 않는다** (preview 전용)

| 항목 | 값 |
|---|---|
| 고정 기준일 | **`2026-06-30`** (60거래일 중 선정 11종목) |
| 산출 방식 | 과거 **종가**로 선정 로직을 돌려 본문 문자열만 생성 (`EOD_CLOSE_PROXY`) |
| **발송** | **하지 않는다** (Telegram 미호출) |
| 산출물 | **`state/three_push/previews/holdings_selection_preview_latest.json`** — 운영 상태와 **디렉터리 분리** |
| 메타데이터 | `basis` · `basis_date` · `generated_at_kst` · 선정 목록 |
| 검증 항목 | 구간 그룹화 · 종목 전부 포함 · 다계좌 중복 제거(`RISE 네트워크인프라 (2개 계좌)`) · 보조 고점 대비 표시 · **면책문구 없음** · **실행시각이 기준일보다 이르다고 주장하지 않음** |

**preview 와 실제 운영 결과를 모두 사용자 확인 대상으로 둔다.**

## 4. 상태 · fingerprint 설계

### 4.1 저장 형식 [V1.1 — reason별 severity]

```
state/three_push/holdings_selection_state_latest.json

{
  "schema_version": "holdings_selection_state.v1",
  "kst_date": "2026-09-03",
  "created_at_kst": "2026-09-03T09:15:02+09:00",
  "updated_at_kst": "2026-09-03T12:30:01+09:00",
  "last_slot": "MIDDAY",
  "entries": {
    "0167Z0": {
      "reasons": {
        "RECENT_DECLINE":            {"state": "D10_PLUS", "value": -10.4},
        "DATA_UNAVAILABLE_OR_STALE": {"state": "ACTIVE",   "value": null}
      }
    }
  }
}
```

**[V1.2] `severity` 를 `state` 로 바꿨다.** 저장 가능한 값은 4개뿐이다 —
`RECENT_DECLINE:D5_8` · `RECENT_DECLINE:D8_10` · `RECENT_DECLINE:D10_PLUS` ·
`DATA_UNAVAILABLE_OR_STALE:ACTIVE`.

**보조 정보(고점 대비)는 상태에 저장하지 않는다** — 변화 판정에 쓰지 않기 때문이다.
primary 와 표시 순서는 저장하지 않고 **매 슬롯 계산**한다.

### 4.2 비교 identity [V1.1 — 필수 수정 2]

```
fingerprint(ticker) = ticker | sorted(reason:state)
```

**V1 의 `ticker | sorted(reasons) | max_severity` 는 결함이었다.**
primary 가 이미 최상위일 때 secondary 가 한 단계 올라가도 max 가 그대로라
**변화가 억제**된다. reason별 state 를 각각 비교해야 한다.

**[V1.2]** `severity` → **`state`**. 구간 이동(`D8_10 → D10_PLUS`)이 재발송 조건이다.

근거 값(`value`)은 identity 에서 **제외**한다. 넣으면 `−10.41 → −10.43` 에도 매
슬롯 발송된다. 값 변화는 severity 단계가 바뀔 때만 의미를 갖는다.

### 4.3 변화 판정

| 상황 | 처리 |
|---|---|
| 이전에 없던 ticker | **새 종목** → 발송 |
| reason 추가·제거 | **새 이유 / 이유 해소** → 발송 |
| **특정 reason 의 state 변경** (primary·secondary 무관) | **구간 이동** → 발송 |
| fingerprint 동일 | **억제** |
| 선정 → 미선정 | **정상 해소** → 발송 |

### 4.4 하루 경계 · 다음 영업일

- **KST** `runtime_date_kst` 기준. 저장된 `kst_date` 와 다르면 상태를 버리고
  **OPEN 과 동일하게 전체 현재 상태 발송**
- **다음 영업일 OPEN 은 동일 상태여도 재발송** — "오늘 아침 현재 상태 전달"이 OPEN 의 계약
- 주말·공휴일은 cron 미실행이라 자연히 초기화

### 4.5 상태 없음 · 손상 — 조용한 억제 금지

```
상태 파일 없음 / JSON 파손 / schema_version 불일치 / kst_date 불일치
  → OPEN 과 동일하게 **전체 현재 상태 발송**
  → record["selection_state_fallback"] = "missing"|"corrupt"|"schema_mismatch"|"date_mismatch"
  → 로그 WARNING
```

**비교 실패를 `변화 없음` 으로 대체하지 않는다.**

### 4.6 발송 성공 후에만 상태 확정 [V1.1 신규 — 필수 수정 3]

원자 교체는 **파일 파손만** 막는다. 순서 계약이 따로 필요하다.

```
① 변화 계산
② Telegram 발송
③ 전체 chunk 성공 확인
④ 상태 파일 원자 교체  ← 여기서만 저장
```

| 계약 | 내용 |
|---|---|
| 저장 조건 | **전체 발송 성공 후에만** 새 상태 저장 |
| 부분 실패 | 이전 상태 **유지** (`telegram_partial_delivery=true` 포함) |
| 전체 실패 | 이전 상태 **유지** |
| 재시도 | 다음 슬롯에서 **같은 변화를 다시 시도** |
| 프로세스 사망 | 발송 후 저장 전 사망 시 **중복 발송 허용** |
| **금지** | **미발송 신호가 발송 완료로 기록되는 것** |
| 예외 | **OPEN 선정 0건**은 전달할 내용이 없으므로 **빈 상태 저장 허용** |

**중복은 허용하고 누락은 허용하지 않는다** — 판단 재료를 조용히 삼키는 쪽이 더 나쁘다.

## 5. 심각도 · 그룹 구조 [V1.1 확정]

### 5.1 [V1.2] 구간 (설계자 확정 · 사실형 명칭)

| reason | state | 범위 | 화면 표기 |
|---|---|---:|---|
| `RECENT_DECLINE` | `D5_8` | `−8% < r ≤ −5%` | `20거래일 하락 5~8%` |
| | `D8_10` | `−10% < r ≤ −8%` | `20거래일 하락 8~10%` |
| | `D10_PLUS` | `r ≤ −10%` | `20거래일 하락 10% 이상` |
| `DATA_UNAVAILABLE_OR_STALE` | `ACTIVE` | — | `데이터 확인 필요` (별도 그룹) |

**`관찰·주의·경고` 명칭은 01A 에서 쓰지 않는다.**

### 5.2 primary reason 결정

1. `DATA_UNAVAILABLE_OR_STALE` 이 있으면 **항상 그것이 primary**
2. 없으면 `RECENT_DECLINE` (구간 무관 — 심각도 서열을 만들지 않는다)

데이터 문제를 앞에 두는 이유: 값이 틀렸을 가능성을 먼저 알려야 나머지 숫자를
믿을지 판단할 수 있다.

### 5.3 그룹 · 정렬 · 보조 표시

- 그룹 키 = **`reason` + `state`** (예: `20거래일 하락 10% 이상`)
- 그룹 표시 순서: `D10_PLUS` → `D8_10` → `D5_8` → `데이터 확인 필요`
- 그룹 내 정렬: 근거 값 악화순 → ticker
- **보조 `RECENT_LOW_OR_DRAWDOWN`** 은 선정된 종목 행 끝에 `[고점 대비 x%]` 로만 붙인다.
  **그룹·fingerprint·severity 를 만들지 않는다**
- **`최대 N개` · 상위 일부 표시 규칙 없음**

### 5.4 완화 · 해소 · 다계좌

- `■ 구간 이동 (n)` / `■ 정상 해소 (n)` 별도 그룹. 값·구간 변화를 `A → B` 로 표기
- 다계좌는 **종목 1행 + `(N개 계좌)`**. 계좌명은 개인정보라 노출하지 않는다
  (`069500` 3계좌 · `367760` 2계좌 — `32 − 29 = 3` 의 정체)

## 6. 연관 BACKLOG 영향 [V1.1 — 설계자 판정 반영]

키워드 적중 **25 / 55건** 중 01A 수용기준에 직접 닿는 것만 올린다.

| BACKLOG 항목 | 01A와 관계 | **설계자 확정 처리** | 이유 |
|---|---|---|---|
| 보유 ETF 종합 위험 구간 분류 (factor·threshold·label) | `RELATED_LATER` | **`KEEP_BACKLOG`** | PUSH 표시용 심각도와 종합 위험 factor·rank 는 **같은 기능이 아니다**. 01A 로 완료 처리하면 더 넓은 원래 계약이 조용히 사라진다 |
| Telegram 메시지 Top N 설정값 UI화 | `RELATED_LATER` | **`KEEP_BACKLOG`** | 제목상 **전체 Telegram 메시지 설정**으로 보인다. 01A 가 없애는 것은 **보유 브리핑의 개수 상한뿐**이다. 원문이 보유 브리핑 전용임이 확인되지 않는 한 폐기하지 않는다 |
| 무릎/머리/어깨 정량 기준 | `RELATED_LATER` | `KEEP_BACKLOG` | 매수·매도 시점 기준이라 목표가 다르다 |
| 계좌별 Telegram 요약 / 채널 분리 | `RELATED_LATER` | `KEEP_BACKLOG` | 01A 는 계좌를 합쳐 1행으로 만든다. 반대 방향 |
| message_text ↔ Telegram 실제 렌더 차이 자동 검증 | `RELATED_LATER` | `KEEP_BACKLOG` | 01A 로 chunk 가 줄어 위험이 낮아진다. 필요조건 아님 |
| 보유 점검과 외부 발굴 가중치 | `RELATED_LATER` | `KEEP_BACKLOG` | PUSH 1↔2 충돌 정책. 01A 는 PUSH 1 내부만 |

> **V1 에서 제안했던 `INCLUDE_IN_STEP` · `DROP_AS_SUPERSEDED` 를 모두 철회한다.**
> **6건 전부 `KEEP_BACKLOG`** 이며, 이번 Step 에서 BACKLOG 를 수정·폐기하지 않는다.

## 9. [V1.3 확정] 공휴일 최소 안전계약

### 9.1 판별 근거 — 이미 가져오는 데이터만 쓴다

`app/market_naver.py:104` 는 Naver `localTradedAt` 을 **필수**로 요구한다.
없으면 quote 자체를 실패로 처리한다. 따라서 **성공한 quote 는 반드시 "그 가격이
언제 체결된 값인지"를 갖는다.**

형식: ISO-8601 + KST (`2026-07-24T15:30:00+09:00`). `price_asof[:10]` 이 체결일이다.

**한국 공휴일에는 KRX 가 열리지 않으므로 Naver 가 직전 거래일 체결값을 반환한다.**
→ 성공한 quote 전부의 체결일이 오늘보다 이르면 **오늘은 거래일이 아니다.**

**신규 휴장일 캘린더를 만들지 않는다. 신규 외부 조회를 하지 않는다.
cron 을 바꾸지 않는다.** 이미 조회하는 값의 필드 하나를 볼 뿐이다.

### 9.2 계약

```
비거래일 판정 (holdings_briefing 전용)
  조건 A: runtime quote 조회 전건 성공        (success == attempted > 0)
  조건 B: 성공 quote **전부**의 price_asof[:10] < 오늘 KST 날짜
  A ∧ B  →  status = skipped
            reason = non_trading_day
```

| 항목 | 처리 |
|---|---|
| Telegram | **미발송** |
| selection state | **미변경** (다음 거래일 OPEN 이 전체 상태를 보낸다) |
| `DATA_UNAVAILABLE_OR_STALE` | **판정하지 않는다** — 휴장일 가격을 stale 로 보지 않는다 |
| 기록 | `record["non_trading_day_evidence"] = {"quote_count": n, "max_price_asof": "YYYY-MM-DD", "today_kst": "YYYY-MM-DD"}` |

### 9.3 왜 이 순서가 안전한가

러너에는 이 지점 **앞에** 이미 `runtime_price_partial_failed` Fail-Closed 가드가
있다(`run_three_push_runtime_oci.py:256`). **일부라도 조회 실패면 여기 도달하기 전에
`failed` 로 끝난다.** 따라서 가드에 도달했다는 것은 **전건 성공**을 뜻하고,
그때의 `price_asof` 는 신뢰할 수 있다.

**조회 실패(A 불충족)를 비거래일로 오인하지 않는다.** 그건 기존 가드가 `failed` 로
잡는다. 이 가드는 "다 가져왔는데 전부 어제 값" 인 경우만 본다.

### 9.4 알려진 한계 (숨기지 않는다)

**보유 29종목 전부가 09:15 까지 한 건도 체결되지 않으면** 거래일인데도
`non_trading_day` 로 판정한다. 보유 목록에 `KODEX 200`(3계좌)·`TIGER 200 IT` 등
대표 유동 종목이 있어 현실적으로 발생하기 어렵지만, **가능성 자체는 남는다.**

**`any` 가 아니라 `all` 을 쓴 이유**가 이것이다. 한 종목이라도 오늘 체결값을
가지면 거래일로 본다 — 오탐(발송 억제)보다 과탐(발송)을 택한다.

### 9.5 테스트

| # | 테스트 |
|---|---|
| **T-19** | 전 quote 의 `price_asof` 가 어제 → `skipped/non_trading_day` · Telegram 미호출 · state 미변경 |

## 11. 설계자 확정 계약 2건 — **확정 완료 (2026-09-05)**

> ✅ **§11.5 가 확정 회신이자 현행 계약이다.** 아래 §11.1·§11.2 는 **확정 전에
> 무엇을 왜 물었는지의 기록**이고, 그 안의 "현재 구현" 서술은 **확정 전 상태**를
> 가리킨다 — 현행 계약으로 읽으면 안 된다.

[V1.4 원문] 구현·검증은 끝났다. 검증자 r2~r4 가 **개발자가 판단할 사안이 아니라고
분류**한 2건만 남았고, 이것 때문에 Step 을 닫지 못한다. 아래는 판단에 필요한
실측만 담았다. 검증 라운드 이력은 결과서(§9.3·§9.5·§9.6)에 있고 여기 옮기지 않는다.

### 11.1 비거래일 완전성 조건 — PLAN 과 구현 불일치

| | 내용 |
|---|---|
| **PLAN §9 확정** | `success == attempted > 0` |
| **현재 구현** | `attempted > 0 and success > 0 and failed == 0` |
| **왜 달라졌나** | 아래 실측 때문. 검증자 r1 이 "가드가 죽어 있다" 고 지적해 고쳤는데, 이게 PLAN 계약 변경이라 r2 부터 승인 대상이 됐다 |

**실측 (2026-09-04, 로컬 원장·DB 읽기 전용)**

```
보유 원장            32 행   ← 같은 종목을 여러 계좌에서 보유
고유 ticker          29 개
collect_target_tickers("holdings_briefing") → 32 행 반환
fetch_many(...)                             → 29 유니크 quote 반환
따라서  attempted=32,  success=29,  failed=0   ← 전건 성공인 정상 상태
```

`success == attempted` 는 **정상 상태에서도 참이 될 수 없다**. 즉 PLAN 대로 두면
비거래일 가드가 영구히 발동하지 않는다. 휴장일에도 29종목 전부가 전일 종가를
근거로 브리핑되거나 `데이터 확인 필요` 로 표시된다.

**선택지**

| 안 | 판정식 | 성질 |
|---|---|---|
| **(a)** | `attempted>0 and success>0 and failed==0` (현재 구현) | 실패가 1건이라도 있으면 휴장일 판정 안 함. 조회 실패를 휴장일로 오인하지 않는다 |
| (b) | `success == 고유 ticker 수` | "완전성" 을 원래 의도대로 유지하되 분모를 행이 아닌 고유 종목으로 정정 |
| (c) | 그 외 설계자 지정 | |

> 개발자 의견을 묻는다면 (a) 다. (b) 는 `fetch_many` 가 항상 고유 ticker 만
> 돌려준다는 가정에 의존해, 그 계약이 바뀌면 같은 방식으로 다시 죽는다.
> 다만 **이건 개발자가 정할 사안이 아니라고 판정받은 항목**이라 구현하지 않고 둔다.

### 11.2 종가 stale 임계 — 승인 없는 신규 비즈니스 값

| | 내용 |
|---|---|
| **현재 구현** | `MAX_PRICE_STALE_DAYS = 7` (달력일) |
| **출처** | 다른 Spike 계약의 7일을 가져왔다. **이번 설계서·PLAN 어디에도 없는 값**이고, 보유 시세·종가에 적용한다는 승인이 없다 |
| **역할** | 20일 수익률의 **분모**(20거래일 전 종가)가 너무 오래된 값이면 그 종목을 `DATA_UNAVAILABLE_OR_STALE` 로 뺀다 |

**실측 — 보유 29종목의 마지막 종가 지연일 (2026-09-04 기준)**

```
지연  0일 : 26 종목
지연 23일 :  3 종목
그 사이   :  0 종목
```

**분포가 두 덩어리로 완전히 갈린다.** 그래서 임계를 1~22일 중 어디에 두든
운영 결과가 **동일**하다 — 26종목 통과 / 3종목 제외.

| 임계 | 제외 종목 |
|---|---|
| 3 · 5 · 7 · 10 · 14 일 | 3 종목 (10.3%) — 전부 동일 |
| 30 일 | 0 종목 |

즉 **7 이라는 숫자 자체는 지금 데이터에서 의미가 없다.** 정할 것은 "그 3종목을
뺄 것이냐" 이고, 임계값은 그 판단을 표현하는 수단이다.

**⚠️ 그 3종목이 왜 23일 지연인지 — 이번에 드러난 별개 사실**

| 확인 | 값 |
|---|---|
| 3종목의 `etf_master` 등재 | **0건** (ETF 가 아니라 **개별주**) |
| 3종목 마지막 종가 | 2026-08-12 |
| ETF 유니버스 최신 종가 | 2026-09-04 (1,167 ticker) |
| `etf_master` 총 등재 | 1,178 |

**개별주가 시세 갱신 파이프라인에 포함돼 있지 않다.** 종목이 상장폐지·거래정지된
게 아니라, 갱신 대상 자체가 ETF 유니버스라 개별주는 2026-08-12 이후로 멈춰 있다.

이건 stale 임계와 **다른 층위의 문제**다. 임계를 어떻게 정하든 이 3종목은 갱신되지
않는 한 계속 제외된다. 본 Step 범위 밖이라 **손대지 않았고**, 별도 판단이 필요하다.

**선택지**

| 안 | 내용 |
|---|---|
| (a) | `7일` 승인 (현행 유지) |
| (b) | 다른 값 지정 — 단 1~22 사이는 현재 데이터에서 결과가 같다 |
| (c) | 달력일이 아니라 **거래일** 기준으로 정의 (휴장 연휴 영향 제거) |
| (d) | stale 판정을 **이번 범위에서 제외** — 분모가 아무리 오래돼도 계산한다 |

> 파싱 실패·미래 일자를 stale 로 보는 **fail-closed 방향**은 임계값과 무관한 안전
> 처리라 그대로 두었다(미래 일자는 DB 오염이다). 확정이 필요한 것은 **임계값뿐**이다.

| 상태 | 처리 | 구현 |

통과시키고 **시장·급등락은 기존대로 `runtime_price_partial_failed` 차단**이다
(테스트로 고정).

#### 확정 ② stale 임계 **폐기** → 정확한 기준일 종가

`MAX_PRICE_STALE_DAYS = 7` 제거. 달력일·거래일 허용 임계를 두지 않는다.

```
기준일 = KRX 거래일 축에서 실행일보다 앞선 20번째 거래일
분모   = 그 ticker 의 **기준일 종가** (정확히 그 날짜)
분자   = 실행 시점의 유효한 runtime 현재가 (price_asof 가 실행일)
```

- 기준일 종가가 있으면 계산, 없으면 `DATA_UNAVAILABLE_OR_STALE`
- **더 오래된 종가로 대체하지 않는다** — 대체하면 20거래일이 아닌 구간의
  수익률을 20거래일이라고 보고하게 된다
- "마지막 저장 종가가 며칠 전인가" 로 배제하지 않는다
- 고점 대비 보조값은 구간이 불완전하면 **보조값만** 생략. 그 때문에 계산
  가능한 `RECENT_DECLINE` 을 버리지 않는다

거래일 축은 신규 캘린더를 만들지 않고 walk-forward 가 이미 쓰는 KODEX200
거래일 시퀀스를 재사용한다(`TRADING_DAY_AXIS_TICKER`). **신규 외부 조회 0건** —
같은 `fetch_history` 를 쓴다.

#### 확정 ③ 개별주 시세 미갱신 → 열린 결함 등재

`docs/backlog/BACKLOG.md` 에 **`DEF-PRICE-EQUITY-REFRESH`** 로 등재했다
(열린 결함 2건 → **3건**). 01A 에서 파이프라인은 고치지 않는다. 재검토 트리거는

임계값으로 숨기지 않는다.

## 13. [V1.7] 매입 대비 손익 추가 — 사용자 요청 (2026-09-06)

### 13.1 왜 바꿨나

r10 `VERIFIED` 이후 사용자가 목업을 보고 지적했다 — **판단용 PUSH 인데 "내가 산
금액 대비" 가 없어 팔지 홀딩할지 정할 수 없다.**

실측이 지적을 뒷받침했다. 같은 `20거래일 하락 10% 이상` 그룹 안에서

| 종목 | 20거래일 | 매입대비 |
|---|---:|---:|
| PLUS 글로벌휴머노이드로봇액티브 | −13.6% | **+64.1%** |
| 삼성SDI | −25.3% | **+21.9%** |
| 1Q 미국우주항공테크 | −18.4% | **−10.7%** |

하락폭만으로는 세 종목이 같은 칸에 있지만 판단은 정반대다.

### 13.2 확정된 계약

**세 지표 모두 같은 runtime 현재가를 분자로 쓴다.** 분모만 다르다.

```
매입 대비 손익률 = 현재가 / 수량가중평균 매입가 - 1
20거래일 수익률  = 현재가 / 20거래일 전 종가     - 1
고점 대비 수익률 = 현재가 / 기간 고점            - 1
```

세 슬롯(09:15·12:30·15:40) 모두 실행 시점 시세 기준이며 **OPEN 만 종가로 바꾸지
않는다**(사용자 확정 — (b)안).

| 결정 | 내용 |
|---|---|
| 다계좌 | **수량 가중평균**(금액합÷수량합). 계좌별 매입가가 실제로 다르다 — KODEX 200 이 84,190(3주)/88,058(15주)/114,941(2주) |
| fingerprint | **제외.** 보조 정보다 — 넣으면 값이 미세하게 흔들릴 때마다 매 슬롯 재발송된다 |
| 매입가 없음 | **손익만 생략**하고 선정은 유지 |
| 배치 | **두 줄(C안)** — 종목명 줄 + `매입대비 · 20거래일 · 고점 대비` |
| 라벨 | **`매입대비`** (설계자 확정 — `매입` 은 매입가인지 손익인지 모호) |

**두 줄로 간 이유**: 발송이 `parse_mode="HTML"` 이라 Telegram 이 **비례 글꼴**로
렌더한다. 한 줄에 몰면 종목명 길이에 따라 뒤가 밀리고 공백 정렬도 성립하지 않는다.
