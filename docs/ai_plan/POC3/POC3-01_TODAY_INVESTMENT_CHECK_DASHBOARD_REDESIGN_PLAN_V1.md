### 3.1 설계자 추가 강제사항 (최상단 정보 구분 — Q2·Q4 반영)

최상단 대표 영역은 다음을 **서로 다른 영역으로 분리**해 표시한다. 아래를 하나로 묶어 `코스피 시장 상태` 라고 라벨링하면 **FAIL**:

1. `코스피 가격 흐름`: 실제 KOSPI close 차트 + 기준일
2. `기존 시장 판정 참고 (KODEX200 기준)`: 상승장·보합장·하락장
3. `KODEX200 기준선 대비 위치`: MA20 대비, MA60 대비 (백엔드 제공 거리%)
4. `흐름 지속 거래일 수`: 개발 중
5. `최근 고점 대비 위치`: 개발 중
6. `거래량 흐름`: 개발 중 (툴팁: 자료 미저장)

> **핵심 FAIL 조건**: KOSPI 차트 옆에 KODEX200 판정을 놓고 전체를 `코스피 시장 상태` 로 묶는 것. → 두 기준은 시각적으로도 라벨상으로도 분리한다.

## 4. 확정 구현 계획 (Q1~Q9 판정 반영)

> 아래는 설계자 판정을 반영한 **확정 구현 골격**이다. 착수 직전 설계서 AC 와 1:1 재대조 후 구현한다.

### 4.1 백엔드 (Q1·Q4 반영)

1. **`GET /market/price-series` 확장 (Q1-a)**: 기존 ETF ticker read 계약을 유지한 채 **저장된 KOSPI benchmark 시계열**(`market_benchmark_daily_price`, benchmark_id='KOSPI')을 읽는 경로 추가. `fetch_benchmark_history("KOSPI")` 재사용 (저장값 read-only, 신규 산식·신규 소스 없음). 파라미터 구조는 개발자 판단(예: `?benchmark=KOSPI` 분기). `market_topn/latest` 는 건드리지 않는다.
2. **KODEX200 MA 거리% 백엔드 제공 (Q4-a)**: `market_context.kodex200` 는 이미 `close/ma20/ma60` 를 준다. `(close-ma20)/ma20*100`, `(close-ma60)/ma60*100` 를 **백엔드 응답에서 제공**. 위치는 개발자 판단(price-series 확장 응답 또는 market_context 파생 필드) — 단 신규 산식 아님(기존 저장값 단순 산술). **프론트에서 계산하지 않는다** (설계서 §4.1 "프런트 신규 산식 금지" + Q4 "백엔드 제공").

> 나머지(흐름 지속 거래일·최근 고점 대비·거래량)는 Q3·Q5 판정에 따라 **백엔드 계산 없음** — 프론트에서 `개발 중` 표시만.

### 4.2 Frontend 신규 화면 `TodayInvestmentCheckView`

- **§4.1 코스피 대표 영역**: KOSPI close 차트(기준일) / 별도 영역에 KODEX200 국면 라벨(`기존 시장 판정 참고 · KODEX200 기준`) / KODEX200 MA20·MA60 대비 거리% / 흐름 지속·고점 대비·거래량 = `개발 중`. **§3.1 분리 강제 준수.**
