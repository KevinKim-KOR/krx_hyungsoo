# 승인·알림 화면 역할 분리 및 재배치 통합 설계 V1

> 출처: 설계자 설계서 (레드팀 PASS). 사용자가 채팅으로 개발자에게 전달(2026-08-01). 본 파일은 검증자 대조용 원본 설계서 보존본 — 개발자가 임의 편집하지 않는다. Q1~Q6 답변 및 설계 정정은 개발 PLAN(`docs/ai_plan/POC3/POC3-APPROVAL_ALERT_ROLE_SEPARATION_V1_PLAN_V1.md`)에 기록.

## 1. 설계 지위

- 독립 Operations Panel: 제외·폐기
- 신규 화면·메뉴·route: 없음
- 기존 approval key와 ApprovalTelegramView: 유지
- 화면 재배치: 현재 작업에 포함
- 잘못된 통합지도 문구: 이번 설계로 대체
- 통합지도·STATE 수정: 구현 완료 시 함께 정리하며 개발 착수의 선행조건으로 삼지 않음

POC3-04라는 번호를 붙여 폐기된 화면을 이름만 바꿔 부활시키지 않습니다.

## 2. 현재 문제

현재 승인·알림 화면에는 성격이 다른 기능이 한꺼번에 놓여 있습니다.

- 투자 판단 초안의 승인·거절
- 운영 PARAM의 OCI 적용
- Market·Holdings·Spike 정보 PUSH 생성·점검
- 신규 ETF 관찰 후보 갱신
- 기존 수동 전달·개발 점검 기능
- 최근 처리 결과

이 때문에 사용자가 다음을 구분하기 어렵습니다.

- 무엇이 사람의 승인을 받아야 하는 투자 판단 초안인가
- 무엇이 메시지별 승인 없이 자동 운영되는 정보 PUSH인가
- 무엇이 OCI에 운영 기준을 적용하는 기능인가
- 무엇이 개발·호환 점검용 기능인가

## 3. 이번 작업의 단일 목표

기존 기능과 계약을 유지하면서 승인·알림 화면을
판단 초안 → OCI 적용 → 정보 PUSH → 상세·점검 순으로 재배치한다.

오늘의 투자 점검처럼 상단에서 현재 상태와 해야 할 행동을 먼저 확인하고, 상세·개발 정보는 아래로 내립니다.

## 4. 반드시 분리할 세 가지 역할

| 영역 | 실제 의미 | 사용자 승인 |
|---|---|---|
| 판단 초안 | PENDING 투자 판단 초안을 확인하고 승인·거절 | 필요 |
| OCI 적용 | PC에서 확정한 운영 PARAM을 OCI에 적용 | 사용자가 적용 버튼 실행 |
| 정보 PUSH | Market·Holdings·Spike 정보를 OCI가 자동 발송 | 메시지별 승인 없음 |

주의할 점은 PENDING_APPROVAL입니다.

- 투자 판단 초안이라면 판단 초안 승인 대기로 표시합니다.
- 정보 PUSH 점검 과정에서 생성된 run이라면 투자 승인처럼 표시하지 않습니다.
- 둘을 구분할 확실한 기존 필드가 없다면 개발자가 추측해서 분류하지 않습니다.

## 5. 최종 화면 구조

### 5.1 화면 상단
제목은 당분간 승인·알림을 유지합니다.
설명: 투자 판단 초안의 승인, OCI 운영 기준 적용, 자동 정보 알림 상태를 역할별로 확인합니다. 정보 PUSH는 메시지마다 승인하지 않습니다.
그 아래에 세 영역의 요약을 표시합니다.
- 판단 초안: 처리할 초안 유무와 현재 상태
- OCI 운영 기준: 적용 상태와 마지막 적용 시각
- 정보 PUSH: Market·Holdings·Spike의 운영 방식
실제 조회값이 없는 항목을 정상, 운영 중으로 만들어 표시하지 않습니다. 실시간 상태가 아니라 정책 안내라면 반드시 운영 기준이라고 표시합니다.

### 5.2 상단 핵심 작업 영역
2열을 기본으로 하되 실제 화면 폭에 맞게 배치합니다. 특정 해상도나 고정 픽셀을 AC로 두지 않습니다.
왼쪽: 판단 초안 — 기존 RunPanel의 판단 초안 기능. 승인·거절은 투자 판단 초안에만. 초안이 없으면 "현재 확인할 판단 초안이 없습니다."로 압축.
오른쪽: OCI 운영 기준 적용 — 기존 ThreePushParamCard 재사용. create → approve → sync → verify 동작 계약 불변. 정보 PUSH 개별 승인 버튼 아님.

### 5.3 정보 PUSH 운영 영역
Market·Holdings·Spike를 같은 위계의 세 카드로. 정확한 실행 시각·최근 정상 실행은 기존 조회 계약으로 확인될 때만. 문서 과거 값 고정 금지.
수동 생성 기능은 아래쪽 미리보기·수동 점검 영역으로. 미리보기/수동 점검용 생성으로 표현, 실제 발송 버튼과 시각 구분. 보유 종목용 생성은 내가 가진 ETF에 있으면 이동 링크만.

### 5.4 최근 처리 결과
기존 화면이 실제로 조회할 수 있는 정보만. 판단 초안 처리 결과·OCI 적용 결과·수동 미리보기·전달 결과·실패 사유·처리 시각. OCI 자동 PUSH 이력 조회 계약 없으면 자동 발송 이력처럼 표시 금지. run_id·raw status·내부 경로·JSON은 상세 펼침 안.

### 5.5 개발·호환 점검
화면 최하단 기본 접힘. 샘플 초안 생성·기존 수동 승인·전달 점검·raw runtime 정보·run 식별자·과거 호환 경로. 삭제하지 않되 정상 운영 동선에서 앞으로 안 나오게.

### 5.6 신규 ETF 관찰 후보 갱신
UniverseRefreshPanel은 승인·알림에서 제거하고 요즘 잘 오르는 ETF로 이동. 복제하지 않고 한 곳에만.

## 6. 개발 전 사실확인
직접 경로: ApprovalTelegramView·RunPanel·ThreePushParamCard·ThreePushDraftCard·UniverseRefreshPanel·MarketDiscoveryView·HoldingsClient·MainPanel draft→approval 경로.
확인: 각 버튼 API·부수효과 / 판단 초안·PUSH run 구분 필드 / OCI·Telegram 결과 조회 범위 / UniverseRefreshPanel 이동 시 공유 상태·캐시 / 컴포넌트 크기·분리 필요성.
질문 조건: 판단 초안·정보 PUSH run 구분 불가 / 컴포넌트 이동으로 데이터 의미 변화 / 자동 발송 결과에 신규 API 필요 / 기존 기능 유지 선택지 복수 & 동선 상이.

## 7. 한 설계 안의 순차 개발 게이트

### A구간 — 역할 분리와 상단 재배치
구현: 상단 요약·판단 초안 영역·OCI 적용 영역·정보 PUSH와 판단 승인의 문구 분리.
사용자 확인 A: 승인 필요 기능/자동 정보 PUSH 구분 / 판단 초안·OCI 적용 상태·버튼 찾기 쉬운가.
미통과 시 A만 수정. A 통과 전 B 금지.

### B구간 — 정보 PUSH와 결과 영역 정돈
구현: Market·Holdings·Spike 운영 기준 구분 / 미리보기·수동 점검 위계 하향 / 기존 자료로 확인 가능한 최근 결과 / 내부 상태와 사용자 문구 분리.
사용자 확인 B: 자동 PUSH ↔ 수동 미리보기·전달 점검 혼동 없나 / 판단 초안 승인·거절이 정보 PUSH마다 필요한 절차처럼 보이지 않나.

### C구간 — 잘못 배치된 기능 이동과 전체 정리
구현: UniverseRefreshPanel 이동 / 개발·호환 기능 기본 접힘 / 기능 누락·중복 점검 / 전체 위계 정리.
사용자 확인 C: 기존 주요 기능 빠짐없이 찾을 수 있고 승인·알림 화면에 역할에 맞는 기능만 남았나.
C 통과 후에만 전체 검증·최종 PASS.

## 8. 개발 완료 AC

1. approval MenuKey와 기존 화면 전환 경로가 유지된다.
2. 신규 사용자 화면·메뉴·route가 0건이다.
3. 신규 API·DB·source·factor·threshold·scheduler 변경이 0건이다.
4. 판단 초안 승인·거절 기능은 판단 초안 영역에만 존재한다.
5. ThreePushParamCard의 기존 적용 계약과 실패 보호가 유지된다.
6. 정보 PUSH 영역에 메시지별 승인이 필요한 것처럼 보이는 문구가 없다.
7. 자동운영 상태와 수동 미리보기 결과를 같은 상태로 표시하지 않는다.
8. UniverseRefreshPanel은 요즘 잘 오르는 ETF에 정확히 한 번 존재한다.
9. 샘플·raw 정보·기존 호환 기능은 기본 접힘 영역에 있다.
10. 기존 실행 기능의 누락과 중복이 0건이다.
11. Frontend 변경 범위의 테스트·lint·build가 통과한다.
12. A·B·C 사용자 확인 결과가 모두 통과한다.

## 9. 친구 프로젝트 반영 판단
반영: 기능 과업별 그룹화 / 상태 요약과 상세 로그 분리.
미반영: 별도 배치 화면·배치 취소·Slack 운영시간·친구 급변 threshold·공격/방어 비중·별도 운영 대시보드·MongoDB·신규 로그 API.
친구 배치 상태·로그를 그대로 가져오려면 신규 조회 계약 필요 가능성 큼 → BACKLOG.
- 보류 사유: 기존 프론트 조회 계약 유무 미확인, 신규 API 필요 가능성.
- 보류된 위험: OCI 자동 발송 실패를 PC 화면에서 바로 확인 못 할 수 있음.
- 재검토 트리거: 실제 Telegram 누락·실패 발생 & 기존 로그만으로 원인 파악 어려울 때.
