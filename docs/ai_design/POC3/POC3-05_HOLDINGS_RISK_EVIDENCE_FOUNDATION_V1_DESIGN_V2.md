## 0. 결론

이번 Step의 목적과 evidence 계약은 유지한다.

> 사용자가 1분 안에 오늘 먼저 확인할 보유 ETF와 그 수치 근거를 찾게 한다.

다만 V1의 `내가 가진 ETF` 한 화면 안에 입력·평가·시장 evidence·확인 근거를 모두 누적하는 구조는 폐기한다.
실제 화면에는 보유 입력행이 많고, 평가·시장 evidence까지 이미 존재하므로 구역 제목이나 접힘만으로는 과밀을 해소할 수 없다.

기존 좌측 메뉴 그룹 `보유·자료 관리` 바로 아래를 다음 네 하위 메뉴로 재구성한다.

1. `보유 현황`
2. `종목 관리`
3. `확인 근거`
4. `데이터 상태`

`내가 가진 ETF`라는 중간 부모 메뉴는 두지 않는다.
기존 그룹 아래에 다시 부모와 탭을 만드는 3단계 구조보다, 네 과업을 바로 선택하는 2단계 구조가 더 단순하다.

이번 개정은 새 기능 확장이 아니다.
기존 기능과 현재 개발 중인 evidence 표시물을 올바른 화면으로 분리하는 **사용 가능성 보정**이다.

## 1. 왜 지금 개정해야 하는가

### 1.1 실제로 확인된 문제

V1은 같은 화면 안에서 다음을 시각적으로만 분리하려 했다.

- 보유 종목 입력·저장
- 시세 갱신과 평가 현황
- 보유 종목과 시장 Evidence
- 신규 `보유 ETF 확인 근거`
- 저장된 보유 종목을 이용한 수동 초안 생성

사용자 실화면 확인 결과, 보유 입력행 아래에 여러 읽기 전용 영역이 계속 이어져 다음 문제가 확인됐다.

- 가장 자주 보는 평가 현황까지 도달하는 데 입력 영역을 통과해야 한다.
- 종목을 수정하려는 작업과 오늘 상태를 확인하려는 작업이 한 화면에 섞인다.
- 기존 시장 Evidence와 신규 확인 근거가 서로 다른 기능처럼 중복 노출될 수 있다.
- 기능은 존재하지만 사용자가 어디서 무엇을 해야 하는지 다시 조립해야 한다.

따라서 이는 색상·간격 문제가 아니라 POC3-05 목표를 막는 화면 구조 결함이다.

### 1.2 사용자에게 생기는 도움

개정 후에는 목적에 따라 바로 들어갈 수 있다.

| 사용자의 질문 | 들어갈 메뉴 |
|---|---|
| 내 보유자산 평가가 지금 어떤가 | `보유 현황` |
| 종목·수량·매입가를 바꾸고 싶다 | `종목 관리` |
| 오늘 먼저 확인할 ETF와 이유가 무엇인가 | `확인 근거` |
| 데이터가 왜 없거나 오래됐는가 | `데이터 상태` |

사용자는 35개 입력행을 지나가지 않고 평가 현황과 확인 근거를 볼 수 있고,
입력·저장 작업도 다른 정보에 가리지 않고 수행할 수 있다.

### 1.3 개정하지 않으면 남는 문제

- POC3-05 evidence가 구현돼도 화면 하단에 묻힌다.
- Dashboard에서 이동한 사용자가 다시 긴 Holdings 화면에서 위치를 찾아야 한다.
- 보유 현황·관리·판단 근거의 역할이 계속 혼동된다.
- 이후 기능이 추가될 때 같은 화면 아래로 붙이는 구조가 반복된다.
- 결과적으로 `기능은 많으나 조합이 안 된 화면`이라는 기존 문제가 재발한다.

## 2. 현재 상태와 개정 범위

### 2.1 현재 Step 상태

- Evidence 계약 사실확인: 완료
- B구간 일부 구현: 진행 중이었으나 사용자 실화면 확인에서 `UI_REDESIGN_REQUIRED`
- 동일 화면 하단 누적 방식: 미통과
- 전체 Step: `PASS / CLOSED` 아님
- 추가 구현: DESIGN_V2와 PLAN_V2 확정 전 보류

이는 데이터 기능 실패가 아니라 화면 배치 실패다.

### 2.2 유지하는 것

- `GET /holdings/enriched`
- `GET /holdings/market-evidence/latest`
- 기존 Holdings 입력·저장 계약
- 기존 평가·시세 갱신 계약
- 기존 선택 종목 상세와 lazy 조회 계약
- 이미 구현된 evidence 조회·정규화·표시 컴포넌트 중 V2 의미와 맞는 부분
- Dashboard와 Judgment Workbench의 기존 역할
- `보유·자료 관리` 그룹과 접힘·활성 표시 방식
- `data_status` 화면과 기능
- OCI·Telegram·PARAM·scheduler 계약

### 2.3 폐기하거나 대체하는 것

- V1 §5.2의 `내가 가진 ETF` 동일 화면 누적 구조
- V1 §5.4·§8의 `신규 메뉴·route·독립 화면 금지`
- V1 AC-1의 기존 메뉴·route 전부 유지 요구 중 Holdings 화면 구조 부분
- V1 AC-9의 Dashboard가 단일 Holdings 화면 내부 영역으로 이동해야 한다는 요구
- V1 AC-10의 같은 화면 안에서 입력·저장과 읽기 전용 영역만 시각 분리하면 된다는 전제

V1의 다른 evidence 의미·금지사항·데이터 정직성 원칙은 V2에 통합해 유지한다.

## 4. 메뉴·화면 정보 구조

### 4.1 좌측 메뉴 구조

기존 최상위 작업군 순서와 다른 그룹은 유지한다.

`보유·자료 관리` 그룹만 다음처럼 개정한다.

| 순서 | 사용자 메뉴명 | 화면 전환 key | 역할 |
|---:|---|---|---|
| 1 | `보유 현황` | 기존 `holdings` 유지 | 평가 현황과 시세 갱신 |
| 2 | `종목 관리` | 신규 `holdings_manage` 허용 | 입력·수정·삭제·저장 |
| 3 | `확인 근거` | 신규 `holdings_evidence` 허용 | 오늘 먼저 볼 ETF와 근거 |
| 4 | `데이터 상태` | 기존 `data_status` 유지 | 수집·적재·가용성 진단 |

확정 규칙:

- 기존 `holdings` key는 삭제하지 않고 `보유 현황`의 진입점으로 유지한다.
- 신규 화면 전환 key는 `holdings_manage`, `holdings_evidence` 두 개만 허용한다.
- 신규 최상위 그룹이나 독립 Risk Dashboard는 만들지 않는다.
- 별도 URL 라우팅 체계는 도입하지 않는다. 현재 MainPanel 화면 전환 방식을 확장한다.
- `내가 가진 ETF`는 부모 메뉴나 다섯 번째 메뉴로 남기지 않는다.
- 네 메뉴는 `보유·자료 관리` 그룹에 각각 정확히 한 번만 귀속한다.
- 기존 9개 MenuKey 체계는 11개가 되며, 누락·중복 시 기존 fail-closed 무결성 검사를 통과시키지 않는다.

### 4.2 `보유 현황`

사용자의 질문:

> 지금 내 보유자산의 평가 상태가 어떤가?

기본 노출:

- 전체 평가 요약
- 기존 계좌별 평가 요약
- ticker별 평가 현황
- 평가액·평가 비중·평가손익
- 가격·평가 기준일과 자료 상태
- 기존 시세 갱신 실행과 결과
- `종목 관리`, `확인 근거`로 이동하는 명확한 연결

금지:

- 보유 종목 입력 폼과 저장 버튼
- 긴 시장 Evidence 표
- 신규 위험 점수·등급
- 수동 초안 생성
- 데이터 상태 화면의 진단 상세 복제

`보유 현황`은 읽기 중심이지만, 현재 평가를 최신화하는 기존 시세 갱신 기능은 유지한다.

### 4.3 `종목 관리`

사용자의 질문:

> 어떤 종목·수량·매입가를 저장하거나 수정할 것인가?

포함:

- 기존 보유 종목 입력행
- 행 추가·수정·삭제
- 기존 필수 입력 검증
- 저장과 저장 결과
- 계좌·매입 정보의 기존 의미
- 저장 완료 후 `보유 현황 보기` 연결

금지:

- 평가·시장 Evidence의 전체 표
- 오늘 확인할 종목 정렬
- BUY·SELL·리밸런싱 제안
- 수동 초안 생성
- 저장되지 않은 변경값을 읽기 전용 평가 결과처럼 표시

`종목 관리`는 입력·저장 전용 화면이다.

### 4.4 `확인 근거`

사용자의 질문:

> 오늘 어떤 보유 ETF를 먼저 봐야 하며, 실제 수치 근거는 무엇인가?

기존 `보유 vs 시장 Evidence`와 신규 `보유 ETF 확인 근거`를 별도 대형 영역으로 나란히 두지 않는다.
하나의 읽기 흐름으로 통합한다.

기본 노출:

- 제목 `보유 ETF 확인 근거`
- Holdings 기준일과 Market Evidence 기준일
- `계산 가능 N/M · 확인 불가 K`
- 빠른 보기 `전체 / 자료 확인 필요`
- ticker별 한 줄 표
- ETF명·ticker
- 평가액·평가 비중·평가손익
- 최근 5일·20일 수익률
- `KODEX200 대비 20일`
- 데이터 상태와 확인 필요 사유
- 사용자 선택 정렬: 평가 비중, 평가손익, 5일, 20일, KODEX200 대비

선택 상세:

- 기존 선택 ticker 가격 차트
- 기존 NAV·괴리율
- 기존 구성종목·중복률
- 각 항목의 기준일과 unavailable 사유
- 필요 시 `ETF 구성종목`, `데이터 상태`, `ETF 비교하기`로 이동

표현 원칙:

- 사용자 화면 명칭은 `확인 근거`와 `자료 확인 필요`다.
- `저위험`, `고위험`, `안전`, `정상 종목`, `매도 필요`를 사용하지 않는다.
- 낮은 5일 수익률은 정렬 기준일 뿐 위험 판정이나 signal이 아니다.
- NAV·구성종목·중복률 부족을 핵심 흐름 전체의 정상·비정상 판정으로 승격하지 않는다.

### 4.5 `데이터 상태`

기존 화면과 역할을 유지한다.

- 수집·적재·가용성 상태 진단
- 데이터 미확인 원인 확인
- 기존 정비 경로

보유 평가나 evidence 표를 이 화면에 복제하지 않는다.

### 4.6 수동 초안 생성 기능의 위치

현재 Holdings 화면의 `저장된 보유 종목으로 초안 만들기`는 보유 입력·평가·확인 근거 어느 역할에도 속하지 않는다.

- Holdings 계열 세 화면에서 제거한다.
- 기존 실행 계약은 삭제하지 않는다.
- `OCI 적용·알림 > 미리보기·수동 전달 점검`에 같은 기능이 이미 있으면 중복 생성하지 않는다.
- 기능이 아직 별도로 남아 있다면 기존 의미와 부수효과를 바꾸지 않고 해당 수동 점검 영역으로 이동한다.
- `판단 초안`, `승인 대기`로 임의 재명명하지 않는다. 현재 `push_kind` 계약에는 투자 판단 초안 식별값이 없다는 POC3-04 결정을 유지한다.

이동 과정에서 새로운 run 종류나 승인 계약이 필요하면 구현하지 않고 설계자에게 복귀한다.

## 5. 다시 조사하지 않는 확정 사실

PLAN_V2는 다음 사실을 다시 전수 조사하지 않는다.

1. `GET /holdings/market-evidence/latest`는 종목별 evidence 배열을 1회 반환해 N+1 없이 사용할 수 있다.
2. `return_5d_pct`, `return_20d_pct`, `excess_vs_kodex200_20d_pctp`가 존재한다.
3. 평가액·평가 비중·평가손익은 `GET /holdings/enriched`와 기존 집계 의미로 사용할 수 있다.
4. 급락 `falling_candidate`는 자동 조회 가능한 안정적 GET 계약이 없어 이번 Step에서 제외한다.
5. `topn_match`는 상승 후보 매칭이므로 이번 확인 근거에 사용하지 않는다.
6. 동일 ticker는 읽기 전용 화면에서 기존 `aggregateHoldingsByTicker`와 같은 의미로 한 줄로 통합한다.
7. 입력·수정 화면은 기존 저장 행과 계좌 구분을 유지한다.
8. 기존 좌측 메뉴에는 `보유·자료 관리` 그룹과 `holdings`, `data_status` key가 존재한다.
9. POC3-04에서 투자 판단 초안을 식별할 계약이 없다고 확정했다.

PLAN_V2에서는 지정 화면·직접 호출 경로와 현재 미커밋 변경만 확인한다.
실제 코드가 위 사실과 충돌할 때만 충돌 지점에 한정해 추가 조사한다.

| KODEX200 대비 20일 | `short_term_momentum.excess_vs_kodex200_20d_pctp` | 표시·로컬 정렬 |
| 상태 | 기존 status·missing 값 | 자료 확인 필요 판정 |
| 상세 참고 | 기존 차트·NAV·구성종목·중복률 | 선택 종목에서만 |

### 6.2 `자료 확인 필요` 기준

다음 중 하나라도 해당하면 해당 ticker를 `자료 확인 필요`로 표시한다.

- `short_term_momentum.status`가 `partial` 또는 `unavailable`
- 5일·20일·KODEX200 대비 20일 값 중 하나가 null 또는 유효하지 않음
- `price_missing=true` 또는 `calc_missing=true`
- 평가액·평가 비중·평가손익 중 하나가 계산 불가
- 관련 조회가 `not_loaded` 또는 실패
- 동일 ticker 통합 과정에서 evidence 값이나 기준일이 서로 충돌함

`partial`이면 존재하는 수치는 그대로 보여주되 `자료 확인 필요` 상태를 유지한다.

NAV·구성종목·중복률의 unavailable은 선택 상세에서 따로 보여주며 목록 전체의 핵심 확인 필요 판정에는 넣지 않는다.

### 6.3 정렬과 Dashboard 요약

- 최근 흐름 낮은 순은 `status=ok`이고 5일 값이 유효한 ticker만 대상으로 한다.
- `return_5d_pct` 오름차순, 동률은 ticker 오름차순이다.
- Dashboard에는 중복 ticker 제거 후 최대 3건만 표시한다.
- unavailable 종목은 최근 흐름 순위에 넣지 않고 `자료 확인 필요`로 분리한다.
- 정렬 결과를 DB·cache·signal·rank로 저장하지 않는다.

### 6.4 기준일과 데이터 정직성

- Holdings와 Market Evidence의 서로 다른 기준일을 하나로 합치지 않는다.
- `not_loaded`, `partial`, `unavailable`을 구분한다.
- 확인하지 못한 값을 `0`, `정상`, `문제없음`으로 바꾸지 않는다.
- 신규 stale 날짜 threshold를 만들지 않는다.
- 기존 계약이 stale을 직접 제공할 때만 그대로 표시한다.

## 14. Closeout과 다음 순서

진행 순서:

```text
DESIGN_V2
→ 레드팀 검토
→ PASS 또는 수용 사항 반영 전체 통합본
→ PLAN_V2와 현재 개발물 보존 목록 확정
→ A 메뉴·보존 계약 확인
→ B 하위 화면 분리·사용자 확인
→ C 화면 연결·사용자 확인
→ 검증자 검증
→ RESULT·STATE·통합지도 Closeout
→ 설계자 PASS / CLOSED 판정
```

최종 PASS 후 다음을 갱신한다.

- `docs/STATE_LATEST.md`: POC3-05 상태·revision·B/C 사용자 실화면 결과
- 통합 구현지도: Holdings Risk Evidence Lane의 실제 완료 범위
- `docs/backlog/BACKLOG.md`: §13 중 canonical backlog에 없는 항목만 정합화
- RESULT: 보존·이동한 개발물, 메뉴 key, B/C 사용자 확인, 검증 결과

레드팀 PASS 전에는 PLAN_V2를 구현 확정본으로 취급하거나 추가 코딩을 재개하지 않는다.
