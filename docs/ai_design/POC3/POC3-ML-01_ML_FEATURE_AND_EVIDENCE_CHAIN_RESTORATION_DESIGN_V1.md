## 1. 현재 단계

지금은 구현 단계가 아니라 **개발플랜 작성 단계**다.

코드·DB·상태 파일·문서를 변경하거나 ML job을 실행하지 말고, 기존 코드와 데이터 계약을 확인하여 구현 가능한 개발플랜을 제출한다.

**[확정 2026-08-24 · M-1]** `ai_design/` · `ai_plan/` · `ai_result/` 는 **정식 산출물이다.**
정식 DESIGN·PLAN·RESULT 외에 **별도 조사·중간보고 Markdown 문서를 추가하지 않는다.**

## 2. 목표

현재 하나로 묶여 있는 `DEF-ML-CHAIN`을 end-to-end로 해소한다.

**[확정 2026-08-24 · M-2]** 실제 구조는 **두 개의 독립 체인**이다. 체인 A 가 체인 B 의
입력인 것처럼 표현하지 않는다. **두 체인 모두 이번 Step 완료 범위다.**

```text
체인 A  가격·벤치마크·NAV → feature 테이블 → sanity · baseline · readiness
체인 B  가격 → relative-upside 모델 → score snapshot → API → UI
```

단순히 feature 테이블만 채우고 끝내지 않는다. 사용자가 현재 화면에서 다음 세 가지를 실제 값으로 확인할 수 있는 상태가 최종 목표다.

* 참고점수
* 참고사유
* 고점 대비(`drawdown_20d`)

## 4. 확정 범위

개발플랜에는 다음 전체 연결을 포함한다.

1. 기존 feature 생성 코드·함수·CLI·job 경로 확인
2. feature 테이블이 0행인 직접 원인 확인
3. 기존 가격 데이터로 과거 feature 생성
4. 이후 일별 증분 생성 경로 복구
5. 기존 score·reasons·drawdown evidence 생성
6. 기존 API payload 전달 확인
7. 현재 UI 소비 경로와 정렬 동작 확인
8. 실패 상태와 sanity 결과가 정상화되는 조건 확인

조사만 하고 종료하는 계획은 허용하지 않는다. 기존 구현이 불완전하면 필요한 최소 구현까지 계획에 포함한다.

## 5. 변경 금지

다음은 이번 Step에서 하지 않는다.

* 신규 외부 데이터 조회 또는 수집
* 신규 API endpoint
* 신규 DB 테이블
* 기존 가격 원천 데이터 수정
* 신규 ML 모델 도입
* RF·XGB·LGBM·Optuna 튜닝
* 새로운 점수 공식 또는 임계값 발명
* 매수·매도·현금 판단 자동화
* UI 재설계
* FDR timeout 결함 수정
* BACKLOG 재조사
* PC package를 정식 PUSH 경로로 복귀
* 관련 없는 운영 코드 정리

기존 점수·feature 정의가 없다면 임의로 만들지 말고, 없는 계약과 영향 범위를 개발플랜에 정확히 표시한다.

## 6. 데이터 생성 원칙

개발플랜에서 다음을 구체화한다.

* feature별 입력 컬럼과 lookback
* 생성 가능한 최초 기준일
* 대상 ETF 선정 조건
* 과거 backfill 범위
* 일별 증분 갱신 방식
* `(ticker, 기준일)` 등의 유일성 계약
* 재실행 시 중복되지 않는 멱등성
* 일부 종목 실패 시 전체 처리 계약
* 결측값과 계산 불가 값 처리
* 원천 가격 최신일과 feature 최신일의 관계
* 예상 처리량과 배치 단위

단순 표본 데이터만 채우는 계획은 허용하지 않는다. 현재 운영과 후속 ML 검증에 사용할 수 있는 범위까지 생성해야 한다.

## 7. 실행 환경 경계

개발플랜에서 다음을 분리해 제시한다.

* 일회성 과거 backfill 실행 환경
* 운영 일별 증분 생성 환경
* PC가 필요한 경우 그 이유와 하드웨어 제약
* OCI에서 계속 수행해야 하는 운영 역할

PC는 ML 계산이나 backfill에 필요할 경우 사용할 수 있지만 PUSH 발송 주체로 해석하지 않는다. OCI의 기존 운영 경계를 변경하지 않는다.

## 8. 완료 조건

다음 조건을 모두 충족할 수 있는 계획이어야 한다.

1. `etf_ml_feature_daily`가 정상 데이터로 채워진다.
2. **[확정 · M-4]** `market_risk_feature_daily` **도 기존 계약에 따라 함께 생성된다**("필요한 경우" 문구 제거).
3. 과거 데이터와 최신 기준일이 계약에 맞게 연결된다.
4. 동일 작업을 재실행해도 중복 또는 값 변형이 발생하지 않는다.
5. 기존 score·reasons·drawdown evidence가 생성된다.
6. **[확정 · M-5]** 기존 `failed` 상태 파일을 **직접 수정·삭제하지 않는다.**
   **정상 실행이 성공한 결과로 기존 상태가 자연스럽게 갱신되는 것**을 완료조건으로 한다.
7. 기존 API에서 실제 값이 전달된다.
8. 현재 UI에서 참고점수·사유·고점 대비가 표시된다.
9. 고점 대비 정렬이 실제 값으로 동작한다.
10. 계산 불가 종목은 `0`으로 위장하지 않는다.
11. 기존 가격 데이터와 운영 PUSH 경계가 변경되지 않는다.

## 9. 개발플랜 제출 형식

다음 순서로 간결하게 제출한다.

1. **현재 코드 경로**

   * 파일·함수·job·CLI·DB 테이블·artifact 연결

2. **0행 및 evidence 부재 원인**

   * 추측과 확인된 사실을 구분

3. **구현 계획**

   * 변경 파일
   * 함수별 변경 내용
   * DB write 범위
   * backfill과 증분 처리 방식

4. **실행 계획**

   * 실행 환경
   * 실행 순서
   * 예상 데이터 범위
   * 실패 시 재개 방법

5. **검증 계획**

   * 단위·통합 테스트
   * 행 수·유일성·최신일·멱등성 검증
   * API payload 검증
   * UI 확인 항목

6. **범위 밖 항목**

   * 이번 구현에 포함하지 않는 사항

7. **설계자 판단이 필요한 사항**

   * 기존 계약만으로 결정할 수 없는 내용만 작성

## 10. 반환 규칙

* 코드와 데이터 계약을 실제로 확인한 근거를 제시한다.
* “추가 조사가 필요하다”만으로 반환하지 않는다.
* 구현 가능한 부분과 정말 결정이 필요한 부분을 분리한다.
* 일부 계약이 없더라도 feature 생성 등 확정 가능한 작업은 계획에서 제외하지 않는다.
* 코드·DB·문서 변경 및 커밋 없이 개발플랜만 반환한다.

## 11. 구현 결정 확정 (2026-08-24)

### D-1. backfill 범위 — **전체 가용 기간**

* 각 ETF 의 **실제 상장 이후**
* feature lookback 을 충족하는 **최초일 이후**
* **원천 가격 최신일까지**
* **안전한 기간 단위로 분할 실행**

### D-2. feature universe — **`etf_master` 등록 + 가격 존재 ETF 전체 = 1,171**

> **[최종 확정 2026-08-24]** **1,174 는 ETF 수가 아니라 `etf_daily_price` 의 전체 ticker 수**였다.
> 차이 3종목(`000660` SK하이닉스 · `005930` 삼성전자 · `006400` 삼성SDI)은 **개별주**이므로
> ETF feature universe 에 포함하지 않는다.

| 구분 | 값 |
|---|---|
| **ETF feature universe** | **1,171** (`etf_master` 등록 + 가격 존재) |
| 가격 테이블 전체 ticker | 1,174 (= ETF 1,171 + 보유 개별주 3) |

**개별주 3종목 취급**

| 대상 | 처리 |
|---|---|
| ETF feature · relative-upside score | **제외** |
| 보유자산 · holdings evidence | **유지** |
| `market_risk` universe breadth | **제외** |
| 가격 데이터 삭제 | **금지** |

세 개별주가 `2026-08-12` 이후 갱신되지 않은 사실은 **ML Step 을 막지 않는다.**
**결과서의 범위 밖 관찰사항으로만 남기고 별도 기능으로 확대하지 않는다.**

**소비 단계의 필터와 feature 생성 universe 를 혼동하지 않는다.**

### D-3. 일별 증분 — **수동 실행**

* 자동 스케줄러 추가 **금지**
* OCI 역할 변경 **금지**
* PC 는 **ML 계산 주체일 뿐 PUSH 발송 주체가 아님**

### D-4. `B-2` **포함** — 순서 + **조건** 동시 수정

> **[최종 확정 2026-08-24]** 개발자 의견 **(나) 수용**. 가드 조건도 함께 바꾼다.

```text
기존:  etf_upserted <= 0 and market_upserted <= 0
변경:  etf_upserted <= 0 or  market_upserted <= 0
```

**이유**: ETF feature 와 market risk 는 evidence-refresh job 의 **필수 산출물**이며,
둘 중 하나라도 없으면 sanity·baseline 이 정상 완료될 수 없다. feature 단계에서 성공으로
넘기면 안 된다.

`market_risk_feature_status="empty"` 가 존재한다고 해서 job 성공을 허용한다는 뜻이 아니다.
그 상태는 **CLI 단독 실행 · 과거/부분 적재 DB · readiness 조회 · 실패 원인 표시** 의
진단 표현으로 계속 유효하다.
→ **상태 모델은 `empty` 를 표현할 수 있지만, evidence-refresh job 의 성공 계약은 더 엄격하다.**

**최종 처리 순서**

```text
feature 생성 · DB upsert
→ ETF 또는 market 중 하나라도 0건이면 실패
→ snapshot 미생성
→ 둘 다 양수일 때만 snapshot 생성
```

**부분 upsert 가 이미 DB 에 반영됐더라도 별도 rollback 을 추가하지 않는다** —
파생 테이블이고 멱등 upsert 이므로 실패 구간 재실행으로 복구한다.

**테스트 4종**

| ETF | market | 기대 |
|---|---|---|
| 0 | 양수 | 실패 · snapshot 없음 |
| 양수 | 0 | 실패 · snapshot 없음 |
| 0 | 0 | 실패 · snapshot 없음 |
| 양수 | 양수 | 성공 · snapshot 생성 |

**기존 상태 파일 원자적 교체 경쟁 조건 수정으로 범위를 확장하지 않는다.**

### B-1 처리 원칙

`_run_sanity`·`_run_baseline` 이 기록하는 **모든 상태 경로를 먼저 열거**한다.

* 테스트 격리가 실제로 빠졌으면 → B-1 수정 + 회귀 테스트 추가
* **이미 모두 격리됐다면 코드 변경하지 않고 근거만 PLAN 에 기록**

**"오염 정황" 만으로 수정 확정하지 않는다.**

## 12. live DB 계약 (필수)

0행 원인 가설이 *"live DB 에서 실행된 적 없음"* 이므로 PLAN 에 다음을 명시한다.

* 실행 대상 **live SQLite 절대경로**
* 해당 경로가 **정본임을 확인하는 방법**
* 실행 전 **가격 테이블 행 수와 최신일**
* 모든 CLI 에서 **명시적으로 사용하는 `--db` 인자**
* **default DB 경로에 의존하지 않는** 실행 명령
* 실행 후 **동일 DB 에서 확인할 feature 행 수와 최신일**

**실행 예시에서 `--db` 를 생략하지 않는다.**

**표현 하향**: *"코드 결함이 없다"* 는 다음으로 낮춘다.

> 읽기 전용 코드 확인에서는 현재 0행을 설명하는 코드 결함을 찾지 못했다.
> **실제 실행 검증 전까지 코드 정상은 확정하지 않는다.**

## 15. 실행 순서 확정

두 체인은 독립이므로 **사용자 화면 복구를 먼저** 수행한다.

```
1. live DB · artifact 경로 확인
2. 체인 B 후보 입력 계약 확인
3. 체인 B 실행
4. API 에서 score · reasons · drawdown 확인
5. 현재 화면 3종과 정렬 확인
6. 체인 A 전체 backfill
7. feature sanity · baseline 실행
8. evidence-refresh job 성공 확인
9. 전체 완료 검증
```

**체인 B 복구가 체인 A 전체 backfill 완료까지 불필요하게 대기하지 않게 한다.**

## 16. 검증 기준 보완

최신일 검증을 `feature max(asof) <= price max(date)` 로만 두지 않는다
— **이 조건은 오래된 feature 도 통과시킨다.**

* `market_risk_feature_daily.max(asof)` 는 **요청 종료일의 마지막 KODEX200 거래일과 일치**
* ETF feature 는 **가격과 lookback 을 충족한 대상별 예상 최신일과 일치**
* 최신일까지 생성되지 못한 ticker 는 **누락 사유가 집계**됨

**프론트 코드를 변경하지 않으면 `tsc`·`eslint`·`vitest` 전체 실행은 필수에서 제외한다.**

필수 검증은 다음으로 한다.

* 변경 코드 대상 테스트
* ML feature · sanity · score 관련 테스트
* **백엔드 전체 pytest 1회**
* DB 행 수 · 유일성 · 멱등성 · 최신일
* API payload
* 사용자 UI 확인
