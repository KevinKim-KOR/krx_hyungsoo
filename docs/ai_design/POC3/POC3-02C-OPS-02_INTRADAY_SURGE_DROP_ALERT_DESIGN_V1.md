## 1. 목표

기존 `holdings_risk_alert` 7회 평가를 확장한다.

- 보유 ETF의 장중 **급락과 급등**
- 승인된 **27개 사업군 대표 ETF**의 급등락
- **신규 진입 검토** 후보
- **신규 진입 회피** 후보

**새 PUSH 종류나 cron 을 만들지 않는다.**

```text
기존 시각    09:30 · 10:30 · 11:30 · 12:30 · 13:30 · 14:30 · 15:20
기존 종류    holdings_risk_alert 유지
```

폐지된 `spike_or_falling_alert` 는 **부활시키지 않는다.**

---

## 2. 조회 대상

매 회차 다음 **합집합만** 조회한다.

```text
현재 보유종목  ∪  활성화된 27개 사업군 대표 ETF
```

- 같은 ticker 는 **한 번만** 조회
- 대표 조회 실패 시에만 **대체 ETF 1개** 조회
- 전체 1,168개 ETF 장중 조회 **금지**
- OCI 가 새로운 사업군이나 대표 ETF 를 선정하는 것도 **금지**

예상 Naver 호출량(정상 기준):

```text
기존            약 290건/일
대표 ETF 추가    27 × 7 = 189건
총              약 479건/일
```

## 3. 가격 기준 필수 게이트

장중 등락률은 **반드시** 다음으로 계산한다.

```text
DAY_RETURN = 현재 무조정 체결가 / 직전 거래일 무조정 종가 - 1
```

**`D-2` 종가를 직전 종가처럼 사용하면 안 된다.**

개발자는 PLAN 에서 먼저 다음을 **실측**한다.

1. 기존 보유 급락 경로가 실제로 사용하는 직전 종가 출처
2. Naver 원응답에 직전 종가가 이미 포함돼 있는지
3. 09:30 에 KRX 무조정 테이블이 정확한 `D-1` 을 가지고 있는지

우선순위:

1. 동일한 Naver 조회 응답에 직전 종가가 있다면 **기존 어댑터에서 함께 추출**
2. 없다면 KRX 공식 API 의 `D-1` 가용 시각 확인
3. 필요할 경우에만 **09:10 KRX 일별 종가 갱신 1회** 검토

**금지**

- `D-2` 로 대신 계산
- 조정 현재가와 무조정 종가 혼합
- 장중 전체 ETF KRX/Naver 반복 조회
- 출처가 다른 가격을 근거 없이 혼합

정확한 `D-1` 이 없으면 **사업군 경로만 건너뛰고** 기존 보유 위험 경로는 유지한다.

## 4. 초기 판정 규칙

수치는 **코드에 고정하지 않고** `INTRADAY_ALERT_CONFIG` 의 승인 PARAM 으로 둔다.

### 4-1. 보유종목

- 기존 급락 임계와 `worst_state` 계약은 **그대로 유지**
- 급등은 기존 급락 단계의 **절댓값을 양수 방향으로 대칭 적용**
- 기존 급락 임계가 단일 값이면 급등도 단일 값
- 기존 급락이 주의/심각 2단계면 급등도 동일한 2단계

> 개발자 PLAN 에는 **현재 운영 중인 실제 급락 임계값을 코드에서 측정해** 명시해야
> 한다. 임의로 새 하락 기준을 만들지 않는다.

### 4-2. 사업군 대표 ETF

| 상태 | 조건 |
|---|---|
| 진입 검토 | 당일 `+1.5% 이상, +4.0% 미만` + 5일 수익률 양수 + 20일 수익률 양수 + 27개 중 상승률 **상위 20%** |
| 진입 회피－급락 | 당일 `-1.5% 이하` + 27개 중 하락률 **하위 20%** |
| 진입 회피－추격주의 | 당일 `+4.0% 이상` |
| 해당 없음 | 위 조건에 들지 않음 |

이 값은 매수·매도 **예측값이 아니라 초기 운영용 단순 규칙**이다. 이후 PC
백테스트·ML 로 PARAM 을 교체할 수 있어야 한다.

현재 **보유 중인 ETF 가 사업군 대표에도 포함되면** 신규 진입 후보에서 제외하고
보유종목 구역에만 표시한다.

## 5. 중복 억제와 cooldown

지속 중인 같은 신호는 반복 발송하지 않는다.

**새 발송 조건**

- 새 ticker 가 임계에 진입
- 상태가 달라짐
- 위험 또는 급등 단계가 심화
- 임계 밖으로 회복된 뒤 다시 진입하고 **120분**이 지남

**발송하지 않는 조건**

- 같은 ticker 의 같은 상태가 계속 유지
- 수치만 조금 달라지고 단계는 같음
- cooldown **120분** 이내 재진입

숫자는 **fingerprint 에서 제외**하고 본문과 이력에는 남긴다.


## 8. 억제 사실 표시

조건형 알림이 억제될 때마다 **별도 Telegram 을 보내지 않는다.** 대신 **15:40 보유
브리핑 끝**에 한 줄을 추가한다.

```text
장중 점검 7회 · 알림 2건 · 중복 억제 3건 · 신호 없음 2건
```

- 15:20 최종 평가까지 포함
- 조회 실패는 별도 `조회 실패 N회` 로 표시
- 집계 불가 시 성공처럼 `0` 으로 표시하지 않고 **`확인 불가`**
- 이 한 줄 때문에 **별도 메시지를 만들지 않음**

## 9. 실패 격리

- 신규 사업군 경로 실패가 **기존 보유 급락 경로를 막으면 안 됨**
- 대표 ETF 실패 시 **대체 ETF 1개만** 시도
- 대표·대체 모두 실패하면 **해당 사업군만 제외**
- config 누락·비활성·손상이면 **기존 보유 급락만 정상 운영**
- 일부 ticker 실패가 전체 메시지를 막지 않음
- 운영 Gate 를 통과한 회차의 관측·집계는 매 회차 기록하고, 발송 진척은
  전체 전송 성공 시에만 전진한다
- 부분 전송이면 성공한 부분과 실패한 부분을 구분
- 실제 외부 호출과 Telegram 은 테스트에서 **차단**

### 13-1. Q1 — 보유종목 급등 단계 = **(a) 3단계 대칭 확정**

```text
U5_7      = +5% 이상,  +7% 미만
U7_10     = +7% 이상, +10% 미만
U10_PLUS  = +10% 이상
```

기존 급락 3단계는 **그대로 유지**한다.

```text
D5_7      = -7% 초과,  -5% 이하
D7_10     = -10% 초과, -7% 이하
D10_PLUS  = -10% 이하
```

급등 단계도 **심각도 1·2·3** 으로 취급한다. 보유종목 급등과 사업군의
「신규 진입 검토」는 **서로 다른 구역이며 합치지 않는다.**

### 13-2. Q2 — 당일 등락률 = **(a) 보유·사업군 모두 Naver `fluctuationsRatio`**

현재의 "무조정 현재가 ÷ 조정 종가" 혼합은 **보존할 계약이 아니라 바로잡아야 할
가격 기준 결함**이다. 임계값·상태·심각도·`worst_state`·중복 억제 계약은 그대로
두고 `DAY_RETURN` 의 **출처만** 정확한 무조정 D-1 기준으로 교체한다.

**필수 계약**

```text
- fluctuationsRatio 값을 직접 사용
- compareToPreviousClosePrice 로 부호를 복원하지 않음
- 현재가로 등락률을 역산하지 않음
- 조정계열 etf_daily_price 로 fallback 하지 않음
- 필드 누락·비수치·비정상·가격시각 부적합이면 해당 ticker 만 판정 제외
- 한 ticker 의 실패가 다른 보유종목을 막지 않음
- 사업군 경로 실패가 보유 급등락 경로를 막지 않음
- 기존 가격 최신성 검사와 거래일 Gate 유지
- 실패 건수는 15:40 점검 요약에 반영
```

기존 급락 경로의 **계산 결과가 바뀌는 사례**는 최근 데이터 재생에서 **전후 목록을
제출**하고 가격 기준 정정으로 설명되는지 확인한다.

### 13-3. Q3 — KS-5 = **회차당 1건 · 일일 조건형 최대 4건 승인**

`KILL_SWITCHES` KS-5 원문은 "시간당 1건 초과 **(급변 상황 제외)**" 다. 이번
조건형 급등락 알림은 **그 예외에 속한다.** 따라서 별도 rolling 60분 제한을 넣지
않는다. 14:30 과 15:20 은 50분 간격이지만 **서로 독립적인 실제 급변 조건이면 각각
발송**할 수 있다.

```text
조건형 = 회차당 최대 1건 · 하루 최대 4건
고정형 = 시장 브리핑 1건 + 보유 브리핑 3건
하루 전체 최대 = 8건
```

12:30 고정 보유 브리핑과 조건형 급등락 알림이 모두 성립하면 2건이 올 수 있다.
**정기 요약과 사건 알림은 서로 억제하지 않는다.**

### 13-4. 호출량 계산 정정 (PLAN §1-5 오류)

PLAN §1-5 는 **위험 알림 조회량과 하루 전체 조회량을 섞어 비교**했다.

| 구분 | 현재 | 구현 후 정상 경로 |
|---|---:|---:|
| 보유 브리핑 3회 | 29×3 = 87 | 87 |
| 조건형 7틱 | 29×7 = 203 | 53×7 = 371 |
| **하루 합계** | **290** | **458** |
| 증가량 | | **+168건 · 약 +58%** |

설계 추정 479건 대비 **108건 감소가 아니라 21건 감소**다.

대체 ETF 는 primary 의 **ticker 단위 실패 때만 한 번** 조회하며 **재귀 대체는
금지**한다. 제공자 전체 장애로 판단되면 대체 조회를 **연쇄 실행하지 않는다.**
RESULT 에는 **정상 458건과 fallback 포함 이론상 상한을 구분**해 보고한다.

```text

- 신규 cron · 신규 push kind 생성 금지
- 구형 spike_or_falling_alert 부활 금지
- 전체 ETF 장중 조회 금지

```

### 13-6. 필수 테스트

### 14-2. 러너 배선은 **검증 전에 반드시** 완료

사용자 목업 확인이 검증자 뒤라는 것은 **배선을 나중에 하라는 뜻이 아니다.**
검증자는 실제 운영 진입점에서 다음을 확인해야 한다.

```text
cron → runner run() → holdings_risk_alert → assemble_holdings_risk_push
     → 보유 급등락 + 사업군 판정 → 메시지 조립 → 전송 결과 → 상태·집계 저장
```

연결할 것:

- `intraday_alert_flow` 를 실제 `holdings_risk_alert` 실행 경로에 연결
- 전체 전송 성공 시 **실제 본문 포함 신호**의 `last_sent_at` 과 `sent_today`
  만 전진한다. 실패·부분 전송·상한 제외 신호는 발송 진척을 전진시키지 않는다
- 신호 없음·중복 억제·조회 실패를 회차 집계에 기록
- 15:40 보유 브리핑이 **실제 7틱 집계**를 읽어 요약
- runner 파일은 **648줄 그대로**

배선에 runner 수정이 필요하면 **임의로 수정하지 말고 중단·보고**한다.

### 14-3. `enabled=false` 의미를 **실제 호출까지** 보장

```text
사업군 대표 조회     = 0건
대체 ETF 조회        = 0건
사업군 판정·본문      = 없음
신규 상태 파일 변경   = 없음
기존 보유 급등락 경로  = 정상
```

**`enabled=false` 인데 본문만 숨기고 대표 ETF 27종목을 조회하면 비활성화가
아니다.** 합집합 53종목 조회는 `enabled=true` 일 때만 허용한다.

비활성 상태의 **기존 본문 형식도 그대로**여야 한다. 신규 구역 형식은 활성
정책을 주입한 테스트에서 검증하면 된다.

### 14-4. 상대순위 최소 커버리지 Gate 추가

"조회에 성공한 사업군 안에서 상위 20%" 만 적용하면 27개 중 3개만 조회돼도 그중
하나가 상위 20% 후보가 된다. **실패 격리가 아니라 왜곡이다.**

```text
sector_min_coverage_pct = 80
유효 대표 수 / 활성 사업군 수 >= 80% 일 때만 상대순위 판정
미달하면 사업군 구역 전체 생략
보유 급등락 경로는 계속 실행
```

코드 상수가 아니라 `INTRADAY_ALERT_POLICY` 에 둔다. 27개 기준 **최소 22개**.

### 14-5. fallback 장애 폭증 방지

```text
ticker 한 건의 응답 누락·오염     → 해당 사업군 대체 ETF 1회 허용
Naver transport/provider 장애    → 대체 ETF 연쇄 조회 **금지**
재귀 대체                        → 금지
```

provider 장애인데 primary 27개 뒤에 fallback 22개까지 다시 호출하면 안 된다.
**이를 구분하는 테스트**를 추가한다.

### 14-6. 실제 진입점 flow-through 테스트 8종

모듈 직접 호출 테스트만으로 종료하지 않는다. 외부 호출을 대역한 **실제 `run()`
경로**에서 확인한다.

```text
1 활성 정책 + 신호 존재      → 통합 본문 1건
2 비활성 정책                → 대표 조회 0건 · 기존 경로 유지
3 설정 누락·손상             → 기존 경로 유지
4 사업군 예외                → 보유 급등락 본문 유지
5 전송 성공                  → 관측 갱신 · 집계 `알림` · 발송 진척 증가·갱신
6 전송 실패·부분 전송         → 관측 갱신 · 집계 기록 · 발송 진척 미전진
7 7틱 기록                   → 15:40 요약에 실제 집계 반영
8 일일 4건 도달              → 이후 조건형 억제
```

실제 Telegram·Naver·OCI write 는 계속 **0건**.

```text

- 실제 7틱 집계 → 15:40 보유 브리핑 말미에 점검 요약 표시
```

#### 상태 저장 계약 (설계자 확정 · OPTION_A_FOR_BOTH)

> 상태 저장에 관해서는 **이 절이 정본**이다. §9 · §14-2 · §14-6 · §15-5 의
> 관련 문구는 이 절에 맞춰 정리했다(설계자 D2·D3 확정).

전송 결과와 관측 상태를 분리한다. "저장 여부" 가 아니라 **"전진 여부"** 로
계약을 표현한다.

1. 관측 상태
   - state
   - continuous
   - day_return_pct
   - sector_key

   활성 정책의 평가 회차마다 저장한다.
   전송 성공·실패·부분 전송·미발송 여부와 관계없이 갱신한다.
   이는 지속 신호, 회복, 재진입 및 다음 틱 재시도 판정에 사용한다.

2. 발송 진척 상태

   이 경로의 영속 발송 상태는 last_sent_at 과 sent_today 이다.
   Telegram 전체 전송 성공 시에만 전진시킨다.

   fingerprint(ticker#state)는 신호 객체에서 계산할 수 있는 파생 식별자일 뿐,
   sector_signal_state_latest.json 의 저장 필드가 아니다.

   holdings_risk_alert 의 runtime registry 중복키에도 fingerprint 를 사용하지
   않는다. 해당 중복키는 실행 시각 HH:MM 이다.

   따라서 실패·부분 전송 계약에서 fingerprint 저장 또는 미저장을 완료 기준으로
   사용하지 않는다. 기존 상태 파일에 fingerprint 필드를 추가하지 않는다.

3. 전송 실패 또는 partial_delivery=True

   활성 정책의 관측 회차에서는 상태 파일과 sent_today 키가 생성될 수 있다.
   sent_today 의 최초값은 0 이다.

   전송 실패 또는 partial_delivery=True 이면 발송 진척 상태를 전진시키지 않는다.

   - sent_today 는 증가시키지 않고 직전 값을 유지한다.
     최초 관측이라면 0 으로 존재할 수 있다.
   - last_sent_at 은 새로 생성하거나 실패·부분 전송 시각으로 갱신하지 않는다.
     이전 성공 기록이 있다면 그 값을 그대로 유지한다.
   - 관측 entries 는 회복·지속·재진입·다음 틱 재시도 판정을 위해 갱신한다.

4. 상태 파일이나 sent_today 키의 존재는 발송 성공의 증거가 아니다.
   발송 성공은 sent_today 증가와 해당 신호의 last_sent_at 갱신으로 판정한다.

5. 정책 비활성 상태에서는 관측하지 않으므로 신규 상태 파일을 만들지 않는다.

6. 관측 결과는 **3상태**다(설계자 D2 확정).

   ```text
   SIGNAL_PRESENT    조건 충족          → continuous=true
   SIGNAL_ABSENT     정상 평가 후 미충족 → continuous=false
   UNEVALUABLE       평가 불가          → 기존 관측 상태 유지
   ```

   회복은 동일 신호를 정상적으로 평가할 수 있었고 조건이 충족되지 않았을 때만
   기록한다.

   provider 장애, 커버리지 미달, 사업군 예외, 필수 데이터 누락 등으로 평가할 수
   없는 경우는 신호 없음이나 회복으로 취급하지 않는다. 해당 범위의 기존 state,
   continuous, day_return_pct, last_sent_at 을 그대로 유지한다.

   평가 불가 회차도 정상 스케줄의 운영 회차이면 15:40 집계에는 실패 1회로
   기록한다.

   적용 범위를 분리한다.

   ```text
   사업군 전체 장애·커버리지 미달   → 사업군 entries 전체 보존
   특정 대표 ETF 만 평가 불가       → 해당 사업군 entry 만 보존
   정상 평가된 다른 사업군          → 평소처럼 지속·회복 갱신
   사업군 실패와 무관한 보유 급등   → 그대로 갱신
   보유 ticker 자체가 평가 불가     → 해당 보유 entry 보존
   ```

   즉, **모르는 것을 회복으로 기록하지 않는다.**

7. 라이브 관측 상태와 회차 집계는 **운영 Gate 를 통과한 회차만** 쓴다
   (설계자 D3 확정).

   ```text
   mode = send
   AND 정책 enabled=true
   AND PUSH_AUTOSEND_HOLDINGS_RISK_ALERT_ENABLED=true
   AND duplicate 실행 아님
   ```

   | 실행 상황 | 관측 상태 | 15:40 집계 | 발송 진척 |
   |---|---|---|---|
   | dry-run | 미저장 | 미저장 | 미저장 |
   | flag-off | 미저장 | 미저장 | 미저장 |
   | duplicate | 미저장 | 미저장 | 미저장 |
   | 정책 누락·손상·비활성 | 미저장 | 미저장 | 미저장 |
   | 정상 운영·신호 없음 | 갱신 | `신호 없음` | 미전진 |
   | 정상 운영·중복 억제 | 갱신 | `중복 억제` | 미전진 |
   | 정상 운영·평가 실패 | 기존 관측 보존 | `조회 실패` | 미전진 |
   | 전체 전송 성공 | 갱신 | `알림` | 증가·갱신 |
   | 전송 실패·부분 전송 | 갱신 | 기존 실패 계약 적용 | 미전진 |

   dry-run 은 메시지를 계산하고 보여줄 수 있지만 `sector_signal_state_latest.json`
   과 `intraday_checkup_tally_latest.json` 을 바꾸면 안 된다. duplicate 회차도
   점검 횟수에 포함하지 않는다 — 같은 틱을 두 번 센 셈이 되기 때문이다.

억제 판정에 쓰는 정보는 ticker · state · continuous · last_sent_at · sent_today
다. fingerprint 는 코드 내부 비교나 감사 설명에 쓸 수 있으나 영속 상태 계약에는
포함하지 않는다.

원래는 수정 필요 시 먼저 보고해야 했으나, 이번 3줄은 **실제 실행 사슬을 닫는
최소 배선**이고 줄 수도 648 로 유지됐다. 되돌리거나 별도 Cleanup 을 열지 않는다.

검증자는 다음만 독립 확인하면 된다.

```text
- 실제 diff 가 보고한 3줄과 일치
- 사업군 단독 신호가 기존 skip_reason 에 묻히지 않음
- 비활성 상태에서 대표 조회와 신규 본문이 모두 0
- 관측·집계 저장 Gate 와 발송 진척 저장 시점을 각각 확인
```

보완 후 전체 회귀·black·flake8 을 다시 실행하고 **바로 검증자로** 넘긴다.
검증 전에는 commit·push·OCI 적용·실발송을 계속 금지한다.
