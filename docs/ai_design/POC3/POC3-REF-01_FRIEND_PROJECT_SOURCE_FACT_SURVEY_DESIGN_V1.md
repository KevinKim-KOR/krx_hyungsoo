# POC3-REF-01 친구 프로젝트 소스 사실 조사 설계서

## 1. 현재 문제

친구 프로젝트는 화면 캡처만으로 일부 구조와 기능을 파악했지만 다음 한계가 확인됐다.

* 제공되지 않은 화면과 메뉴를 놓칠 수 있다.
* 메뉴명만으로 실제 기능을 단정할 수 없다.
* 화면 구성, 갱신 방식, 데이터 흐름은 캡처만으로 확인할 수 없다.
* 자동 손절·비중 조절·알람 등이 어디까지 시스템 판정인지 알 수 없다.

그러나 친구 소스 전체를 목적 없이 전수 분석하면 현재 POC3 진행을 지연시키고, 개발자에게 설계 판단까지 떠넘기게 된다.

따라서 전체 메뉴의 존재와 연결 관계는 빠짐없이 확인하되, 상세 조사는 이후 예정된 작업에서 바로 참고할 세 영역으로 제한한다.

---

## 2. 이번 Step의 단일 목표

> 친구 프로젝트의 전체 메뉴와 실제 연결 기능을 소스에서 확인하고, 대문·메뉴 트리·위험 축에 필요한 구조적 사실을 조사하여 이후 설계 판단의 근거를 확보한다.

이번 Step은 사실 조사 단계다.

우리 프로젝트에 무엇을 채택할지 판정하거나, 대시보드에 기능을 추가하거나, 친구 기능을 구현하지 않는다.

---

## 3. 조사 전제

친구 소스는 다음 조건이 충족된 경우에만 조사한다.

* 친구가 소스 열람 범위를 알고 제공했거나 열람을 허용했다.
* 현재 프로젝트와 분리된 참조 소스로 준비돼 있다.
* 기준 브랜치·커밋 또는 전달 시점이 고정돼 있다.
* 친구 프로젝트와 현재 프로젝트를 병합하지 않는다.
* 코드 복사 가능 여부는 별도로 판단하며, 소스 열람 허용을 코드 복사 허용으로 간주하지 않는다.

소스 제공 또는 열람 범위가 불명확하면 조사를 시작하지 않는다.

---

## 4. 조사 범위

### 4.1 전체 메뉴 확인

소스에 정의된 모든 메뉴를 빠짐없이 확인한다.

각 메뉴에서 확인할 사실은 다음으로 제한한다.

* 메뉴명과 상위 그룹
* 실제 연결된 화면
* 현재 구현 여부
* 화면에서 수행하는 핵심 사용자 과업
* 직접 연결된 데이터 또는 기능
* 상세 조사가 필요한 영역인지 여부

메뉴가 존재하지만 연결 화면이나 기능을 확인할 수 없으면 추측으로 채우지 않고 `확인 불가` 또는 `미구현`으로 구분한다.

이 조사의 목적은 메뉴별 상세 설계가 아니라, 캡처에서 보이지 않았던 기능을 포함한 전체 기능 지도를 확보하는 것이다.

### 4.2 대문·대시보드 축 상세 조사

현재 대시보드 개선에 참고할 다음 사실을 확인한다.

* 홈 화면의 주요 정보 구성
* 한 화면에 정보를 배치하는 방식
* 실제 사용 중인 차트·시각화 요소
* 자동 갱신과 수동 갱신 방식
* 캐싱 또는 재사용 구조
* 화면에서 데이터가 표시되기까지의 흐름

패키지 설치 여부만으로 사용 기술을 판단하지 않고, 실제 화면에서 사용되는 구조만 조사한다.

### 4.3 메뉴 트리·라우팅 축 상세 조사

메뉴 재편에 참고할 다음 사실을 확인한다.

* 메뉴 그룹과 실제 화면의 연결 구조
* 독립 메뉴와 화면 내부 상세 기능을 나눈 기준
* 조건부·숨김·미구현 메뉴
* 동일 기능으로 연결되는 중복 진입점
* 캡처로 파악한 메뉴 구조와 실제 소스의 차이

이번 Step에서 우리 프로젝트의 메뉴 구조를 설계하거나 변경하지 않는다.

### 4.4 위험·알람 축 상세 조사

향후 위험 신호 설계에 참고할 다음 사실을 확인한다.

* 위험·손절·알람 기능의 입력 데이터
* 판정 로직과 임계값의 존재 위치
* 판정 결과의 저장 여부
* 화면 표시와 알림 전달 흐름
* 사용자 확인 또는 개입 지점
* 자동 주문·자동 손절·비중 조절과의 연결 여부

위험 기능은 구현 방식을 조사할 수 있지만, 친구의 판정 산식이나 행동 체계를 우리 프로젝트의 정책으로 채택하지 않는다.

향후 적용 여부를 판단할 때는 다음 경계를 별도로 검토한다.

```text
자동 판정·자동 행동
→ 계산 가능한 evidence와 주의 신호
→ 사용자 알림
→ 사용자 최종 판단
```

---

## 5. 유지할 것

* 현재 POC3 진행 순서
* 형수님이 수정한 현재 대시보드
* 기존 대시보드 하단의 `개발 중 판단 기능` 영역
* 인간 최종 판단 원칙
* 친구 화면과 소스는 참고 자료라는 지위
* 확인된 사실과 추론을 구분하는 원칙
* 전체 메뉴는 놓치지 않되 상세 조사는 필요한 영역으로 제한하는 원칙

---

## 6. 조사 산출물

이번 Step의 산출물은 하나의 소스 조사 결과 문서다.

문서에는 다음만 포함한다.

1. 참조 소스의 기준 버전과 열람 범위
2. 전체 메뉴–화면–확인 기능 대응표
3. 대문·대시보드 축 조사 결과
4. 메뉴 트리·라우팅 축 조사 결과
5. 위험·알람 축 조사 결과
6. 확인 불가·추가 조사가 필요한 항목
7. 조사 범위 밖에서 발견됐지만 현재 추적하지 않은 항목

조사 결과에는 다음을 섞지 않는다.

* 우리 프로젝트 채택 여부
* 적용 화면
* 개발 우선순위
* 예정 Step
* 대시보드 등록 여부
* 구현 지시

이 판단들은 조사 결과를 받은 뒤 별도 설계 단계에서 수행한다.

---

## 7. 중단 조건

다음 상황에서는 임의로 조사 범위를 넓히지 않고 중단 사유를 보고한다.

* 메뉴와 화면의 연결 관계를 지정 범위에서 찾을 수 없음
* 다른 저장소나 외부 서비스가 없으면 기능 확인이 불가능함
* 전체 실행환경 구축이 필요함
* 친구의 전략·계정·개인정보 등 허용 범위를 벗어난 자료가 필요함
* 조사 대상이 대문·메뉴 트리·위험 축을 넘어 대규모 기능 분석으로 확장됨
* 확인된 사실만으로 복수 해석이 가능해 설계 판단이 필요함

---

## 8. 하지 않는 것

* 친구 저장소 전체 파일 전수 분석
* 모든 메뉴의 내부 로직과 API 심층 추적
* 전체 실행환경 구축
* 친구 프로젝트 수정 또는 현재 프로젝트와 병합
* 코드 복사
* 친구 기능의 채택·변형·제외 판정
* 우리 프로젝트의 메뉴 재설계
* 기존 대시보드 하단 항목 추가
* 신규 DB·API·외부 데이터 계약 설계
* BUY·SELL·자동 손절·자동 주문·자동 리밸런싱 도입
* 조사 과정에서 발견한 기능의 즉시 구현

---

## 9. 완료 기준 AC

* **AC-1**: 참조 소스의 열람 허용 범위와 기준 버전이 명확하다.
* **AC-2**: 소스에서 확인 가능한 전체 메뉴가 누락 없이 목록화돼 있다.
* **AC-3**: 각 메뉴의 연결 화면과 핵심 사용자 과업이 확인되거나 `확인 불가·미구현`으로 구분돼 있다.
* **AC-4**: 캡처 기반 메뉴 구조와 실제 소스 구조의 차이가 확인돼 있다.
* **AC-5**: 대문·대시보드의 정보 구성, 시각화, 갱신 및 데이터 흐름이 확인돼 있다.
* **AC-6**: 메뉴 그룹과 실제 라우팅 구조가 확인돼 있다.
* **AC-7**: 위험·알람 기능의 입력부터 표시·전달·사용자 개입까지의 흐름이 확인돼 있다.
* **AC-8**: 자동 주문·손절·비중 조절과 연결되는 기능이 별도로 식별돼 있다.
* **AC-9**: 확인된 사실과 추측이 섞이지 않는다.
* **AC-10**: 확인할 수 없는 사항과 추가 조사가 필요한 사항이 명시돼 있다.
* **AC-11**: 채택 판단, 대시보드 반영, 기능 구현이 수행되지 않았다.
* **AC-12**: 조사가 전체 소스 전수 분석으로 확장되지 않았다.

## 10. Step 종료 후 게이트

이번 Step의 조사 결과가 검증된 뒤에만 다음 작업을 별도 Step으로 시작한다.

다음 작업은 조사 결과를 근거로 다음을 판단하는 설계 단계다.

* 기존 기능으로 대응되는 항목
* 통합할 항목
* 독립 기능으로 채택할 항목
* 사용자 판단 구조로 변형할 항목
* 제외하거나 추가 조사할 항목

그 판단이 끝난 뒤에야 확정된 필수 기능을 기존 대시보드 하단 `개발 중 판단 기능`에 반영하는 후속 UI Step을 설계한다.

## 11. 결과 문서 보완 지시 (설계자 추가 · 검증자 대조용)

> 조사 재수행·설계 확장 없이 **기존 결과 문서(`docs/ai_result/POC3/POC3-REF-01_..._RESULT_V1.md`)만 보완.** 아래는 검증에서 확인된 누락 보완 지시다.

### 11.1 1차 보완 지시 (반영 완료 4 / 미완 3)
1. 19개 메뉴 대응표에 과업·직접 API·구현구분 채움. 2. 대시보드 갱신 방식(버튼·폴링·서버캐시·batch/cron). 3. 숨김/조건부/미구현/중복 진입점(없으면 "확인되지 않음"). 4. 위험·알람 2흐름 분리+임계값 위치·저장. 5. 자동주문 "발견 못 함" 보수적. 6. 스냅샷을 "파일 목록 지문"+내용 트리 해시. 7. 채택·비교 판단 삭제.
- **1차 판정: REWORK_REQUIRED.** 4·5·6·7 반영. **1·2·3(실질 완성도) 미완** → 2차 보완.

### 11.2 2차 보완 지시 (현재 유효 · POC3-REF-01 PARTIAL 유지)
기존 결과 문서만 보완. 새 설계·기능·코드 변경 금지.
1. **핵심 과업이 `[추정]`/`확인되지 않음` 인 15개 메뉴**의 `page.tsx`+직접 연결 컴포넌트·호출 API만 **한정 확인** → 실제 사용자 과업 · 직접 호출 API·서비스 · 화면 구현/placeholder/빈 화면 여부. 기능 없으면 `지정 경로에서 발견하지 못함`.
2. **`web/app/api/dashboard/route.ts` + 직접 데이터 로더만** 확인 → 서버 캐시 존재 여부 · 데이터 원천 · batch/cron 이 대시보드 데이터 생성하는지 · 화면 조회 시 실시간 계산인지 스냅샷 조회인지.
3. **위험·알람 직접 경로만** 확인 → 레짐 임계 기준 실제 코드 위치 · 알람 수치 조건 존재 여부 · cron 정확한 실행 주기 · 판정/알림 결과 저장 여부·위치 · 손절 관련 조건/호출 존재 여부.
4. **`weight_allocator.py` 직접 호출자만** 확인 → 비중 산식이 (계산만 / 화면·알림 표시 / 파일·DB 저장 / 주문 실행 연결) 중 무엇인지.
5. 확인 안 된 기능은 **부재로 단정하지 말되**, 열람 가능한 **직접 경로를 조사하지 않고 `심층 미조사` 로 남기지 않는다**.

**흐름**: 개발자 2차 보완 → 보완 결과 확인 → 검증자 재검증. 검증자 PASS 전까지 채택·후속 Step 없음.
