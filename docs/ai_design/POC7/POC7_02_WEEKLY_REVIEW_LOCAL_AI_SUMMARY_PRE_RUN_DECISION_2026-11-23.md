# POC7-02 · 로컬 AI 주간 ETF 검토 한 장 요약 · 실행 전 설계 판정

2026-11-23 KST · 총괄 설계자 · 형수님과 개발자

**맥북 구현 r5 VERIFIED 수용 · Windows 실측 진행 승인 · AC1~AC4 최종 판정 대기**

검증자가 맥북에서 합성 묶음의 실행·회수·한 장 대조를 확인했다. F13은 미완본과 완료본을 어느 순서로 가져와도 서로 다른 두 실행으로 보존되고, 두 순서 모두 AC4가 ‘판정 불가’였다. 제출 시험 435건과 독립 재현 17건을 수용한다. Windows 호환성과 GPU 사용, 실제 요약과 읽기 시간은 이번 실측에서 확인한다. 근거는 개발 결과서 §18~§19, 설계 V1 §4, 11월 23일 PLAN 판정이다.

## 1. 최초 출력과 결과 전달

| 질문 | 판정 |
|---|---|
| Q-A · 본 시도 뒤 재실행 | **사례당 한 번.** `main_started.json`이 완성된 시점부터 한 번을 사용한 것으로 센다. 기술 실패·입력 미확인·전원 종료도 그 시도로 보관한다. PLAN §2-2의 ‘실행 실패를 고친 경우에만 다시 실행’은 본 호출 전에 멈춘 경우에 적용한다. |
| Q-B · 본 시도가 둘인 경우 | **둘 다 보관 · AC4 판정 불가.** 각 실행 ID로 센다. 시작 시각이나 회수 순서는 시도 선택에 사용하지 않는다. |
| Q-E · 한 장이 없을 때 | **사용 비교는 판정 불가.** 해시 검증을 통과한 최초 한 장으로 채점·읽기 비교를 한다. 원문을 회수할 수 있으면 AC2에서 확인 가능한 내용과 오류를 기록한다. 원문에서 다시 만든 한 장은 장애 분석 참고본으로 표시한다. |
| Q-F · Windows 전체 시작 표지 | **현재 폴더 안의 시작 표지와 회수 대조를 사용한다.** 본 사례 ZIP은 비어 있는 Windows 폴더 한 곳에 한 번 푼다. 본 호출 전 환경을 고친 경우 그 폴더에서 이어간다. 모든 결과 폴더의 회수 여부를 원본에서 확인한다. |
| Q-Q · 실행 ID만 손상된 미완본 | **다른 ID는 별도 시도로 센다.** 표지만으로 동일 실행임을 입증할 수 없으면 원본이 나중에 도착해도 두 기록과 ‘판정 불가’를 유지한다. 손상 정황은 결과서에 남긴다. |
| Q-S · 결과 폴더 이름 | **이번 한 건은 폴더 단위 전달로 해결한다.** 묶음 또는 압축을 푼 위치가 다르면 USB의 별도 상위 폴더 아래로 모든 결과 폴더를 원래 이름 그대로 복사한다. 같은 이름의 복사 확인 창이 뜨면 취소하고 새 상위 폴더를 사용한다. 원본에 있는 결과를 모두 회수하기 전에는 사용 이점을 판정하지 않는다. 같은 목적지로 여러 결과를 모으는 반복 사용이 생기면 실행 ID가 붙은 이름을 검토한다. |
| Q-D · 소스와 자료 전달 | **소스는 기존 git에 보관하고 이번 실측 전달은 USB 직접 왕복으로 확정한다.** 실제 복사문·기존 AI 답·입력 ZIP·결과는 로컬 연구 자료다. 공유 폴더 방식은 실제 반복 사용에서 전달 경로를 정할 때 검토한다. |

## 2. 본 호출 전후의 멈춤과 회수

| 질문 | 판정 |
|---|---|
| Q-C · 본 호출 뒤 버전·digest 재조회 | 본 호출 전과 직전의 버전·digest 대조를 필수로 둔다. 본 호출 뒤 재조회만 실패하면 미확인 사실을 기록한다. 값이 달라졌음을 확인하면 기술 실패로 처리하고 첫 출력은 보존한다. |
| Q-G · 호출 직전 멈춤 | 조회 자체의 실패와 Ollama 버전 변경은 환경 중단이다. 환경을 고친 뒤 같은 폴더에서 합성 점검부터 진행한다. 응답은 읽혔으나 고정 digest가 빠졌거나 다르면 모델 중단으로 처리한다. |
| Q-H · 메모리와 CPU 단독 | 메모리 부족과 합성의 CPU 단독은 설정 중단 근거로 수용한다. CPU 단독이면 GPU와 드라이버 상태도 확인한다. 설정을 고치는 경우 조정 대상은 문맥·출력 길이다. 장치를 관측하지 못한 경우는 환경 문제로 기록한다. 혼합 실행은 GPU 사용 근거와 혼합 상태를 남긴다. |
| Q-I · 본 호출의 출력 여유 | **실측 입력 토큰 + `num_predict` ≤ 요청 `num_ctx`** 조건을 수용한다. 본 실행 뒤에는 세기와 본 호출의 입력 토큰, 실제 할당 문맥, 종료 이유와 잘림 기록을 대조한다. |
| Q-K · 기록 미완의 보강 | 같은 실행 ID에서만 받는다. 미완본끼리는 공통 표지와 결과의 바이트가 같고 원문이 같거나 기존 바이트에서 이어질 때 더 담긴 사본을 사용한다. 앞서 보관한 바이트도 남긴다. 완전한 원본은 Q-P를 적용한다. |
| Q-L · 시계 차이 | 시각 역전은 메모한다. 실행 순서는 앞 실행 목록과 같은 작업 폴더 안의 순번으로 확인하고, 실행 소요시간에는 실행기의 단조 시계 값을 사용한다. |
| Q-M · 응답 뒤 중단·실행기 오류 | **기술 실패.** 첫 원문과 확인 가능한 한 장을 보관한다. 같은 첫 출력의 정체·내용을 대조할 수 있으면 AC2 채점은 계속한다. 검증된 한 장의 중요 오류는 ‘품질 미달’ 근거로 남긴다. 실행 또는 응답 완료가 빠진 경우 시간상 사용 이점은 판정 불가다. |
| Q-N · 마지막 기록 미확인 | 순서를 입증할 앞 실행 목록이 없거나 여러 작업 폴더로 갈려 마지막이 모호하면 새 묶음과 길이 변경을 멈추고 기존 기록을 보존한다. |
| Q-O · 새 묶음과 같은 폴더 재실행 | **본 시도 시작 전**, 앞의 모든 묶음을 회수하고 마지막으로 실제 실행한 기록이 설정·모델 중단으로 확인됐을 때 새 묶음을 허용한다. 설정 중단에서 문맥·출력 길이 조정을 허용한다. 모델 중단은 고정 모델을 복구하는 조치를 먼저 확인하고 설정을 이어받는다. 모델 자체 변경은 PLAN 판정 Q3의 별도 결정 대상이다. 본 호출 전 환경·설치·중단은 사유를 고쳐 같은 폴더에서 이어가고, 파일이 바뀐 경우 원본 묶음을 확인해 복구한다. |
| Q-P · 완전한 원본으로 회수 보강 | 새 폴더가 해시와 실행 내용 대조를 통과하고 기존 표지의 사례·묶음·실행 ID·결과 폴더가 모두 맞으면 같은 실행으로 받는다. 나머지 바이트 차이는 기록하고 앞 사본도 보존한다. |

## 3. 시간 측정

| 질문 | 판정 |
|---|---|
| Q-J · 시간 입력 범위 | **86,400초를 비교표 입력 상한으로 수용한다.** 직접 시간은 양수이며 전체 경과 이하다. 로컬 전체 경과는 실행기의 단조 시계 소요시간 이상이다. 실제 경과가 하루를 넘으면 실제값과 사유를 따로 기록하고 해당 비교값은 미측정으로 둔다. |
| Q-R · 개발자 반복 시간 | **보관된 `pack`·`merge` 시간의 합은 확인된 하한으로 사용한다.** 판정에는 개발자가 직접 잰 반복 작업 시간을 넣는다. 실제로 한 재포장·재회수·거부된 회수·파일 확인 등 사람이 쓴 시간을 포함한다. 같은 실행의 복사본을 여러 번 옮겼다면 실제 사람이 작업한 만큼 센다. 직접값이 없으면 하한과 출처를 기록하고, 하한만으로 총 사람 시간이 절감됐다고 판정하지 않는다. 평소 방식의 개발자 반복 시간은 0이다. |

형수님 직접 시간과 개발자 반복 시간은 각자 재고 총 사람 시간에 합산한다. 모델 대기는 전체 경과에 들어간다. 일회성 설치 시간은 따로 기록한다. 두 방식 모두 같은 시점에 보관한 자료에서 출발해 같은 세 답을 제출할 때 끝낸다.

## 4. 실측과 최종 판정

1. 형수님이 「주간 ETF 점검」에서 실제로 볼 후보 하나를 고른다. 같은 검토 건에 이미 있는 AI 답은 작성자와 함께 넣을 수 있다. 개발자가 같은 응답의 선택 정보와 복사문을 보관하고 본 출력 전에 필수 사실·자료 공백·세 질문의 채점 메모를 잠근다.
2. 필요한 Ollama 또는 지정 모델이 없을 때만 설치·수신 범위를 형수님께 확인한다. 시간 측정을 준비한 뒤 **r5에서 검증한 실행기**를 시작한다. 실행기는 Windows 환경과 지정 모델을 확인하고, 합성 점검과 본 호출 직전 관문을 통과한 경우 실제 요약을 호출한다.
3. 최초 출력·한 장과 GPU 사용 기록을 회수한다. 한 장을 열어 보는 로컬 방식(L)을 먼저, 같은 자료의 평소 방식(U)을 나중에 한 번씩 비교한다. 당시 근거와 최초 한 장의 내용 오류·누락, 직접 시간과 반복 작업 시간, 고친 사실·다시 열기·세 답·재사용 의사를 결과서에 남긴다.
4. AC1은 Windows에서 얻은 최초 출력·한 장의 대응 및 GPU 근거, AC2는 사전 채점 메모 대비 중요 오류 0건, AC3은 두 방식의 실제 읽기 기록으로 판정한다. AC4의 ‘사용 이점 관찰’에는 L의 세 답에 ‘틀림’ 0건과 각 답 L ≥ U, 형수님 직접 시간과 총 사람 시간 모두 감소, 사실 수정 비증가, 재사용 ‘예’가 필요하다. 중요 오류가 확인되면 ‘품질 미달’이다. 자료나 실측이 부족한 항목은 그 사유와 함께 ‘판정 불가’로 적는다. 결과의 적용 범위는 실제 비교한 한 사례다.

개발자는 이 판정서를 `docs/ai_design/POC7/`에 보관하고, 확정 PLAN과 결과서 §14-5·§16-4·§18-4에서 이 판정을 참조한다. `STATE_LATEST.md`와 `PROGRAM_TRUTH.md`의 현재 상태는 **r5 VERIFIED 수용 · 설계 검토 완료 · Windows 실측 예정**으로 기록한다. 실측 후 결과서를 설계자에게 돌려준다. POC6 종료 인계서는 예정한 단계 마감 시점의 문서 묶음에 함께 올린다.
