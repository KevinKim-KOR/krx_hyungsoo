# POC5-27 PLAN 판정 — PC에서 OCI 운영 기준 실제 활성화

작성: 2026-10-20 · 설계자 → 개발자 / 사용자
근거: 제출 PLAN V1 · 사용자 목업 '그대로' 확인 · 사용자 원격 쓰기 구현 승인('PLAN 권장 방식', 2026-10-20).

**판정: PASS. Q1~Q4 모두 (a)를 수용하고 아래 보완을 같은 구현에 반영한다. PLAN 재제출·목업 재확인·이미 받은 원격 쓰기 승인 재요청은 필요 없다.**

## 1. Q1 — PC 승인값의 DB 발행으로 한정

(a)를 채택한다. PC가 원격 DB 파일을 직접 열어 쓰는 방식이 아니라, PC에서 확정하고 사용자가 승인한 값을 OCI의 짧은 로컬 도구가 검증·기록·활성화하는 DB 발행이다. JSON은 요청 전달 자료이며 활성 정본은 DB 하나다. OCI의 독자적인 기준 계산·선정·튜닝·승격을 허용하지 않는다.

근거는 사용자 승인만이 아니다. 기반 의도의 'PC 승인 PARAM의 DB 기반 발행' 조항, 현재 JSON 전달이 활성 DB를 바꾸지 않는 사실, 기존 수동 도구가 전달값 대신 코드 기본값을 만드는 사실과 이번 직접 대조 결과가 있다. 운영 DB 쓰기가 발생한다는 점을 숨기지 않되 승인된 발행과 OCI 자율 정책 생성을 구분한다.

기존 금지 원문은 보존하고 PROJECT_ORIGIN_INTENT·ASSUMPTIONS·KILL_SWITCHES의 해당 경계에 아래 날짜 주석을 연결한다. 별도 기반 문서 개정 Step이나 승인 왕복은 만들지 않는다.

> 2026-10-20 POC5-27 한정 해석: 사용자가 PC에서 명시 승인한 현행 허용 PARAM 값을 OCI 로컬 도구가 그대로 검증·발행·활성 확인하는 경로를 허용한다. PC의 OCI DB 직접 접속·개방과 OCI의 자율 PARAM 계산·선정·생성/승격 금지는 유지한다. 근거는 POC5-27 PLAN §1~§5의 소스 대조 및 사용자 원격 쓰기 구현 승인이다. 이 허용은 새 정책 생성·ML·seed 변경·자동 발송으로 확대되지 않는다.

## 2. Q2 — 중복 발송 키 유지

(a)를 채택한다. 러너·원장·registry_key는 이번에 바꾸지 않는다. 값이 다른 PARAM으로 전환한 뒤 같은 날 같은 칸을 수동 재실행하면 기존 param_id 포함 키 때문에 중복 발송 가능성이 있다는 한계를 RESULT·복구/점검 절차에 남긴다.

적용 자체가 발송·러너 재실행을 하지 않는 경계를 시험한다. 검증을 위해 운영의 같은 칸을 다시 돌리지 않는다. 같은 유효값일 때는 OCI 새 버전·포인터 변경이 없어야 한다. 이 조건은 OCI 쪽이며 PC의 기존 PARAM 생성·이력까지 쓰기 0이라는 뜻은 아니다.

## 3. Q3 — 적용 요청에서 얻은 값으로 ① 갱신

(a)를 채택한다. 명시 적용 요청 안에서 얻은 실제 활성값·확인 시각을 응답과 ① '운영 기준 활성' 캐시에 함께 반영한다. 이는 기존 기동 1회 조회 원칙에 대한 **명시 적용 결과 반영**이며, 별도 새로고침·상시 폴링·다른 OCI 상태 재수집을 추가하지 않는다.

캐시는 해당 활성 행만 갱신한다. 적용 결과를 확인하지 못했다면 그 상태를 ①에도 반영하고, 기동 때의 일치 값을 방금 확인한 성공처럼 보이지 않게 한다. 실제로 읽지 않은 값·시각을 채우지 않는다. HTTP 200인 상태 행과 '값 확인 성공/일치'는 구분한다.

## 4. Q4 — 임시 업로드 방식, 복구는 즉시 가능하게

(a)를 채택한다. 검증된 도구를 명시 적용 때 임시 업로드·OCI venv 실행·정리하고, OCI에 이미 있는 저장 함수를 재사용한다. 적용을 위해 OCI pull을 선행할 필요는 없다.

다만 **복구를 다음 OCI pull 뒤에만 할 수 있다는 부분은 보완한다.** PLAN/RESULT에 'PC의 같은 검증 도구를 기존 SSH/SCP 경로로 임시 업로드 → --list → 사용자가 고른 --activate-version 실행 → 활성값 확인 → 임시 도구 정리' 절차를 실제 사용 가능한 명령으로 남긴다. OCI에 아직 없는 scripts 파일이 있다고 가정한 명령만 제공하지 않는다. 이후 저장소 pull로 도구가 배치되면 PLAN의 상주 명령도 사용할 수 있다. 새 복구 UI·상시 도구 관리 체계는 필요 없다.

복구 명령은 격리 DB에서 확인하며 시험을 위해 실제 운영 정책을 바꾸지 않는다. 웹 응답·화면의 ID 비노출은 유지하되, 운영자가 버전을 골라야 하는 복구 CLI의 버전 ID 출력은 허용한다.

## 5. 적용 경계 보완과 결과 의미

- 같은 호출 경로의 네 문제(확인 전 JSON 교체, verify=skipped 성공, 안팎 시간 제한 불일치, 서버 중복 실행 방어 부재)는 이번에 함께 고친다. JSON 확인 뒤 교체, 확인 누락의 실패 처리, 외곽 120초보다 짧은 전체 작업 예산, 현재 프로세스의 적용 잠금 하나를 수용한다. 다른 운영 체계의 전수 정비로 넓히지 않는다.
- 후보를 DB에서 다시 구성해 러너의 from_dict와 요청 유효값 비교를 통과시킨 뒤 전환한다. 빈 정책·누락값을 기본값으로 보충하지 않는다. 공유 validator 전역 변경 대신 이번 발행 경계에서 확인한다.
- 활성화 명령을 시작한 뒤 timeout·응답 단절·읽기 실패가 나면 기존 값 유지로 단정하지 않는다. 0·2·5초의 제한된 읽기 확인은 같은 요청의 예산 안에서만 허용하며, 자동 쓰기 재실행은 없다.
- 정상적으로 읽은 값이 요청과 다를 때 직전 버전으로 되돌리는 안은 수용한다. **되돌림 후 실제 이전 활성값까지 확인된 경우만** FAILED와 기존 값 유지로 보고한다. 되돌림 실패·결과 미확인은 unconfirmed다. 단순 통신 실패에 대한 자동 역전환은 금지한다.
- 현재 값 선택 UI는 없고 PC 코드 기본 14값으로 기준을 만드는 사실을 명시한다. 이번에는 그 생성 방식을 유지하고 사용자가 명시 승인한 확정값을 그대로 발행한다. 새 정책 편집 화면을 추가하거나 OCI에서 다른 기본값을 다시 만들지 않는다.
- 옛 전달 기록은 '미적용'이라고 단정하지 말고 **'이전 전달 기록 · 활성화 확인 없음'**으로 표시한다. 그 기록의 증거 수준과 현재 ①의 실제 값 일치 여부는 다르다. 현재 14/14 일치인데 과거 기록 때문에 실제 운영값이 불일치한다고 보이지 않게 한다. 같은 자리의 문구 정정이므로 목업을 다시 받지 않는다.

## 6. 구현·검증·종료

위 내용을 PLAN에 반영한 뒤 바로 구현한다. PLAN §6의 격리 DB·가짜 SSH·실제 도구 실행 계약·동일값 무변경·실패/미확인 구분·① 반영 및 필요한 기존 검사를 수행한다. 동작하는 복구 절차도 RESULT에 포함한다.

사용자 실화면·검증자 확인 후 RESULT를 제출한다. 구현 승인과 커밋·push 승인은 구분하며 이미 받은 동일 범위 승인은 존중한다. 배포 뒤 실제 적용 버튼 1회와 OCI 읽기 전용 대조를 통과하면 원 설계대로 재판정 없이 종료할 수 있다. 현재처럼 같은 값이면 '일치·변경 없음'과 새 OCI 버전 0이 정상이며, 다른 값의 전환은 격리 시험 근거와 구분한다. 새 발송·거래일 대기·별도 인계 문서는 없다.
