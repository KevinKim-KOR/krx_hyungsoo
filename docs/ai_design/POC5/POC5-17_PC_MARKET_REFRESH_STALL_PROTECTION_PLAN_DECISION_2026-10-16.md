# POC5-17 PC 수동 갱신의 멈춤 보호 — PLAN 판정

작성일: 2026-10-16 · 작성자: 설계자 · 독자: 개발자

**판정: PASS — 아래 보충을 PLAN에 반영하고 구현 진행. PLAN 재제출 불필요.**

## 1. 근거와 목적

- 첨부 REQUEST와 PLAN V1을 읽고 판정했다. 코드 위치·설치된 FDR 동작·최근 8회 소요 시간·로컬 소켓 실측은 개발자 조사 근거로 수용하며, 설계자가 저장소를 직접 검사했다고 기록하지 않는다.
- 목적은 PC 버튼 갱신에서 응답 없는 외부 조회가 계속 대기하는 경우를 줄이고, 실패를 마친 뒤 사용자가 다시 실행할 수 있게 하는 것이다.
- 기존 보호 함수 재사용과 PC 호출부의 선택 인자로 구현한다. OCI·PUSH 동작, 새 메뉴·DB 표·의존성·대기 시간·일일 횟수 제한·자동 재시도는 이번 범위에 넣지 않는다.
- 독립 검토 에이전트의 연결 실패는 기록대로 둔다. PLAN에 적힌 직접 조사와 로컬 시험을 근거로 판정하며, 구현 전 같은 검토를 다시 실행하는 것을 게이트로 만들지 않는다.

## 3. 요청 20초의 의미와 수용하는 한계

- ETF 목록·ETF 가격·보유 개별주 단계에 기존 fdr_request_timeout 기본 20초를 적용하는 안을 수용한다. 기존 명시적 timeout과 보호 함수 자체의 동작을 바꾸지 않는다.
- **20초는 연결·읽기 대기 설정이며, 종목 하나 또는 갱신 작업 전체가 반드시 20초 안에 끝난다는 뜻이 아니다.** 여러 주소 연결, DNS 대기, 조금씩 계속 오는 응답 등은 별도 한계다.
- PLAN의 약 100초 및 약 6.6시간은 요청 하나가 종목마다 약 20초에 끝나는 단순 가정의 계산 예로만 적는다. 최대 시간이나 종료 보장으로 표현하지 않는다. 다른 단계 소요 시간도 포함한 수치가 아니다.
- 최근 8회 실패 0은 관측 사실로 수용한다. 앞으로 정상 요청이 영향받지 않는다는 보장으로 확대하지 않는다. 목록 최대 1.6초 대비 20초는 약 12.5배이며, 종목당 평균값은 개별 요청의 최대값이 아니다. PLAN의 '60배 이상'은 대상 수치에 맞춰 정정한다.
- 이번에는 이 연결·읽기 대기 보호 수준으로 진행한다. 잔여 한계를 이유로 범용 작업 관리 체계를 새로 만들지 않는다.
- 종료 시 DEF-FDR-TIMEOUT은 'PC 버튼 경로에 요청 timeout·연속 timeout 중단 적용, DNS·느린 연속 응답에 대한 전체 종료 보장 없음'으로 범위를 명시한다. 이 결함의 모든 경로가 완전히 해소됐다고 기록하지 않는다. 단계 종료와 잔여 한계 기록은 양립한다.

## 4. 연속 5종목과 상태 처리

- 연속 판정 단위는 HTTP 호출 수가 아니라 실제로 조회한 ETF **종목의 결과**다. 기본적인 requests.exceptions.Timeout 계열을 포함해 실제 시간 초과로 식별되는 경우에만 센다. 일반 HTTP 오류·빈 자료·파싱 오류·기타 예외를 시간 초과로 묶지 않는다. 예외 메시지의 문자열만으로 분류하지 않는다.
- 시간 초과가 아닌 결과가 하나라도 끼면 연속 횟수를 0으로 되돌린다. 성공 결과뿐 아니라 시간 초과 아닌 실패도 연속 timeout을 끊는다.
- 다섯 번째 연속 시간 초과를 처리한 뒤 남은 ETF는 조회하지 않는다. '원천 전체 장애 확정'으로 단정하지 않고 '가격 조회가 연속으로 시간 초과되어 나머지를 받지 않음'으로 기록한다.
- 이 중단 조건은 PC가 선택 인자를 넘긴 경우만 활성화한다. 인자 미지정 공유 함수·OCI 배치의 순회·예외·기록 결과는 기존과 같아야 한다.
- ETF 가격의 조기 중단 때문에 다른 갱신 단계의 실행 정책을 새로 바꾸지 않는다. 기존 단계 흐름을 유지하고, 뒤 단계가 성공해도 이 회차의 최종 failed가 completed로 덮이지 않게 한다.
- 최종 기록 뒤 running이 해제되고, 이 실패가 새 성공 갱신 시각을 만들거나 6시간 대기를 시작하지 않아야 한다. 다른 단계 실행 중에는 기존 잠금을 유지한다.
- 작업은 실제로 끝난 뒤 잠금이 풀려야 한다. 기다리는 스레드는 남겨 놓고 상태만 failed로 바꾸는 방식은 수용하지 않는다. 기존 서버 재시작 시 정리는 유지한다.

## 5. 자료와 기록의 정확성

- 성공적으로 받은 자료는 기존 즉시 저장 방식을 유지한다. 실패·미조회 종목의 기존 자료를 삭제하거나 빈 값으로 덮지 않는다.
- **조회하지 않은 종목을 '시도한 종목'이나 '시간 초과된 종목'으로 세지 않는다.** 실제 시도·성공·실제 실패·중단 뒤 미조회 건수를 구분할 수 있어야 한다.
- 기존 로그가 요청 대상 전체와 미완료를 합산하는 계약이면 기존 의미를 보존하되, 미조회 건수를 기존 사유/요약에 별도로 적어 해석 가능하게 한다. 이를 위해 새 DB 표나 화면을 만들 필요는 없다.
- 요약의 '저장된 종목 수'는 해당 반환값의 실제 저장 의미와 일치해야 한다. 숫자를 확보할 수 없다면 '앞서 받은 자료는 보존했습니다'라고 쓰고 임의 숫자를 넣지 않는다.
- 예: '가격 조회가 연속으로 시간 초과되어 남은 N종목은 받지 않았습니다. 앞서 받은 자료는 보존했습니다. 갱신 작업 종료 후 다시 실행할 수 있습니다.'
- ETF 목록 실패·보유 개별주 일부 실패·일부 ETF 실패는 PLAN 표의 기존 상태와 문구 정책을 유지한다.

## 6. 기존 보호 함수의 적용 범위

- Session.request 교체는 프로세스 공통임을 한계로 기록한다. 새 보호 범위는 필요한 PC FDR 단계 블록에 한정하고, 성공·예외 경로 모두 기존 함수로 복원한다.
- 기존 전체 갱신/VIX 재시도의 공통 잠금과 명시적 timeout 보존을 유지한다. 이 단계에서 공유 보호 함수 자체나 다른 호출부를 함께 개편하지 않는다.
- 새 선택 인자와 필요한 내부 중단 정보 전달은 허용한다. 공개 HTTP 경로·응답 필드·화면 변경은 요구하지 않는다.

## 7. 검증과 종료 순서

- PLAN §5의 tmp DB·로컬 소켓 시험과 관련/전체 회귀 계획으로 진행한다. 실제 외부 서버 장애나 라이브 DB 변경을 만들지 않는다.
- 특히 다음 결과를 확인한다: 실제 요청 timeout 발동, 세 FDR 단계 보호, 예외 뒤 함수 복원, 정확히 다섯 종목에서 중단, 성공/일반 오류 사이의 연속 횟수 초기화, 미조회 건수 구분, 이미 저장한 자료 보존, 뒤 단계 성공에도 최종 failed 유지.
- failed 뒤 running이 남지 않고 바로 재실행 accepted가 되는지와, 일부 실패 completed에는 기존 대기가 유지되는지를 서비스 경계에서 확인한다. 인자를 주지 않은 공유 함수 경로의 동등성도 확인한다.
- 화면을 바꾸지 않으므로 목업은 필요 없다. 정상 갱신의 실제 실행은 사용자에게 필요할 때 하면 되며, 외부 장애 실재현이나 다음 거래일 대기를 종료 조건으로 추가하지 않는다.
- 구현 → 검증자 검증 → RESULT 판정으로 진행한다. RESULT에는 처리 범위와 전체 종료 보장 부재를 정확히 적는다. 커밋·push는 이 PLAN 판정 자체가 새 승인인 것으로 해석하지 않고, 해당 작업에 대한 사용자 승인 범위를 따른다.
- 판정 원문은 기존 PLAN에 이어 기록해도 된다. 별도 저장소 인계 문서는 요구하지 않는다.
