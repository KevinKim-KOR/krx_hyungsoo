# POC5-27 PC에서 OCI 운영 기준 실제 활성화 — 설계 V1

작성: 2026-10-19 · 설계자 → 개발자 / 사용자
근거: 사용자 백로그 #50 개발 요청(POC5-25 RESULT §11) · 설계자 후속 순서 #19 → #50 → #48.

**목표: PC에서 명시적으로 적용한 운영 기준을 OCI 러너가 다음 기준 읽기부터 실제로 사용하고, 화면이 그 결과를 정확히 보여 준다.**

## 1. 출발점과 범위

제공 문서상 현재 PC의 '전달'은 OCI JSON을 바꾸고, 러너는 DB 활성 PARAM을 읽는다. 실제 활성화는 OCI 수동 스크립트로 한다. OPS-04는 이 차이를 화면에서 구분했고, 이번 요청은 수동 활성화 연결까지 포함한다. 개발자가 현행 소스로 이 경계를 먼저 대조한다.

- 기존 「OCI 운영·적용」 화면·현재 운영 기준·SSH·PARAM 저장소·활성화 도구를 재사용한다. PC에서 고른 현행 허용 운영값만 적용한다. 현재 비교 계약의 유효값 14개를 기준으로 조사하되, 실제 허용키가 바뀌었다면 PLAN에 알린다.
- 기존 적용 경로를 보강한다. 새 메뉴·관리 서버·DB 표·큐·스케줄러·자동 정책 선정·새 .env 플래그는 만들지 않는다. 필요한 좁은 실행 도구·선택 응답 필드·helper는 허용한다.
- Holdings·관찰 후보군·원장·ML·가격 수집·알림 본문을 바꾸지 않는다. 이번 사용자 적용이 앞으로 러너가 읽는 운영값을 바꾼다는 효과는 화면에서 분명히 한다.

## 2. 사용자 동작과 화면

- 기존 전달 버튼의 의미를 **[현재 기준 OCI 적용]**으로 바꾼다. 적용은 버튼을 명시적으로 눌렀을 때만 실행한다. 기동·조회·PC 기준 저장·파일 전달만으로 자동 활성화하지 않는다.
- 적용 전 현재 PC 값과 마지막 확인한 OCI 활성값의 차이를 기존 비교 영역에서 볼 수 있게 한다. 같은 값이면 같은 값이라고 표시한다. 긴 구현 설명 대신 'OCI 러너가 이후 실행에서 읽는 기준을 적용합니다' 정도의 짧은 안내를 둔다.
- 실행 중 같은 버튼의 중복 실행은 막고, 응답 뒤 실제 활성값 확인 결과로 '일치/다름/확인 안 됨'을 갱신한다. 기존 ID가 달라도 유효값이 같으면 일치라는 계약을 유지한다.
- 이미 시작해 기준을 읽은 실행은 그때 읽은 기준으로 계속 간다. 적용 때문에 실행 중 러너를 중단·재시작하거나 PUSH를 한 번 더 보내지 않는다.
- 별도 설정 창·상시 폴링·자동 재시도·일반적인 적용마다 추가 확인 팝업은 도입하지 않는다. 사용자 전체 화면 목업으로 버튼 의미와 결과 표시를 확인한다.

## 3. 원격 적용 계약

1. **값 확정**: 적용 버튼 시점의 유효 운영값을 고정하고 기존 검증을 통과시킨다. 빠진 필드를 기본값으로 채워 다른 정책을 활성화하지 않는다.
2. **실제 상태 읽기**: OCI의 현재 DB 활성값을 읽는다. 같은 유효값이면 새 버전을 늘리지 않고 '이미 일치·변경 없음'으로 끝낼 수 있다.
3. **후보 준비**: 다르면 OCI에 전달한 정확한 값으로 유효한 후보 버전을 준비한다. 기존 생성·승인 규칙과 허용값 검증을 재사용한다. 일반 기본 seed나 다른 파일 값을 대신 활성화하지 않는다.
4. **활성 전환**: 준비가 끝난 뒤 기존 DB 트랜잭션으로 활성 포인터를 전환한다. 실패하면 직전 활성값을 보존한다. 운영자가 임시로 빈 활성 상태를 거쳐야 하는 방식은 쓰지 않는다.
5. **확인**: OCI DB에서 실제 활성 버전·유효값을 다시 읽고 요청값과 대조한 결과를 PC에 돌려준다. 성공은 JSON 전달·스크립트 종료 코드만으로 정하지 않는다.

**러너의 정본은 DB 활성값 하나다.** JSON은 기존 전달 자료이며 DB와 두 개의 동등한 활성 정본으로 만들지 않는다. 두 파일·두 DB의 동시 원자 교체나 별도 manifest 정합 체계를 만들지 않는다. PC 값이 저장됐지만 OCI 적용이 실패했다면 PC의 의도한 값과 OCI의 이전 값을 구분해 보인다.

기존 SSH 경로에서 저장소의 짧은 실행 도구와 기존 Python 저장 함수를 호출하는 방식을 우선한다. 새 원격 서비스·외부 패키지·루트 권한이 필요한 구조는 만들지 않는다. 실제 함수·CLI 재사용 가능성은 PLAN에서 확인한다.

## 4. 실패·재실행·복구

| 상황 | 처리 |
|---|---|
| 검증·전달·후보 준비·활성 트랜잭션이 전환 전에 실패 | 적용 실패를 알리고 직전 OCI 활성값을 보존한다. 새로 준비된 비활성 후보가 있어도 운영 적용 성공으로 보지 않는다. |
| 활성 전환 뒤 응답 단절·확인 읽기 실패 | '적용 결과 확인 불가'로 둔다. 이전 값이 그대로라고 단정하거나 화면을 성공으로 바꾸지 않는다. |
| 사용자가 다시 적용 | 실제 활성값을 먼저 읽는다. 이미 요청값과 같으면 추가 전환 없이 일치 확인으로 끝낸다. 별도 재시도 원장·요청 ID 저장소는 만들지 않는다. |
| 사용자가 이전 기준으로 복구해야 함 | 기존 OCI 버전 저장소와 활성화 기능으로 유효한 이전 버전을 선택·확인해 복구하는 절차를 PLAN에 명시한다. 전환 실패의 DB 롤백과 성공 후 사용자가 정책을 되돌리는 동작을 구분한다. 새 복구 UI는 이번에 추가하지 않는다. |

전환 후 통신 오류만으로 자동 역전환하지 않는다. 실제 활성 상태를 먼저 확인한다. 비밀값·SSH 정보·.env 내용은 화면·응답·일반 로그에 넣지 않는다. 현행 운영값·버전 정보만 기존 상태 계약 안에서 다룬다.

## 5. 짧은 PLAN과 목업

개발자는 다음 여섯 가지 사실만 확인한다.

1. 현재 버튼→API→SSH→JSON 전달→실제 활성화의 호출 경계 및 재사용 함수.
2. 기존 OCI 후보 생성·승인·활성 전환의 트랜잭션 경계와 이전 버전 복구 방법.
3. 현행 유효값 비교·활성 버전 읽기·실패 표시를 재사용하는 위치. PC/OCI 버전 ID 일치를 강제하지 않는 방법.
4. 새 원격 실행 도구 또는 기존 도구의 최소 수정과 배포 대상. API 경로 신설 없이 가능해야 하며 충돌 시 사실과 최소 대안을 질문한다.
5. 현재 OCI 활성값·사용 가능한 도구를 기존 권한 안에서 읽기 전용으로 한 번 확인한 결과. 운영 전체 로그·과거 발송 이력 조사로 확대하지 않는다.
6. 격리 SQLite·가짜 SSH로 성공/동일값/전환 전 실패/전환 뒤 확인 불가/재실행/복구를 검증할 방법.

개발자가 「OCI 운영·적용」 전체 화면 1440/1000px 목업을 만든다. 일치·값 다름·적용 중·성공·실패·확인 불가가 읽히면 충분하다. 목업 촬영을 위해 실제 OCI 활성값을 바꾸지 않는다. 사용자 목업 확인과 PLAN 판정 뒤 구현한다. 필요한 파일 책임 분리는 해당 변경 안에서 하며 별도 리팩터 Step을 만들지 않는다.

## 6. 검증·배포·종료

- 요청값과 실제 활성값 일치, 같은 값의 중복 버전 방지, 전환 전 실패의 기존 값 보존, 확인 불가의 정직한 표시, 기존 수동 복구 경로를 격리 자료로 검증한다. 관련 기존 검사와 프로젝트 필수 절차를 따른다.
- 검증자 확인과 RESULT 판정 뒤 사용자 승인 범위에서 커밋·push한다. OCI 실행 파일 변경이 있으면 사용자께서 기존 배포 절차로 pull한다. 배포는 기존 거래시간 회피 규칙을 따르며 버튼에 새 사용 시간 제한을 만들지 않는다.
- 배포 뒤 사용자가 버튼을 한 번 누르고 개발자가 실제 활성값을 읽기 전용으로 확인한다. 실제 정책 변경 필요가 없으면 동일값 확인으로 진행하고, 다른 값의 포인터 전환은 격리 시험에서 확인한 사실을 구분해 기록한다. 시험 때문에 실제 정책을 임시로 바꾸지 않는다.
- 위 확인을 통과하면 종료 기록 후 별도 재판정 없이 닫는다. 실패하면 구체 결과를 보고한다. 다음 거래일까지 대기·새 PUSH 발송·별도 인계 문서를 종료 조건으로 삼지 않는다.
