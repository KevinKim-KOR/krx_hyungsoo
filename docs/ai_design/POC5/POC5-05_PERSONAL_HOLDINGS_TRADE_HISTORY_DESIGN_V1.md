## 1. 사용자 작업과 이번 범위

사용자는 「종목 관리」에서 **한 번의 매매 입력**으로 수량·평단·이력을 갱신한다. 보유를 저장한 뒤 같은 내용을 별도 이력 구역에 다시 입력하는 방식은 폐기한다.

| 사용자 동작 | 현재 보유 | History |
|---|---|---|
| 새 종목 최초 매수 | 새 보유 생성 | 새 보유 기간과 BUY 기록 |
| 보유 줄에서 추가매수 | 수량 증가·평단 갱신 | 같은 보유 기간에 BUY 추가 |
| 보유 줄에서 분할매도 | 수량 감소·남은 평단 유지 | SELL·실현손익 기록 |
| 전량매도 | 해당 보유 줄 제거 | 종료된 보유 기간으로 보존 |
| 같은 종목 재매수 | 새 수량·새 평단으로 시작 | 새 보유 기간 생성·이전 기간 조회 |
| 입력 실수 정정 | 정정한 사실에 맞게 갱신 | 실제 매매와 구분한 정정 기록 |

이번 구현은 통합 입력·보유 계산·과거 보유·History 손익·저장된 가격을 이용한 수동 시장 흐름 요약이다. 증권사 연동·주문·현금 계정·세금 계산·과거 거래 일괄 복원은 추가하지 않는다. 실제 ML 재진입 판정은 §8의 후속 설계에서 다룬다.

## 2. 화면과 입력

기존 「종목 관리」를 사용한다. 현재 보유 줄을 누르면 그 종목·계좌가 고정된 매매 입력 창을 연다. 추가매수/분할매도/전량매도를 선택하고 거래일·체결단가·수량을 넣는다. 전량매도 수량은 현재 잔량으로 채우며 저장 직전 서버에서 다시 확인한다. 총 매매대금은 단가×수량으로 계산해 보여 주고 따로 입력시키지 않는다.

- 새 보유 추가도 최초 매수 입력으로 처리한다. 아직 실제 거래를 모르는 기존 잔고 등록은 ‘잔고 등록’으로 구분한다.
- 거래일은 KST 날짜, 오늘 또는 과거다. 실제 시각은 선택이며 미상 시각을 00:00이나 저장 시각으로 채우지 않는다. 거래일이 휴장일이라는 이유만으로 기록을 막지 않는다.
- 단가·수량은 유한한 양수다. 종목·계좌구분은 기존 검증을 재사용하고 실계좌번호를 새로 받지 않는다.
- 폼은 동일 폭의 열을 가진 두 줄 배치로 만든다. 첫 줄은 날짜·선택 시각·종류, 둘째 줄은 단가·수량·계산 금액이다. 좁은 화면에서는 열을 줄여도 각 줄의 정렬을 유지한다.
- 저장 후 현재 목록과 History를 함께 갱신한다. 현재 수익률은 기존 현재가·가격 상태와 변경된 수량·평단으로 계산한다. 체결단가를 현재가로 덮어쓰지 않는다.
- 각 보유 줄에 History 버튼을 두고, 같은 화면의 접힌 ‘과거 보유’ 목록에서도 History를 연다. 새 메뉴나 별도 거래 입력 목록은 만들지 않는다.
- 재매수 입력에서는 이전 보유 기간을 조회할 수 있다. History 조회나 종목 선택만으로 시장 조회·ML을 실행하지 않는다.

History에는 보유 기간별 매수·매도·수량·단가·매매대금, 매도별 실현손익·수익률, 누적 실현손익·수익률을 표시한다. 현재 보유의 미실현손익과 과거 매도의 실현손익은 각각 표시한다. 사용자가 남길 수 있는 메모는 선택이다.

## 3. 평단과 실현손익

**이동평균 방식**으로 계산한다. 종목·계좌·보유 기간별로 수량 Q, 남은 원가 C를 관리한다. 매수 수량 b, 매도 수량 s, 체결단가 p라 할 때:

```text
추가매수: Q' = Q + b
          C' = C + b×p
          평단' = C' / Q'

분할매도: 매도분 원가 = C×s/Q
          매도대금 = s×p
          실현손익 = 매도대금 - 매도분 원가
          Q' = Q - s
          C' = C - 매도분 원가
          남은 보유의 평단은 유지

전량매도: 남은 C 전체를 매도분 원가로 배분
          Q' = 0, C' = 0, 해당 보유 기간 종료
```

매도 수량이 잔량을 넘으면 저장하지 않는다. 매도 이익을 남은 평단에서 빼는 계산은 하지 않는다.

매도별 실현수익률은 실현손익/매도분 원가×100이다. 보유 기간의 누적 실현수익률은 실현손익 합계/매도분 원가 합계×100이다. 개별 수익률을 합하거나 평균하지 않는다. 수수료·세금·배당을 반영하지 않은 계산임을 손익 표 옆에 표시한다. 실제 증권사 정산손익·연환산 수익률로 이름 붙이지 않는다.

검증 예: 10주×10,000원에 5주×12,000원을 추가하면 15주·원가 160,000원·평단 10,666.666…원이다. 6주×13,000원 매도 시 원가 64,000원·실현이익 14,000원·수익률 21.875%, 잔량 9주·원가 96,000원이다. 남은 9주를 10,000원에 팔면 손실 6,000원, 기간 합계는 이익 8,000원·5%다. 다음 재매수에는 이 기간의 원가를 넘기지 않는다.

수량·단가·원가·손익은 Decimal로 계산하고 이력에는 십진 문자열로 보존한다. 새 거래의 수량은 개정 1의 소수 6자리 한도를 유지하고, 체결단가는 소수 2자리까지 받는다. 계산된 매매대금은 입력값의 곱을 보존하며 소수 2자리로 잘라 저장하지 않는다. 기존 기준잔고의 정밀도에는 새 입력 한도를 소급하지 않는다. 내부 나눗셈은 Decimal 정밀도 28 이상을 사용하며 화면 반올림 값을 다음 계산에 쓰지 않는다. 전량매도 때 원가 잔액을 모두 배분해 계산 잔여액을 남기지 않는다. 기존 holdings 소비자가 요구하는 수량·평단 숫자는 계산 결과의 호환용 표현이다. 기존 float의 정밀도 손실을 복원했다고 주장하지 않는다. 개정 1의 ‘선택 금액’은 새 매매 입력의 필수 체결단가와 계산 금액으로 대체한다.

## 4. 기존 32줄과 보유 기간

첫 변경 저장 때 기존 보유를 **기준잔고**로 기록한다. 현재 수량과 입력 평단은 유지하고 원가 기준을 수량×입력 평단으로 둔다. 이는 계산을 시작하기 위한 기준이며 실제 최초 매수 금액·매수일을 새로 알아낸 것이 아니다.

- 기존 보유의 최초 매수일은 ‘미상’, 손익은 ‘입력 평단 기준·기록 시작 후’로 표시한다. 등록일을 매수일로 채우지 않는다.
- 이미 기준잔고에 포함된 과거 매수를 추가매수로 다시 더하지 않는다. 이번 단계는 기존 32줄의 전체 거래를 복원하는 도구를 만들지 않는다.
- 새로 기록한 최초 매수에는 실제 거래일을 사용한다. 전량매도 후 같은 종목·계좌를 사면 새 cycle_id를 발급한다. 기간 사이의 미보유 구간과 종료 손익을 보존한다.
- position_id는 선택한 보유 줄, cycle_id는 하나의 보유 기간을 식별한다. 평단이 바뀌어도 ID는 바뀌지 않는다. 계좌별 보유·손익을 자동 합치지 않는다.
- 현재는 종목·계좌 중복이 없지만 기존 규칙은 평단이 다른 여러 줄을 허용한다. 기존 줄을 임의 병합하지 않고 줄별 ID로 처리한다. 새 매수에서 이미 보유 중인 줄을 선택하면 그 줄의 추가매수다.

거래일 순으로 계산한다. 같은 날 여러 거래의 계산 순서는 별도 순번으로 유지하고, 과거 입력을 끼워 넣을 때 같은 날의 앞/뒤를 지정할 수 있게 한다. 시각 미상 거래의 계산 순번을 실제 체결 시각의 증거로 사용하지 않는다. 순서 변경·정정 뒤 수량 경로가 음수가 되면 관련 거래를 보여 주고 저장을 막는다.

## 5. 저장 — 보유와 이력을 한 번에 반영

PC의 기존 **state/holdings/holdings_latest.json을 확장해 한 파일을 정본으로 사용한다.** 개인 이력 DB와 보유 JSON을 따로 저장하는 개정 1 구조는 폐기한다. 거래와 보유가 서로 다른 저장 성공 상태에 놓이지 않도록 한 문서에서 계산·저장한다.

최소 문서 구조:

| 부분 | 내용 |
|---|---|
| schema_version / revision | 문서 형식과 변경 번호 |
| holdings | 현재 잔량이 있는 보유의 기존 필드 + PC용 position_id·cycle_id |
| personal_trade_history | 보유 기간·기준잔고·거래·정정/취소 연결·계산에 필요한 십진값 |
| 기록 식별자 | 저장 동작별 record_id·recorded_at·종류·대체 대상 |

holdings는 현재 목록의 호환용 계산 결과다. 이력의 기준잔고·유효 거래·명시적 입력정정에서 재생성할 수 있어야 한다. 별도 SQLite 이력 정본·동기화 큐·대사 서비스는 만들지 않는다. 파일 크기를 이유로 지금 다른 저장 구조를 추가하지 않는다.

모든 PC 보유 쓰기는 같은 저장 경계를 통한다: 최신 문서 읽기 → 재시도/버전 확인 → 변경된 기간 계산·전체 문서 검증 → 같은 디렉터리 임시 파일 작성 → 파일 교체. PC backend의 쓰기를 직렬화하고 문서 revision으로 오래된 화면의 덮어쓰기를 막는다. 실제 PC backend 실행 방식에 맞는 최소 구현을 PLAN에서 제시한다.

- 파일 교체 전 실패하면 기존 보유·이력 모두 유지한다. 교체 후 응답이 끊겼을 때 같은 record_id로 재시도하면 기존 결과를 반환한다. 같은 ID·다른 내용은 충돌이다.
- 중복 요청 확인은 오래된 revision 거절보다 먼저 한다. 응답에는 저장된 거래와 최신 현재 보유를 함께 돌려준다.
- 조회·기동·History 열기는 기준잔고나 거래를 저장하지 않는다. 기존 형식은 읽을 수 있어야 하며 첫 명시적 변경에서 기준잔고와 함께 새 형식으로 저장한다.
- 읽기 실패·손상은 빈 보유로 바꾸지 않는다. 파일이 없는 최초 설정에서는 사용자가 최초 매수/잔고 등록을 저장하는 동작으로 초기화한다.
- 전 종목 매도에 필요한 **유효한 빈 holdings 배열**을 허용한다. 파일 없음·손상·정상 빈 보유를 구분한다.
- 기존 저장 함수가 새 메타데이터를 버리지 않도록 한다. 이력 포함 문서를 읽은 구판 writer가 덮어쓰지 않는 운용으로 PC 코드를 함께 갱신한다.

현재 GET/PUT /holdings와 적용 API는 필요한 부분을 변경할 수 있다. 기존 입력이 이력을 삭제하는 우회 저장 경로로 남아서는 안 된다. 새로 만든 GET/PUT /holdings/trade-history는 조회와 통합 매매 명령의 진입점으로 재사용한다. 현재 보유 변경 금지였던 기존 계약·테스트는 이 개정에 맞춰 바꾼다.

## 6. 실제 매매와 입력 정정

실제 BUY/SELL, 거래 오기 정정, 현재 잔고의 직접 정정을 구분한다.

거래 오기 정정·취소는 기존 record_id를 대상으로 새 기록을 추가한다. 이전 입력과 대체/취소 관계를 보존하고 해당 보유 기간만 다시 계산한다. 뒤의 매도가 잔량을 넘거나 종료 기간이 다시 열려 이후 재매수 기간과 충돌하면 자동 합치지 말고 관련 기록을 정정할 수 있게 안내한다. 종료 기간의 가격만 고치는 정정은 새 보유 기간의 평단을 바꾸지 않는다.

직접 수량·평단을 고치는 ‘입력 정정’은 ADJUSTMENT로 남긴다. 매매대금이나 실현손익을 만들지 않는다. 종목명 등 표시값 정정도 매매가 아니다. 직접 정정으로 원가 기준이 바뀐 구간은 History에서 표시하고 기간 전체 손익을 완전한 실제 거래 손익으로 표현하지 않는다.

줄 삭제는 전량매도와 입력정정 중 목적을 구분한다. 전량매도는 거래일·단가를 받고 손익을 계산한다. 잘못 등록한 보유 제거는 정정으로 종료하며 매도 이익을 만들지 않는다. 수정 전후 값과 이력은 보존한다.

기존 전체 보유 PUT도 같은 저장 경계를 사용한다. 기존 줄의 ID를 보존하며 실제 매매 의도가 없는 수량·평단 변경은 입력정정이다. 새 형식으로 저장된 뒤 revision 없는 전체 덮어쓰기는 충돌로 거절한다. ID 없는 요청을 안전하게 매칭할 수 없는 경우 새로고침을 요청하고 임의로 거래·기간을 재연결하지 않는다. 갱신된 화면은 revision과 ID를 전달한다. 최초 구형 잔고 등록은 허용하며, 현재 내용과 같은 재저장은 정정 기록을 중복 추가하지 않는다.

## 7. OCI와 기존 원장 경계

OCI 적용은 기존 ‘적용’ 버튼을 유지한다. 매매 저장 때 SSH·OCI 쓰기를 실행하지 않는다. PC에서 보유가 바뀌면 미적용 상태를 보여 준다. OCI의 보유는 사용자가 적용한 현재 목록이다.

**기존의 PC 파일 바이트 전체 전송은 변경해야 한다.** 허용 목록인 ticker·quantity·avg_buy_price·name·account_group만으로 기존 형태의 holdings payload를 생성해 보낸다. 개인 이력·ID·실현손익·메모·과거 보유는 포함하지 않는다. 적용 hash·확인도 이 전송 payload를 기준으로 한다. History만 정정하고 현재 보유가 같으면 OCI 미적용 변화로 잡지 않는다.

PC 및 OCI의 보유 소비 경로는 현재 holdings만 읽는다. 과거 보유 목록을 정기 flow·가격 수집·PUSH 대상에 합치지 않는다. OCI도 빈 현재 목록을 정상 처리해야 전량매도 후 이전 종목이 남지 않는다. 공용 loader 등의 변경이 필요한지는 PLAN에서 확인하고, 필요하면 해당 코드의 OCI 배포를 포함한다. ‘OCI 코드 변경 0’으로 미리 단정하지 않는다.

01B/02/03 원장·피드백·기존 price_outcome은 변경하지 않는다. 개인 이력은 원장 export·동기화·Telegram·일반 로그에 넣지 않는다. 기존 PC DB에 만들어 둔 개인 표가 있다면 조회로 현황을 확인한 뒤 보존하며 원장 동기화 때문에 지우지 않는다.

## 8. 시장 흐름과 ML 재진입 검토

History는 과거 거래 사실을 보는 화면이고 **분석은 별도 사용자 동작**이다. 과거 보유를 정기 flow·시세 갱신·재진입 판정 대상 목록에 자동 합치지 않는다. 저장된 과거 자료를 사용자가 실행하는 사후 ML 학습·평가에 쓰는 것은 별개이며 제한하지 않는다.

이번 05의 ‘시장 흐름 보기’는 사용자가 선택한 종목·보유 기간에 대해 기존 PC 가격 자료만 읽는다. 거래일의 종가와 최신 저장 종가 사이의 변화, 알려진 매수일부터 매도일까지의 종가 변화를 수치·정형 문장으로 보여 준다. 체결단가로 계산한 개인 손익과 종가 변화는 구분한다. 거래일이 비거래일이면 기존 캘린더의 다음 거래일을 사용하고 실제 기준일을 표시한다. 같은 가격 계열·정해진 기준일의 자료가 없으면 인접일이나 다른 계열로 메우지 않고 ‘자료 없음’으로 표시한다. 시장 비교는 같은 기준일의 기존 시장 자료가 있을 때만 제공한다. 매수일 미상인 기준잔고의 매수 전후 변화는 계산하지 않는다. 자료 날짜·출처·가격 계열을 표시한다. History 열기만으로 외부 조회하지 않고, 이 기능을 위해 매도 종목의 정기 수집을 늘리지 않는다. 자유 생성 코멘트·새 모델은 05에 추가하지 않는다.

**후속 POC5-06은 사용자가 누르는 ‘재진입 검토’ 방향으로 설계한다.** 선택한 종목의 과거 매매·당시 시장·현재 판단 시점까지의 자료를 모아 재진입 판단에 도움이 되는 근거·불확실성을 제시한다. 필요한 수동 조회 범위와 ML 모델·기존 기준 대비 검증은 그 설계에서 확정한다. 05 화면에 실행되지 않는 ML 판정 버튼이나 임시 성공 판정을 넣지 않는다.

사용자 평가가 있으면 별도 근거로 사용하고, 없어도 알림·객관적 결과·거래 자료를 사용할 수 있다. 평가 없음은 데이터 제외나 부정 신호가 아니다. 사후평가에 사용하는 이후 가격·나중 입력한 평가는 당시 예측 입력에 소급하지 않는다. 모델이 만든 평가를 사용자 평가로 저장하지 않는다. 매매 사실만으로 특정 알림의 성공을 판정하지 않는다.

05 로컬 구현 중 06 설계를 병행할 수 있다. 10-12 가격 결과 확인·10-23 공식 R0·일일 사용자 평가·특정 성숙 기간을 05 완료나 06 설계 착수의 새 게이트로 두지 않는다.

## 9. 수용 기준

1. 최초 매수·추가매수·분할매도·전량매도 각각 한 번의 저장으로 현재 보유와 이력이 함께 바뀐다. 별도 보유 재입력은 없다.
2. §3 계산 예와 손실 매도·잔량 초과·소수 수량을 확인한다. 분할매도 평단 유지·전량매도 원가 0·재매수 원가 분리를 확인한다.
3. 기존 32줄 기준잔고는 수량·평단을 유지하며 매수일 미상을 보존한다. 다른 계좌·기존 복수 줄의 원가를 섞지 않는다.
4. 저장 중 실패·응답 유실 재시도·오래된 화면·정정/취소 재계산에서 보유와 이력이 어긋나지 않는다. 반복 요청이 수량을 두 번 바꾸지 않는다.
5. 전량매도한 종목은 현재 목록에서 빠지고 History에 남는다. 전 종목 매도 후 정상 빈 보유가 PC·OCI 소비 경로에서 처리된다.
6. 입력정정·삭제를 실제 BUY/SELL·수익으로 만들지 않는다. 종료 기간 정정이 새 기간의 평단을 바꾸지 않는다.
7. OCI payload는 허용된 현재 필드만 포함한다. 개인 이력 포함 파일·과거 보유·이력만 바뀐 파일로 전송/hash/미적용 판정을 검증한다. 기존 원장·피드백·가격 결과는 불변이다.
8. 목업의 칸 정렬·행 매매 입력·History·과거 보유·재매수 연결을 확인한다. History 기본 조회는 외부 호출·ML·과거 종목 정기 수집을 유발하지 않는다.
9. 변경된 보유 저장·적용·소비 경로의 의미 있는 회귀와 정적 검사·KS-10을 수행한다. 실제 사용자 화면 확인은 거래일과 무관하게 할 수 있다.

테스트는 tmp 보유 파일·tmp DB·목표 경로 mock을 사용한다. 실거래를 만들거나 사용자 라이브 보유를 시험용 매매로 바꾸지 않는다. 공용 OCI 코드 변경이 필요한 경우 배포·정상 빈 보유 읽기 확인을 포함하되 실발송·새 영업일 관찰을 형식상 추가하지 않는다. 기존 02/03 및 공식 R0 운영 확인 일정은 그대로 유지한다.

## 10. 개정 2 PLAN 제출 지시(제출 완료 · 현재 작업은 §11 판정 우선)

1. 모든 PC holdings writer·GET/PUT·enrich·공용 loader의 실제 위치와 새 문서 보존·빈 목록 영향 확인.

3. OCI 적용의 현재 전체 바이트 전송을 허용 필드 payload로 바꿀 위치·hash 연결·빈 목록 소비·필요한 배포 파일 확인.

6. 기존 화면 행 동작·History/과거 보유 컴포넌트·변경 파일·테스트·KS-10 실측과 정렬된 목업 제시.

위 범위를 반영한 PLAN 개정 원문과 실제 코드 충돌만 추천안을 붙여 설계자에게 전달한다. 새 설계를 구현할 권한을 사용자에게 다시 묻지 않는다. 목업은 통합 보유 화면으로 한 번 갱신해 사용자가 동작·정렬을 확인한 뒤 frontend를 진행한다. 실제 ML 구현은 별도 후속 설계다.

### 11-2. 본문에서 바로 고칠 계산 순서

PLAN §2-2의 ‘BASELINE·REGISTER·첫 BUY를 맨 앞’은 다음으로 정정한다.

- BASELINE·REGISTER는 매수일 미상인 기간의 시작 기준이다. 그 기간의 기준잔고로 먼저 적용한다.
- **실제 최초 매수로 시작한 기간은 Q=C=0에서 모든 유효 BUY/SELL을 거래일·seq 순으로 계산한다.** 첫 입력한 BUY를 날짜와 무관하게 맨 앞에 고정하지 않는다.
- 거래 오기 정정은 대체된 유효 내용의 날짜·순서로 재계산한다. VOID된 BUY를 잔고 계산에 남기지 않는다. 초기 BUY 취소 뒤 다른 유효 매수가 없으면 현재 보유에서 빠지고 취소 이력이 남는다.
- Q-E의 잔고 확정은 위 순서 안의 해당 위치에서 적용한다. 기존의 음수 잔량·기간 충돌 거절은 유지한다.

검증 예: 10-08 최초 BUY 10주×10,000원 뒤, 누락된 10-07 BUY 5주×20,000원과 SELL 2주×30,000원을 추가하면 실제 날짜 순서에서 해당 SELL 원가는 40,000원·이익은 20,000원이다. 10-08 BUY를 앞에 고정하면 이 매도 원가가 달라진다. 이 경우와 최초 BUY 날짜 정정/취소를 기존 계산 테스트에 포함한다. 새 검증 라운드를 따로 만들지는 않는다.

### 11-3. 저장·적용·화면 계획 수용과 보완

- records 정본·계산 결과 비저장·Decimal prec=40·조회 무저장·v1 줄 ID·동일 position의 새 cycle·재시도 우선·threading.Lock·revision·단일 파일 교체 계획을 수용한다. 보고된 단일 PC backend 방식에 맞춰 구현하며 분산 잠금·추가 DB를 만들지 않는다.
- 명시적 재매수는 선택한 position_id를 사용한다. 기존에 같은 종목·계좌의 과거 줄이 여러 개라 연결이 모호하면 임의 병합하지 말고 선택하게 한다.
- 저장 형식 v2·허용 5필드 전송·payload hash를 같은 커밋에 넣는다. 마지막 성공 hash 보존을 수용한다. 성공 기록이 없으면 pending_apply=null은 ‘적용 여부 확인 안 됨’이며 ‘적용 완료’로 표시하지 않는다.
- publication CLI의 거절 검사는 최상위뿐 아니라 **행의 허용 5필드**에도 적용한다. 최상위가 holdings뿐이어도 행에 개인 메타데이터가 있으면 원문 바이트를 게시하지 않는다. 정상적인 기존 5필드 파일은 기존 검증 경로를 유지한다.
- 재매수 전용 창·position별 History 한 창·접힌 과거 보유·정렬된 두 줄·입력 정정 모드·저장 후 값 미리보기는 **사용자 확인 완료**로 수용한다. 목업 재확인은 요구하지 않는다. ML 재진입 검토는 POC5-06이며 05에 버튼을 두지 않는다.
- PLAN §5의 매수→분할매도→정정→취소→전량매도→재매수 시험은 격리 파일/테스트 자료로 한다. 라이브 보유에 가짜 거래를 넣지 않는다. 실화면 확인과 실제 보유 적용은 사용자에게 필요한 정상 동작으로 확인하며 시험 때문에 보유를 바꾸거나 다음 실제 거래를 기다리지 않는다.

정정의 ‘원래 수량’은 **이번 supersedes_id가 가리키는 유효한 정정 대상 기록의 수량**이다. 전체 목록에서 가장 최근에 저장된 다른 거래의 수량이나 정정 체인의 최초 수량을 뜻하지 않는다.

바로 그 수량을 유지한 단가·날짜·시각·메모 정정에는 수량 한도를 새로 적용하지 않는다. 더 이전 기록의 수량으로 되돌리는 입력은 현재 대상과 다른 새 수량으로 검사한다. 다만 그 매도로 해당 기간의 잔량이 정확히 0이 되는 경우는 이미 구현된 잔량 전부 매도 예외를 그대로 적용한다. 숫자가 과거 어딘가에 있었다는 이유만으로 추가 예외 검색·복원 기능을 만들지 않는다. 보고된 구현·시험을 이 계약으로 수용하며 재작업은 없다.

결과서 §6-4의 남은 판단도 수용한다. 이력 없는 기존 형식의 정상 빈 holdings 문서는 허용하며 손상된 v2 문서와 구분한다. 저장된 기록 ID에 UUID 패턴을 재강제하지 않고 비어 있지 않은 유일 문자열로 판정하는 방식을 수용한다. 중복 ID·대체/취소 관계 검사는 유지한다.

### 12-3. 알려진 한계 12건

§5의 12건을 이번 범위의 한계·확인 잔여로 수용한다. 같은 날 앞/뒤만 가능한 입력 순서, 입력정정 이후 과거 전량매도 시 기간 충돌, 입력정정의 float 호환 범위, 기존 종목코드 처리에 새 기능을 붙이지 않는다. 기존 가격 자료·캘린더 범위·이력만 바뀐 파일 mtime·종목명 자동 채움·취소만 남은 줄의 목록 제외는 그대로 기록한다.

- 극소 잔량의 ‘0’ 표시 한계는 계산상의 보유 0과 구분한다. 현재 보유는 정수 수량이라는 보고와 정확 잔량 전량매도 구현을 근거로 이번 배포를 수용한다. 양수 잔량을 명확히 표시하는 개선은 후속 UI 보완이며 배포 게이트로 추가하지 않는다.
- 시장 흐름은 마지막 저장일까지의 참고 자료다. 개별주 자료 없음·2026 외 캘린더 기본값을 감추거나 실제 최신 시세로 표현하지 않는다.
- Mac의 적용 경로 확인을 Windows 지원 검증 완료로 확대하지 않는다. 첫 정상 적용은 사용자가 실제 실행하는 PC에서 확인한다. 별도 OS 전체 검증이나 거래일 대기를 요구하지 않는다.
- §4-4의 중복 평단 적용 차단은 위 12건과 별도로 §5에 함께 명시한다. 이 문서 정리는 코드 변경·RESULT 재제출 사유가 아니다.

### 12-4. 백업·배포·종료

사용자 승인 후 VERIFIED 뒤 만든 배포 전 백업, 원본과 같은 sha256·32줄·5,701바이트·읽기 전용·추적 제외·앱 미사용 경로라는 보고를 수용한다. 라이브 보유에 시험 매매 0건과 사용자의 ‘화면 데이터 입력은 아직’ 진술도 반영한다.

백업은 **배포 전 보유 복원용**이다. 앞으로 v2에 실제 기록을 저장한 뒤 이 백업만 덮어쓰면 새 기록은 복구되지 않는다. 그때 되돌릴 필요가 생기면 변경 후 문서를 먼저 보존하고 변경분을 확인한다. 자동 롤백·새 백업 서비스는 만들지 않는다.

진행 순서는 기존 §11-4와 결과서 §7-3대로다.

1. 개발자가 RESULT 판정을 설계서·결과서·STATE에 기록하고 사용자 승인 절차에 따라 커밋·push한다. 미커밋 상태를 배포 완료로 바꾸지 않는다.
2. 사용자 OCI pull로 보유 소비 변경과 해당 모듈의 신규 의존 파일을 함께 배포한다. 거래일 08:05~15:45 회피를 유지하며 휴장일에는 이 거래일 제외 구간을 적용하지 않는다.
3. PC 재기동 뒤 사용자는 보유 표·매매/정정 창·History·미적용 표시를 확인한다. 실제 거래 입력은 필요할 때 한다. 확인을 위해 가짜 매매를 저장하거나 기존 32줄을 다시 입력하지 않는다.
4. 기존 보유 그대로 첫 정상 수동 OCI 적용을 할 수 있다. 개발자가 읽기 전용으로 허용 필드·최상위 holdings 하나·개인 이력/ID 없음·현재 보유 일치를 확인한다.
5. PC 실화면과 첫 정상 적용 확인 뒤 POC5-05를 종료 기록한다. 실제 첫 매매·v2 저장·전량매도·다음 영업일 관찰을 새 종료 조건으로 추가하지 않는다.

코드 재작업·새 검증 라운드·목업 재확인·RESULT 재제출은 요구하지 않는다. 기존 10-12의 02/03 운영 확인과 10-23 공식 R0는 별도로 유지한다. POC5-06 수동 재진입 검토/ML 사후평가 설계는 배포 확인과 병행할 수 있으며, 사용자 평가 없는 알림도 사용한다는 계약을 유지한다.
