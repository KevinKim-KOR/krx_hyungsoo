## 2. 이번 목적과 완료 모습

사용자가 현재 가격 흐름과 함께 **거래량이 기존 관측에 비해 어느 정도인지** 확인할 수 있게 한다. 가격과 거래량을 함께 볼 재료를 추가하는 단계다.

- 「확인 근거」에서 보유 ETF를 선택하면 종목 상세에 거래량 기준일·거래량·비교 평균·배수가 보인다.
- 「오늘의 투자 점검」의 기존 KODEX200 정보 영역에는 KODEX200 거래량의 같은 관찰값을 보조 줄로 보인다.
- 새 메뉴·화면·갱신 버튼은 만들지 않는다. 기존 화면 조회에서 받은 값으로 표시한다.
- 가격 변화는 기존 표시를 유지한다. 거래량만으로 상승·하락 원인, 위험 등급, 매매 신호를 확정하지 않는다.

자료 저장 확인 근거는 대조표 P-10이다: PC etf_daily_price.volume에 ETF 자료가 있고 KODEX200도 저장 중이다. KOSPI 지수 표에는 거래량 칸이 없다. **KODEX200 거래량을 KOSPI 전체 거래량으로 부르지 않는다.**

## 3. 표시값과 계산

이 단계의 평균은 **“직전 20개 저장일 평균”**으로 이름 붙인다. 모든 거래일이 연속으로 확보됐다고 가정하는 20거래일 평균이나 최적 투자 기간으로 설명하지 않는다.

| 표시 | 정의 |
|---|---|
| 거래량 기준일 | 해당 ETF의 저장 가격 자료에서 가장 최근 날짜 D. 거래량이 없는 경우에도 더 오래된 날을 최신으로 대체하지 않음 |
| 거래량 | 날짜 D에 저장된 volume. 유효한 0은 0으로 표시 |
| 직전 20개 저장일 평균 | D를 제외한 바로 앞 20개 서로 다른 저장 가격 날짜의 거래량 산술 평균. 날짜와 자료 창은 그 ETF 기준 |
| 평균 대비 | 날짜 D 거래량 ÷ 위 평균. %가 아니라 배수 |
| 자료 설명 | 기준일·출처 및 비교 구간 시작/끝. 평균용 유효 자료 수를 함께 제공 |

예시: 기준일 거래량 150만, 직전 20개 저장일 평균 100만이면 “평균 대비 1.50배”다. 이 예시가 위험 또는 상승 신호의 임계값은 아니다.

- 평균은 앞선 20개 저장일 모두 거래량이 유효할 때 계산한다. 값이 없거나 음수·유한수가 아닌 값은 유효 자료로 세지 않는다. 누락을 0으로 채우거나 창 밖의 더 오래된 날로 메우지 않는다.
- 평균용 자료가 부족하면 실제 기준일 거래량은 표시하고 평균·배수는 “자료 부족”으로 둔다. 확보 수는 N/20으로 알린다.
- 기준일 거래량이 없으면 그 값과 배수는 “자료 없음”이다. 평균은 계산 가능하면 표시할 수 있다.
- 평균이 0이면 평균 0을 표시하고 배수는 “계산 불가”로 둔다.
- 계산은 원래 숫자로 하고 마지막 표시에서만 반올림한다. 비교 평균·배수는 소수 둘째 자리로 표시한다. 거래량 단위는 저장 자료의 실제 단위를 PLAN에서 확인해 명시한다.
- 기준일을 포함한 평균, 달력상 20일, 이미 계산된 다른 연구 지표로 임의 대체하지 않는다. 기존 계산 함수가 위 정의와 같으면 재사용할 수 있다.

이 비교 창은 저장 자료를 설명하기 위한 간단한 기준이다. 종합 위험 감지나 ML 성능 검증을 먼저 통과해야 숫자를 보여줄 수 있다는 조건은 만들지 않는다.

## 4. 구현 경계

- 기존 PC 시장 DB의 ETF 거래량을 조회한다. 새 수집·DB·테이블·적재·research artifact·의존성은 추가하지 않는다.
- 기존 GET /holdings/market-evidence/latest 및 GET /market/topn/latest의 **PC 화면용 응답에 선택 필드**를 보완하는 방향이다. 새 API 경로는 만들지 않는다.
- 조회 대상은 보유 ETF와 KODEX200이면 충분하다. 요청 때 전체 ETF를 다시 수집하거나 전수 계산할 필요는 없다.
- 두 화면은 같은 거래량 계산 정의를 사용한다. API 전용 조립에서 붙여 PUSH 본문·선정·원장·운영 artifact·가격 계산을 바꾸지 않는다.
- 거래량 자료가 없다고 기존 가격·NAV·차트·정렬을 가리지 않는다. 거래량 영역에만 실제 자료 상태를 표시한다.
- 오래된 자료는 기준일을 분명히 보인다. 수동 갱신의 횟수·사용 시간·대기시간 제한이나 자동 갱신을 이번에 추가하지 않는다.
- API·실행 호출자 대조에서 OCI 영향이 없도록 변경 위치를 정한다. 불가피한 OCI 실행 경로 변경이 확인되면 그 지점만 PLAN에 보고한다. 당연히 OCI 배포가 필요하다고 가정하지 않는다.

## 5. 화면과 안내 문구

기존 상세·시장 카드 양식을 따른다. 숫자 네 항목은 같은 폭으로 정렬하며 한 줄이 부족하면 두 줄로 배치한다. 긴 설명은 기준일·출처 줄과 짧은 도움말로 둔다. 새 버튼·설정 창은 필요 없다.

KODEX200 영역은 “KODEX200 거래량”, 보유 상세는 해당 ETF의 거래량임을 명시한다. 가격 자료와 거래량 자료의 기준일·출처가 다르면 각각 구분해 표시한다.

P-10의 낡은 “거래량 자료 미저장” 문구는 이번 구현의 실제 제공 범위에 맞게 정정한다. ETF·KODEX200 관찰값 제공과 KOSPI 지수 거래량 미저장을 나눈다. 두 안내 카드 전체 삭제나 다른 미구현 기능 폐기는 이 단계에 넣지 않는다.

## 6. 개발 PLAN에 필요한 확인

대조표로 저장 여부는 확인했다. PLAN은 다음 변경 지점만 확인해 작성한다.

1. volume의 실제 단위·최근 날짜와 조회 함수, 기존 비교 함수의 정의 일치 여부.
2. 두 기존 API 응답의 필드 추가 위치와 화면 타입. 공유 PUSH 호출에 영향이 없는 위치.
3. 보유 종목 수 규모의 조회 소요와 선택한 화면 배치의 작은 표시 예.
4. 정상 계산·현재일 제외·자료 부족·0·값 없음의 시험 및 기존 화면 값 보존 확인.

전체 백로그 재조사·새로운 운영 감사·대규모 성능 체계를 만들지 않는다. 사실과 맞지 않는 요구가 있으면 해당 차이만 보고하고 관련 없는 준비는 계속한다.

## 7. 검증·종료·백로그 처리

계산 예와 자료 부족 분기, 화면의 종목·단위·기준일, KOSPI 거래량으로 오인하지 않는 표시, 기존 관찰값·선정 불변을 검증한다. 검사는 변경 범위와 저장소 필수 절차에 맞추며 OCI 실거래일 확인이나 라이브 파일 전수 해시를 새 조건으로 추가하지 않는다.

기존 PLAN 판정 → 구현·검증 → RESULT → 사용자 실화면 확인의 절차로 진행한다. 새 기능 숫자·문구는 실화면에서 확인한다. API 전용 PC 변경으로 구현되면 OCI pull·거래일 대기가 필요 없다.

BACKLOG·STATE·PROGRAM_TRUTH·통합지도에는 P-10의 **ETF·KODEX200 저장 거래량 관찰 근거 제공분**이 해소됐다고 기록한다. KOSPI 전체 거래량이나 종합 위험 구간 분류까지 개발 완료로 처리하지 않는다. 10-23 R0는 별도로 유지한다.

### 2. Q-A — 배수 사유 우선순위

추천안을 수용한다. 배수 칸은 다음 우선순위로 하나를 표시한다.

1. 기준일 거래량 없음 → “자료 없음”
2. 평균용 유효 자료 20개 미만 → “자료 부족”
3. 평균 0 → “계산 불가”

평균 칸은 자기 상태와 N/20을 따로 보인다. 가격 행 자체가 없으면 “거래량 자료 없음” 한 줄이라는 계획을 수용한다. 0 거래량은 유효값이며 평균이 양수이면 배수 0으로 표시한다.

### 4. Q-C — PC 가격 근거의 날짜 정정

선택지 **(b)를 우선 적용**한다. 다만 날짜 표시만 붙이는 데 그치지 않고, 다른 날짜의 값을 현재 비교·우선 점검에 쓰지 않도록 정정한다. 기존 결함 ID DEF-PRICE-EQUITY-REFRESH를 재개하고 PC 화면 영향을 기록한다.

#### 4-1. 기준일을 계산 입력과 연결

- 종목별 5일·20일 가격 흐름의 실제 계산 기준일을 표시한다. KODEX200 비교의 실제 기준일과 기간도 연결한다.
- 기준일은 실제로 계산에 쓴 이력에서 가져온다. 전체 DB 최신 날짜를 그 종목의 날짜로 대신하지 않는다.
- PC 공통 비교 기준은 기존 KODEX200 가격 흐름에 사용한 저장 자료 기준이다. 무조건 오늘이나 기대 직전 거래일과 같아야 한다는 새 조건은 만들지 않는다.
- 모든 ETF가 10-08 자료인 상태라면 “PC 저장 가격 기준일 10-08”을 분명히 보인다. 기준일이 다른 개별주는 따로 구분한다. 날짜 예는 이번 실측이며 코드에 고정하지 않는다.

#### 4-2. 「확인 근거」의 현재 값과 역사 자료 구분

- 종목 기준일이 PC 비교 기준일과 다르면 현재 점검 표의 5일·20일·KODEX200 대비를 정상 비교값처럼 표시·정렬하지 않는다. 해당 칸은 “—”, 행은 “자료 확인 필요”로 구분한다.
- 상세에는 “저장 가격 기준일: 2026-08-12 / PC 비교 기준일: 2026-10-08 — 기준일이 달라 현재 비교에 사용하지 않습니다.” 같은 실제 날짜의 사유를 표시한다.
- KODEX200 대비는 같은 비교 기간의 시작·끝 날짜일 때만 유효하다. 기간이 다르면 비교값을 비워 둔다. 기존 계산 기간을 추적하며 새 기간 산식은 만들지 않는다.
- 보유 행·수량·평단·보유 시세·NAV·과거 가격 차트는 유지한다. 이 지시는 가격 흐름의 현재 비교 가능성에 한정한다. 저장 이력을 삭제하거나 보유 자체를 제외하지 않는다.

#### 4-3. 「오늘의 투자 점검」 최대 3개

- PC 비교 기준일에 맞는 유효 가격 흐름 후보만 기존 선정 함수에 넘긴다. 그 후보 안에서 기존 5일 변화·동점 규칙으로 최대 3개를 채운다.
- 이미 고른 3개에서 오래된 종목만 지워 자리를 비우는 방식은 피한다. 정상 후보가 충분하면 기존 규칙으로 다음 종목을 채운다.
- 같은 기준일의 ETF들이 있을 때 08-12 SK하이닉스 수치가 현재 약세 우선 목록에 들어가지 않아야 한다.
- 제외된 종목은 자료 확인 사유로 보인다. 과거 하락값을 현재 위험 경보로 다루지 않고, 제외를 정상·안전 판정으로 표현하지 않는다.

#### 4-4. PC 전용 변경 경계

API의 응답 사본·PC용 조립에서 날짜와 비교 가능성을 보완한다. 필요하면 해당 응답 사본의 현재 비교값을 null과 사유로 정규화한다. PC 최대 3개 생성 위치와 후보 전달 위치는 추가 PLAN에 명시한다.

공유 builder·OCI PUSH 선정 함수·운영 원장·가격 DB 원본을 바꾸지 않는다. 실제 보유·매매 이력·갱신 버튼 제한도 변경하지 않는다. 거래량은 자기 저장 기준일을 그대로 표시할 수 있으며 오래된 개별주 값은 과거 저장 자료임을 구분한다.

### 5. 거래량 구현안의 나머지 수용 및 작은 보완

기준일 제외·직전 20개 저장일·0 유효·자료 부족 처리·두 API 조립에서 선택 필드 추가·공용 표시·실제 폭 목업을 수용한다. 보유 개별주 3종목의 기존 저장 거래량까지 보여주는 것도 수용하되, 자산을 ETF로 재분류하지 않고 §4의 날짜 설명을 적용한다.

### 2. 09 검증에서 추가로 확인할 두 가지

#### 2-1. 계산값과 날짜가 같은 입력에서 나오는가
RESULT §5-3은 공유 builder 계산 뒤 가격을 다시 읽어 날짜를 붙이며, 두 읽기 사이 갱신 가능성을 인정한다.
그러면 이전 가격으로 계산한 변화율에 새 날짜를 붙여 정상 비교값으로 받는지 확인해야 한다.
이 계약은 '실제 계산 이력의 날짜'를 표시하는 것이다. '드문 경우 · 재조회로 맞춰짐'만으로는 한계를 수용하지 않는다.

검증자는 두 읽기 사이 가격이 바뀌는 경우를 작은 fixture로 재현하거나 실제 데이터 전달 경로로 입증한다.
값과 날짜가 어긋나면 09에서 정정한다. 같은 계산 입력의 날짜를 전달하거나 기존 읽기를 재사용하는 최소 변경을 우선한다.
별도 동시성 관리 체계는 요구하지 않는다. 뒤에 다시 읽은 날짜만으로 기존 값이 최신임을 보장했다고 처리하면 안 된다.
추가 변경이 공유 경로에 닿으면 영향 범위를 결과서에 명시하고 PUSH·초안의 기존 결과가 유지됨을 확인한다.

#### 2-2. 최대 3개의 비중·손익은 종목 합산값으로 표시
RESULT §5-6의 KODEX200 사례는 확인된 표시 오류다.
같은 종목이 여러 계좌에 있으면 「확인 근거」에서는 14.0% · +23.88%인데, 최대 3개에서는 첫 계좌의 1.5% · −2.82%를 보인다.

다음 범위로 09에서 보완한다.
- 「확인 근거」가 쓰는 기존 종목별 합산 규칙·함수를 재사용한다.
- 비중 = 그 종목의 전체 계좌 평가금액 / 전체 보유 평가금액. 최대 3개만을 분모로 삼지 않는다.
- 손익률 = (종목 합산 평가금액 − 종목 합산 매입금액) / 종목 합산 매입금액.
- 계좌별 손익률을 단순 평균하거나 합산하지 않는다. 결측·부분 자료는 기존 합산 규칙을 따른다.
- 바꾸는 것은 PC 최대 3개에 표시하는 비중·손익이다. 후보 조건·5일 변화 정렬·최대 3개 규칙·PUSH 공유 선정은 유지한다.
- 기존 응답·보유 자료를 연결하며 새 조회나 API를 추가하지 않는다. 보유 수량·평단·계좌 기록은 바꾸지 않는다.

한 종목에 이익 계좌와 손실 계좌가 함께 있는 사례에서 두 화면의 합산값 일치를 확인한다.
이 범위 추가는 본 문서로 승인한다. 별도 PLAN 판정 회차를 만들 필요는 없다.

### 3. 09 기존 요구의 검증 범위
- 기준일이 다르면 자기 변화율과 대비값을 비우고 최대 3개를 다시 고른다.
- 기준일은 같고 비교 기간만 다르면 해당 대비값만 비운다. 자기 5일 값이 유효한 종목은 후보에 남는다.
- 날짜는 오늘 또는 T-1을 강제하지 않고 실제 PC 저장 계산 기준을 쓴다.
- 거래량 평균은 기준일을 제외한 직전 20개 저장일이다. 0은 유효하며, 무효 값을 빼고 더 오래된 날로 채우지 않는다.
- 거래량 출처는 기준일 행에서 얻는다. 배수 사유 우선순위·옛 자료 표시·두 카드 문구는 기존 판정대로 확인한다.
- 응답 사본 정정 전후 공유 입력·PUSH·초안·원장·DB 쓰기 불변을 확인한다.

캐시 문제는 개발자 설명으로만 확정하지 않는다. 검증 소스 상태를 고정하고 변이 잔여 파일·캐시의 영향을 제거해 관련 시험을 확인한다.
통과한 전체 회귀를 이유 없이 여러 번 반복하지 않는다. 새 정정에 맞는 회귀와 필수 검사를 완료하면 된다.

### 4. 10 PLAN 질문에 대한 확정
| 질문 | 결정 |
|---|---|
| Q-1 단계 번호 | `POC5-10`으로 확정 |
| Q-2 보유 파일 읽기 실패 | 제안 (a). ETF 갱신은 유지하고 개별주 단계 실패를 따로 기록 |
| Q-3 결과 기록 | `market_refresh_log`의 별도 행 `holdings-equity-prices-<refresh_id>` 사용. ETF 시도·성공·실패 수와 합치지 않음 |

유효한 빈 보유 또는 대상 0종목은 정상적인 '대상 없음'이다. 보유 파일 읽기 실패를 빈 보유로 대체하지 않는다.
실패는 기존 화면의 `error_summary`에도 한국어로 알린다.
예: '보유 개별주 가격 갱신 일부 실패(N종목)' / '보유 목록을 읽지 못해 개별주 가격을 갱신하지 못했습니다'.
기술 식별자는 로그에 남기고 화면 설명에는 위 문구를 쓴다.
별도 로그 행이 기존 '마지막 전체 갱신' 조회·ETF 건수·전체 작업 ID를 잘못 대체하지 않는지도 확인한다.
그 문제가 있으면 해당 조회의 행 구분만 보완한다. 새 로그 체계·표는 만들지 않는다.

### 5. 10 구현 경계와 완료 확인
- 대상은 현재 보유 − ETF master, 중복 제거. 개별주를 ETF master에 넣지 않는다.
- 기존 `refresh_approved_prices`에 PC DB 경로와 같은 갱신 작업의 `end_date`를 전달한다.
- 기존 마지막 저장일부터 증분 수집한다. 경계일 중복 조회·upsert는 기존 방식대로 허용한다.
- 누락 구간을 받으며 최신 하루만 붙이지 않는다. 실제 반환 자료 없이 기준일을 앞당기지 않는다.
- 공유 수집 함수 본문·OCI 운영 상태·cron·PUSH는 바꾸지 않는다. 재사용 함수가 지정한 PC DB와 로그만 쓰는지 확인한다.
- 추가 대상은 현재 3종목이다. 내부 외부 요청 수가 반드시 3번이라고 단정하는 PLAN 표현은 고친다.
- 자동 갱신·새 버튼·수동 갱신 횟수 제한·FDR 시간 상한은 이번에 추가하지 않는다.

시험은 격리 DB와 가짜 수집기로 한다. 대상 선정·증분 구간·종목별 실패·보유 읽기 실패·대상 없음·로그 구분을 확인한다.
09의 날짜 판정과 연결해 날짜가 맞으면 복귀하고, 실패해 옛 자료가 남으면 계속 비교에서 빠지는지 확인한다.
실제 수집은 사용자의 기존 갱신 버튼 1회로 확인한다. 실제 저장 날짜·누락 구간·화면을 확인한 뒤 수집 원인 결함을 닫는다.
