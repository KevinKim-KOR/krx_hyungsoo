## 1. 완료 모습과 범위

| 리포트 | 답할 질문 | 하지 않는 판정 |
|---|---|---|
| R0 | 실행·item·전달·가격 결과가 계약대로 연결되고 쌓이는가 | 투자 신호의 좋고 나쁨 |
| R1 | 당시 상태 뒤 +1/+5/+20의 원시 가격 분포가 어떠했는가 | 추천 적중률·성공/실패·매매 지시 |

V1은 PC의 수동 읽기 전용 CLI와 Markdown·JSON 출력으로 만든다. 새 화면·메뉴·API·DB·cron·자동 SSH·외부 조회·신규 의존성을 추가하지 않는다. 사용자가 매일 평가하거나 리포트를 실행할 필요는 없다.

원장 snapshot과 계산된 outcome을 소비할 뿐, 01B 실행·02 성숙·03 동기화·피드백 저장 코드를 바꾸지 않는다. 기존 자료를 다시 채우거나 outcome을 UPDATE하지 않는다.

## 2. 입력과 재현성

- 기본 입력은 03이 동기화한 PC 원장 사본이다. 입력 DB는 `mode=ro`와 단일 읽기 트랜잭션으로 읽는다.
- 공식 R0의 OCI runtime 대조 근거는 기존 01B 대조 CLI의 읽기 전용 결과를 개발자가 제공한다. 새 리포트는 SSH를 자동 실행하지 않는다.
- PC `runtime_state.sqlite`를 OCI 실행 근거로 대신 쓰지 않는다. OCI 대조 근거가 없거나 기간이 다르면 `RUNTIME_RECONCILIATION=NOT_CHECKED`다.
- 원장 시점·동기화 성공 시각·cohort 시작 meta·계약 버전·행 수·대조 근거의 기간/시각을 출력한다.
- report 종료일은 사용자가 지정하거나 마지막 완료 한국 거래일을 사용한다. 오늘 장중을 완료 일자로 간주하지 않는다.
- 날짜 축은 02에서 확정한 운영 거래일 캘린더를 사용한다. 가격 행 유무로 휴장일을 추정하지 않는다.
- report 버전·입력 행 snapshot의 결정적 digest·필터·bootstrap 설정을 함께 기록한다. 같은 입력과 설정이면 통계값이 같아야 한다.
- 입력 digest에는 보고서가 사용하는 최신 사용자 평가도 포함한다. 평가를 추가·변경하면 digest와 평가 부가 표는 달라질 수 있으나, 원시 가격 표본·가격 통계·bootstrap 값은 같아야 한다. 별도 hash 체계를 추가하지 않는다.
- 출력 파일 위치는 PLAN에서 기존 artifact 관례를 따른다. DB에는 리포트나 성공 이력을 쓰지 않는다.

## 3. R0 시점과 상태

- PRIMARY 시작은 원장의 시작 meta를 정본으로 한다. 보고된 첫 활성일은 2026-10-08이며 설계서 상수로 고정하지 않는다.
- 공식 R0는 시작일을 포함해 **완료된 한국 거래일 자료 10일**이 쌓이고 마지막 일자의 가격 배치가 끝난 뒤 실행한다. 정확한 날짜는 운영 캘린더로 계산한다.
- PLAN의 운영 캘린더 조사에 따른 D10=2026-10-22, 실행 예정=2026-10-23 09:30 이후를 수용한다. 이 시각은 실행 계획이며, 시계가 09:30을 넘었다는 사실이나 그 뒤 동기화했다는 사실만으로 배치 완료를 대신하지 않는다.
- 실제 report 종료일에 해당하는 가격 배치의 완료 시각·상태를 기존 `--ops-evidence`에 기록하고, 그 뒤 동기화한 PC 사본을 사용한다. `--end`가 D10보다 늦으면 그 종료일의 배치와 사본을 확인한다. 기존 status·로그를 읽어 개발자가 제공하며 새 cron·SSH 호출·DB 표·완료 감시 기능은 만들지 않는다.
- 그 전에도 동일 CLI를 개발·진단에 사용할 수 있다. 상태는 `NOT_READY`이며 R0 완료로 기록하지 않는다.
- 시작 meta가 없거나 OCI 대조가 빠지면 원시 점검표는 출력하되 공식 R0 완료 판정을 하지 않는다.
- +20의 성숙 완료는 R0 조건이 아니다. 아직 도래하지 않은 horizon은 정상 대기다.

R0의 판정은 `COLLECTION_OK / CHECK_REQUIRED / NOT_READY`다. `COLLECTION_OK`는 수집 계약 점검 결과이며 투자 효과를 뜻하지 않는다.

대조 근거가 없거나 읽을 수 없거나 시작·기간 정보를 확인할 수 없으면 `RUNTIME_RECONCILIATION=NOT_CHECKED`다. 유효한 대조 결과가 누락·STARTED·원장에만 있는 실행 등을 보고하면 해당 건수·ID를 보존하고 `CHECK_REQUIRED`로 처리한다. `status!=OK`라는 이유만으로 검출된 오류를 `NOT_CHECKED`로 버리지 않는다. 정상 대조와 확인된 배치·운영 오류를 함께 기록하되, 실제 오류를 `COLLECTION_OK`로 처리하지 않는다.

기존 대조 CLI는 누적 결과이므로 `floor`와 개발자가 붙인 `captured_at`을 실제 근거 기간으로 명시한다. report 종료일까지 포함하는 더 넓은 누적 구간의 정상 결과는 대조 근거로 수용한다. 그 뒤 실행까지 포함한 오류 건수를 종료일 이전의 정확한 오류 건수로 표현하지 않는다. 오류가 보고되면 실제 대조 기간과 함께 점검 대상으로 남긴다.

## 4. R0 점검표

1. 기존 OCI 대조: runtime ↔ ledger 연결·누락·원장에만 있는 실행·종료 미확정 STARTED. 모집단을 ledger에 이미 있는 행으로만 좁히지 않는다.
2. 날짜·kind별 실행 건수: 예정 시각과 실제 기록을 대조한다. 조건상 미발송인 `skipped/no_selection`도 정상 실행 기록에 포함한다.
3. 무결성: orphan item·delivery·outcome, 중복 키, FINALIZED와 delivery 관계, 계약 버전·cohort 분리.
4. 가격 결과: 예상 item/series/horizon 슬롯과 MATURED·PENDING·T0_MISSING·PRICE_MISSING·UNTRACKED_AFTER_EXIT·UNSUPPORTED_PRICE_SOURCE 건수.
5. PENDING: 평가일 미도래와 평가일 도래 후 대기를 나눠 표시한다. 기존 21/31거래일 채우기 창 안의 대기를 영구 결측으로 바꾸지 않는다. `PENDING_DUE`는 '평가일 도래·결과 미기록'이며, 행이 없다는 것만으로 원인이 정상 뒤채우기 대기라고 확정하지 않는다. 사본에서 확인할 수 없는 원인은 미확인으로 남기고 기존 배치·오류 근거와 함께 보고한다.
6. 운영 대조: 기존 배치 status·원장 오류·PUSH 동작에 대한 개발자의 읽기 전용 확인을 함께 기록한다. 보고서 생성만으로 전체 PUSH 회귀를 새로 실행하지 않는다.

예상 가격 슬롯·결과 대상은 02·03의 실제 계약을 재사용한다. index_group의 여러 ticker 때문에 item 수×3으로 단순 계산하지 않는다. 자료 부족·미지원·매도 뒤 미추적은 별도 상태이며 무조건 수집 실패로 합산하지 않는다.

공식 R0에서 누락·미종료·참조 오류가 있으면 `CHECK_REQUIRED`와 구체적인 키/건수를 남긴다. 행을 자동 수정하거나 과거 outcome을 다시 만들지 않는다.

## 5. R1 표본 계약

- 기본: `FINALIZED AND PRIMARY_LIVE AND off_schedule=0`의 가격 결과 대상 item.
- 표는 저장된 exposure에 따라 `PRIMARY`(주 표) · `SECONDARY`(보조 표) · `NONE`(별도 표)의 세 구분으로 낸다. `NONE`은 보고서에서 SQL NULL을 표시하는 키이며 문구는 **'노출 분류 없음'**이다. 현재 상태를 다시 계산해 exposure를 재분류하거나 원장의 NULL을 변경하지 않는다.
- not_selected·시장·기초지수 등 exposure가 NULL인 가격 결과 대상도 `NONE` 표에 포함한다. PRIMARY와 합치지 않고, 원장의 최초 신호·반복 신호 분류가 적용되지 않았음을 표시한다. NULL이 투자 판단의 부정·무평가·결과 대상 아님을 뜻하지 않는다. evaluable·subject 등 가격 결과 대상 조건은 기존 02 계약대로 별도 적용한다.
- **관측 분포**: sent·suppressed·cut·not_selected의 평가 가능한 항목을 포함한다.
- **전달된 본문 항목 분포**: `disposition=sent AND delivery_status=sent`만 별도 집계한다. partial은 실제 전달된 item 범위를 알 수 없으므로 별도 건수로 둔다.
- 관측과 전달 집계는 알림 효과의 인과 비교가 아니다. 잘림·억제에 가격 결과가 있어도 사용자가 수신했다고 가정하지 않는다.
- LEGACY_DIAGNOSTIC·off_schedule·evaluable=0은 PRIMARY 가격 분포에 섞지 않고 제외 사유 건수를 남긴다.
- **user_feedback 0행은 제외 조건이 아니다.** 필요하면 평가 있음/없음 건수와 선택 평가 분포를 부가 정보로만 낸다. 평가 완료율을 사용자 과제로 만들지 않는다.
- 반환값 통계는 `status=MATURED`만 계산한다. 나머지 상태와 대기를 분모에서 숨기지 않고 건수로 함께 보고한다.

그룹은 `push_kind · subject 유형 · state · contract_version · price_basis · horizon`을 기본으로 한다. PRIMARY/SECONDARY/NONE과 관측/전달 구분도 유지한다. 시장 SP500 상태 옆에는 KOSPI 원시 결과를 두며 방향 채점을 하지 않는다.

index_group의 ticker별 outcome은 개별 가격 관측으로 유지한다. 그룹 평균 가격 계열을 만들지 않는다. `n_event / n_item / n_price_observation / n_signal_date`를 따로 표시해 여러 ticker를 여러 독립 알림으로 세지 않는다.

## 6. R1 출력과 날짜 블록

- 각 그룹/horizon: 성숙 건수·미성숙/상태 건수·원시 수익률 평균/중앙값/25·75분위·최소/최대.
- 0건은 통계 NULL, 1건은 그 관측값으로 표시한다. 분위는 정렬값의 `(n-1)×p` 위치를 선형 보간하며 bootstrap percentile에도 같은 규칙을 쓴다.
- `max_up_raw / max_down_raw`의 중앙값도 별도로 낸다. 원시값은 저장된 값을 사용하고 표시용 반올림만 한다.
- 성공 임계·양수 비율 적중률·모델 점수·상태별 유리한 방향은 만들지 않는다. KRX 무조정 계열의 분배락 포함 특성은 가격 기준으로 표시한다.
- 알림 단위 독립 bootstrap은 사용하지 않는다. 사건의 `runtime_date_kst`를 묶음으로 하고 연속 한국 거래일 블록을 재표집한다. 같은 날짜의 모든 item/ticker는 함께 움직인다.
- 날짜 축에서 알림 없는 날을 삭제해 비연속 날짜를 이어 붙이지 않는다. 빈 날짜는 빈 묶음이며 수익률 0으로 채우지 않는다.

V1 기본은 moving-block bootstrap, 평균 수익률의 percentile 95% 구간, `block_days=max(5,horizon)`, 1,000회, 고정 seed=0이다. 블록 길이·회수·seed는 report에 명시한다.

- 해당 그룹의 성숙 결과가 있는 서로 다른 사건 날짜가 `2×block_days` 미만이면 구간은 NULL, `INSUFFICIENT_SAMPLE`로 출력한다. 단순 기술통계와 건수는 계속 낸다.
- 재표집에서 계산 불가 표본이 생기면 그 사실을 명시하고 정상 구간으로 위장하지 않는다. 단독 행 bootstrap으로 대체하지 않는다.
- 이 기준은 V1의 출력 보류 규칙이며 통계적 충분성을 보장하는 표본 수 공식이 아니다. 구간을 신호의 PASS/REJECT나 매매 판단으로 사용하지 않는다.
- block 알고리즘 참고: D. N. Politis, *The impact of bootstrap methods on time series*, §2.2–2.3, https://math.ucsd.edu/~politis/impactBOOT.pdf . 위 기본 수치와 날짜 묶음은 이 프로젝트의 설계 선택이다.

## 7. 사용자 평가·ML 경계

- 명시적 사용자 평가는 도움이 됐는지의 선택 정보다. 무평가를 중립·부정·모델 라벨로 대입하지 않는다.
- 같은 event의 반복 평가를 여러 독립 알림으로 세지 않는다. 평가를 요약할 때는 snapshot 시점의 최신 평가만 쓰며 기존 이력은 보존한다.
- R1은 저장된 원시 결과를 보여 주는 리포트이며 ML 사후평가 모델 자체를 실행하지 않는다.
- 향후 ML은 당시 근거를 입력 후보, 이후 가격 결과를 결과 자료로 사용한다. 사용자 평가가 있으면 별도 평가 근거로 함께 쓰고 없어도 해당 기록을 사용할 수 있다.
- 원시 snapshot을 바꾸거나 이후 수익률·사후 평가를 당시 예측 입력으로 소급하지 않는다. 구체적인 적절성 목표와 학습/시험 분리는 후속 ML PLAN에서 정한다.

## 8. 수용 기준

1. 임시 원장·대조 근거로 연결 정상/누락/STARTED/orphan과 NOT_READY가 정확히 구분된다.
2. +20 미도래와 채우기 창 안의 대기를 가격 결측·수집 실패로 오인하지 않는다.
3. 다중 ticker·PRIMARY/SECONDARY/NONE·관측/전달·partial·LEGACY·off_schedule 분모가 정확하다. not_selected와 시장의 NULL exposure가 빠지지 않는다.
4. feedback을 없애거나 추가해도 원시 가격 표본·통계가 바뀌지 않는다. 입력 digest와 평가 부가 표의 변경은 허용한다. 조회가 feedback을 생성하지 않는다.
5. 알려진 값 fixture의 평균·분위·max_up/down 요약이 맞고 같은 입력/seed의 결과가 같다.
6. bootstrap은 날짜 묶음과 연속 거래일 블록을 보존하며 소표본에서 구간을 만들지 않는다.
7. report 생성 전후 입력 DB·원장 행·기존 라이브 파일이 불변이고 SSH·Telegram·외부 조회가 0건이다.
8. 마지막 전체 회귀·정적 검사·KS-10을 통과한다. 별도 사용자 화면 테스트는 없다.

### A. 지시문 외 변경 5건 — 모두 수용

| 변경 | 판정과 의미 |
|---|---|
| 실행 failed · 전달 failed/partial → CHECK_REQUIRED | 수용. 이미 기록된 운영 실패·불완전 전달을 점검 대상으로 남긴다. 오류가 충실하게 수집됐더라도 운영 점검이 필요할 수 있다. CHECK_REQUIRED는 원장 수집 결함 확정이나 이번 개발의 REJECT를 뜻하지 않는다. |
| ops_error_count 필수 | 수용. 공식 R0에서 운영 오류 확인 근거가 없으면 NOT_READY, 양수이면 CHECK_REQUIRED. 기존 읽기 전용 확인을 텍스트로 제공하는 범위이며 신규 수집기·자동 감시·독립 검증 절차는 추가하지 않는다. |
| 운영 메모 가리기 | 수용. 비밀값 노출을 줄이는 최소 처리이며 전문적인 비밀 탐지 기능으로 확대하지 않는다. |
| --end 형식·오늘 이전·거래일 검사 | 수용. V1의 완료 거래일 보고 범위와 일치한다. |
| 기존 비공개 helper 재사용 | 수용. 대상·슬롯 규칙의 중복을 피하고 02 코드를 바꾸지 않는 범위다. |

정상적인 skipped/no_selection·반복 억제·상한 제외는 운영 실패로 추가 분류하지 않는다. 과거 failed/partial 기록을 지우거나, 이미 확인한 실패를 COLLECTION_OK로 바꾸려고 같은 기간을 반복 점검하지 않는다. 확인할 원인·영향·현재 조치 상태를 공식 R0 보고에 남긴다. 자동 수정·재발송·PRIMARY 시작일 재설정은 하지 않는다.

### B. r1 정정과 알려진 한계 — 현행 V1 수용

- 필수 사본 표 누락과 생성 기록 뒤 결과 표 소실을 손상으로 구분한 정정을 수용한다. 결과 표 생성 전의 정상 대기와 분리되며, R0 CHECK_REQUIRED / R1 invalid_input은 적절하다.
- iterations 1 미만을 거부하는 정정을 수용한다. 재표집을 하지 않은 계산을 OK로 표시하지 않는다.
- 계산 불가 재표본이 하나라도 있으면 구간을 NULL(RESAMPLE_UNDEFINED)로 두는 보수적 구현을 수용한다. 기술통계는 계속 표시하며, 구간 부재가 개발 종료나 후속 설계를 막지 않는다.
- 근거 텍스트의 진위는 도구가 검증하지 않으며, 누적 대조의 실제 범위와 종료일 뒤 포함 여부를 밝히는 한계를 수용한다. 서명·추가 대조 서비스·CLI 변경을 요구하지 않는다.
- digest는 입력 원장 행과 최신 평가를 대상으로 하고, 근거·캘린더·동기화 시각은 별도 출처 정보로 밝히는 현재 범위를 수용한다. digest를 실행 환경 전체의 동일성 증명으로 설명하지 않는다.
- 비거래일 관측이 있는 경우 기술통계에는 포함되지만 bootstrap 거래일 축에는 빠진다는 한계를 수용한다. n_matured_outside_axis가 양수인 보고서의 구간은 거래일 축 자료를 재표집한 범위이며, 비거래일 관측까지 포함한 전체 평균의 구간으로 해석하지 않는다. 이 V1 한계를 결과서에 보존하며 별도 코드 재작업을 요구하지 않는다.
