## 1. 이번에 만드는 것

「종목 관리」에서 기존 보유의 **가격 비교 기준일**을 일괄 설정하고, History에서 기간별로 수정·해제할 수 있게 한다. 사용자가 제안한 `2026-01-02`를 초기 입력값으로 보여 준다. 저장은 사용자가 실행한다.

| 구분 | 의미 |
|---|---|
| 실제 매수일 | 실제 BUY 기록의 거래일. 기존 BASELINE·REGISTER 기간에서는 계속 미상 |
| 가격 비교 기준일 | 사용자가 정한 종가 비교의 출발점. 그날 보유했다는 증거가 아님 |
| 수량·평단 | 기존 기준잔고와 실제 거래·입력 정정에서 계산. 기준일 설정으로 변경하지 않음 |

`2026-01-02` BUY를 만들어 넣지 않는다. 현재 잔고를 그날의 잔고로 간주하거나 ‘2026년 투자 수익률’·당시 매수금액을 계산하지 않는다. 현재 보유 수익률·실현손익은 기존 계산을 사용한다.

## 2. 화면과 설정 대상

- 기존 보유 표에 **[가격 비교 기준일 설정]**을 둔다. 새 메뉴는 만들지 않는다.
- 창에는 날짜 한 칸, 대상 보유와 건수, **[설정]**을 표시한다. 종목·계좌를 확인할 수 있고 기존 폼의 폭·정렬을 재사용한다.
- 기본 대상은 현재 보유 중 BASELINE·REGISTER로 시작했고 기준일이 없는 기간이다. 이미 설정된 기간은 일괄 설정에서 덮어쓰지 않는다. 대상이 없으면 안내만 표시한다.
- 설정 대상은 화면에서 확인한 position_id·cycle_id로 고정한다. ‘32줄’은 보고 당시 수치이며 실행 시 최신 상태로 확인한다. 다른 계좌·복수 보유 줄을 합치지 않는다.
- History의 해당 기간에 **‘실제 매수일: 미상’**, **‘가격 비교 기준일: 2026-01-02’**, **[수정/해제]**를 함께 표시한다. 날짜가 없어도 기존 History와 매매는 정상 동작한다.
- 종료된 BASELINE·REGISTER 기간도 History에서 설정할 수 있다. 재매수로 만든 새 기간에는 이전 기준일을 복사하지 않는다. 실제 BUY로 시작한 기간은 기존 거래일 표시·시장 흐름을 유지한다.
- 기준일은 유효한 YYYY-MM-DD이며 KST 오늘 이하로 받는다. 가격이 없는 날이라는 이유로 설정 자체를 거절하지 않는다. 해제는 날짜 없음으로 되돌린다.

## 3. 저장과 호환

정본은 기존 `state/holdings/holdings_latest.json` 한 문서다. 새 DB나 별도 기준일 파일을 만들지 않는다.

기존 `personal_trade_history.records`에 **REFERENCE_DATE** 종류를 추가한다. position_id·cycle_id와 기록 ID·저장 시각을 사용하고 payload는 `{reference_date: "2026-01-02"}` 또는 해제의 `{reference_date: null}`이다. 같은 기간의 마지막 설정 기록이 유효하다. 기존 BASELINE·REGISTER 원문은 수정하지 않는다.

- REFERENCE_DATE는 비교용 메타데이터다. BUY·SELL·ADJUSTMENT가 아니며 수량·원가·손익·거래 순서·기간 시작/종료 계산에 참여하지 않는다. 기존 거래 정정·취소의 대상에도 넣지 않는다.
- 존재하는 BASELINE·REGISTER 기간만 대상으로 받는다. 다른 position의 cycle이나 존재하지 않는 기간을 연결하지 않는다. 현재 유효한 기준일은 records에서 읽고 별도 정본으로 중복 저장하지 않는다.
- 기존 `holdings_store.commit`의 재시도 확인·revision·문서 검증·원자적 파일 교체를 재사용한다. 일괄 설정도 한 번의 저장으로 모두 반영하며 일부만 저장하지 않는다.
- 기존 다중 기록 저장 방식에 맞춰 요청 ID를 재사용한다. 같은 요청·같은 내용은 중복 추가하지 않고, 같은 ID·다른 내용은 충돌이다. 오래된 revision은 새로고침을 요청한다. 이 때문에 새로운 잠금·작업 큐를 만들지 않는다.
- v1 파일은 첫 명시적 설정 저장에서 기존 v2 전환을 재사용한다. 기존 가상 position_id·cycle_id를 보존하고 수량·평단을 유지한다. 조회·기동·History 열기는 파일을 바꾸지 않는다.
- 기준일 없는 v2 문서는 그대로 읽는다. 허용된 새 종류를 문서 무결성 검사·공용 읽기 경로가 함께 이해하도록 수정한다. 알 수 없는 종류를 일괄 무시하는 방식으로 검사를 느슨하게 하지 않는다.
- 현재와 같은 날짜를 다시 설정하거나 미설정 기간을 해제하는 동작은 변경 없음으로 처리한다. 기록을 추가하거나 revision을 올릴 필요가 없다.

기존 `/holdings/trade-history` 명령·조회에 최소 확장을 붙인다. 경로 추가 없이 구현하는 안을 우선한다. 정확한 요청·응답 필드와 다중 기록 재시도 연결은 PLAN에 현재 코드 기준으로 적는다.

## 4. 시장 흐름에 사용하는 방식

History의 기존 **[시장 흐름 보기]**를 누를 때만 사용한다. 실제 매수일을 모르는 기간은 가격 비교 기준일부터 마지막 저장일까지의 **종가 변화**를 보여 준다. 기준일이 없으면 매수 전후 변화는 계속 계산하지 않는다.

- 이름은 **‘가격 비교 기준일 이후 종가 변화’**다. ‘매수 후 수익률’·개인 실현손익으로 표현하지 않는다. `2026-01-02` 설정만으로 현재 수량·평단에 따른 당시 손익을 만들지 않는다.
- 종료된 기간은 기준일→매도 기준일, 매도 기준일→마지막 저장일을 각각 표시할 수 있다. 실제 매도가 없는 입력 정정 종료는 기존 동작을 유지하며 가상의 매도일을 만들지 않는다.
- 비거래일의 다음 거래일 처리, 실제 사용일 표시, ETF 저장 종가·KOSPI 비교·출처와 가격 기준 표시는 POC5-05 확정 계약을 재사용한다.
- 해당 기준일 가격이 없거나 종료일보다 늦으면 그 구간은 ‘비교 자료 없음’이다. 최신 저장일이 기준일보다 이른 경우도 같다. 인접 가격·다른 계열로 메우지 않는다. 개별주 자료 없음도 기존대로 표시한다.
- 실제 매수일이 있는 기간의 계산은 바꾸지 않는다. 기준일 때문에 새 가격 수집·외부 조회·과거 보유 정기 flow를 추가하지 않는다.

## 5. OCI·원장·ML 영향

OCI로 보내는 데이터는 기존 현재 보유의 허용 5필드뿐이다. REFERENCE_DATE·개인 이력·ID는 보내지 않는다. 기준일만 설정·수정·해제하면 전송 payload와 hash, 마지막 적용 기록, `pending_apply`는 같다. PC 원문 파일·revision·문서 hash가 바뀌는 것은 정상이다.

POC5-01B/02/03 원장·피드백·가격 결과와 POC5-04 리포트 집계는 변경하지 않는다. 기준일을 알림 발생일이나 성숙 날짜로 사용하지 않는다.

POC5-06은 같은 종목·가격 자료·가격 기준일에서 학습 표본·검증 MAE·추정값이 같아야 한다. `2026-01-02`로 학습 기간을 자르거나 당시 보유·매수 사실을 추정하지 않는다. 연구 산출물의 보유 문서 hash가 달라지는 것은 허용한다. 사용자 평가가 없는 알림을 쓰는 기존 계약도 유지한다.

PC 기능으로 구현한다. OCI 설정·cron·PUSH 계약 변경은 없다. 공용 파일을 수정하더라도 OCI가 받는 기존 5필드 문서를 읽는 동작은 유지한다. PLAN에서 실제 OCI 실행 경로 변경 여부를 확인하고, 필요 없는 OCI pull이나 새 거래일 관찰을 완료 조건으로 만들지 않는다.

## 6. 필요한 확인

1. 설정·수정·해제 전후 수량·평단·원가·실현손익·기간 연결·OCI payload/hash가 같다. v1 첫 전환과 실제 매매가 있는 v2에서 각각 확인한다.
2. 여러 보유 일괄 설정은 한 번에 저장된다. 응답 유실 재시도·ID 충돌·오래된 revision·교체 전 실패에서 일부 저장이나 중복 기록이 없다.
3. 현재/종료 기간·다른 계좌·재매수 기간을 구분하며 새 기준일이 BUY나 매수일로 표시되지 않는다. 같은 값 재설정과 해제의 변경 없음도 확인한다.
4. 유효한 날짜·미래 날짜·휴장일·해당 종가 없음·날짜 역전의 표시를 확인한다. History 열기나 설정 저장으로 외부 가격 조회·ML을 실행하지 않는다.
5. 같은 가격 자료로 POC5-06 학습 표본·MAE·추정값을 비교한다. 바뀐 문서 hash를 모델 변화로 오인하지 않는다.

격리 파일로 저장·계산을 시험한다. 라이브 보유에 시험 BUY/SELL을 넣지 않는다. 기존 보유·History·OCI 적용·재진입 검토의 관련 회귀와 필요한 정적 검사를 수행하고, 실제 변경 범위에 맞춰 전체 회귀를 실행한다.

## 7. 진행과 종료

개발자는 기존 저장·무결성·History·시장 흐름 경계의 변경 위치와 검증 계획을 담은 짧은 PLAN을 제출한다. 코드와 충돌하는 사항이 없으면 질문을 만들 필요가 없다. 새 DB·공개 경로·가격 수집·모델은 제안하지 않는다.

PLAN 확정 뒤 backend와 frontend를 이어 구현한다. 새 메뉴·복잡한 화면 구조가 없으므로 별도 목업 승인 대기를 추가하지 않는다. 검증·RESULT 판정 후 기존 승인 범위에 맞춰 커밋·push·PC 재기동하고 실화면을 확인한다. 사용자에게 필요한 실제 기준일 설정으로 확인할 수 있으며 다음 실제 거래를 기다리지 않는다. 실화면 통과 뒤 종료 기록·인계를 남기고 종료 재판정은 요구하지 않는다.

10-12의 POC5-02 첫 결과 행·POC5-03 가격 결과 표시 확인과 10-23 공식 R0는 **독립된 운영 점검**이다. 이 설계·구현·로컬 검증을 그 날짜까지 미루지 않는다. R0가 점검 필요를 내면 그 관측에 맞는 보정을 따로 다룬다.

다음 설계는 **알림의 ML 사후평가**다. 사용자가 평가하지 않은 알림도 객관적 가격 결과로 사후평가하고, 사용자 평가가 있으면 별도 근거로 함께 쓴다. POC5-06의 ETF 가격 연구와 알림 평가를 같은 모델로 간주하지 않는다. 07 구현 중 목표·평가 단위·자료 계약 설계를 진행할 수 있고, 실데이터의 성숙 여부는 실행 결과의 충분성 조건으로만 다룬다. 실제 성과 판단은 표본과 결과가 충분할 때 하며, 그 전에도 설계·구현·격리 검증을 진행한다.

### 9-1. 수용하는 구현

- **계산 제외 수용:** REFERENCE_DATE는 무결성 검사를 거친 뒤 기간 재생 계산에서 제외한다. 종료된 기간에도 설정할 수 있고 수량·원가·손익·거래 순서·기간 순서/종료는 같다. 종가 비교용 값은 records의 저장 순서에서 마지막 설정을 읽는다. 저장 시각을 정렬해 과거 설정을 다시 활성화하지 않는다.
- **단건·일괄 저장 수용:** 기존 PUT 경로의 `action="reference_date"`, 대상 1~200, 중복 대상 거절, `request_id/request_hash` 재시도 확인 후 revision 확인, 전체 판정 뒤 파일 교체 1회를 수용한다. 변경 없는 요청은 저장·revision 증가가 없다. V1 첫 실제 변경은 기존 ID를 유지하는 V2 전환을 쓴다.
- **무결성 수용:** payload 한 칸, 날짜 또는 null, BASELINE/REGISTER 기간 연결, supersedes 금지, 기존 알 수 없는 종류 거절을 유지한다. REFERENCE_DATE를 매매·취소 사건 목록에 넣지 않는 계획을 수용한다.
- **시장 흐름 수용:** 기준일→마지막 저장일을 별도 항목으로 표시하고, 실제 매도로 끝난 기간은 기준일→마지막 매도 기준일도 표시한다. 매도 뒤 변화는 기존 항목을 쓴다. 실제 매수일 미상 표시는 유지하며, 자료 없음·종료일 역전·개별주·가격 기준 차이는 기존 05 규칙대로 처리한다.
- **OCI·ML 수용:** 기존 5필드 문서에서 계산 모듈을 사용하지 않는 조사와 OCI 실행 파일 변경 0 계획을 수용한다. OCI pull은 요구하지 않는다. 기준일만 변경한 OCI payload/hash·적용 상태와 같은 가격 입력의 06 ML 표본·MAE·추정값 불변은 구현 검증으로 확인한다.
- **화면·세부 6건 수용:** 기본 일괄 대상 제한은 화면 대상 목록과 revision으로 보장한다. 서버에 별도 덮어쓰기 금지 표지를 추가하지 않는다. History에서 같은 창을 겹치지 않는 기간별 수정/해제, 06 ‘내 거래’ 유지, 기준일 가격 없음의 저장 허용을 수용한다. PLAN §2-6은 아래 두 문장으로 의미를 명확히 한다.

### 9-2. 구현하면서 반영할 명확화

1. **저장일 상한:** 무결성에서 날짜를 비교할 때 `recorded_at`의 **KST 날짜**를 사용한다. 입력의 ‘KST 오늘 이하’와 같은 날짜 축이다. KST 자정 부근 저장의 검증을 기존 날짜 시험에 포함한다.
