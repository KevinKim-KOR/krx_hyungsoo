CPU 2개·메모리 약 954MB·가용 약 530MB·빈 디스크 39GB에서 순차 수집·종목별 스트리밍·학습 모듈 미적재라는 접근은 타당하다. 보관량 연 0.75GB와 네이버 약 8~11분은 추정이다. **저장 공간의 여유와 메모리/응답 시간 검증을 같은 것으로 보지 않는다.** 실제 실행의 최대 RSS·경과 시간·출력량은 별도로 남긴다.

## 3. Q2 — 네이버 가격 저장: (a) 수용

네이버/FDR 수신 창은 증거 파일에만 보존한다. `etf_daily_price`, `etf_master`, KRX·지수 운영 표에는 쓰지 않는다. 낡은 OCI `etf_master`를 보관용 수집의 최신 목록으로 간주하지 않고, 새로 받은 목록은 evidence 안에서 관리한다.

OCI DB의 새 쓰기는 POC6-01과 같은 스키마의 `market_macro_daily`·`market_investor_flow_daily`에 한정한다. `capture=None`인 PC 호출의 기존 동작을 유지한다. capture 실패 시 해당 값은 upsert하지 않으며, 다른 계열과 기존 보관본을 보존한다.

OHLC가 기존 응답에 함께 있는 경우 허용 수치로 보관할 수 있다. 이 보관을 새 feature·모델·해석의 구현으로 기록하지 않는다. 비정상 종가 행을 삭제한 뒤 과거 행을 당겨 61일을 채우지 않는다. 61행 미만 표시는 관측 창의 부족이며 장기 학습 자료나 모델 적격성 통과를 뜻하지 않는다.

## 4. Q3 — 연구 등록: (a) 수용

POC6-02·03·04의 공식 22파일만 우선 등록·업로드한다. 내용 중복 1개는 같은 object를 참조할 수 있다. 기존 파일은 바이트 그대로 보존한다. 1.86GB 봉인 KRX 판은 OCI 미전송 계약을 유지하고 경로·hash·바이트를 참조한다.

POC5-06·08은 이번 OCI 등록에서 제외하며 PC 원본은 보존한다. 개인 필드를 지워 다른 파일을 만들거나 과거 연구를 다시 실행하지 않는다. 두 연구를 폐기·보관 완료로 기록하지 않는다. 03의 기존 파생 보고서 보관을 수용하되, ‘같은 계정/본인 서버이므로 모든 원천 자료를 자유롭게 복제할 수 있다’는 일반 허용 근거로 쓰지 않는다.

04의 행 단위 예측 미저장, 02/04의 학습 가중치 미저장, 원본 절대경로로 인한 다른 경로에서의 실행 한계를 그대로 표시한다. 보관·읽기 복구가 학습된 모델 파일 복원이나 기존 CLI의 무수정 재실행까지 증명한 것은 아니다.

과거 연구의 코드 연결은 다음을 구분한다.

- 현재 수집/보관 프로그램은 실제 실행 commit을 기록한다.
- 과거 연구의 실행 당시 commit을 확인할 수 없으면 미상으로 둔다. 나중에 코드가 처음 들어간 commit·결과서 재현 근거·GPU `code_sha256`은 각각의 근거 종류로 기록한다.
- `git rev-parse HEAD`나 최초 포함 commit을 과거 학습 실행 commit으로 대입하지 않는다. 이를 확인하려고 전체 Git 역사나 모델 실행을 다시 조사하지 않는다.

## 5. Q4 — 네이버 수집 제한: (a) 수용, 시간 상한의 뜻 정정

요청 간격 최소 0.25초, 기존 요청 timeout 20초·연속 timeout 5회 중단, 연속 실패 종류 무관 20회 중단을 수용한다. 성공하면 연속 실패 수를 초기화한다. 명확한 HTTP 403/429가 전달되면 이번 네이버 단계를 즉시 멈추고 남은 종목을 미시도로 기록한다. 차단을 피하기 위한 새 접속 방식·자동 재시도는 추가하지 않는다.

**30분은 단계 시작 후 새 요청을 시작하지 않는 시간 예산**으로 정한다. 요청/간격 대기 전후에 경과 시간을 확인한다. DNS 대기나 느린 연속 응답까지 포함한 강제 종료 보장이 아니므로, PLAN의 ‘10:30 알림 전에 끝남’이라는 보장 표현은 삭제한다. 남은 종목·중단 원인·실제 종료 시각을 남긴다. 이번에 범용 timeout/감시 체계를 새로 만들지 않는다.

첫 승인 실연결은 소수 종목의 순차 처리에서 RSS를 확인한 뒤 전체 실행으로 넓힌다. 한 번 승인받은 범위 안의 점검이며 별도 부하 시험·새 Step·반복 승인 요구로 만들지 않는다. 운영 프로세스에 쓸 메모리 여유를 확보하지 못하면 전체 실행을 강행하지 않고 보존한 부분 결과와 제한을 보고한다. torch·sklearn 설치나 OCI 증설을 자동 후속으로 붙이지 않는다.

## 6. 구현 전 반영할 필수 보완

### 6-1. 공개 순서가 다른 묶음의 동기화 누락 방지

PLAN의 `list-runs --after <마지막>`을 **시작 시각 기반 run_id 커서로 구현하지 않는다.** 예를 들어 09:40에 시작한 수집이 09:50에 공개되고, 09:45에 시작한 연구 등록이 먼저 공개되면 PC가 앞의 수집을 영구히 놓칠 수 있다.

이번 규모에서는 완료 manifest의 전체 목록(run_id·manifest hash)을 매번 대조하고, PC에 없는 manifest/object만 전송한다. 자료 파일의 증분 전송은 그대로다. 별도 커서·분산 동기화 엔진은 만들지 않는다. `catalog.jsonl`은 재생 가능한 색인이므로 manifest 공개 후 색인 append 전에 끊겨도 완료 묶음이 영구 누락되지 않아야 한다.

### 6-2. 날짜·부분 실패·공개 시각

- 국내 새 완료 거래일 판정은 마지막 전체 실행 날짜만으로 하지 않는다. **직전 국내 단계가 PARTIAL/FAILED이거나 같은 기준일의 목록·가격에 미확보분이 있으면, 다음 일일 실행에서도 그 단계를 시도할 수 있어야 한다.** 새 거래일이 없다는 이유로 이전 실패를 정상 휴장 skip으로 감추지 않는다. 이미 성공한 자료는 이전 판을 명시해 재사용할 수 있다. 별도 당일 재시도 스케줄은 없다.
- 실제 공급자에 새 완료 가격이 없는 날과 수집 실패를 구분한다. 토요일에 받은 금요일 네이버 봉을 금요일에 확보한 자료로 기록하지 않는다. KRX가 같은 날을 아직 제공하지 않은 경우 각 최신일과 미확보 사유를 그대로 남긴다.
- `observed_at`은 실제 수신 시각, `available_at`/`published_at`은 검증된 묶음의 최초 공개 시각, `imported_at`은 과거 자료 등록 시각, `copied_at_pc`는 PC 수신 시각이다. 같은 공개 사건의 `available_at`과 `published_at`은 같은 기준으로 둔다. 원래 공개 시각은 PC 전송·catalog 재생성으로 바꾸지 않는다.
- export는 공개된 정상 자료 파일과 `available_at ≤ as-of`를 함께 검사한다. 단순히 요청한 관측일 이전의 행이라는 이유로 나중에 확보한 정정 판을 넣지 않는다. PARTIAL 묶음의 유효 자료는 실패 범위·이전 판 참조를 포함해 읽을 수 있고, FAILED/미완료/손상 자료는 정상 입력으로 내보내지 않는다.
- 전체 상태는 정상 확보/재사용 자료가 있는 부분 실패는 PARTIAL, 모든 필요한 확보가 실패했거나 묶음 무결성/공개가 실패하면 FAILED로 둔다. 정상적인 ‘새 자료 없음’은 SKIPPED_NO_NEW로 구별한다. 상태와 자료원별 성공·실패·미시도 분모가 맞아야 한다.

### 6-3. 날짜 축·이전 판 참조를 실제로 복구 가능하게 보관

달력 CSV와 연구 축에 사용한 KOSPI 저장일 목록은 hash만 적지 말고 **실제 내용 파일도 object로 보관**한다. 기존 fallback 정책·파일 유무·축 버전을 참조할 수 있어야 한다. 파일이 없으면 없었다는 사실을 기록하고 새 달력을 제작하지 않는다.

최근 21거래일 KRX/지수 delta와 수집 상태 파일 보관은 수용한다. 최초 보관 범위와 그 뒤 delta/이전 판 연결을 명시한다. ‘변화 없음’이면 이전 object를 참조하며, export·복구에 필요한 참조를 함께 가져온다. 최근 21일 밖의 과거 정정까지 모두 보존했다고 주장하지 않는다. 이를 위해 전체 과거 DB 재적재나 봉인 DB 전송을 추가하지 않는다.

관련 DB 행·날짜 축은 짧은 읽기 전용 트랜잭션에서 일관되게 읽고 외부 대기·압축 전에 연결을 닫는다. DB의 마지막 쓰기 시각을 최초 원천 확보 시각으로 승격하지 않는다.

### 6-4. 수집량·자원 수치의 뜻

`/proc/self/io`는 네트워크 다운로드 바이트의 측정값으로 사용하지 않는다. 기존 HTTP 경계에서 수신량을 정확히 셀 수 없다면 `network_received_bytes=null`과 미측정 사유를 남긴다. 측정 가능한 파일 보관 바이트·시간·최대 RSS를 기록하는 것으로 충분하며 새 네트워크 계측 도구는 추가하지 않는다.

연 0.75GB는 국내 수신 창 약 250회 기준 추정이고, 매일 받는 해외/수급·manifest·미완료 임시 파일 등은 별도다. 실제 증가량을 한 번 기록하고 추정으로 표시한다. Linux RSS 값의 단위를 확인해 저장하며 맥북과 같은 원시 단위라고 가정하지 않는다. 네이버가 전체 이력을 내려준 뒤 120일로 자르므로 실제 수신량·일시 메모리는 보관 파일 크기와 다를 수 있다.

목록의 95% 규칙은 공급자 응답 급감에 대한 임시 보류 기준으로 수용한다. 새 응답·차이 수·사유를 보존하고 기존 목록을 stale로 사용한다. 이를 실제 대규모 상장폐지 확정이나 새 목록의 영구 폐기로 해석하지 않는다. 이번에 자동 대체 목록이나 심사 UI를 만들지 않는다.

## 7. 검사와 문서 반영

기존 PLAN 시험에 다음 경계만 보완한다: 늦게 공개된 낮은 run_id도 다음 pull에 포함, manifest 공개/색인 append 사이 중단, 동일 기준일의 부분 실패 후 다음 일일 시도, 과거 as-of에서 미래 정정 배제, 날짜 축/이전 판 참조를 포함한 복구, timeout 시간 예산·연속 실패/403·429 중단.

기존 02·03·04 공식 학습·GPU 실행·성과 보고서를 재생성하지 않는다. 관련 검사와 마지막 전체 회귀 한 번, 검증자 확인을 따른다. 사용자 화면 변경이 없으므로 목업·실화면 확인은 없다.

PLAN §4·§6·§7과 상태 문서에 이 판정을 반영한다. 설계서 원문은 그대로 두고 본 판정 경로를 연결한다. §2의 예외는 기반 문서 세 곳에 원문 그대로 추가한다. 문서 전수 정리·백로그 재감사는 하지 않는다.

## 8. 승인·실행·종료
