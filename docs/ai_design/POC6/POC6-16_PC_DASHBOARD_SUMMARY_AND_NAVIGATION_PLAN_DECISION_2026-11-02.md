## 3. 사용자가 눌러야 할 버튼을 분명하게

요약 행마다 주요 이동 하나를 강조하고 보조 이동은 테두리/텍스트 버튼으로 구분한다. 모든 버튼을 같은 크기·파란 강조로 반복하지 않는다. 작은 문구·역할 정리이므로 확인된 전체 배치를 다시 설계할 필요는 없다.

| 목적 | 기본 표시·동작 |
|---|---|
| 이 PC의 저장 값을 다시 읽기 | 상단 **[요약 다시 읽기]**. §2의 6개 조회만 실행 |
| 오래된 PC 시장 자료를 갱신하기 | 자료 확인 줄에서 **[시장 자료 갱신 화면]**을 주요 이동으로 제공. 기존 `market_discovery`로 이동하며, 짧게 **‘이동 후 [최신 시장 데이터 갱신]을 누르세요’**라고 설명 |
| 다른 자료 정비 항목 확인 | **[자료 최신화 목록 ↓]**을 보조 이동으로 유지. 구성종목·기준가 등은 원래 정비 항목으로 연결 |
| 시장 근거 확인 | **[시장 흐름 자세히]**를 주요 이동으로, **[KOSPI 차트 ↓]**를 보조 이동으로 구분 |
| 보유 점검 | **[확인 근거 보기]**와 **[보유 현황 보기]**의 역할을 구분. 조회 실패 시에도 가능한 기존 상세 이동을 유지 |
| 후보·연구 확인 | 기존 목록 화면과 **[예측과 결과 비교]**로 이동. 새 계산/예측 명령을 붙이지 않음 |

시장 자료 갱신 화면 이동은 **버튼을 누른 즉시 갱신되는 동작이 아니다.** 대시보드에 POST `/market/refresh`를 추가하거나 화면 이동 뒤 자동으로 그 명령을 실행하지 않는다. 기존 시장 화면의 사용자 클릭이 갱신을 시작한다.

상단 버튼 옆에는 **‘저장된 값만 다시 읽습니다. 시장 판정·후보 목록 재계산은 제외합니다. 최신 시세는 시장 자료 갱신 화면에서 받습니다.’**라는 뜻을 쉬운 말로 짧게 적는다. 시장 자료를 갱신해도 다른 자료 정비 항목 전부가 자동 해결된다고 약속하지 않는다.

폴더/메뉴 이동과 같은 화면 안 스크롤은 실제 목적지를 가리키며 키보드로 사용할 수 있게 한다. 스크롤 뒤 목적 영역을 찾을 수 있게 제목을 보이게 하되 새 팝업이나 자동 실행은 만들지 않는다. 기존 정비 구역의 [업데이트]와 새 읽기 버튼은 명령 대상·효과를 합치지 않는다.

### 3-1. 지금 필요한 작업을 먼저 안내

버튼과 기준일만 나열하고 사용자가 해야 할 일을 스스로 추측하게 두지 않는다. **기존 자료 점검에서 갱신 필요가 확인되면, 이유·해야 할 작업·해당 버튼을 한 묶음으로 기본 노출**한다. 안내를 보려면 도움말을 열거나 상세 화면까지 내려가야 하는 구조로 만들지 않는다.

예시(날짜는 실제 응답 사용):

> **시장 자료 갱신이 필요합니다.** KOSPI는 10월 22일, ETF 가격은 10월 23일 자료입니다.
>
> **[시장 자료 갱신 화면]** → 이동 후 **[최신 시장 데이터 갱신]**을 눌러 주세요.

이 안내는 요약 카드 상단 또는 첫 화면에서 보이는 자료 확인 줄에 둔다. 기존 자료 확인 줄의 문구·버튼을 재사용하며, 같은 작업의 강조 버튼을 두 군데 새로 만들지 않는다. 시장 갱신 외 다른 정비 항목도 기존에 원인과 해결 동선이 확인된 범위에서 같은 방식으로 안내한다.

| 확인된 상태 | 안내 |
|---|---|
| 기존 점검이 시장 자료 지연·갱신 필요를 알림 | 실제 자료일과 ‘시장 자료를 갱신해 주세요’ + 기존 갱신 화면 이동 |
| 기존 점검이 보유 현재가 결측 등 다른 정비 필요를 알림 | 기존 원인·대상에 맞는 작업과 해당 버튼. 시장 갱신으로 전부 해결된다고 쓰지 않음 |
| 처음 조회가 실패해 자료 상태 자체를 모름 | ‘자료 상태를 확인하지 못했습니다. 다시 읽어 주세요.’ + 읽기 버튼. 미갱신으로 단정하지 않음 |
| 점검 결과 갱신 필요가 해소됨 | 해당 작업 안내를 해제. 항상 갱신하라고 요구하지 않음 |
| 연구 결과가 정상 대기 중 | 대기 상태만 표시. 불필요한 재학습·소급 실행을 할 일로 만들지 않음 |

안내의 근거는 **자료 기준일과 기존 점검 상태**다. 기록이 없는 ‘버튼을 마지막으로 누른 날’이나 ‘며칠 동안 안 누름’을 추정하지 않는다. 사용자가 눌렀지만 실패했을 수도 있으므로 ‘오랫동안 누르지 않으셨습니다’라고 확정해서 쓰지 않는다. 새 클릭 이력·임계값·알림 원장 없이 기존 상태로 구현한다.

안내는 해당 상태가 확인되면 화면에 자동으로 보이지만 갱신 작업 자체를 자동 실행하지 않는다. 갱신 화면으로 이동하거나 작업을 시작한 것만으로 안내를 지우지 않는다. 기존 무효화·재조회 뒤 실제 점검 상태가 해소되면 지우고, 실패/일부 미해결이면 남은 사유와 작업을 유지한다. 새 팝업·Telegram·정기 알림·닫기 이력 저장은 추가하지 않는다.

## 4. PC 자료 지연과 캐시 시각

현재 보고된 PC 자료일은 KOSPI 10-22, KODEX200·후보·보유 저장 가격 10-23, 수급·환율·유가 10/22까지다. 이는 당시 조회 사실이며, 갱신 버튼이 실행되지 않은 것이 확정 원인이라는 판정은 아니다. OCI 연구 수집·PC 전향 기록의 기준일과도 별개다.

기존 정비 상태가 자료 지연을 알리면 위 갱신 동선을 잘 보이게 한다. 날짜가 과거라는 이유만으로 새 지연 임계값을 만들지는 않는다. 오래된 값의 시장·보유 결론은 기준일을 가까이 표시하고 ‘현재 시장’의 확정 판단처럼 과장하지 않는다. 보완 구현·검증을 기다리느라 사용자의 기존 시장 갱신 버튼 사용을 막을 필요는 없다. 이 판정으로 개발자의 조사 중 자동 수집을 지시하는 것은 아니다.

캐시에 성공 시각 한 칸을 추가하는 안은 수용하되 다음을 지킨다.
- **성공 데이터와 그 성공 시각을 같이 기록**한다. 실패·캐시 재사용·재마운트 때 성공 시각을 현재 시각으로 갱신하지 않는다.
- 이전 결과를 보이면 그 결과의 성공 시각과 현재 실패를 함께 표시한다. 시각을 보관하지 못한 값은 ‘조회 시각 미확인’이다.
- 서로 다른 원천이 섞인 시장/보유 줄은 각 기준일·실패를 보존한다. 상단 시각 하나를 모든 값의 새 조회 시각으로 쓰지 않는다.
- 상단 시각은 ‘이번 요약 확인 시각’이다. 시장 판정·후보는 마지막 목록 조회 값이라는 안내를 유지한다. OCI 기동 캐시 시각도 그대로이며 다시 읽었다고 오늘 운영 확인으로 바꾸지 않는다.
- 조회 중 중복 클릭을 막고, 요청한 조회가 모두 끝난 뒤 완료/일부 실패를 표시한다. 한 실패 때문에 다른 정상 영역을 가리거나 새로 성공한 값을 버리지 않는다.

공유 `queryCache`의 시각 추가는 이 의미에 필요한 작은 변경으로 한정한다. 기존 API·다른 화면의 캐시 무효화/요청 공유·오류 의미를 바꾸거나 장기 저장소를 추가하지 않는다.

## 5. 요약 문구·분모 보완

후보의 ‘10개’는 요청 상한이지 항상 실제 결과 수가 아니다. **실제 응답의 목록 길이 N으로 ‘1개월 수익률 상위 N개’**를 표시하고, 필요하면 ‘최대 10개’ 조건을 구분한다. 후보 0개·1~2개·일부 결측도 임의로 10개로 채우지 않는다. 상위 3개는 기존 순서를 재사용한다.

대시보드의 고정 1개월·제외 조건을 해당 줄에 명시한다. 종목별 실제 시작/끝일이 모두 같을 때만 하나의 기간으로 쓴다. 다르면 ‘종목별 계산 기간 다름’과 기존 상세 동선을 제공하고 선두 종목 날짜를 전체의 기간으로 붙이지 않는다. 이동한 목록 화면의 사용자 선택 기간이 다를 수 있으면 그 차이를 안내한다. 이번에 없는 필터 전달 체계를 새로 만들 필요는 없다.

시장 국면의 두 원천이 다르면 각각의 원천·기준을 표시한다. 하나를 다른 값으로 덮거나 새 국면 계산을 프런트에서 하지 않는다. 수급·환율·유가 중 일부만 실패하면 확인 가능한 기존 관측은 남기고, 확인 못 한 대상을 구분한다.

연구 결론은 기존 `forwardConclusion`을 재사용한다. 세 비교별 분모·정상 비교 없음·보고 부재·보고/실행 기록 손상을 보존한다. 예측 건수와 방법별 예측 수·성숙 건수·공통 비교 행 수를 섞지 않는다. **‘20거래일이 지나야 결과가 나옵니다’는 ‘기준일 뒤 20거래일 자료가 확보되면 결과를 비교합니다’로 고친다.** 시점 경과만으로 평가 성공·누락 없음·모델 채택을 보장하지 않는다.

장면 B는 현재 격리된 표시 예시다. 후보 재조회 실패 상태를 표현하려고 [요약 다시 읽기]에 후보 계산을 추가하지 않는다. 실제 가능한 캐시 실패 경로와 정상 응답을 시험에서 구분한다. 1000px 가로 넘침 없음과 첫 화면 노출은 구현·실화면 확인에서 확인한다.

## 6. 진행과 필요한 확인

사용자의 기본 목업 확인을 PLAN에 기록하고 본 판정으로 Q1~Q3·조회표·버튼·문구를 보충한다. 지정된 보완은 같은 배치 안의 역할 정리이므로 별도 PLAN 재제출·목업 재승인 없이 구현한다.

검증은 다음에 집중한다.
- 같은 입력에서 요약과 원래 영역의 값·기준일·상태·후보 수·기간이 일치함.
- 초기 진입·왕복·6개 다시 읽기·연구 캐시·후보 계산 추가 0·명령 자동 호출 0이 계약과 같음.
- 캐시 성공 시각이 실패/캐시 재사용에 바뀌지 않으며, 부분 실패·이전 결과·첫 조회 실패가 구분됨.
- 버튼 이동/스크롤 목적지, 기존 정비 버튼의 명령·재조회 동작, 읽기 완료·일부 실패 피드백이 맞음.
- 자료 지연 시 이유·해야 할 작업·버튼 안내가 기본 노출되고, 상태 정상화 뒤 해제됨. 이동/실행 시작만으로 지워지지 않으며 첫 조회 실패·정상 연구 대기를 미갱신 작업으로 오인하지 않음.
- 프런트 타입·lint·관련/전체 프런트 시험과 저장소 필수 검사. 백엔드 무변경이면 백엔드 전체 회귀·모델 재실행·OCI 점검은 붙이지 않음.

실화면에서는 요약을 읽고 필요한 버튼을 찾아 상세로 이동할 수 있는지 확인한다. 외부 갱신·새 학습·새 성숙 결과를 실제로 실행해야 이번 화면이 완료되는 것은 아니다. 개발자는 보완·실행 경계·실측을 결과서에 적고 검증자 이후 RESULT 판정을 받는다.

새 API·백엔드·DB·외부 자료원·패키지·OCI pull·cron·키·새 업로드·별도 handoff는 없다. 커밋·push는 해당 시점의 사용자 승인 범위로 하며 사용자 소유 handoff·연구 산출물·개인 캐시·로컬 연구 브랜치는 넣지 않는다. 자료·UI·ML을 함께 발전시키는 방향과 Q6 OPEN·운영 ML 미승격·기존 미완료 요구·05/06/13 운영·12 SOURCE_BLOCKED는 유지한다.
