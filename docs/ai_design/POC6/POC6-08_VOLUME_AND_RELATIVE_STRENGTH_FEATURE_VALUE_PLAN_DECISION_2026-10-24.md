## 2. 재사용·모듈·실행 흐름 수용

- 기존 축·가격 검사·P 5열·D20·원래 HGB 설정·날짜 균형 평가 함수의 재사용을 수용한다. 06 코드·protocol·저장 형식은 변경하지 않는다.
- V는 기존 POC5-09 함수의 **반올림 전 배수**를 사용한다. 기준일 제외·직전 0 포함·평균 0 결측의 정의를 유지한다. R의 `C(i)/C(i-20) - B(i)/B(i-20)`는 설계 식과 수학적으로 같으므로 수용한다. R 단위는 소수 수익률 차다.
- 새 `app/feature_gain/`과 `scripts/run_feature_gain.py`, 예상 책임 분리와 KS-10 범위를 수용한다. 기존 코드를 범용화하기 위한 별도 리팩터는 필요 없다.
- `lock → run → verify`를 수용한다. lock은 파일·행 식별자·유효성·기간·분모·가용성·recipe를 고정하는 단계다. 목표 크기·오차·후보 순위는 계산하지 않는다. X/y와 실제 성과는 run 산출물로 구분한다.
- 큰 하락의 날짜·ticker 수는 공식 실행에서 처음 센다. 아직 그 수를 모른다는 이유로 구현을 멈추거나 목표 값을 미리 들여다보지 않는다.
- 1분 안쪽은 실행 시간 추정으로 기록한다. 성능 판정이나 개발 성공 기준으로 쓰지 않는다. 실측 결과 때문에 표본·epoch·모델 설정을 바꾸지 않는다.

## 3. 구현 전에 명확히 할 기존 계약

아래는 새로운 실험이나 추가 조사를 요구하는 내용이 아니다. 설계에 이미 정한 계산·보존 의미를 PLAN에 명확히 반영한다.

### 3-1. 같은 행과 같은 가중치의 적용 범위

PLAN §3·§5의 ‘여섯 구성 같은 행·같은 가중치’는 다음처럼 구분한다.

- 여섯 구성은 기본 P·목표가 유효한 **같은 행 집합**을 사용한다. V/R 결측으로 후보 행만 빼지 않는다.
- **HGB 네 구성끼리** 같은 공동 학습 행과 날짜별 1/n_d 가중치를 사용한다.
- MEDIAN/RIDGE는 같은 집합에서 **종목별 학습 날짜 동일 비중**이다. HGB 공동 학습의 날짜 가중치를 Ridge나 중앙값에 새로 적용하지 않는다.
- G_REVIEW는 같은 모델의 평가 행만 제한한다. 15종만 다시 학습하거나, 그 범위로 학습 가중치를 다시 계산하지 않는다.

### 3-2. 기존 judge 재사용과 A/B 판정

기존 함수는 동일한 계산 접점으로 재사용하되, 02의 연구 판정 전체를 그대로 새 상태명에 연결하지 않는다. 특히 02에서 두 기준을 함께 판단하던 경로가 있다면 08의 A에서는 **HGB_P 하나와의 비교**로 한정한다. 02 함수를 바꾸지 말고 필요한 연결은 08에 둔다.

- **A:** HGB_P 대비 전체 5% 개선·두 구간 이상 우위·구간별 5% 초과 악화 없음. PV·PR·PVR 및 G_ALL/G_REVIEW를 각각 평가한다.
- **B:** A와 별도로 RIDGE_P 대비 전체 5% 개선·MEDIAN_P보다 작은 MAE·큰 하락 표본 수·U 악화 제한을 평가한다. A 통과 사실을 B 미충족 때문에 지우지 않는다.
- 전체 비교 기준 MAE=0이면 해당 비교는 `NO_BASELINE_HEADROOM`이다. **한 구간의 기준 MAE=0은 전체 기준 0과 구분한다.** 전체 기준이 양수라면, 그 구간에서 후보도 0인 경우 동률이며 A의 ‘두 구간 우위’에는 세지 않는다. 후보가 양수이면 해당 구간 악화 조건을 충족하지 못한다. 0 나눗셈이나 무조건적인 전체 `base_zero` 변환을 하지 않는다.
- B의 RIDGE/MEDIAN 비교가 이미 미충족이면 `FEATURE_GAIN_ONLY`로 두고, 큰 하락 부족 여부도 별도 표시한다. 비교 조건을 충족했지만 큰 하락 표본만 부족하면 `TAIL_DATA_SHORT`, 충분한 표본에서 U 조건을 못 넘으면 `FEATURE_GAIN_ONLY`다. 필요한 비교의 전체 기준이 0이면 B의 `NO_BASELINE_HEADROOM`을 명시하고 A 결과는 유지한다.
- 자료 부족·실행 실패·개선 미확인·정보 효과만 확인·사용 검증 후보를 하나의 ‘모델 실패’로 합치지 않는다. 반올림 전 값과 실패 조건을 모두 남긴다.

### 3-3. 저장·복원과 공식 실행 근거

- Ridge를 ‘계수 저장’이라고만 적지 않는다. 원시 P 입력으로 예측을 복원할 수 있도록 **계수·절편·scaler 평균/scale·feature 순서**를 보존한다. 원시 입력 기준 계수/절편으로 환산해 저장하는 방식이라면 그 정의를 명시한다. 학습 직후·복원 후 원시 예측과 범위 제한 예측을 대조한다.
- 공식 실행 때 새 코드는 미커밋일 수 있다. 이전 HEAD만 이번 구현의 코드 판으로 쓰지 않는다. HEAD는 base_commit으로 구분하고, 새 모듈/CLI와 실제 재사용한 계산 파일의 내용 해시·환경 판을 함께 고정한다. 전체 저장소나 가상환경을 재감사할 필요는 없다.
- run은 잠근 입력·설정·코드 근거가 같은지 확인한다. 일회성 공식 실행은 동시 실행 두 개가 모두 통과하지 않도록 기존의 작은 실행 잠금/일회성 쓰기 방식으로 지킨다. 새 작업 큐나 서비스를 만들지 않는다.
- 실행 오류·복원 실패는 실패 기록과 부분 산출물을 보존한다. 코드 결함을 고쳐 다시 실행해야 한다면 기존 실행을 덮지 말고 정정 관계와 이유를 남긴다. 이를 새로운 독립 실험이나 처음 본 성과로 쓰지 않는다. 성과를 바꾸려는 재실행은 허용하지 않는다.
- verify는 새 fit 없이 저장된 행·예측에서 지표·판정·분모를 대조한다. G_REVIEW 결과를 G_ALL로 오인하거나 각 구성의 행이 어긋나는 경우도 확인한다.

## 4. 조사 스크립트 정정과 검증 범위

임시 조사 스크립트의 반복문 함수 참조 오류를 밝히고 고친 처리를 수용한다. 폐기한 15~22%를 현행 결과로 기록하지 않으며, 이 일만을 별도 제품 결함이나 개발 단계로 만들지 않는다.

공식 lock은 08 구현으로 종목별 행/가용 개수를 다시 만들고 PLAN 표와 대조한다. 조사 결과와 다르면 성과 계산 전에 `CHECK_REQUIRED`로 멈춰 원인을 확인한다. 집계 수만 맞추려고 기준을 바꾸지 않는다. 종목마다 다른 거래량·가격 경로를 가진 작은 fixture로 마지막 종목의 자료를 반복 사용하는 결함이 검출되는지 확인한다. 별도 전체 원천 재조사는 필요 없다.

현재 실제 자료의 V/R 가용률이 100%여도 결측·평균 0·기간 불일치·기준 0·큰 하락 부족 분기는 격리 시험으로 확인한다. PLAN §5 시험에 §3의 가중치·판정·복원 계약을 포함한다. 같은 계약의 중복 시험 단계를 늘리지 않는다.

독립 검토 1회·적절한 변이·저장소 필수 검사·마지막 전체 회귀의 제안 범위를 수용한다. 통과 뒤 근거 없이 전체 회귀나 공식 성과 실험을 반복하지 않는다. 연구 가설이 기준에 미달한 것은 코드 결함과 구분한다.
