## 2. 다음 우선순위

**기존 보유 판단 흐름에서 투자용 현금과 보유 비중의 분모가 어떻게 관리되고 AI 검토로 전달되는지 확인한다.** 다음 모델이나 문턱을 바꾸는 실험은 현재 지시하지 않는다.

이유는 사용자가 최근 반도체 관련 보유를 늘렸고, 기존 투입액 정도의 별도 현금을 선택적으로 투자할 수 있다고 알려 왔기 때문이다. 현금 보유액·주식 평가액·사용자가 정한 투자 총예산은 서로 다른 값이다. 추가 현금을 전부 투자예산으로 간주하거나, 주식 안의 종목 비중을 현금을 포함한 자산 비중으로 부르면 실제 판단에 오류가 생긴다.

제공된 2026-11-03 PROGRAM_TRUTH에는 보유 현황의 총 평가금액·계좌별 구성·종목 비중과 매매 이력 기능이 기록돼 있다. 그러나 별도 투자용 현금·추가 투입 한도·AI 근거 전달 계약은 해당 문서에서 확인되지 않았다. **문서에 없다는 이유로 현재 기능도 없다고 판정하지 않는다.**

이번 확인은 새 UI·자금 관리 기능 개발을 확정하는 단계가 아니다. ML의 유용한 추가 효용과 비용 후 초과성과라는 미완료 목표도 그대로다. 자금·비중 확인으로 그 목표를 달성했다고 처리하지 않는다. 확정 A/B/C·사용자 최종 주문·PC/OCI 역할은 바꾸지 않는다.

## 3. 개발자에게 전달할 읽기 전용 확인 범위

지금 필요한 개발자 산출물은 **짧은 사실 회신 한 건**이다. 별도 POC 번호·구현 PLAN·학습·성과 계산은 만들지 않는다.

| 확인 항목 | 회신할 사실 |
|---|---|
| 보유 현황의 총 평가금액과 종목 비중 | 각각의 분모, 포함 계좌/자산 범위. 현금 포함 여부와 미평가 보유 처리 |
| 투자용 현금 | 입력·저장·수정 기능이 실제 있는지. 있으면 메뉴·필드·저장 위치·기준 시각과 계좌 범위 |
| 투자 총예산·추가 투입 한도 | 기존 필드/계약이 있는지. 투입원금·현재 평가액·예산을 구분하는지 |
| AI 투자 세션의 보유 판단 근거 | 종목 비중의 분모와 위 현금/예산 정보 중 실제 전달되는 항목, 전달되지 않는 항목 |

먼저 기존 `GET /holdings/enriched`의 계산 경로와 `EnrichedHoldingsSection.tsx`·`HoldingsHero`의 표시 경로, 그 결과를 보유 비교/AI 세션 근거로 넘기는 직접 호출 경로를 본다. 기존 조사·최신 STATE/PROGRAM_TRUTH에서 확인된 내용은 재조사하지 않는다. 위 경로에서 정의 위치를 찾지 못할 때만 관련 필드/호출을 한정 검색한다.

각 항목은 **지원됨 / 지원 안 됨 / 확인 못 함**과 근거 파일·함수/필드만 적는다. 지원돼 있다면 바로 사용할 기존 메뉴와 값의 뜻을 알려주면 된다. 사용자 실제 보유 금액·계좌번호·비밀정보는 회신에 복사하지 않는다.

코드·UI·API·DB 스키마·설정·.env 파일은 바꾸지 않는다. 실제 시장 갱신·외부 API·OCI 조회·주문·새 통계·현금 수익률 계산도 하지 않는다. 기존 기능의 현재 계약을 확인하는 데 필요한 코드/스키마 정의·문서만 읽는다. 현재 연구 원본·사용자 handoff는 대상이 아니다.

## 4. 확인의 완료와 설계 경계

위 네 항목의 현재 지원 범위가 확인되면 이 확인은 끝난다. 사실 회신은 현재의 코드/계약 확인 결과이며 사용자 현금 운용 방침의 결정으로 취급하지 않는다.

현재 기능으로 충분하면 있는 흐름을 사용한다. 빠진 부분이 확인되면 그 공백 하나를 기준으로 설계자가 다음 단일 범위를 판단한다. 확인 전에는 현금 입력 화면·새 테이블·반도체 분류·자산배분·매수/매도 문턱을 선확정하지 않는다. 임의의 ‘반도체 최대 몇 %’나 ‘현금 최소 몇 %’도 정하지 않는다.

닫힌 POC6-23을 다시 열거나 이 확인 때문에 종료 커밋을 추가하는 요구는 없다. 실제 공백과 변경 필요가 확인되기 전까지 새 기능 구현은 없다.
