# POC6-14 PLAN 판정 — 전향 ML 비교 결과의 PC 조회

작성: 설계자 · 2026-10-30 · 독자: 개발자·사용자·검증자

저장 권장 위치: docs/ai_design/POC6/POC6-14_FORWARD_MODEL_COMPARISON_PC_VIEW_PLAN_DECISION_2026-10-30.md

**판정: PASS_WITH_REQUIRED_CORRECTIONS. Q1·Q2·Q3은 모두 권장안을 수용한다. 아래 보완을 기존 PLAN에 반영하며 PLAN 재제출은 필요 없다. 사용자 목업 확인이 완료된 범위에서 구현한다.**

## 1. 근거와 확인 범위

첨부 PLAN V1 전체와 이미지 5개를 DESIGN V1과 대조했다. PLAN SHA-256은 3b25920a5c04457d2464c17abe91675ec41451ad32c237c9d3b14a99265b9f32다.

첨부에서 기본 카드·표·도움말·행 바로 아래 상세·보고 경고·없음/오류 구분을 확인했다. 로컬 HTML을 직접 조작하거나 사용자 맥북/연구 파일을 실행한 검증은 아니다. 캡처 밖의 누적 비교 전체와 1000px 전체 동작까지 확인했다고 기록하지 않는다.

다음은 개발자의 구조 확인 보고로 수용한다.
- 주 기록·영수증·재시도·진단 분리는 06 records의 기존 읽기를 재사용할 수 있고, 조회 import에 모델 패키지가 적재되지 않음.
- 예측/목표는 ratio, MAE/under_estimate는 이미 %p. 비율만 API 한 곳에서 ×100.
- 기존 06 조회 화면/API가 없고, 06 코드를 고치지 않는 새 GET 한 개·작은 조회/표시 모듈로 연결 가능.
- JSON 22개 전후 해시 불변, 13분 구조 확인, 기반 문서에 추가 예외가 필요하지 않다는 대조.

사용자가 목업을 확인했다는 기록은 이번 회신에 없다. 설계자의 배치 검토를 사용자 확인으로 바꾸지 않는다. 별도로 이미 확인받았다면 그 기록을 재사용하고 같은 확인을 다시 요구하지 않는다.

## 2. Q1 — 「진단·상태 › ML 실험」 맨 위 카드 수용

맨 위에 연구 카드 하나를 추가하고 기존 다섯 카드의 내용·순서는 유지한다. 새 최상위 메뉴는 없다. 예측값과 결과 상태의 기본 노출, 상세가 선택한 행 바로 아래에 나오는 배치를 수용한다.

현재 화면 소개 문장에는 “여기서는 ML 자료가 쓸 만한 상태인지만 확인”한다고 돼 있다. 연구 예측/비교까지 추가되는 이번 범위에 맞게 **“학습 자료 상태와 저장된 전향 예측·비교 결과를 확인하는 화면입니다.”**로 정정한다. 기존 페이지의 나머지 기능 개편으로 넓히지 않는다.

## 3. Q2 — 이 화면·복사 공용의 작은 표시 함수 수용

forwardText.ts에 이 조회용 표시 함수를 두고 화면과 복사가 함께 쓴다. 기존 fmtPct/fmtPctp의 전역 동작은 바꾸지 않는다.

- 표시를 소수 둘째 자리로 만들었을 때 0.00인 D20은 부호 없이 “0.00%”다. +0.00%와 -0.00%를 섞지 않는다.
- MAE와 큰 하락을 작게 추정한 정도는 원래 0 이상인 크기이므로 부호 없는 %p로 보인다.
- **표시 전에** 원기록의 숫자·유한성·허용 범위를 검사한다. 음수 MAE를 abs로 바꾸거나 잘못된 양수 D20을 반올림해 0으로 살리지 않는다. null·실패도 0이 아니다.
- 기존 보고에 실제 비교 차이값을 표시할 경우에는 그 부호를 보존한다. “%p는 모두 부호 제거”라는 공용 규칙으로 만들지 않는다.
- 원기록·비교 판정·저장 숫자는 바꾸지 않는다. 예측/목표 ratio의 ×100은 API 한 곳이고, 이미 %p인 보고 값은 다시 곱하지 않는다.

## 4. Q3 — NOT_EVALUATED · “성숙 확인 전” 수용

최신 예측은 같은 run의 성숙 평가 이후 만들어지므로, 아직 어느 저장 회차에도 그 행의 평가 상태가 없을 수 있다. 기존 06에 상태 파일을 새로 쓰지 않고 조회 응답에만 NOT_EVALUATED를 둔다.

의미는 **“현재 보관된 기록에서 이 행의 성숙 평가 상태를 아직 확인할 수 없음”**이다. PENDING_NOT_DUE와 구분하며, 아직 20거래일이 안 지났다는 달력 판단이나 앞으로 반드시 평가된다는 보장은 아니다.

- 유효 목표가 있으면 MATURED, 없으면 가장 최근의 해당 (ticker,D) 평가 상태를 재사용한다.
- 유효 목표도 해당 평가 상태도 없으면 NOT_EVALUATED. 날짜를 세거나 조회 때 mature/run을 실행해 상태를 채우지 않는다.
- 파일/상태를 읽다가 난 오류·스키마 불일치·손상을 “성숙 확인 전”으로 숨기지 않는다.
- 표의 짧은 문구는 “성숙 확인 전”, 근거 줄/도움말은 “이 기준일의 성숙 평가 상태 기록이 아직 없습니다”로 정리한다. 과거 실행을 전혀 안 했다는 이력 인증으로 쓰지 않는다.

## 5. 보고 대기 조건 정정 — per_date 부재만으로 판단하지 않음

PLAN의 “보고 per_date에 선택 D가 없으면 보고서 확인 대기”는 그대로 고정하지 않는다. **누적 보고가 정상 생성됐어도 그 D의 성숙 비교 행이 없으면 날짜별 오차 항목이 없을 수 있다.** 생성 여부·예측 포함 범위·성숙 비교 날짜를 구분한다. 원설계 §5의 “대응 보고”도 이 뜻으로 명확히 한다.

1. 정상 저장 보고가 있고 비교 행 0/MAE null이면 정상 보고다. “아직 비교할 결과 없음”으로 표시한다.
2. 저장 보고가 아예 없으면 보고 미생성/대기다. 새 run에 대응하는 보고가 아직 없다는 사실은 기존 run-id/보고 참조 등으로 확인할 수 있는 범위에서만 표시한다.
3. per_date가 어떤 날짜를 담는지 기존 코드·산출물 구조를 좁게 확인한다. **per_date에 없다는 이유 하나로 새 예측의 보고가 미생성됐다고 하지 않는다.**
4. 선택 D 예측 표와 누적 보고는 별도다. 누적 보고의 실제 생성 시각·집계 분모·평가 날짜 범위를 보여 주고, 그 범위가 선택 D의 성적이라고 바꾸어 부르지 않는다.
5. 보고에 예측 포함 범위를 확정할 칸이 없다면 그 한계를 표시한다. 이를 위해 06 보고 형식을 바꾸거나 새 inventory·보고를 작성하지 않는다.
6. 뒤의 보고 파일을 읽지 못하면 최신 보고 확인 필요를 표시하고, 이전 정상 보고는 그 id·시각과 함께 보여 줄 수 있다. 파일명 UTC 접두는 미확인 후보를 찾는 보조이며 읽지 못한 본문의 생성 시각을 인증하는 값은 아니다. 경고를 숨겨 이전 보고를 최신 정상으로 가장하지 않는다.

정상 미성숙 보고와 실제 보고 부재·손상 사례를 각각 시험한다. 성숙 자료를 실제로 만들거나 새 지표를 계산할 필요는 없다.

## 6. 머리말 시각과 가짜 자료의 일관성

- 선택 D에 여러 주 기록/회차가 섞이면 공개 확인뿐 아니라 입력 확정·성숙 상태 근거도 확인된 값의 범위 또는 “여러 시각/회차”로 표시한다. 임의의 한 행·가장 최근 모델 판을 모두의 근거로 붙이지 않는다.
- 해당 행의 실제 시각·판·상태 출처는 행 상세에 남긴다. PLAN의 단일 input_cutoff/maturity_basis가 여러 값을 표현하지 못하면 필요한 응답 칸만 보완한다. 새 계산·원천 조회는 없다.
- 첨부의 가짜 보고 경고 화면에는 D=10-30인데 공개 확인이 10-30 오전으로 남아 있다. 성숙 가짜 화면도 D와 입력 수신 시각을 함께 맞춘다. **완료 종가를 쓴 정상 전향 기록처럼 그리는 fixture는 D·입력·공개 확인·실제 마감의 관계를 맞춘다.**
- 서로 다른 미래 상황의 예시라는 표시를 유지한다. 가짜 행을 실제 신규 예측·성숙 결과로 기록하지 않는다. 날짜를 맞추려고 실제 06을 실행하지 않는다.

기본 배치와 긴 안내를 ? 안에 둔 방식은 수용한다. 이 보완은 문구·시각·상태 의미의 정정이며 전체 목업을 새로 설계하라는 지시가 아니다.

## 7. 구현·검증 범위 수용

PLAN의 읽기 모듈·API·작은 화면 컴포넌트·GET 한 개·기존 파일의 연결만 추가하는 방식을 수용한다. 실제 파일 수/줄 수는 구현 뒤 맞추고 예상치를 강제하지 않는다.

기존 records 읽기의 주 기록/영수증·재시도 규칙, 고정 연구 표본, 제한 예측만 반환, 원문 실패 사유의 경로 가림, 요청 경합 방지와 같은 표시 응답에서의 복사를 유지한다. 모델 로드·학습·성숙·SSH·외부 수집·쓰기 함수는 호출하지 않는다. 기존 report.write나 CLI를 조회 경로로 실행하지 않는다.

검증은 새 소비 경계·단위·실패 상태·선택 응답·기존 읽기 재사용과 위 보완에 한정한다. 미사용 파일의 생성 이력 인증·모든 기록을 함께 맞춘 위조 방지·성숙 전 성과 판정은 요구하지 않는다. 필수 검사가 끝나면 전체 연구·06/13·OCI를 다시 검사하는 라운드를 붙이지 않는다.

최종 사용자 실화면 확인은 현재 저장 기록의 읽기·대기 상태·행 상세·복사로 충분하다. 미래 성숙·다음 달 학습을 기다리지 않는다.

## 8. 다음 순서와 상태

1. 판정 원문을 보관하고 기존 PLAN에 질문 판정·§5~§6 보완을 덧붙인다. PLAN 재제출은 없다.
2. 목업의 문구/가짜 시각을 맞추고 사용자 목업 확인을 기록한다. 이미 확인된 배치를 처음부터 다시 승인받을 필요는 없다. 아직 사용자 확인이 없으면 그 확인 뒤 구현한다.
3. 구현 → 새/관련 검사 → 사용자 실화면 확인 → 검증자 → RESULT 판정으로 진행한다.
4. 문서 상태는 “PLAN PASS_WITH_REQUIRED_CORRECTIONS·보완 반영·사용자 목업 확인 여부”를 사실대로 나눠 적는다. 설계자의 이 판정 자체가 사용자 목업 확인이나 커밋/push 승인은 아니다.

기반 문서 추가 예외가 필요하지 않다는 판단을 수용한다. POC6-12 SOURCE_BLOCKED·13 종료·05/06 자동 운영·Q6 OPEN·운영 ML 미승격·기존 PUSH·미완료 요구는 유지한다. 같은 POC6 안의 handoff는 없다.

12·13 종료 문서의 stage 상태와 이후 커밋 여부는 실제 git에서 확인해 합산한다. 사용자 소유 handoff·연구 산출물·비공개 연구 브랜치는 포함하지 않으며 유효한 사용자 승인 범위를 적용한다.
