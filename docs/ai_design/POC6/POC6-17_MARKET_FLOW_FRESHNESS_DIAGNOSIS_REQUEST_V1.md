## 1. 이번에 답할 질문

**시장 자료를 갱신한 뒤에도 「시장 흐름」 문장이 ‘10/22까지’로 남은 이유는 무엇이며, 사용자가 최신 근거를 확인하려면 어느 연결을 보완해야 하는가?**

수집이 멈췄다고 미리 단정하지 않는다. 수집·저장, OCI와 PC의 역할, 조회의 기준일 선택, 화면의 캐시를 좁게 대조한다. 원인이 정상적인 날짜 선택이나 명시된 운용 경계이면 그 사실도 유효한 결론이다.

이번 목적은 투자 판단에 쓰는 자료의 연결을 확인하는 것이다. UI 정리와 별개로 필요한 작업이며, 새 ML 성능 실험은 아니다. POC6-15·16의 UI 정리 범위는 완료 상태를 유지한다. 전체 ‘자료 → 학습 → 예측 → 결과’ 상태 화면은 아직 없지만 이번에 함께 만들지 않는다.

## 3. 시간과 작업 경계

- **조사 상한은 준비·접속을 포함해 30분, 한 차례다.** 끝나면 확인한 범위와 남은 질문을 보고한다. 원인을 못 찾았다고 연속 조사나 전체 저장소 탐색으로 늘리지 않는다.
- 관련 코드, PC 운영 DB의 읽기 전용 조회, 기존 수집 로그·보관 목록, 필요한 OCI 읽기만 허용한다. 기존 접속이 안 되는 구간은 ‘미확인’으로 남긴다.
- 라이브 DB는 읽기 전용으로 연다. 최신 날짜 주변의 소수 행과 관련 실행 기록만 확인하고 전체 DB를 복사하거나 큰 자료를 다시 해시하지 않는다.
- 기존 `GET /market/flow-context`와 화면이 받은 응답을 대조할 수 있다. 새 공급자 호출 없이 저장 자료를 읽는 경로인지 먼저 확인한다.
- **외부 공급자 API 호출, 갱신 POST, 수집·pull·학습·예측·업로드 실행, DB 쓰기, cron·키·환경 설정 변경, 서버 재기동은 하지 않는다.** 기존 정기 작업을 멈추지도 않는다.
- API 키·토큰·계정·IP·개인 보유값은 회신에 넣지 않는다. 접속 정보 파일의 내용을 출력하지 않는다.
- 별도 PLAN·목업·성과 계산·검증자 라운드는 두지 않는다. 이번 회신은 원인 확인과 수정 범위 제안까지다.

## 4. 확인 순서 — 끊긴 구간을 찾으면 거기까지

### 4-1. 문장에서 저장 자료까지 거슬러 확인

1. 현재 PC의 `GET /market/flow-context` 응답과 「시장 흐름 자세히」·대시보드가 실제 사용하는 칸을 확인한다. 기존 `today_lines` 등 실제 필드명을 적는다.
2. ‘10/22까지’에 해당하는 날짜를 고르는 함수·조건을 찾는다. 수급의 마지막 유효일, 여러 자료의 공통 끝일, 고정 연구 기준일, 조회 기간 제한 중 무엇인지 구분한다.
3. 그 함수가 읽는 **실제 DB 경로·표·원천 구분**을 확인한다. 원/달러·WTI는 수급의 날짜 선택에 영향을 주는 범위까지만 함께 본다.
4. PC 표의 마지막 저장일과 문장에 실제 채택되는 마지막 유효일을 비교한다. 원시 최대 날짜만으로 최신이라고 판정하지 않는다.

### 4-2. 필요한 경우에만 OCI까지 연결

PC 저장 단계에서 원인이 설명되지 않거나 OCI와의 연결 확인이 필요하면 다음을 읽는다.

- 해당 자료의 OCI 최근 수집 실행 기록·보관 목록·운영 표. 이미 확인한 동일 자료는 다시 조회하지 않는다.
- 최근 실행의 성공 표시와 실제 자료의 마지막 유효일. 수집 시각이 오늘이어도 값의 기준일이 오늘인 것은 아니다.
- OCI 보관본을 PC 운영 표로 가져오는 코드가 **있는지**, 있다면 어떤 명령·버튼이 담당하고 언제 실행됐는지.
- PC의 「최신 시장 데이터 갱신」(`POST /market/refresh`)이 수급·환율·WTI를 어느 범위까지 갱신하도록 되어 있는지. 이번에는 이 명령을 실행하지 않는다.
- 관련 PC·OCI 코드 판이 다르면 해당 경로에 영향을 주는 차이만 기록한다. `git pull`이나 배포는 하지 않는다.

**OCI 보관 → PC 운영 표 연결이 원래 없으면 ‘기존 연결의 결함’으로 단정하지 않는다.** 승인된 역할 분리인지, 사용자 기대에 비해 빠진 요구인지 구분해 설계자에게 올린다.

### 4-3. 저장 값과 서버 응답이 맞으면 화면만 확인

서버 문장은 최신인데 화면만 옛 문장이면 기존 응답·캐시 키·성공 시각·다시 읽기 연결을 대조한다. 캐시를 강제로 지우거나 서버를 재시작해 증상을 없애지 않는다. PC DB부터 오래됐으면 화면 캐시 전수 점검으로 넓히지 않는다.

## 5. 회신 형식 — 날짜와 근거를 한 표에

먼저 **결론 3줄**을 쓴다: 확인된 원인 / 영향 범위 / 최소 후속 작업. 원인 미확정이면 후보와 미확인 구간을 구분한다.

다음 표를 채운다. 읽지 않은 칸은 빈칸 대신 ‘미확인’과 이유를 쓴다. 원/달러·WTI가 수급 문장의 끝일에 무관하면 코드 근거와 함께 그렇게 적고 조사를 줄인다.

| 자료 | OCI 수집·보관의 마지막 유효 자료일 | OCI 운영 표의 마지막 유효일 | PC 운영 표의 마지막 유효일 | API가 문장에 쓴 기간 끝·선택 이유 | 화면 표시 |
|---|---|---|---|---|---|
| 코스피 투자자 순매수 | | | | | |
| 원/달러 | | | | | |
| WTI | | | | | |

- 관측 시각(KST), 자료 기준일, 수집·저장 시각을 서로 구분한다. 0·없음·조회 실패도 구분한다.
- 원인 판단에 사용한 코드 경로·함수, 기존 갱신 담당 동작, 관련 실행 시각을 적는다. DB 경로는 저장소 기준 상대 경로 등 비공개 접속 정보가 없는 방식으로 쓴다.
- 최신성은 기존 기준과 공급자 날짜 의미로 판단한다. 이번 조사에서 새 지연 일수 기준이나 임의 영업일 규칙을 만들지 않는다.
- 같은 시각에 정기 수집이 진행됐다면 전후 차이를 기록하고, 관측 시각이 다른 값들을 같은 판으로 단정하지 않는다.
- 최소 후속안에는 수정할 연결·파일 범위, 데이터 쓰기·외부 호출·OCI 반영 필요 여부, 사용자에게 보일 동작을 적는다. 원인 설명에 필요하지 않은 숫자·전체 로그는 붙이지 않는다.

## 6. 원인에 따른 후속 판단

| 확인 결과 | 설계자가 정할 다음 범위 |
|---|---|
| 수집·저장이 실제로 지연 | 기존 수집 경로의 원인만 보완한다. 즉시 새 원천·전체 재수집으로 넘어가지 않는다. |
| OCI에는 최신 자료가 있으나 PC에는 없음 | 기존 수신·갱신 경로의 누락인지, 연결이 없는 운용 계약인지 확인해 필요한 연결만 설계한다. |
| PC 저장은 정상이나 API 날짜 선택·필터가 다름 | 기존 정의와 비교해 오류 여부를 정한다. 정상적인 공통 기간이면 각 자료 날짜를 어떻게 설명할지 정한다. |
| API는 정상이나 화면만 과거 값 | 해당 캐시·다시 읽기 연결만 보완한다. |
| 정해진 기준에 따른 정상 표시 | 코드 수정을 억지로 만들지 않는다. 사용자가 누를 동작 또는 날짜 설명이 부족한지만 판단한다. |
| 30분 안에 원인 미확정 | 확인된 구간과 빠진 근거를 제출한다. 다음 확인이 필요하면 대상·시간·기대 답을 좁혀 제안한다. |

여러 원인이 함께 있으면 확인된 것들을 나눠 적는다. **‘10/22’라는 글자만 최신 날짜로 바꾸거나, 다른 경로의 날짜를 대신 쓰는 수정은 하지 않는다.**

## 7. 제출과 완료 경계

이 요청서를 원문 그대로 보관하고, 회신은 대화에 위 형식으로 제출한다. 별도 조사 결과 파일은 필수가 아니다. 이번 확인만을 위한 커밋·push는 요구하지 않으며 사용자 소유 handoff 문서는 건드리지 않는다.

**이번 확인의 완료는 원인·영향·최소 후속 범위를 설명하는 데까지다.** 코드·데이터 변경은 회신을 본 뒤 설계자가 범위를 정한다. 이 조사 수용을 POC6-16 재판정, 최신화 완료, 전체 상태 화면 완료, 추천 효용 검증 또는 운영 ML 채택으로 기록하지 않는다.
