# POC6-25 PLAN 판정과 전체 통합설계 V1.1

작성: 총괄 설계자 · 2026-11-07(KST)  
판정: **PLAN PASS · Q1 (a) 수용 · 구현 승인 대기**

## A. PLAN 판정

### A-1. 결론과 근거

첨부된 POC6-25 개발 PLAN V1 전체와 원 설계 V1을 대조해 **PASS**로 판정한다. 최신 사용자 보고에 따른 POC6-24 CLOSED와 현재 보고 HEAD a3ac13ed를 유지한다. 설계자가 실제 저장소의 코드를 직접 검사한 결과는 아니다.

이번에 확정하는 범위는 **두 입력 필드(current_price·eval_amount)의 표시 세 곳**이다. 보유 행의 현재가, 같은 행 상세의 현재가, 상세의 평가금액이다. 이 판정과 B의 통합설계 V1.1이 원 설계·PLAN의 해당 부분보다 우선한다.

### A-2. Q1 — 상세 현재가도 정정: (a) 수용

수용 이유: 같은 current_price를 보유 행에서는 미확인, 펼친 상세에서는 0원으로 보이게 두면 사용자가 같은 값을 반대로 이해하게 된다. 이번 단일 목표를 완성하기 위해 같은 파일·같은 필드의 상세 표시를 함께 고친다.

| 위치 | 값 없음(null/누락) | 정상 숫자·명시적 0 |
|---|---|---|
| HoldingRow 현재가 | 현재 미확인 | 기존 표시 유지 |
| DetailRowFields 현재가 | 항목명 '현재가' · 값 '미확인' | 기존 표시 유지 |
| DetailRowFields 평가금액 | 항목명 '평가금액' · 값 '평가 불가' | 기존 표시 유지 |

형식화 전에 값 없음을 구분한다. 상세의 미확인 항목은 숨기지 않고 해당 자리에 표시한다. 행·상세의 확인된 매입가는 유지한다. 공통 숫자 함수·다른 화면·다른 필드로 확대하지 않는다.

### A-3. 시험·실행 방식과 범위 밖 보고

- 기존 실제 컴포넌트 렌더 시험 재사용과 null·정상·0·누락 네 경우를 수용한다. Q1을 반영해 상세의 현재가까지 단언한다. 수정 전 결함 경로의 실패와 정정 후 통과를 구분해 기록하며 정상·0원 대조까지 모두 실패해야 하는 것은 아니다.
- 프런트 타입·lint·전체 vitest·격리 사본 build를 완료 때 한 번 확인하는 계획을 수용한다. 백엔드 무변경이면 전체 pytest·라이브 DB 검사·변이 시험은 추가하지 않는다.
- PLAN §5②의 '저장소 .next 사용·삭제 없음'은 **build에 실제 저장소 .next를 사용하거나 삭제하지 않는다**는 뜻으로 명확히 적는다. 사본의 build 산출물과 원래 dev 서버가 정상 사용·갱신하는 .next는 구분한다. 프런트만 중지·복구하고 백엔드와 훅은 유지하는 방식은 수용한다.
- 상세 매입비중은 수정하지 않는다. 정상 저장 검증 경로에서는 해당 null 상황이 재현되지 않는다는 개발자 확인을 사실 보고로 받아 둔다. 모든 과거/손상 자료에서 발생 불가능하다는 결론으로 넓히지 않는다. 이번 정정·추가 조사·정식 BACKLOG 등록은 하지 않는다.

### A-4. 반영과 다음 절차

이 판정 원문을 보관하고 원 설계에 우선 적용 연결을 둔다. 기존 PLAN에는 Q1 수용·상세 현재가의 시험·build 문구만 반영한다. 상태는 'PLAN PASS · 구현 승인 대기'로 맞춘다. 새 PLAN 작성·원인 재조사·목업은 필요 없다.

이번 결정대로 반영하면 추가 설계자 재판정 없이 PLAN §5의 기존 네 항목 승인 묶음으로 진행한다. Q1의 세 표시 정정이 포함된 구현·시험, 프런트 중지/build/복구, 사용자 정상 화면 확인, 검증자 확인·설계자 최종 RESULT 뒤 커밋·push다. POC6-24 승인을 새 단계로 확장해 쓰지 않는다.

현재는 구현·시험·검증·종료가 완료된 상태가 아니다. 같은 계약 안의 구현 세부는 개발자가 정하고, 실제 접점에서 새로운 범위/데이터 의미의 충돌이 확인되면 그 부분만 다시 알린다.

## B. 전체 통합설계 V1.1

작성: 총괄 설계자 · 2026-11-07(KST)  
상태: 통합설계 V1.1 · PLAN PASS · 구현 승인 대기

### B-1. 현재 문제와 시작 근거

최신 종료 보고를 근거로 POC6-24를 IMPLEMENTED_VERIFIED_CLOSED로 인수한다. 구현 종료 f2782680·기록 a3ac13ed 모두 push됐고, 보고된 현재 HEAD는 a3ac13ed다. 해당 종료를 다시 판정하거나 검사하지 않는다. 설계자가 저장소를 직접 조회했다는 뜻은 아니다.

POC6-24 결과서 §4-4·§7과 최종 RESULT 판정 §4에서 두 표시 결함을 인수했다. 이번 PLAN에서 같은 상세의 현재가도 같은 원인임을 확인했으므로 아래 세 위치를 이번 범위로 확정한다.

- 시세 없는 보유 행의 현재가가 '0원'으로 보인다.
- 행 상세의 계산되지 않은 평가금액이 '0원'으로 보인다.
- 같은 행 상세의 현재가도 시세가 없는데 '0원'으로 보인다. 보유 행과 같은 current_price 필드의 표시다.

보고된 원인은 기존 fmtMoney 호출에 값 없음이 들어가면서 숫자 변환 과정에서 0으로 보이는 것이다. 원천 시세나 평가금액이 실제 0으로 저장됐다는 뜻은 아니다. POC6-24에서 자금 카드와 비중의 null 구별은 이미 완료됐다. 이 사실을 다시 조사하지 않는다.

### B-2. 이번 Step의 단일 목표

**「보유 현황」의 현재가(행·상세)와 평가금액(상세), 세 표시에서 미확인·평가 불가와 확인된 실제 0원을 구별한다.**

사용자가 해야 할 과업은 보유 행과 상세를 보며 '값이 0인 것인지, 시세가 없어서 알 수 없는 것인지' 구분하는 것이다. 새 기능·배치·데이터 계산을 추가하지 않는다.

### B-3. 표시 계약

| 위치·입력 상태 | 표시 |
|---|---|
| 보유 행의 현재가가 없음(null 또는 기존 응답에서 값 누락) | 현재가 자리에 '현재 미확인'. 매입가 등 확인된 기존 값은 유지한다. 미확인 값에 원 단위를 붙여 0원처럼 만들지 않는다. |
| 행 상세의 현재가가 없음(null 또는 값 누락) | 기존 항목명 '현재가'에 값 '미확인'을 표시한다. 보유 행의 '현재 미확인'과 뜻이 같아야 한다. |
| 행 상세의 평가금액이 없음(null 또는 값 누락) | 평가금액 자리에 '평가 불가'. 임의로 수량×다른 가격을 계산하거나 0으로 채우지 않는다. |
| 확인된 정상 숫자 | 기존 금액·단위·반올림·색상·배치를 유지한다. |
| 원시값이 명시적인 숫자 0 | 값 없음으로 바꾸지 않고 기존 0원 표시를 유지한다. 현재가의 유효성 판단 등 기존 API 계약을 새로 정의하지 않는다. |

분기는 형식화 전의 값 없음 여부로 한다. 0과 미확인을 함께 처리하는 조건을 사용하지 않는다. API 응답·보유 정본·평가 계산·비중 분모는 그대로다.

기존 행의 매입가→현재가 위치와 상세의 현재가·평가금액 위치를 사용한다. 설명을 상세 도움말에만 숨기지 않고 해당 값 자리에서 바로 구별되게 한다. 상세 펼침·접힘과 기준일·자료 상태 표시는 유지한다. 신규 카드·메뉴·상태 체계·경고 등급은 만들지 않는다.

### B-4. 변경 범위와 우선 접점

접점은 frontend/app/components/EnrichedHoldingsSection.tsx 한 제품 파일이다. HoldingRow의 current_price, DetailRowFields의 current_price·eval_amount 표시에서 형식화 전에 값 없음을 구분한다. PLAN에서 확인된 이 접점과 기존 EnrichedHoldingsSection.eval.test.tsx 렌더 시험을 재사용한다.

이 두 필드의 접점은 확인됐으므로 다시 조사하지 않는다. 내부 분기·변수명·시험 배치는 같은 계약 안에서 개발자가 정한다. 공통 fmtMoney·toFiniteNumber의 모든 호출자나 저장소 전체를 조사·수정하지 않는다. 매입비중은 이번 수정 대상에 넣지 않는다.

유지할 것: 기존 정상 금액·손익·비중·부분 합계 경고, POC6-24의 자금 카드·저장·AI 원문·정상 0원, 기존 레이아웃과 사용자 최종 판단.

제외: 공통 숫자 처리 전역 정비, 다른 화면의 일괄 정정, 자금/보유 저장 변경, API·DB·시세 수집·외부 조회·OCI·PUSH·PARAM·연구/ML 변경, Cleanup. 지정 범위 밖의 별도 결함이 확인되면 사실만 알리고 이번에 자동으로 합치지 않는다.

### B-5. 완료 기준 AC

1. 시세 없는 보유 행에서 현재가가 '현재 미확인'으로 표시되고, 같은 자리의 잘못된 0원 표시가 사라진다. 확인된 매입가는 유지된다.
2. 상세를 펼치면 현재가가 없을 때 '현재가 미확인', 미계산 평가금액은 '평가금액 평가 불가'로 구별된다. 확인된 정상 금액과 명시적 0원은 기존대로 표시된다. 값 없음 때문에 해당 항목 자체를 숨기지는 않는다.
3. 화면이 입력 데이터를 변경하거나 새 금액을 계산하지 않는다. 부분 평가의 기존 경고·자금 합계 미계산·두 비중·가격/현금 기준일 계약이 유지된다.
4. 기존 가상 응답으로 실제 보유 컴포넌트를 렌더하고 상세를 펼쳐 세 위치를 확인한다. 시세 없음(null)·정상 숫자·명시적 0·필드 누락 네 경우를 대조한다. 수정 전에는 미확인 경로의 결함 단언 실패를 확인하고 정정 뒤 통과를 본다. 정상/0원 대조는 수정 전에도 통과할 수 있다. 단순 문구 상수나 새 helper만 검사해 실제 호출부의 정정을 놓치지 않는다.
5. 변경에 필요한 프런트 검사와 회귀를 통과한다. 관련 렌더 시험을 먼저 수행하고 프런트 타입·lint·build 및 프런트 전체 회귀는 완료 시 한 번 확인한다. 백엔드 무변경이면 전체 pytest·라이브 DB 검사·변이 시험은 이번 요구에 넣지 않는다.
6. 실제 「보유 현황」에서 기존 정상 행·상세 배치가 유지됨을 확인한다. 미확인 사례가 실제 보유에 없으면 격리된 가상 응답과 동일 컴포넌트로 확인하며, 실제 데이터를 고치거나 새 시세 조회로 사례를 만들지 않는다. 실제 금액·계좌 정보·개인 화면은 결과 문서에 옮기지 않는다. 검증자 확인과 설계자 최종 RESULT로 완료를 판단한다.

### B-6. 진행과 종료 경계

제출된 짧은 PLAN을 PASS로 판정했다. 개발자는 Q1의 상세 현재가와 해당 시험만 기존 PLAN에 반영한다. PLAN을 다시 작성하거나 이미 확인된 원인을 재조사하지 않는다. 구조·배치는 그대로이므로 별도 목업과 승인 라운드는 요구하지 않는다.

다음은 기존 PLAN §5의 네 항목을 한 묶음으로 승인받는 절차다. 구현·가상 응답 시험, 프런트 dev 서버만 일시 중지한 격리 사본 build와 원래 서버 재기동/HTTP 200 확인, 사용자 정상 행·상세 배치 확인, 검증자·설계자 최종 RESULT 뒤 종료 반영이 포함된다. build는 사본의 .next를 사용하고 실제 저장소 .next를 build에 사용·삭제하지 않는다. 원래 dev 서버의 정상적인 .next 사용·갱신과는 구별한다. 백엔드는 유지한다. POC6-24의 일회성 승인을 재사용하거나 전역 훅을 변경·우회하지 않는다.

이번 Step은 두 입력 필드의 세 표시 정정에서 끝낸다. 다른 화면의 미확인 표시·개인 파일 보호 등 기존 별도 항목을 이 설계의 완료 조건으로 추가하지 않는다. 더 넓은 정비 필요는 실제 추가 사례가 확인될 때 별도 판단한다. 새 모델·운용 문턱·후속 실험은 여기서 정하지 않는다.
