## 1. 근거와 열람 범위

첨부 결과서 전체(379줄, §0~§11)를 PLAN 판정과 대조했다. 코드 정정의 동작은 검증자 r2의 독립 재현·정상 대조를, 실제 연결과 사용성은 개발자의 앱 확인 보고 및 사용자의 2026-11-02 실화면 확인을 근거로 수용한다. 설계자가 사용자 저장소·git index·실서버·연구 파일을 직접 확인하거나 시험을 실행한 판정은 아니다. 이번 첨부에는 실제 앱 캡처가 없어 설계자가 최종 화면을 직접 조작·시각 검수했다고 기록하지 않는다.

- 심사한 결과서 SHA-256: `19c8b7bbe8f5490c01edfffecf66612d83d3e3906a04104ede3197dd596ff890`
- 대조한 PLAN 판정 SHA-256: `5a5a6d9b9cd2c1421e427c390040041b04fac16a0135e9c142fa40998db74cd0`

이 해시는 이번 심사 판을 식별한다. 아래 종료 기록을 붙인 뒤 결과서 해시가 달라지는 것은 정상이다.

검증자 r2의 관련 시험 249건과 기존 독립 재현·대조 5건, 합계 254건 및 정적 검사 통과를 수용한다. 개발자 프런트 전체 77파일·1063건과 정정 변이 2종은 개발자가 실행한 근거로 구분한다. 이를 설계자가 반복 실행했거나 백엔드·연구 모델까지 재검증한 것으로 쓰지 않는다.

## 2. 수용하는 구현과 정정

| 항목 | 판정 |
|---|---|
| 「ML 연구」 폴더와 두 화면 | 수용. 기존 `ml`은 ‘예측과 결과 비교’ 1카드, 새 `ml_legacy`는 ‘이전 자료·실험’ 5카드다. |
| 두 자료 흐름의 구분 | 수용. 이전 자료를 다시 만들어도 현재 예측 비교의 입력·모델이 갱신되지 않는다는 설명을 보존한다. |
| 결론·주요 버튼 우선, 상세·개발 정보 접기 | 수용. 현재 결론을 위에서 읽고 필요한 근거로 내려갈 수 있게 정리했다. |
| 쉬운 한국어·숫자·날짜·원문 | §3의 두 표시 보완을 전제로 수용. 원시 식별자를 상세에 남기고 값·단위·계산 의미는 유지한다. |
| 폴더·선택 화면·조회 분리 | 수용. 접기·펼치기는 본문 재조회/초기화 없이, 메뉴 이동은 명령 호출 없이 동작한다. |
| 공용 표시 부품·오류 요약·시각 표시 | 수용. 작은 부품으로 결론과 개발 정보를 공유하고, 날짜를 해석할 수 없을 때 원문을 보존한다. |
| r1 F1 정정 | 해소 수용. 세 비교의 존재 여부를 결론·표·복사문이 같은 함수로 판단하고 각 분모를 보존한다. |

F1에서 중요한 것은 **네 방법 공통 행이 0이어도 일부 방법의 비교 결과는 있을 수 있다**는 점이다. HGB만·MLP만·서로 다른 줄에서 비교 가능한 경우를 포함한 기존 재현과 정상 대조가 r2에서 모두 통과했다. 비교별 건수를 합쳐 하나의 공통 분모로 만들거나, ‘비교 결과 있음’을 모델의 우위·채택 결론으로 해석하지 않는다.

결과서 §4-1의 오래된 CLI 안내 정정, 지표 설명을 실제 계산 의미에 맞춘 정정, 미채택 원문의 개발 정보 이동, 현재 상태와 원문 보존, 카드별 독립 검토에서 정정한 13건을 이번 표시 개선 범위로 수용한다. 명령 핸들러·막힘 조건·반복 조회·API를 유지한 대조와 검증자 확인을 근거로 한다.

사용자 요청에 따라 코드 검증을 먼저 하고 실화면 확인을 나중에 마친 순서도 수용한다. 실화면 대기를 코드 결함처럼 재검증할 필요는 없다. r2의 ‘코드 검증 범위’는 그때의 범위로 보존하고, 이후 완료된 사용자 확인을 별도 사실로 연결한다.

## 3. 종료 전 표시 문구 두 곳만 보완

결과서 §5에 공개한 아래 두 한계는 데이터/계산을 고치지 않고도 기본 결론의 과한 표현을 줄일 수 있다. 사용자에게 먼저 보이는 결론을 정확히 만드는 이번 목적에 따라 표시 문구만 정리한다.

| 위치·현재 문구 | 최종 표시 | 유지할 것 |
|---|---|---|
| 상대상승 참고점수의 `unavailable` → ‘데이터 부족’ | **‘결과를 사용할 수 없음’** | 바로 아래 기존 응답 사유. 파일 손상·실행 기록 없음·학습 자료 부족·후보 0건의 실제 원인을 새로 추정하지 않음 |
| Baseline의 보고 `ok` 배지 → ‘계산 정상’ | **‘보고 있음’** | 아래 경고·오류·날짜 순서 이상을 그대로 표시. 보고 존재와 모든 점검 정상 여부를 구분 |

이는 기존 상태의 **한글 표시만 바꾸는 수정**이다. 상태 분기·오류 판정·버튼 조건·백엔드·산식·응답을 고치지 않는다. 필요한 경우 짧은 설명 ‘점검 결과는 아래 경고·오류를 확인하세요’를 함께 둘 수 있다. 미채택·연구용 표시는 유지한다.

두 카드의 기존 시험 기대 문구를 맞추고 해당 카드 시험만 한 번 실행한다. 이 문자열 정리 때문에 새 시험 체계·전체 프런트 회귀·사용자 실화면 재확인·검증자 재검증을 요구하지 않는다. 지정한 문구·설명 외 새 동작 변경을 추가하지 않는다.

## 4. 수용하는 한계와 남길 범위

다음은 결과서 §5에 남기며 이번 완료로 해소했다고 적지 않는다.
- 자료 → 학습 → 예측 → 결과 전체의 실제 상태 화면은 아직 없다.
- 상대상승의 ‘아직 계산 안 함’은 이 화면에서 아직 실행하지 않았다는 뜻이며, 과거 실행 기록이 없다는 인증이 아니다. 기존 요청 오류 핸들러가 버리는 원문은 이번에 복구하지 않았다.
- 해석하지 못하는 시간 형식은 원문으로 보이고, 실제 사용 환경 밖 모든 브라우저의 시간 해석까지 보장하지 않는다.
- 자료 점검 응답이 null일 때의 화면 중단, 죽은 작업이 ‘실행 중’으로 남을 때의 반복 조회 등 기존 동작은 미해소다. 이번 수정으로 모든 비정상 응답·작업 복구 경로가 견고해졌다고 선언하지 않는다.
- 1000px 일부 표의 줄바꿈은 가로 넘침 없이 확인된 배치의 한계로 수용한다.

이 한계들을 이유로 이번에 백엔드 복구·작업 만료 판정·API 방어 전반으로 범위를 넓히지는 않는다. 이미 존재하는 결함 기록이 있으면 그 식별자를 유지하고 중복 등록하지 않는다. 실제 사용을 막는 문제가 확인되면 별도 현재 결함으로 처리하며 대시보드 개선 완료에 묻어 두지 않는다.

실제 비교 결과가 아직 0인 화면과 일부 방법만 비교 가능한 가짜 자료의 검증은 서로 다른 근거다. 사용자에게 아직 오지 않은 성숙 결과를 확인받으려고 기다리거나 연구를 재실행하지 않는다.

## 5. 문서 정리·커밋·종료

1. 이 판정 원문을 보관하고 결과서 다음 절(현재 기준 §12)에 붙인다. §3 표시 보완과 해당 시험 결과를 짧게 덧붙이며 기존 개발·검증 기록을 재작성하지 않는다.
2. 결과서 상단 `VERIFIER`의 ‘사용자 실화면 확인·설계자 RESULT 판정은 별도 대기’는 현행 상태에 맞춘다. **실화면은 11-02 완료, 코드 검증은 r2 VERIFIED, 설계자는 본 판정**으로 나누어 적는다. 검증자 §10·§11의 당시 대기 문장은 원문이므로 보존한다.
3. 결과서·PLAN·STATE·PROGRAM_TRUTH의 현행 상태를 맞춘다. 원문·과거 측정 기록은 보존하며 한계는 미해소로 남긴다.
4. 실제 최종 변경 파일·stage와 작업 트리 일치·서식 검사를 확인하고, 해당 파일 목록을 근거로 사용자에게 커밋·push를 한 번에 승인받는다. 이미 유효한 승인이 있다면 그 범위를 따른다. 보고된 31개는 판정 원문 추가 전이므로 최종 수를 다시 센다.
5. 승인된 커밋·push와 PC 반영 확인이 끝나면 `IMPLEMENTED_VERIFIED_CLOSED`로 기록하고, 실제 커밋·push·PC 반영 사실만 짧게 보고한다. 지정 문구 보완·문서 정리만 마쳤다면 추가 RESULT 재판정은 없다.

이번 두 문구 변경은 기존 개발 서버 자동 반영과 응답/화면의 짧은 확인으로 반영 사실을 남기면 된다. 사용자가 두 화면을 다시 전부 확인할 필요는 없다. OCI pull·cron·키·새 수집·업로드·모델 실행·별도 handoff는 이번 종료에 필요 없다.

사용자 소유 handoff·연구 산출물·개인 캐시·로컬 전용 연구 브랜치는 넣지 않는다. 이 판정은 사용자 커밋·push 승인을 대신하지 않는다.

## 6. 이번 진전과 다음 설계의 기준

이번 완료는 **현재 연구와 이전 실험을 구분하고, 결론을 먼저 읽고, 쉬운 말로 근거를 확인하도록 만든 사용성 개선**이다. 투자 판단을 돕는 시스템의 실제 진전으로 기록한다. UI 개선을 단지 ML 성능 개선의 보조 작업으로 취급하지 않는다.

사용자와 합의한 기준은 다음과 같이 유지한다. 자료의 정확한 축적, 이해하기 쉬운 화면과 동선, 검증된 ML 활용을 함께 발전시키되 어느 하나가 전체 목적을 대신하지 않게 한다. ML 활용은 계속 중요한 미완료 요구이며, 이번 완료를 추천 효용 검증·총수익 확보·운영 ML 채택으로 확대하지 않는다. Q6 OPEN·기존 미완료 요구·12 SOURCE_BLOCKED·05/06/13 운영을 유지한다.

다음 설계는 **기존 대시보드의 요약 구조와 이동 동선 재정비**를 대상으로 한다. 늘어난 정보를 새 요약으로 무조건 복제하지 않고, 현재 대시보드·영역별 요약·상세가 맡는 역할과 연결을 먼저 좁게 확인한다. 자료 → 학습 → 예측 → 결과 현황 요구도 이 과정에서 기존 자료로 어디까지 제공할 수 있는지 구분한다. 구체적인 카드·조회·구현 범위는 별도 설계에서 정한다.
