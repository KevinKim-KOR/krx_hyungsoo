## 2. Q1 — pull 안의 동시 실행 잠금 수용

**(a) 수용.** 임시 칸을 정리하는 현재 동작과 병행 실행이 실제로 충돌하므로, `transfer.pull`에 같은 PC 보관 루트 기준의 기다리지 않는 잠금 하나를 둔다. CLI 바깥에만 두지 않아 06의 함수 호출도 같은 보호를 받게 한다.

이는 설계 §3 ‘05 pull 동작 유지’의 **동시 실행에 대한 한정 보완**이다. 전송 대상·공개 형식·기존 검증·운영 DB 쓰기 금지는 유지한다. pull/export가 수급 표에 쓰도록 바꾸는 허용이 아니다.

필수 동작:

1. 잠금을 얻은 뒤에 임시 칸 정리·전송·검증·공개를 시작한다. 잠금을 못 얻은 쪽은 다른 실행의 임시 칸을 지우거나 수정하지 않는다.
2. 경합은 즉시 ‘다른 가져오기 진행 중’으로 끝나며 기계적으로 구분할 이유를 남긴다. 성공·자료 손상으로 바꾸지 않는다. 기존 출력·종료 규약과 호출자의 처리를 유지한다.
3. 잠금은 자기 전송·임시 쓰기가 끝날 때까지 유지한다. 정상 종료·예외·중단 뒤에 후속 실행을 영구 차단하는 잠금이 남지 않아야 한다.
4. 버튼 쪽 150초 상한을 수용한다. 시간 초과 시 pull의 하위 전송 프로세스까지 종료·회수돼, 잠금이 풀린 뒤 이전 전송이 계속 쓰지 않게 한다. 기존 프로세스 정리 수단을 재사용하고 범용 작업 관리기를 추가하지 않는다.
5. 정상 pull, 두 pull 경합, 시간 초과 뒤 재실행을 격리 확인한다. 06에서 경합을 받으면 기존 실패·재시도 규약으로 처리되고 새 주 기록을 거짓 성공으로 만들지 않는지 확인한다. 06·13의 학습·실행 규칙 변경은 요구하지 않는다.

## 3. Q2 — 검증된 PC 보관본 반영 수용

**(a) 수용.** 전송 실패와 이미 공개·검증된 입력의 사용 가능성은 별개다. 네트워크·SSH 실패, 시간 초과, 다른 pull 진행 중일 때 이번 17 수급 단계는 PC에 있는 유효한 미반영 사본을 사용할 수 있다.

- 반영 시작 때 사용할 **공개 완료 묶음 목록을 고정**하고 실제 수급 참조·hash·내용을 검증한다. 진행 중 임시 파일이나 미완료 묶음은 읽지 않는다.
- 전송 실패를 입력 검증 생략의 이유로 삼지 않는다. 손상·충돌·형식 오류가 난 반영 대상 묶음은 실패 처리한다. 알 수 없는 모든 예외를 ‘PC 사본 사용’으로 넘기는 처리는 금지한다.
- 최신 원격 목록을 확인하지 못했으므로 ‘OCI 최신 수급과 일치’라고 쓰지 않는다. 정상 반영됐다는 사실과 새 OCI 자료 확인 여부를 구분한다.
- 가져오기와 반영 결과를 별도로 보존·조회한다. 기존 단계 기록과 반영 표를 사용하고 `flow_link`는 필요한 만큼만 확장한다. 전송 실패 뒤 반영 성공을 일반 `applied` 하나로 정상화하지 않는다.
- 문구 예: **‘가져오기 실패 · PC에 이미 받은 10/30까지의 수급 반영 완료 · 새 OCI 자료는 확인하지 못했습니다.’** 경합이면 ‘다른 가져오기 진행 중’을 사용한다.
- 유효한 미반영 자료가 없으면 ‘기존 PC 수급 유지’와 해당 전송 상태를 표시한다. 같은 사본뿐인데 새 자료를 반영했다고 쓰지 않는다.
- 이 예외는 **17 버튼의 수급 단계에만** 적용한다. 06의 `run --pull` 실패를 기존 사본으로 통과시키는 변경은 하지 않는다.

설계 §3의 ‘실패하면 기존 PC 수급 유지’는 입력 검증·반영 실패에 그대로 적용한다. 전송 실패 뒤 유효한 기존 사본 사용은 이번 판정으로 명확히 허용한다. 직접 키움 조회로 대체하지 않는 경계는 유지한다.

## 4. 구현 전에 반영할 보완 조건

### 4-1. 같은 값도 최신 관측 순서를 보존

PLAN의 ‘값이 같으면 출처·시각을 그대로 둠’은 그대로 적용하지 않는다. 예를 들어 기존 행 관측이 10/23이고, 11/02 관측에서도 값이 같았는데 행 시각을 10/23으로 남기면, 뒤늦게 온 10/25의 다른 값이 최신 값으로 잘못 들어올 수 있다.

**같은 값이라도 OCI `observed_at`이 더 늦으면 현재 행의 관측 기준을 그 시각까지 갱신한다.** 기존 `collected_at`과 `…_VIA_OCI` 출처를 사용한다. 값 정정 건수와 동일값의 출처·시각 갱신 건수는 구분한다. 원본 보관본·과거 실행 기록은 바꾸지 않는다.

- 더 과거 관측은 값이 같아도 최신 관측 기준을 내리지 않는다.
- 같은 관측 시각의 다른 값은 충돌이다. 시각이 불명인 기존 행의 다른 값을 임의로 덮지 않는다.
- 이미 반영한 동일 묶음의 재실행은 시각을 새로 만들지 않는다.
- 회귀 사례는 **동일값의 최신 관측을 반영한 뒤, 그보다 과거인 다른 값이 도착하는 순서**를 반드시 포함한다.

따라서 최초 반영의 실제 쓰기 범위는 신규 6일만이 아닐 수 있다. 기존 동일값 행의 출처·관측시각 갱신 범위도 실제 승인 설명과 RESULT에 적는다.

### 4-2. 최초 실패 묶음과 손상된 반영 대상을 구분

초기 두 일일 묶음은 수급 FAILED·object 없음이라고 보고됐다. 이를 정상 반영 입력으로 삼지 않으며, **이 두 묶음 때문에 뒤의 정상 수급을 영원히 반영하지 못하게 하지 않는다.**

- 명시된 수급 수집 실패·미시도 묶음은 반영 대상에서 제외하고 수집 상태 근거로만 유지한다.
- 유효한 수급을 가졌다고 표시된 반영 대상의 object 손상·누락·충돌은 해당 묶음 실패이며 거기서 멈춘다.
- 다른 자료 때문에 묶음 전체가 PARTIAL이어도 수급 자체가 정상이라면 반영할 수 있다.
- 수급 자체가 PARTIAL이면 반환된 수급 object 전부의 검증을 통과한 범위만 묶음 단위로 반영할 수 있다. 실패·미시도 날짜는 채우지 않고 미완료 상태를 남긴다.
- 최신 수집 상태는 실제 수집·공개 시각을 보고 판단한다. 옛 실패보다 뒤의 수급 성공이 있으면 옛 실패를 현재 장애로 표시하지 않는다.

이미 반영한 묶음의 입력을 다시 값에 적용하지 않는 안은 수용한다. 같은 run_id의 manifest hash 충돌은 계속 확인한다. 기존 운영 표에 반영된 과거 object의 전수 재검증을 새 수급 반영 조건으로 요구하지 않는다.

### 4-3. 시각·숫자와 최신 판 선택

run_id는 식별자와 결정적인 순회 순서로 쓸 수 있으나 **수집 시작 시각만으로 최신 관측을 판정하지 않는다.** 값의 우선순위는 시간대가 명확한 `observed_at`을 해석해 판단한다. 이번 판정은 같은 묶음 안의 여러 시각도 행별 비교로 보호하는 방식을 수용한다.

지수값은 bool이 아닌 **유한한 양수**로 검사한다. NaN·무한대, 시각의 시간대 미상은 확인 필요로 처리하며 로컬 시간대로 추정하지 않는다. 기존 ±0.005 지수 대조 규칙은 유지한다. 순매수는 이미 원 단위인 정수이므로 환산을 다시 하지 않는다.

### 4-4. 기준일 제한과 할 일의 우선순위

- `D < min(kospi_E, flows_E)`이면 두 최신일이 서로 달라도 공통 날짜의 결측을 확인해야 한다. ‘두 최신일이 같은데 D가 이른 경우’만 gap으로 처리하지 않는다. 공통 날짜가 없으면 D·제한 원인을 확인할 수 없는 상태로 둔다.
- **확인된 최신 OCI 수급 수집 실패 안내는 반복 갱신 버튼 생성보다 우선한다.** `limited_by=flows`가 함께 있어도 ‘다시 누르면 해결’ 할 일을 만들지 않는다. 기존 다른 자료의 할 일은 유지한다.
- Q2의 전송 실패·경합과 실제 자료일을 함께 표시한다. 전송 실패만으로 수급 값이 오래됐다고 단정하지 않는다.
- 같은 작업 버튼 하나, 원/달러·WTI 최신 단기 날짜 보존, 네 출력의 공통 설명이라는 PLAN 방향은 수용한다.

## 5. 새 표와 실제 확인 방법

`market_investor_flow_import` 한 표의 설계는 수용한다. 반영할 자료와 manifest 식별·반영 기록은 같은 트랜잭션의 성공 경계에 둔다. 전체 import 작업 중 앞 묶음만 성공하면 실제 완료 범위와 실패한 묶음을 구분한다.

**첫 실제 확인은 (나) 같은 핵심 함수의 단독 실행(pull + 반영)을 기본안으로 권고한다.** 이번 연결과 관계없는 공급자를 다시 호출할 필요가 없다. 실제 반영 뒤 기존 GET·화면·복사문을 읽어 D와 설명을 확인한다. 기존 전체 버튼의 호출 연결·완료 문구는 격리 관통 시험으로 먼저 확인하며, 성공한 단독 확인 뒤 전체 버튼 재실행을 필수로 요구하지 않는다.

실제 적용 전 개발자는 다음을 한 묶음으로 제시한다.

1. 기존 시장 DB의 새 표 생성과 수급 행·동일값 출처/관측시각 갱신.
2. 05 pull의 경합 처리 보완과 실제 확인 중의 기존 SSH 읽기·보관 사본 쓰기.
3. (나) PC 실제 반영 1회 및 이후 읽기 확인. 외부 공급자 호출·OCI DB 쓰기·수집·cron·키 변경 없음.
4. 해당 시점의 커밋·push 범위. 기존에 같은 승인 범위를 받았다면 다시 묻지 않는다.

이 PLAN 판정은 설계·코드·임시 DB 시험 진행을 허용하는 것이며 실제 PC DB 쓰기 승인을 대신하지 않는다. 승인은 사용자가 실제 범위를 검토할 수 있는 상태에서 한 번에 받는다. 지금 IP 등록이나 집에서 키움 직접 조회를 선행할 필요 없다.

## 6. 검사·진행·종료

PLAN 시험에 §2~§4의 경합·시간 초과 정리, 전송 실패/반영 성공 분리, 동일값 최신 관측 뒤 과거 다른 값, 초기 수집 실패 제외, gap·할 일 우선순위를 더한다. 정상 pull과 06 호출 경계의 관련 검사는 필요하지만 과거 학습·성과·GPU 실행은 다시 하지 않는다. 전체 회귀는 PLAN대로 관련 검사 뒤 마지막 한 번 시행한다.

설계·판정 원문과 조사 회신 핵심을 보관하고 PLAN을 고친 뒤 구현한다. **이 보완만을 위한 PLAN 재제출·추가 조사·전체 목업은 필요 없다.** 구현·부분 화면 문구 확인·검증자 확인 뒤 RESULT 판정을 요청한다. RESULT에는 새 표·실제 쓰기 범위·동시 실행 예외와 검증 범위를 명시한다.

기존 05 pull/export의 운영 DB 쓰기 0, 06·13 실행 규칙 유지, OCI 수집 유지, 운영 ML 미승격·Q6 OPEN을 유지한다. 기존 POC6-15·16은 다시 열지 않는다.
