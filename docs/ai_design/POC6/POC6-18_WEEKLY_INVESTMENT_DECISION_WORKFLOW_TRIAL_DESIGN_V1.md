# POC6-18 설계 V1 — 주간 투자 판단·기록·다음 검토의 사용 흐름 확인

작성: 2026-11-02 · 설계자 → 개발자·사용자
저장: `docs/ai_design/POC6/POC6-18_WEEKLY_INVESTMENT_DECISION_WORKFLOW_TRIAL_DESIGN_V1.md`
단계: **기존 기능의 사용 확인부터. 새 코드·수집·모델 실험을 전제하지 않는다.**

## 1. 목적과 방향

**기존 자료·비교·판단 근거·AI 세션·기록을 사용해 ETF를 검토하고, 그 판단을 기록한 뒤 다시 꺼내 다음 검토로 이어갈 수 있는지 확인한다.** 실제로 끊기는 부분이 있을 때만 필요한 보완을 정한다.

최근 15·16의 UI 정리와 17의 수급 연결은 완료를 유지한다. 이제 상태 화면·자료원을 계속 늘리는 것보다 사용자 판단의 한 흐름을 확인한다. 기존 기능으로 충분하면 추가 개발 없이 사용 단계로 넘어가는 것도 이번 단계의 정상 결과다.

이미 합의한 주 1회 정기 검토, 수주~수개월 기대 보유, 비용 후 KODEX200 대비 초과성과라는 목적을 다시 협의하지 않는다. 이 단계에서는 관측·AI 토론·사용자 판단의 사용 가능성을 확인하며, 추천의 성과나 ML 효용까지 입증했다고 쓰지 않는다.

## 2. 지금 추가 수집이 필요한가

**첫 확인에는 추가 수집이 필요 없다.** 17 종료 보고에서 수급과 공통 기간 끝이 10-30까지 반영됐고 가져오기도 정상이었다. 이 자료의 실제 기준일을 명시한 채 검토·기록 흐름을 확인할 수 있다.

- 11-02 수급은 예정된 11-03 09:40 OCI 수집이 성공한 뒤 다음 PC 반영에서 들어온다. 집에 도착했다는 이유로 같은 수급을 직접 다시 조회하지 않는다.
- 이번은 저장 자료로 진행하는 사용 흐름 확인이다. 10-30 자료를 오늘 확정 자료라고 쓰거나 그 자료만으로 즉시 실거래를 유도하지 않는다.
- 이후 실제 투자 판단 때는 화면의 기존 자료 상태를 확인한다. 확인된 지연이 판단을 막는 경우에만 해당 기존 갱신 동작을 안내한다. 먼저 모든 수집·전체 이력·키움 인증을 재실행하지 않는다.
- 기존 OCI 수집·맥북 전향 기록은 계속 운영한다. 이번 단계 때문에 일정을 바꾸거나 별도 실행을 추가하지 않는다.

설계자는 현재 PC를 새로 실측하지 않았다. 현재 화면이 이 보고와 달라졌으면 개발자가 그 차이만 기록한다.

## 3. 사용할 두 사례

| 사례 | 수행할 검토 | 실제로 확인할 것 |
|---|---|---|
| A · 비보유 ETF 한 개 | 신규 진입을 검토하거나 보류 | 후보를 고른 이유, KODEX200과의 기존 비교 근거, 반대 근거·자료 한계, 사용자 판단을 남길 수 있는가 |
| B · 보유 ETF 한 개 | 유지·축소·청산 검토 또는 판단 보류 | 보유 검토 근거, 이전 판단을 바꿀 사유, 사용자 판단을 남기고 다시 열 수 있는가 |

사용자가 대상을 고르면 그대로 사용한다. 준비 단계에서 선택이 없으면 개발자는 현재 접근 가능한 각 목록의 코드순 첫 항목을 **기능 확인용 임시 사례**로 준비할 수 있다. 그 선택은 매수 추천·성과 표본 선정이 아니며 실제 판단과 기록 대상은 사용자와 구분한다.

- 기존 개인 보유는 사용성 확인에만 쓴다. 시스템 이전 매수 손익을 시스템·ML 성과로 계산하지 않는다.
- 실제 매매를 하지 않았다면 매매 이력에 가짜 매수·수량·평단을 입력하지 않는다. 판단 보류도 유효한 결과다.
- 자료 부족이 실제로 드러나면 그 한계와 보류를 기록한다. 성공 화면을 만들려고 결측을 숨기거나 실제 자료를 일부러 손상시키지 않는다.
- 검토 권고와 사용자 결정을 구분한다. 기각된 모델을 운영 추천으로 복귀시키거나 새로운 매수·매도 임계값을 임의로 만들지 않는다.

## 4. 기존 기능으로 진행할 순서

아래 화면 이름은 기존 완료 보고의 접점이다. 현재 기능의 정확한 저장·재개 방법은 개발자가 확인한다. 없는 기능을 이미 있다고 기록하지 않는다.

| 순서 | 사용자 작업 | 기존 기능에서 확인할 접점 |
|---|---|---|
| 1 | 자료 기준일과 현재 확인할 내용을 읽음 | 「오늘의 투자 점검」·「지금 할 일」·시장 흐름 |
| 2 | ETF를 비교하고 검토 근거를 확인 | 「요즘 잘 오르는 ETF」·ETF 비교·보유 확인 근거·판단 근거 미리보기 |
| 3 | 근거를 AI와 검토 | 기존 AI 복사문·AI 세션 진입·대화 저장 또는 연결 방법 |
| 4 | 최종 판단과 이유를 기록 | 기존 판단/검토 기록. 주문·실제 매매 기록과 구분 |
| 5 | 같은 기록을 다시 열어 당시 근거를 읽음 | 기존 기록 목록·상세·AI 세션 또는 근거 연결 |
| 6 | 다음 검토에서 이전 판단과 새 근거를 함께 봄 | 원래 기록 보존과 이후 검토를 연결할 기존 방법 |

AI가 잘하는 해석을 새 점수·규칙 엔진으로 다시 만들지 않는다. 기존 근거를 전달하고 사용자와 토론하는 흐름을 우선 사용한다. AI 제안과 사용자 최종 판단을 같은 것으로 저장하지 않는다.

**당일에는 저장한 기록을 다시 여는 기능까지 확인한다.** 다음 주가 된 것처럼 날짜를 바꾸거나 미래 결과를 만들어 한 주 운영을 마쳤다고 쓰지 않는다. 실제 다음 정기 검토의 관측은 이후 사용 기록이며, 한 주를 기다려야 개발 준비를 끝낼 수 있는 조건으로 두지 않는다.

## 5. 기록에서 확인할 최소 내용

새 표나 입력 항목을 먼저 만들지 않는다. 기존 저장 본문·연결로 아래 내용을 보존할 수 있는지 본다.

1. 어떤 ETF를 무엇 때문에 검토했는지.
2. 당시 근거의 실제 기준일·주요 값·출처 또는 당시 복사문.
3. AI가 제안한 검토 내용과 사용자 최종 판단의 구분.
4. 사용자 판단: 신규 진입 검토·유지·축소 검토·청산 검토·보류 등 실제 선택과 이유.
5. 다시 확인할 질문 또는 판단을 바꿀 조건. 사용자가 정하지 않은 수치 기준을 대신 만들어 넣지 않는다.
6. 기록 시각과 다음 검토 때 다시 찾을 수 있는 위치.

기존 본문 저장으로 충분하면 별도 구조화·자동 추출·새 평가 표를 추가하지 않는다. 기록의 링크가 최신 화면만 가리켜 당시 근거를 복원할 수 없는 경우에는 그 사실을 핵심 공백으로 적는다. 과거 기록을 나중 자료로 조용히 다시 쓰지 않는다.

## 6. 개발자의 첫 작업과 회신 — 준비 30분 이내

전체 저장소·백로그를 다시 감사하지 않는다. 현재 작업 규칙·STATE와 위 경로에 필요한 코드/화면만 확인한다. 기존 화면의 저장 자료 조회·통상 계산은 사용할 수 있으나 새 수집·학습·성과 실험·DB 구조 변경·pull·OCI 접속/쓰기는 하지 않는다.

첫 회신은 **사용자가 누를 순서와 기존 기록 위치를 적은 짧은 표 하나**면 된다.

| 구간 | 실제 화면·버튼·기록 위치 | 가능한 것 | 막힌 부분 |
|---|---|---|---|
| 비교 → 근거 → AI 검토 | | | |
| 판단 기록 | | | |
| 기록 다시 열기 → 다음 검토 | | | |

- 첫 문장은 사용자가 지금 시작할 화면·버튼 한 개로 안내한다. 개발 내부 용어보다 쉬운 한국어를 쓴다.
- 기록 쓰기 직전까지 준비한다. 실제 사용자 판단은 사용자가 하며 개발자가 임의 판단·매매를 대신 저장하지 않는다.
- 사용자와 기존 UI로 두 사례를 진행하고, 저장·다시 열기 결과를 확인한다. 실제 주문은 없다.
- 막힘이 발견되면 원인·현재 가능한 대안·한 흐름을 완성하는 최소 보완안을 함께 회신한다. 새 개발은 설계자가 그 범위를 정한 뒤 진행한다.
- 사용 순서를 확인하기 위한 별도 전체 목업·시험·검증자 라운드는 두지 않는다. 코드 변경이 필요할 때만 그 변경에 맞는 PLAN·필요한 화면 확인·검사를 적용한다.

## 7. 종료 기준과 ‘우물파기’ 방지

**종료 기준은 두 사례에서 검토 근거 → 사용자 판단 기록 → 같은 기록 재열기가 연결되는지 확인하고, 다음 검토에서 사용할 방법을 설명하는 것이다.** 사용자 수행 전에는 ‘준비 완료’이며 실제 사용 확인 완료가 아니다.

| 결과 | 다음 처리 |
|---|---|
| 기존 기능으로 연결됨 | 사용 확인 완료. 새 기능을 만들지 않고 실제 주간 사용으로 이어감 |
| 사용법 안내만 부족 | 실제 필요한 안내만 보완. 메뉴·대시보드 전체를 다시 설계하지 않음 |
| 기록·근거 보존·재개가 끊김 | 실제 차단 구간의 최소 보완 범위만 설계자에게 제출. 주변 정비 목록으로 확대하지 않음 |
| 좋은 추천 근거·ML 효용이 부족 | 미완료를 유지. 기록 화면이나 임의 규칙 추가로 그 부족을 해결했다고 쓰지 않음 |

코드가 없으면 ‘사용 흐름 확인 완료(코드 변경 없음)’라고 보고한다. IMPLEMENTED로 꾸미거나 새 성과 실험을 통과한 것으로 처리하지 않는다. 코드 보완이 발생하면 해당 구현·확인 범위를 구분해 기록한다.

추천의 투자 효용, 비용 후 초과성과, 위험 판단 효용과 ML 요구는 별도 미완료다. Q6 OPEN·운영 ML 미승격, 05 보관·06 전향 기록·13 일정, 종료된 15~17을 유지한다. 전체 ML 상태 화면·새 자료원·새 모델·모의 주문 엔진은 이번 범위에 자동으로 붙이지 않는다.

## 8. 기록과 전달

이 설계 원문을 보관하고 첫 회신은 대화 또는 같은 문서의 후속 기록으로 제출한다. 사용 확인 결과는 수행 시각·가능/차단 구간·필요 보완만 짧게 적는다. 공개 문서에는 개인 보유 여부·금액·AI 대화 본문을 복사하지 않고 사례 A/B와 확인 결과만 남긴다.

문서만 변경되면 이 확인을 위한 별도 코드 검증을 만들지 않는다. POC6-17 결과서에 남은 현재 상태 문구 정정은 앞서 정한 대로 다음 문서 커밋에 함께 넣을 수 있다. 커밋·push는 유효한 승인 범위로 처리하고 사용자 소유 handoff는 제외한다. 같은 POC6 안에서 새 handoff를 만들지 않는다.

## 개발자 전달문

POC6-18은 기존 기능의 주간 투자 판단·기록·재개 흐름 확인입니다. 추가 수집이나 새 기능 구현부터 시작하지 않습니다. §6처럼 30분 이내에 기존 버튼 순서와 기록 위치를 확인한 짧은 표를 먼저 제출해 주세요. 사용자와 사례 A/B를 수행하고 기록을 다시 열어 봅니다. 이미 연결돼 있으면 그대로 사용하고, 실제로 끊기는 구간만 최소 보완안으로 올립니다. 새 모델·전체 상태 화면·새 기록 시스템은 자동으로 만들지 않습니다.
