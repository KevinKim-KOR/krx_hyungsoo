# POC6-34 OCI 운영·적용과 ETF NAV 조회 · RESULT 판정

2026-11-19 KST · 설계자 · 수신 개발자

**조건부 PASS.** 검증자 r3의 VERIFIED_WITH_NOTES를 수용한다. 결과서 §18에서 R1-F1~F3, R2-F4, KS-10 정정을 확인했다. §7의 형수님 격리 화면 확인과 r1·r2 재확인도 수용한다. 아래 표시 보완과 기록, 커밋 전 백엔드 전체 회귀를 완료하면 PASS로 확정한다.

이번 판정의 근거는 최종 격리 사본을 대조한 결과서 §15·§17·§18, 11/19 사용자 확인, 확정 PLAN V1과 PLAN 판정이다. §18의 관련 시험은 프런트 287건·백엔드 269건 통과다. 전체 백엔드 회귀는 커밋 전 확인으로 남아 있다.

## 1. K1~K3 판정

| 항목 | 판정과 근거 |
|---|---|
| K1 · 보유 급등·급락 경계 | **r1 정정 수용.** 실제 판정은 프로그램 고정 경계인 급등 +5·+7·+10%, 급락 −5·−7·−10%를 사용한다. 저장된 +3%·−3% 후보로 재현한 경우도 같은 실행 경계가 적용됐다. 두 행에서 저장 설정값과 실제 경계를 구별하고, 저장값이 없을 때도 확인된 프로그램 경계는 설명한다. 화면·서버 상수를 공용 시험 자료와 대조하는 방식은 이번 I-22 예외로 승인한다. 경계가 바뀔 때 이 시험으로 화면과 실행의 불일치를 확인한다. |
| K2 · 한도에 밀린 재진입 신호 | **기존 발송 결함으로 판단한다.** 회복 뒤 120분을 채우고 다시 잡혀 이미 발송 후보였던 신호가 구역 한도에 밀렸다면 관측과 성공 전달을 구별해야 한다. 다음 점검에서 조건이 지속되고 발송 한도에 여유가 있으면 다시 후보로 평가할 수 있어야 한다. 결과서 §11의 메모리 재현에서는 ‘이어짐’으로 분류돼 이 재평가가 빠졌다. PROGRAM_TRUTH의 OPS-02 §3-2가 정한 성공 전달 기준에 비춰 후속 운영 결함으로 남긴다. |
| K3 · 재진입 시 120분 미만 | **현행 정책으로 수용.** 재발송 대기 120분은 이전 성공 발송 회차의 실행 시작 시각부터 재진입 회차의 실행 시작 시각까지 실제로 경과한 시간이다. 재진입 시점이 119분대면 대기 조건 미충족이다. 그 뒤 같은 상태가 지속되면 동일 신호 억제 규칙을 적용한다. 시간표상 두 회차 간격과 실제 120분 경과를 구별해 설명한다. |

K2는 제출된 메모리 재현을 근거로 판단했고 실제 운영 발생 빈도는 미확인이다. 후속 재검토는 해당 재진입 건을 구역 한도로 떨어뜨린 뒤 다음 회차에 조건과 자리가 남는 사례를 재현하는 데서 시작한다. K3를 바꿀 필요가 생기면 대기 중 재진입 상태를 대기 경과 후에도 평가할지 별도 운영 기준으로 정한다. 이번 표의 재발송·구역 한도 설명에는 검증된 현행 동작을 사용한다.

## 2. C1~C9 판정

| 항목 | 판정과 처리 |
|---|---|
| C1 · 카드 단독 조회 분기 | **이번에는 유지.** 운영 조립에서 ①의 응답을 ②에 전달해 한 번 읽는 동작이 검증됐다. 단독 조회는 카드 시험이 사용하는 구조 메모로 남긴다. 카드 연결을 다시 정리하는 작업에서 시험을 운영 경로에 맞춘 뒤 제거를 검토한다. |
| C2 · 적용 세부와 좁은 카드 | **수용.** §4-2의 사용 범위와 `fit-content(50%)` 정정을 수용한다. 표·각주·시각 표기는 아래 보완 판정의 문안을 적용한다. |
| C3 · 응답이 불완전한 이번 시도 | **로직 수용, 라벨 보완.** 응답이 없거나 HTTP 오류 응답이라 적용 결과를 확인할 수 없는 경우에는 ‘최근 적용 시도’에 버튼을 누른 시각과 ‘결과 확인 불가’ 사유를 표시한다. 바로 아래의 ‘이전에 확인한 서버 요청 기록’에는 마지막으로 확인된 서버 요청 종료 시각과 결과를 표시한다. 연속으로 응답을 못 받았을 때도 이 서버 기록의 출처는 같다. 정상 요청 기록에서는 기존 서버 종료 시각을 사용한다. |
| C4 · 후보 정책 읽기 | **수용.** 후보의 값은 후보 응답에서 읽고 값이 빠지거나 형식이 다르면 ‘확인 불가’로 쓴다. 변경 건수에는 확인된 사업군·설정 변경만 센다. 비교할 수 없는 켜짐 여부는 기존 별도 문장으로 알린다. 보유 급등·급락의 확인된 실행 경계 설명은 K1을 적용한다. |
| C5 · 표 위 설명 | **보완 필요.** ‘사업군 판정과 발송 조건은 설정 버전에서 확인합니다. 보유 급등·급락 판정에는 프로그램의 고정 경계를 적용합니다.’로 쓴다. PC의 대표 ETF 선정과 버전 단위 승인 설명은 같은 위치에서 읽을 수 있게 한다. |
| C6 · 활성 버전 없음 | **수용.** 정상 조회로 활성 버전이 없음을 확인한 첫 설정은 `false`다. 저장 상태 손상·읽기 실패 등 켜짐을 알아낼 수 없는 경우의 값은 `null`이며 ‘확인 불가’다. |
| C7 · 현재 상태 미확인과 후보 | **전환 문구 수용.** 현재가 미확인이면 후보 켜짐·꺼짐을 표시하고 현재 상태 미확인을 붙인다. ‘새로 켜짐’은 현재 꺼짐이 확인된 전환에 쓴다. 어느 쪽을 읽지 못했는지 적는 r2 문구도 수용한다. 함께 보이는 발송 안내는 ‘발송 조건을 충족한 장중 알림에는 아래의 하루 최대 한도가 적용됩니다.’로 맞춘다. 후보에 따라 달라질 수 있는 한도는 표의 후보값에서 읽는다. |
| C8 · 켜짐 여부만 확인된 경우 | **화면 보완.** 활성 버전에서 정책 상태 값이 빠졌거나 확인 가능한 상태로 읽히지 않으면, 실제로 확인한 값에 따라 ‘켜짐 · 정책 상태 확인 불가’ 또는 ‘꺼짐 · 정책 상태 확인 불가’를 표시한다. 활성 버전이 없는 첫 설정에는 C6을 적용한다. 켜짐 여부를 확인할 수 없는 경우에는 r2의 ‘장중 알림 설정 확인 불가’를 쓴다. |
| C9 · 회차당 최대 각주 | **문안 보완.** 값이 확인되면 기존 회차당 최대 건수 설명을 쓴다. 값이 없으면 문장 전체를 ‘회차당 최대 건수는 이 설정에서 확인할 수 없습니다.’로 쓴다. 후보값이 빠진 경우도 이 문안을 적용한다. |

조회 성공률의 설명은 **‘이 표에 표시한 설정의 사업군 가운데’**로 적는다. 후보가 있는 예에서도 제목·설정값·해석이 후보 버전을 가리키도록 하는 문구 보완이다.

## 3. POC6-34 PASS 확정 조건

1. **표시 변경분을 확인한다.** C3의 시도·서버 기록 라벨, C5의 고정 경계 안내, C7의 발송 안내, C8의 정책 상태 표기, C9의 미확인 각주, 조회 성공률의 대상 문구를 관련 화면 시험과 고정 응답으로 확인한다. K1의 저장값과 실행 경계가 다른 예, R1-F2 시각과 결과의 짝, R1-F3·R2-F4의 후보·활성값 확인 불가 분기를 함께 대조한다. 형수님의 §7 화면 확인을 이번 판단의 사용자 근거로 사용한다.
2. **기록을 맞춘다.** 결과서에 설계자 판정과 표시 보완 확인을 덧붙인다. PLAN §2-3·I-22·I-23과 관련 상태 문구는 이 판정을 기준으로 갱신한다. K2의 운영 결함과 K3의 기존 정책 수용을 각 항목에 남긴다. `STATE_LATEST.md`와 `PROGRAM_TRUTH.md`는 실제 반영 상태를 기록한다.
3. **커밋 전 검사를 마친다.** 최종 변경분의 관련 시험과 계획한 백엔드 전체 회귀 1회 결과를 남긴다. 충족 후 ‘설계자 RESULT PASS · 반영 승인 대기’로 기록한다. 커밋은 형수님 승인 후 진행하며 push는 별도 승인 범위다.

## 4. 별도 운영 확인

- **K2 재진입 후 미전달:** 발송 관측과 실제 성공 전달을 구분하는 운영 정정 후보다. 재현 조건과 빈도를 확인하는 별도 변경 단계에서 다룬다.
- **운영 `enabled` 판독:** 손상된 문자열 `"false"`를 운영 코드가 참으로 읽을 수 있다는 결과서 §5-2-3을 남긴다. 표시 API의 미확인 처리와 운영의 정책 값 해석은 각각의 동작이다. 손상된 활성 자료가 관측되거나 해당 실행 경로를 점검할 때 운영 정합성을 확인한다.
- **대표 ETF 선정 자료와 원장 사본:** PC 선정용 종가 표의 9/11 하루치와 PC 원장 사본의 10/23 동기화 기록은 §13의 후속 점검 근거로 남긴다. 각각 PC 자료와 OCI에서 실제 사용하는 자료, PC 사본과 원장의 자료 시점을 대조할 때 재검토한다.
