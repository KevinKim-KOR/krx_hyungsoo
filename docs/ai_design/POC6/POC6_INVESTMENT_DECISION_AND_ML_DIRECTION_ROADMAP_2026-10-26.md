# POC6 방향·성공 기준·후속 작업 정리 V1

작성: 설계자 · 2026-10-26 · 독자: 사용자·설계자·개발자·검증자

저장 권장 위치: `docs/ai_design/POC6/POC6_INVESTMENT_DECISION_AND_ML_DIRECTION_ROADMAP_2026-10-26.md`

**목적:** POC6-10 종료 뒤 나눈 대화를 기준으로 사용자 목적과 앞으로의 순서를 고정한다. 구체적인 운용 수치는 아직 정하지 않은 항목으로 구분한다. 같은 논의를 다음 세션에서 다시 시작하거나, 개별 연구 목표를 프로젝트 전체 목표로 바꾸는 일을 막기 위한 문서다. 새 구현 설계서·PLAN·배포 승인을 대신하지 않는다.

## 1. 프로젝트가 제공하려는 것

**한국 상장 ETF에서 후보를 추천하고, 보유 중에는 유지·축소·매도를 검토할 근거와 권고를 제공한다. 사용자는 AI와 함께 검토하고 최종 결정·주문을 직접 한다. ML을 연결해 이 판단의 추가 효용을 검증하고, 입증된 범위에서 활용한다.**

사용자가 기대한 것은 수치·관측값을 나열하는 화면을 넘어선 판단 지원이다. 관측값 제공과 사용 가능한 추천 기능의 완성을 같은 것으로 기록하지 않는다. 앞으로의 수익이나 하락을 확실하게 보장하는 시스템을 목표로 삼지도 않는다.

### 1-1. 이번 대화로 분명해진 원칙

| 항목 | 정리 |
|---|---|
| 추천과 주문 | 매수 후보·유지·축소·청산 검토 권고는 기대 기능이다. 실제 주문의 자동 실행은 제외한다 |
| ML 목표 | ML 연동 요구를 삭제하거나 룰만으로 대체 완료 처리하지 않는다. 단순 연결과 효용 검증·운영 채택은 구분한다 |
| 성과 목적 | 같은 기간 KODEX200 대비 초과성과를 확인하려는 목적을 유지한다 |
| 위험 관리 | 수익과 함께 평가할 제약·판단 축이다. 둘 중 하나를 완전히 포기해야 한다고 전제하지 않는다 |
| 사용 형태 | 본업을 병행하는 저빈도 판단·매매에 맞춘다. 일별 자료 활용과 매일 매매는 별개다 |
| 평가 대상 | 시스템이 사전에 기록한 추천·모의 포트폴리오를 평가한다. 시스템 전에 산 개인 보유를 시스템 성과로 삼지 않는다 |
| 외부 참고 | 공개된 모델·입력 정의·목표·운용 규칙·평가 방식을 함께 참고한다. 필요 이상의 플랫폼 이식은 피한다 |
| 기존 자산 | 채택하지 않은 모델·코드·입력·실험 기록도 비교 근거로 보존한다 |

이 표는 사용 목적의 정리다. 기존 코드의 추천 어휘 검사나 실제 출력 정책을 지금 일괄 해제한 것은 아니다. 차기 설계에서 금지의 대상이 자동주문인지, 근거 없는 성과 단정인지, 추천 자체인지 구분하고 필요한 문서·검사만 정합화한다. 금지가 만들어진 원인을 확인 없이 특정 사용자 발언이나 특정 AI의 잘못으로 단정하지 않는다.

### 1-2. 성과와 위험의 우선순위

확인한 PROJECT_ORIGIN_INTENT의 7월 26일 보관본 §5에는 같은 기간 KODEX200 대비 초과수익이 성과 목표이고, MDD 숫자는 2차 기준으로 적혀 있다. §9.5는 ML을 상승 후보 점수화와 위험 감지의 두 축으로 둔다. 따라서 우선순위나 ML 목적이 처음부터 없었다고 다시 설명하지 않는다.

**차기 설계의 기본안은 비용 후 초과성과를 주목적으로 두고, 위험·매매 빈도를 제약으로 관리하는 것이다.** 허용 낙폭·거래 빈도·최소 개선 폭 등 수치는 §4에서 확정한다. 원문의 ‘추천 ETF 평균이 마이너스’라는 감지 기준과 상대성과 목표가 하락장에서 어떻게 함께 적용되는지도 그때 명시한다. 항상 양의 수익이라는 보장으로 해석하지 않는다.

## 3. D20을 앞으로 어떻게 취급할 것인가

### 3-1. 의미와 직접적인 출발점

D20은 **기준일 종가 대비 이후 20거래일 안의 최저 종가 변화이며, 모든 종가가 기준일보다 높으면 0**이다. 예를 들어 기준일 100, 이후 최저 92, 20일째 110이면 D20은 −8%다.

지금 이어진 D20 연구의 직접적인 출발점은 POC5-06의 수동 재진입 검토다. 설계자가 ‘최근 가격 상태로 이후 20거래일 최저 종가 변화를 설명할 수 있는가’라는 질문을 정했다. 그 설계 §9는 D20·모델·연구 길이를 설계 결정으로 명시한다. POC6-02는 기존 방법과의 비교를 위해 이 목표·입력을 유지했고, 후속 연구가 이를 이어받았다.

확인한 범위에서 사용자가 ‘20일을 보유하겠다’거나 D20의 20을 직접 정했다는 근거는 없다. 진행 승인과 연구 기간의 직접 제안은 구분한다. 친구 전략의 D20 기준을 가져온 것으로도 설명하지 않는다.

### 3-2. 세 기간을 분리한다

| 기간 | 의미 |
|---|---|
| 과거 관측 기간 | 최근 5·20·60일 변화나 이동평균을 계산할 때 돌아보는 길이 |
| 예측·평가 기간 | 미래 어느 구간의 어떤 결과를 맞히거나 비교하는지 정한 길이 |
| 실제 보유 기간 | 진입·유지·축소·청산·재진입 규칙에 따라 정해지는 기간 |

20거래일은 대략 한 달이지만, 그 사실만으로 사용자에게 적합한 투자 기간이 되지는 않는다. D20은 의무 보유 기간·20일째 수익률·MDD·손실 확률이 아니다. 저빈도 판단이 20일 보유를 뜻하지도 않는다.

D20은 제한된 재진입/손실 경로 연구로 유효한 질문이었다. 다만 사용자의 전체 추천 목적에 자동으로 승계하지 않는다. 다음 목표는 **판단 주기·기대 보유 기간·행동 규칙을 정한 뒤** 선택한다. 필요하면 D20을 보조 위험 지표로 남길 수 있으나, 그것만의 오차 개선을 최종 투자 성공으로 삼지 않는다.

### 4-1. 다음 설계에서 정할 운용·평가 계약

| 결정 항목 | 정할 내용 |
|---|---|
| 검토 주기·기대 보유 | 하루/주 단위 판단 빈도, 기대 보유 기간의 범위, 예외적으로 더 빨리 대응할 조건 |
| 대상 | 한국 상장 ETF 범위·유형 필터·과거 상장/폐지 처리. 개인 보유와 분리한 대상 선정 |
| 진입 권고 | 후보 선정 기준·최대 종목 수·비중·매수 가능 시각·추천하지 않을 조건 |
| 보유·축소·청산 | 단순 상태 설명과 행동 권고의 차이, 판단 조건, 과잉 교체 방지 |
| 청산 이후 | 현금 유지·다른 후보 교체·재진입의 조건과 시각 |
| ML 과제 | 후보 순위·향후 상대성과·조건부 손실 위험 등에서 실제 개선할 목표. D20 고정 승계 없음 |
| 비교·가격 | 같은 기간 KODEX200, 거래 비용·체결·현금·분배금/조정 가격의 의미를 맞춘 평가 |
| 효용 기준 | 비용 후 초과성과의 최소 기준, 허용 위험·매매 빈도, 기간별 안정성·비용 변화 공개 |
| 연구 예산 | 후보/설정 탐색·실행 시간 상한, 개발 종료·채택·보류·재개 조건 |

사용자 선택이 필요한 항목은 설계자가 기존 요구와 자료를 바탕으로 권장안을 묶어 제시한다. 한 항목씩 되묻거나 임의 숫자를 사용자 확정값으로 기록하지 않는다. 기존 1·2·5%p, 20일, 상위 5개, −8% 같은 다른 연구의 수치를 새 운용 계약으로 자동 복사하지 않는다.

### 4-2. 외부 참고를 사용하는 방식

Qlib LightGBM+Alpha158은 **우선 대조 후보**이며 설치·플랫폼 채택 결정이 아니다. 공식 설정의 개별주 집합·일별 예측/교체·학습/검증 구간·목표·비용과 한국 ETF 저빈도 사용을 먼저 비교한다. 코드를 읽어 판단할 수 있는 것은 설치 전에 끝낸다.

원형 재현이 어떤 판단을 해결하는지 분명할 때만 실행한다. 원자료·버전·평가 조건을 맞출 수 없으면 정확 재현으로 부르지 않는다. 외부 환경에서 재현된 성과와 한국 ETF에서의 성과를 구분한다.

‘7개 대 158개’의 효과를 주장하려면 자료·종목·목표·모델·평가 조건을 맞추고 입력만 바꿔야 한다. 시장과 목표까지 바뀐 두 결과의 차이를 입력 개수의 효과로 해석하지 않는다. 먼저 재사용할 정의 몇 개를 선별할 수 있으며, 158개 전부의 도입이나 SQLite→Qlib 전면 이식을 전제하지 않는다.

친구의 공개 코드에서 확인한 구조와 확인하지 못한 실제 DB 설정·모의 운용 성과도 구분한다. 외부 성공을 무시하거나 그대로 국내 수익 보장으로 받아들이지 않는다.

## 5. 룰·ML·검증의 관계

| 역할 | 원칙 |
|---|---|
| 운용 룰 | 판단 주기·종목 수·비중·진입/청산·현금·체결처럼 사용 형태를 명확히 정의 |
| 룰 기준선 | 비교 가능한 단순 방법. 최종적으로 최선이라고 미리 확정하지 않음 |
| ML | 같은 판단 과제에서 순위·추정·위험 판단의 추가 효용을 검증. 유효한 부분을 채택 |
| 사용자 | 권고와 근거를 검토하고 실제 매매를 결정·주문 |

추천 출력에는 무엇을 권고하는지, 근거·기준일·적용 범위·불확실성·자료 부족 여부가 연결돼야 한다. 추천을 제공하려고 검증되지 않은 추정을 확정적 판단으로 포장하지 않는다. 연구 결과를 모의로 연결할 수는 있지만 실제 참고용 채택과 같은 상태로 표시하지 않는다.

평가 원칙은 다음과 같다.

- 시스템 이전 개인 보유 손익 대신 **사전에 고정·기록한 시스템 추천의 모의 성과**를 평가한다. 실제 사용자 매매는 별도의 사용 결과이며 신호 효과를 곧바로 인과 입증하지 않는다.
- 룰과 ML은 같은 날짜·모집단·정보 가용 시각·체결·비용으로 비교한다. 데이터의 사후 조정·표본 선택·상관·겹치는 목표 기간의 한계를 공개한다.
- 예측오차·순위 지표·실제 행동 규칙의 성과를 구분한다. MAE가 좋아졌다고 수익 개선, MAE 기준 미달이라고 모든 추천 효용 부재를 자동 선언하지 않는다.
- 투자 효용을 판단할 때 가격·분배금·비용 기준을 맞춘다. 합성 가격지수 연구를 실제 계좌 총수익으로 바꾸어 부르지 않는다.
- 합리적 모델 조정은 사전 탐색 예산과 학습/검증 자료 안에서 할 수 있다. 같은 시험 결과를 보며 기간·종목·임계·설정을 바꿔 합격을 찾지 않는다.
- 원문·고정 입력·모델/설정·예측·실행 실패·결과를 보존한다. 코드 결함, 자료 부족, 효용 미입증은 별도로 보고한다.

가격 정보이므로 ML이 불가능하다거나, 입력이 많으면 성공한다거나, 국내 ETF에서는 모멘텀이 항상 최선이라는 결론은 현재 근거로 확정하지 않는다. 초기 연구의 적격 4종을 이후 모든 연구의 영구적 한계로 설명하지도 않는다.

## 6. 완료·성공·중단을 구분한다

### 6-1. 무엇이 완료돼야 하는가

| 구분 | 판단 기준 |
|---|---|
| 연구 단계 완료 | 정한 가설을 계약대로 구현·실행·검증하고 채택/기각/부족의 이유까지 판정 |
| 기능 개발 완료 | 추천 생성→근거 확인→사용자 판단→기록→사후평가가 정의된 범위에서 실제로 연결됨 |
| ML 요구 충족 | 유용한 ML 역할을 검증하고 정한 수준으로 연결. 실행만 했거나 실패 기록을 보존했다는 사실만으로 충족 처리하지 않음 |
| 투자 효용 확인 | 사전에 정한 비교·위험·비용 기준을 만족하는 근거 확보. 장래 수익 보장과는 구분 |

연구 기각으로 한 단계는 닫을 수 있다. 그 사실만으로 프로젝트 핵심 추천·ML 목표가 달성된 것은 아니다. 유효한 모델을 확보하지 못하면 그 부분은 미달·보류로 정직하게 남긴다. 반대로 이 이유로 기반 구축의 모든 가치를 무효화하지 않는다.

### 6-2. 반복 연구를 멈추는 조건

매 실험 전에 목적·가설·자료·평가·탐색/시간 예산·기각 시 종료 범위를 정한다. 이 범위가 기각되면 같은 자료로 이름이나 임계만 바꾼 후속을 자동으로 열지 않는다.

재개는 새 정보가 생겼을 때 판단한다. 예를 들어 사전에 정한 충분한 새 성숙 표본, 새 자료의 검증 가능한 정보 가치, 사용자 목적에 맞는 다른 과제, 이식 가치가 확인된 외부 방법, 실제 결함 정정이 근거가 될 수 있다. 성과가 마음에 들지 않는다는 이유는 재실행 근거가 아니다.

‘연구가 몇 번째이므로 영구 중단’, ‘2027년 1월이거나 자료가 1년치면 자동 재개’로 정하지 않는다. 달력 날짜와 필요한 증거 조건을 구분한다. 다음 가설이 없으면 운영·증거 축적을 유지하며 해당 연구를 보류한다. 새 모델을 계속 만들어야 프로젝트가 진행되는 것으로 보지도 않는다.

## 7. 역할과 방향 점검

| 역할 | 책임 |
|---|---|
| 사용자 | 사용 목적·투자 제약·최종 판단·승인 |
| 설계자 | 전체 이력과 목적을 연결해 범위·기준·우선순위를 결정. 방향 변경과 미달을 먼저 설명 |
| 개발자 | 실제 코드·자료·환경을 확인하고 구현·검사·한계·충돌을 보고 |
| 검증자 | 구현·자료 시각·계산·계약·보존을 확인. 코드 통과가 투자 효용 통과를 뜻하지 않음을 구분 |
| 조언자 | 제한된 정보로 박스 밖 질문·대안·누락을 제기. 제한된 정보의 설명을 전체 이력의 확정 사실로 대신 쓰지 않음 |

방향 점검은 대단계 종료, 목표/자료/운용 조건 변경, 비슷한 부정 결과가 반복되거나 사용자가 요청할 때 한다. 작은 문구 수정마다 전체 프로젝트를 재심사하지 않는다.

점검에서는 세 질문에 답한다.

1. 이번 일이 사용자 추천 목적에 어떤 결과를 더하는가?
2. 기존 연구와 무엇이 달라 새로 알 수 있는가?
3. 어디까지 끝내며, 결과가 부정적이면 무엇을 닫고 무엇을 유지하는가?

원래 목적을 바꾸거나 크게 넓혀야 하면 설계자가 이유·영향·대안을 먼저 제시해 사용자 결정을 받는다. 실험 편의 때문에 목표를 축소하거나, 단계 종료를 전체 성공처럼 보고하지 않는다.

## 8. 바로 다음 작업과 문서 사용법

**다음 설계는 §4-1의 ‘추천 행동과 최종 성과 검증 기준’이다. Qlib 설치나 새 모델 학습부터 시작하지 않는다.** 그 설계에 필요한 사실은 이미 확인한 문서·코드 접점을 재사용하고, 실제 빈자리만 좁게 확인한다.

개발자에게 이 파일을 전달하면 우선 지정 위치에 원문을 보관하고 STATE_LATEST의 다음 작업에 연결한다. 기존 기반 문서와 추천/어휘 경계가 충돌하는 부분은 해당 문장·적용 범위만 정리해 차기 설계에 올린다. 이 문서 저장만을 위한 코드·DB·OCI·새 외부 조회는 없다. 커밋·push는 유효한 사용자 승인 범위로 처리한다.

다음 설계/PLAN을 시작할 때는 저장소 작업 규칙과 최신 STATE, 이 방향 문서, 해당 설계를 읽는다. 원문 문서와 최신 사용자 결정이 충돌하면 최신 사용자 결정을 우선하고 관련 정본을 명시적으로 정정한다. 이 문서를 기존 합의나 사용자 소유 handoff 파일을 덮어쓰는 근거로 사용하지 않는다.

이 문서는 별도 handoff가 아니다. 같은 POC6 안에서는 단계마다 handoff를 만들지 않는 기존 원칙을 유지한다. 확정된 방향이 바뀌면 이 파일의 개정 이력에 변경·이유·사용자 결정·영향받는 문서를 남긴다.
