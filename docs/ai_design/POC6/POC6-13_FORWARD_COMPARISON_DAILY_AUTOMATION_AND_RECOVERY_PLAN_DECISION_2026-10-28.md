## 2. Q1 — 봉인 DB OCI 미전송 계약 유지, C는 로컬 외장 사본으로 정정

기존 계약과 충돌한 OCI 권장 목적지는 설계자가 놓친 부분이다. 이 단계에서 KRX 이용 조건을 새로 해석하거나 기존 계약을 바꿔 원격 전송하지 않는다.

**C의 봉인 DB뿐 아니라 08~11 원본 연구 산출물과 코드 bundle까지 한 묶음으로, 사용자 소유의 다른 물리 저장소에 보관한다.** 기본 권장 대상은 맥북에 연결한 외장 SSD/HDD/USB 저장장치다. 이는 PLAN Q1(a)의 목적지를 C 전체로 통일하는 범위 정정이다.

- 08~11에는 봉인 자료의 파생 가격·행 단위 결과가 포함돼 있다. 02~04 일부 파일의 과거 OCI 승인만으로 다른 연구 전체의 전송 허용을 확대하지 않는다. 이번에는 새 원자료/파생자료 권리 분류 조사를 열지 않는다.
- C를 위한 OCI private_backups 생성·scp·원격 sha256sum·원격 mv는 구현·실행 대상에서 뺀다. 코드만 별도로 OCI에 올리는 분할 백업도 만들지 않는다. 기존 05/06의 승인된 OCI 보관은 그대로 유지한다.
- C의 실제 목적지 절대 경로와 물리 장치 식별을 기록한다. 맥북 내부 디스크의 다른 폴더나 APFS 볼륨만으로 두 번째 물리 사본을 충족했다고 쓰지 않는다. 장치가 없거나 마운트되지 않았으면 C만 WAITING_TARGET으로 남긴다. 목적지가 사라졌을 때 내부 디스크의 같은 이름 폴더를 만들어 대신 쓰지 않는다.
- 기존 묶음·manifest·파일별 해시·코드 bundle·입력 참조는 재사용한다. 외장 장치의 임시 이름에 복사하고 해시 확인 후 완료로 전환한다. 그 사본을 맥북의 빈 별도 경로로 되가져와 파일 해시와 필요한 Git 커밋 7개를 확인한다. 상태는 COPY_INCOMPLETE / COPY_HASH_OK / RESTORE_VERIFIED처럼 실제 경로에 맞춰 정정한다.
- 로컬 연구 브랜치는 비공개 bundle 안에 보존한다. 원격 Git 브랜치를 만들거나 main에 병합하지 않는다. 없는 과거 코드 판을 최신 코드로 대체하지 않는다.
- 원본 삭제·외장 장치 포맷·기존 백업 덮어쓰기·상시 클라우드 동기화는 추가하지 않는다. 사용자 선택으로 나중에 NAS 등 다른 목적지를 쓸 경우 그 연결/비공유 범위만 별도로 확인하며 지금 범용 백업기를 만들지 않는다.

장치가 정해지기 전에도 가짜 외장 경로로 C의 복사·해시·복원 시험을 만들 수 있다. 실제 C 완료는 장치 연결과 사본 확인 뒤다. 장치 미정을 C 완료나 제외 승인으로 처리하지 않는다.

## 3. Q2 — (b) 수용: 업로드 작업당 원격 목록 1회

매 묶음마다 같은 전체 목록을 다시 읽는 비용은 현재 작아도 일일 누적으로 확정적으로 늘어난다. 이번에 작은 공통 접점 변경으로 줄인다. “170묶음이면 반드시 10분”은 목록 조회만으로 계산한 추정이며, 자료량·망 상태를 포함한 실행 보장은 아니다.

- 한 번의 archive --upload 호출 시작 때 원격 완료 목록을 한 번 읽고, 그 작업 안에서 재사용한다. 프로세스 밖의 영구 캐시·새 DB·목록 커서·분산 동기화 계층은 만들지 않는다.
- 단순 run_id 존재 또는 로컬의 예전 업로드 성공 기록만으로 건너뛰지 않는다. 기존의 manifest/내용 일치·없음·손상·충돌 판정과 accept-upload 확인을 그대로 보존한다. 원격 조회 실패를 빈 목록으로 바꿔 전량 업로드하지 않는다.
- 작업 중 새 업로드가 원격 확인까지 끝나면 그 결과만 작업 내 목록에 반영한다. 실패한 업로드를 성공 목록에 넣지 않는다. 다음 호출은 새 목록을 읽는다. 목록을 읽은 뒤 다른 실행이 먼저 올린 경우도 기존 불변/충돌 처리로 안전하게 끝나야 한다.
- 기존 단건 호출의 동작·호환성을 유지한다. PLAN의 app/ml_evidence/transfer.py와 06 archive 호출부를 중심으로 필요한 작은 변경만 한다. 05 pull의 전체 완료 목록 대조·늦게 공개된 낮은 run_id 수신 계약은 바꾸지 않는다.
- 신규 실제 대량 업로드나 6개월 대기를 하지 않는다. 170개 이상 가짜 묶음에서 목록 호출 1회, 이미 있는 것/새 것/손상/조회 실패/업로드 중 실패의 결과 보존을 시험한다. 큰 내용 파일을 전송하는 시간까지 일정하다고 주장하지 않는다.
- 10분 상한과 ARCHIVE_PENDING 표시는 유지한다. 상한 전에 완료하지 못한 보관은 다음 정해진 시도에서 처리한다. OCI API·허용 형식·서버 코드 변경은 이번 안에 필요하지 않다는 PLAN 근거를 유지하되 구현 중 실제 차이가 있으면 그 차이만 보고한다.

## 4. Q3 — 가동 여건은 활성화 전 확인, 실행 중 유휴 절전 방지는 수용

A·B의 격리 구현은 진행한다. **실제 활성화 전에는 사용자가 낮에 이 맥북을 사용하는지 확인한다.** 낮에 거의 닫혀 있다면 이 배치로 매일 기록을 확보할 수 있다고 설명하지 않는다. 그때는 실행 장치/가동 방식을 다시 정하며 자동 깨우기·상시 OCI 학습을 임의로 추가하지 않는다.

“10:00~15:20에 한 번 열면 반드시 실행된다”는 표현은 정정한다. RunAtLoad는 로그인 시 호출이고 모든 덮개 열기 이벤트가 아니다. 깨어날 때 아직 놓친 달력 일정이 없으면 다음 예약 시각까지 기다릴 수 있다. **유효 창에서 예약/로그인/놓친 일정 복귀 중 하나가 실제 시작되고, 기기를 작업 완료까지 사용할 수 있어야 한다.**

- PLAN의 caffeinate -i는 수용한다. 다만 06 자식만 보호하고 끝내지 말고, 실제로 진행하는 A·B의 수신/예측/보관과 C 복사·복원 각각의 작업 생애 동안만 유휴 절전을 막는다. 상태 조회·대기 중·종료 뒤에는 유지하지 않는다.
- 이것은 작업 중 임시 assertion이다. pmset 설정·예약 깨우기·덮개 닫힘 동작은 바꾸지 않는다. 덮개 닫기·강제 잠자기·전원/배터리 문제까지 막는다고 보장하지 않는다.
- timeout/실패 때 자기가 시작한 프로세스 그룹과 임시 assertion이 남지 않게 종료한다. 기존 수동 실행 프로세스를 종료하거나 그 잠금을 지우지 않는다. 상한·종료 후 상태는 기존 시험 범위에서 확인한다.
- 가동 여건 답변을 기다리며 새 장치 지원·Windows/NAS 설치를 병렬로 개발하지 않는다. 현재 맥북용 구현과 기존 수동 실행을 유지한다.

## 5. 구현 전 필수 보완 — 현재 PLAN의 상태·흐름을 명확히 할 것

### 5-1. 오늘 DONE은 공개 확인과 실제 D를 포함

PLAN §3-2의 status/미예측 수/방법 실패 수만으로 DONE을 결정하지 않는다. 해당 protocol/cohort/D의 주 기록과 영수증이 연결되고, 실제 confirmed_at이 그 D의 close_cutoff_at보다 이른 근거가 있어야 한다. exit 0·publication_confirmed 없는 OK·다른 D의 영수증은 완료가 아니다.

ALREADY_RECORDED도 같은 검사를 한다. “오늘 run 파일이 생겼다”는 이유로 오래된 D를 오늘 필요한 예측으로 표시하지 않는다. 기존 06의 이번 입력/달력에 대한 유효 기준일 판정을 재사용한다. 필요한 D의 최신성을 확정할 근거가 없으면 “기록 존재·필요 기준일 확인 불가”로 남기고 예정된 추가 점검을 막지 않는다. 이를 위해 새 달력/가격 계산을 복제하지 않는다.

주말·휴장일에는 같은 D가 여러 달력일에 정상적으로 이어질 수 있다. D가 어제 날짜가 아니라는 이유만으로 실패로 만들지 않는다. 실제 수신·달력·주 기록 근거로 판정한다. 실제 cohort 분모와 방법별 실패를 유지하고 일부 성공을 전체 완료로 표시하지 않는다.

### 5-2. 예측 DONE이어도 보관 대기는 별도로 처리

PLAN의 “오늘 완료면 06 호출 안 함”은 **예측 호출만 건너뛴다는 뜻**으로 확정한다. 유효 자동 창에서 보관 대기가 있으면 B의 시도 상한 안에서 archive --upload를 별도로 호출한다. 그렇지 않으면 첫 예측 성공 뒤 업로드 실패가 영구히 남을 수 있다.

A의 오늘 완료·시도 수와 B의 보관 완료·시도 수를 분리한다. 15:20 이후 tick에서 새 예측·업로드를 시작하지 않는 PLAN은 유지하고, 남은 보관은 다음 허용 창에 처리한다. 예측·보관 어느 하나의 성공이 다른 하나의 실패를 덮지 않는다.

### 5-3. 15:20 자동 시작 종료와 실제 예측 마감을 구분

PLAN의 하루 상태 DEADLINE_PASSED를 15:20부터 적용하지 않는다. **15:20은 AUTO_WINDOW_CLOSED**, 실제 D의 close_cutoff_at에 도달했을 때만 DEADLINE_PASSED다.

15:25에도 실제 15:30 마감 전일 수 있고, 금요일 D를 토요일에 다루는 경우 실제 마감은 다음 거래일일 수 있다. 자동 창이 닫혔다는 이유로 “이 D는 영구히 없다”고 확정하지 않는다. 실제 D/마감을 확정하지 못하면 그 사실을 표시한다. 기존 수동 명령의 유효 시간 경계를 앞당기지 않는다.

다음 날 로그인 때는 지난 자동 점검의 미실행/실패도 남긴다. 날짜를 오늘로 바꿔 지난 공백을 지우거나 과거 예측을 만들지 않는다. 설치 전의 D=10-23·10-26 미기록은 기존 사실 그대로다.

### 5-4. 표시의 추정과 전달 확인 한계

SCHEDULED/CATCH_UP을 시각 ±2분으로 나누는 것은 호출 사유의 추정이다. 실제 깨어남 이벤트를 확인했다는 표현은 쓰지 않는다. 별도 OS 이벤트 수집기는 만들지 않는다. osascript의 알림 요청과 실제 화면 전달을 구분하는 PLAN은 그대로 수용한다.

## 6. 검사·문서·진행

기존 PLAN 시험에 §3·§5의 경계만 추가한다. 특히 원격 목록 재사용과 오류 보존, exit 0이지만 영수증 없음, 오래된 D의 ALREADY, 주말 같은 D, 예측 DONE+보관 실패 후 재시도, 15:20/15:30/다음 거래일 마감 차이를 확인한다. caffeinate는 작업 시작·종료/timeout의 실제 생애와 자식 정리까지 확인한다.

Q2 공유 코드 변경을 포함하므로 관련 05·06·13 시험과 마지막 전체 회귀 한 번을 수행한다. 기존 공식 연구·학습을 재실행하지 않는다. 결과서에는 실제 자동 명령/보관 상태와 외장 복원 결과를 나누고, 옛 코드 보존 공백을 그대로 적는다. 새 위조 방지 체계·전수 Git 조사·모델 재평가를 추가하지 않는다.

설계서 원문과 기존 판정은 그대로 보존하고 본 문서를 연결한다. 같은 PLAN에 Q1~Q3 판정·§5 보완을 반영한 뒤 바로 격리 구현한다. 기술 세부 선택을 다시 사용자에게 묻거나 PLAN 전체를 다시 제출하지 않는다. C 장치가 미정이어도 A·B 구현·검증·실제 반영 준비를 진행할 수 있다.

**실제 설치·자동 upload·외장 장치 쓰기·임시 정리·커밋/push는 구체적인 범위를 준비한 뒤 유효한 사용자 승인을 적용한다.** 현재 판정이 새 실행 승인은 아니다. 이미 승인된 동일 범위는 재승인을 요구하지 않는다. C를 보류한 채 종료하려면 그 잔여를 명시적으로 결정하고 전체 백업 완료로 기록하지 않는다.

12 API는 사용자가 집에서 확인하는 병행 작업이다. 13은 그 결과를 기다리지 않는다. 운영 ML 미승격·Q6 OPEN·기존 미완료 요구·05/06 운영·사용자 소유 handoff 제외를 유지한다.
